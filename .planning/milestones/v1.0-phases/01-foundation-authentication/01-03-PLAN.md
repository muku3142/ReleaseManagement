**`config/JiraRestClientConfig.java`** — one `@Bean` producing a `RestClient.Builder`-derived `RestClient` with **no base URL** (the site URL arrives per call) and explicit timeouts read from configuration:
```java
@Bean
RestClient jiraRestClient(RestClient.Builder builder,
                          @Value("${app.jira.connect-timeout}") Duration connectTimeout,
                          @Value("${app.jira.read-timeout}") Duration readTimeout) {
    ClientHttpRequestFactorySettings settings = ClientHttpRequestFactorySettings.defaults()
            .withConnectTimeout(connectTimeout)
            .withReadTimeout(readTimeout);
```

**`adapters/jira/JiraRestAuthAdapter.java`** — `@Component @Profile("!stub-jira")`, implements `JiraAuthPort`, constructor-injects the `RestClient`:
```java
@Override
public JiraIdentity validate(String siteBaseUrl, String email, String apiToken) {
    String basic = Base64.getEncoder().encodeToString((email + ":" + apiToken).getBytes(StandardCharsets.UTF_8));
    try {
        JiraMyselfResponse body = restClient.get()
                .uri(siteBaseUrl + "/rest/api/3/myself")
                .header(HttpHeaders.AUTHORIZATION, "Basic " + basic)
                .header(HttpHeaders.ACCEPT, MediaType.APPLICATION_JSON_VALUE)
                .retrieve()
                .body(JiraMyselfResponse.class);
        if (body == null || body.accountId() == null) {
            throw new JiraAuthenticationException(JiraAuthFailureReason.JIRA_ERROR);
        }
        return new JiraIdentity(body.accountId(), body.emailAddress(), body.displayName());
    } catch (HttpClientErrorException.Unauthorized e) {
        throw new JiraAuthenticationException(JiraAuthFailureReason.INVALID_CREDENTIALS);
    } catch (HttpClientErrorException.Forbidden e) {
        throw new JiraAuthenticationException(JiraAuthFailureReason.JIRA_FORBIDDEN);
    } catch (HttpClientErrorException.TooManyRequests e) {
        throw new JiraAuthenticationException(JiraAuthFailureReason.JIRA_RATE_LIMITED);
    } catch (HttpServerErrorException e) {
        throw new JiraAuthenticationException(JiraAuthFailureReason.JIRA_ERROR);
    } catch (ResourceAccessException e) {
        throw new JiraAuthenticationException(JiraAuthFailureReason.JIRA_UNREACHABLE);
    } catch (RestClientException e) {
        throw new JiraAuthenticationException(JiraAuthFailureReason.JIRA_ERROR);
    }
}
```
Hard rules for this class:
- Never log `basic`, `apiToken`, the `Authorization` header, or the upstream response body. If any logging is added at all, log only `siteBaseUrl` and the resulting `JiraAuthFailureReason`.
- `body.emailAddress()` may legitimately be `null` (Jira Cloud email-visibility settings, RESEARCH.md Open Question 1) — pass it through rather than failing; a null email is not an authentication failure. Only a null `accountId` is fatal.
- Do **not** attempt to read the token's expiry date. Jira Cloud does not expose a signed-in user's own API-token expiry through any REST endpoint (RESEARCH.md Pitfall 3), and advance expiry warning is an explicitly deferred idea.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Application → Jira Cloud | The user's Jira email and API token cross here in an `Authorization: Basic` header |
| Jira Cloud → application | Untrusted JSON of an undocumented-stability shape crosses back |
| Application → logs / error responses | Credential material must never cross here |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Information Disclosure | The `Authorization: Basic base64(email:token)` header or the raw API token leaking into logs or a `ProblemDetail` body | mitigate | `JiraRestAuthAdapter` logs neither the header, the token, nor the upstream body; `ProblemDetail` details are fixed strings carrying only the `reason` enum. Grep-gated in this plan's acceptance criteria and re-gated project-wide in plan 08 |
| T-03-02 | Spoofing / Information Disclosure | A generic 500 on a revoked token, leaving the user unable to tell "credential dead" from "Jira down" and inviting credential-guessing confusion | mitigate | Six distinct reasons with distinct HTTP statuses; `INVALID_CREDENTIALS` returns the actionable "Your Jira credential is no longer valid" message (D-04) |
| T-03-03 | Tampering / SSRF | `siteBaseUrl` is concatenated into the outbound URI, so a hostile value would redirect the credential to an attacker-controlled host | mitigate | The only writer of that value is `PUT /api/settings/jira-site`, pinned by plan 01's `^https://[A-Za-z0-9][A-Za-z0-9-]*\.atlassian\.net$` regex; plan 05 additionally requires authentication to change it |
| T-03-04 | Denial of Service | An unbounded Jira call hanging a servlet thread, or a retry storm amplifying a Jira outage | mitigate | Explicit connect (5 s) and read (10 s) timeouts on the `RestClient`; no retry policy in this phase, so one user action is at most one upstream call |
| T-03-05 | Elevation of Privilege | Any Jira account that authenticates gains full write-side access to the tool (releases, approval documents) | accept | D-01/D-02 record this deliberately for an internal tool. The documented upgrade path is a Jira group-membership check at sign-in, administered in Jira — explicitly not built now |
| T-03-06 | Tampering | Jira changing the `/myself` response shape and silently producing a half-populated identity | mitigate | `@JsonIgnoreProperties(ignoreUnknown = true)` plus a fatal null-`accountId` check mapped to `JIRA_ERROR`; WireMock cases 3 and 9 lock both behaviours in |
| T-03-07 | Repudiation | An external Jira call happening with no user to attribute it to | mitigate | No `@Scheduled`, no `@EnableScheduling`, no startup Jira call anywhere (D-14); grep-gated |
</threat_model>
