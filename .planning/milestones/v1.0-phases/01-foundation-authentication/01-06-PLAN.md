<objective>
Compose plans 03, 04 and 05 into the actual sign-in surface: `POST /api/auth/login` validates a Jira email and API token live against the configured site, stores the token encrypted, and issues the cookie-borne session; `POST /api/auth/refresh` rotates the idle window without extending the absolute cap; `POST /api/auth/logout` clears the session; `GET /api/auth/session` reports who is signed in. Alongside them, establish the per-user credential resolution mechanism that every later phase's Jira read goes through.

Purpose: this closes AUTH-01 on the server and satisfies AUTH-02 structurally — Phase 2's ticket reads must use the signed-in user's own credential, and the only way to guarantee that permanently is to make per-principal lookup the single available path and leave no shared-credential alternative to reach for.
Output: `AuthenticationService`, `JiraAccessContextService`, `CurrentUserPort` and its Security-context adapter, `AuthController` with four endpoints, two token-free DTOs, and integration tests covering the full flow under the `stub-jira` profile.
</objective>

**`application/AuthenticationService.java`** — `@Service`, constructor-injects `JiraSiteConfigService`, `JiraAuthPort`, `JiraCredentialRepository`, `JwtTokenService`. Two public methods plus the two records:

`login(String email, String apiToken)`:
1. `String siteBaseUrl = jiraSiteConfigService.get().baseUrl();` — a missing site propagates plan 01's `JiraSiteNotConfiguredException`, already mapped to 409 `SITE_NOT_CONFIGURED`.
2. `JiraIdentity identity = jiraAuthPort.validate(siteBaseUrl, email, apiToken);` — this is the live validation AUTH-01 requires; it happens **before** anything is persisted and before any token is minted. Let `JiraAuthenticationException` propagate untouched so `GlobalExceptionHandler` produces the right status and `reason`; never catch it and substitute a generic failure (D-04).
3. `credentialRepository.upsert(identity.accountId(), email, apiToken);` — store the **submitted** email, not `identity.email()`. Jira Cloud's `/myself` may return a null `emailAddress` depending on the account's email-visibility setting, and the stored email is the one that must reconstruct `Basic base64(email:token)` for future calls. Store the token only after validation succeeded.
4. `TokenPair pair = jwtTokenService.issue(identity.accountId(), email);`
5. Return `new LoginResult(pair, new SignedInUser(identity.accountId(), email, pair.absoluteExpiry()))`.

`refresh(String refreshTokenValue)`:
1. `TokenPair pair = jwtTokenService.refresh(refreshTokenValue);` — `SessionRefreshException` propagates.
2. Read the subject and email from the **new** pair's access token? No — do not decode here. Instead have `JwtTokenService.refresh` already carry them: read `accountId` and `email` from the `SignedInUser` that `JwtTokenService` exposes on `TokenPair`, or if `TokenPair` does not carry them, decode the returned access token with the injected access decoder. Prefer the simplest form available from plan 05's actual `TokenPair`; if it carries only the three fields in its record, add a `@Qualifier("accessTokenDecoder") JwtDecoder` to this service and read `getSubject()` and the `email` claim from the freshly issued access token. Do **not** widen `TokenPair`'s record in plan 05's file.
3. Return a `LoginResult` with the same `absoluteExpiry` the pair carries — which plan 05 guarantees is the original cap copied forward, never recomputed (D-06, D-07).

There is deliberately **no** `revoke`, `logoutAll`, `listSessions` or denylist method: D-09 accepts that a session cannot be force-revoked before expiry, and adding any of those would require the server-side state D-05 rejects. There is also no group-membership or allowlist check (D-01/D-02) — a token that validates is sufficient.

**`application/JiraAccessContextService.java`** — `@Service`, constructor-injects `CurrentUserPort`, `JiraCredentialRepository`, `JiraSiteConfigService`. **This is the AUTH-02 mechanism and the single supported way any code in this project obtains Jira credentials for an outbound call.**
```java
public JiraAccessContext currentContext() {
    String accountId = currentUserPort.currentAccountId()
        .orElseThrow(() -> new JiraAuthenticationException(JiraAuthFailureReason.INVALID_CREDENTIALS));
    JiraCredential credential = credentialRepository.findByAccountId(accountId)
        .orElseThrow(() -> new JiraAuthenticationException(JiraAuthFailureReason.INVALID_CREDENTIALS));
    String siteBaseUrl = jiraSiteConfigService.get().baseUrl();
    return new JiraAccessContext(siteBaseUrl, accountId, credential.email(), credential.apiToken());
}
```
Both failure paths map to `INVALID_CREDENTIALS`, which `GlobalExceptionHandler` already renders as 401 with the actionable "Your Jira credential is no longer valid. Enter your Jira email and a current API token." — exactly D-04's requirement that a revoked credential surfaces clearly on the next Jira-backed call rather than as a generic 500.

Hard rules that make AUTH-02 structural rather than aspirational, and that Phase 2 inherits:
- The lookup key is **only** ever `currentUserPort.currentAccountId()`. There is no overload taking an accountId, no `contextFor(String)`, and no configuration key naming a service account or default credential. If a later phase needs Jira access, it calls `currentContext()` from within an authenticated request — there is no other path, so a shared credential cannot be introduced by accident.
- The returned `apiToken` is plaintext in memory for the duration of one call. Never log it, never put it in an exception message, and never place `JiraAccessContext` in a response DTO (D-13).
- Nothing here is cached, scheduled or pre-warmed. Every resolution happens inside a user-triggered request (D-14).

**`AuthController.java`** — `@RestController @RequestMapping("/api/auth")`, constructor-injects `AuthenticationService` and `AuthCookieWriter`:

```java
@PostMapping("/login")
public SessionResponse login(@Valid @RequestBody LoginRequest request, HttpServletResponse response) {
    LoginResult result = authenticationService.login(request.email(), request.apiToken());
    cookieWriter.write(response, result.pair());
    return toResponse(result.user());
}

@PostMapping("/refresh")
public SessionResponse refresh(
        @CookieValue(name = AuthCookieWriter.REFRESH_COOKIE, required = false) String refreshToken,
        HttpServletResponse response) {
    if (refreshToken == null || refreshToken.isBlank()) {
        throw new SessionRefreshException(SessionRefreshException.Reason.INVALID_SESSION);
    }
    LoginResult result = authenticationService.refresh(refreshToken);
    cookieWriter.write(response, result.pair());
    return toResponse(result.user());
}

@PostMapping("/logout")
@ResponseStatus(HttpStatus.NO_CONTENT)
public void logout(HttpServletResponse response) {
    cookieWriter.clear(response);
}

@GetMapping("/session")
public SessionResponse session(@AuthenticationPrincipal Jwt jwt) {
    return new SessionResponse(
        jwt.getSubject(),
        jwt.getClaimAsString(JwtTokenService.CLAIM_EMAIL),
        Instant.ofEpochSecond(jwt.getClaim(JwtTokenService.CLAIM_ABSOLUTE_EXP)));
}
```
Notes that must hold:
- The tokens travel **only** as `Set-Cookie` headers written by `AuthCookieWriter`. Never add them to the response body, never add a `token` query parameter, never echo the submitted `apiToken` back.
- `logout` is deliberately stateless: it clears two cookies and nothing else. There is no server-side invalidation, because there is no server-side session (D-05, D-09).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → `POST /api/auth/login` | An unauthenticated caller submits credential material here |
| Browser → `POST /api/auth/refresh` | A long-lived credential cookie is presented by an unauthenticated caller |
| Application → response body / logs | The Jira API token must never cross this boundary |
| Authenticated principal → stored credential | The lookup that decides whose Jira data can be read |
