**`frontend/src/api/credentialStatus.ts`** — a dependency-free external store, so any component can react to "the stored Jira credential was rejected" without prop-drilling and without adding a state library:
```ts
let invalid = false;
const listeners = new Set<() => void>();
function emit() { listeners.forEach((l) => l()); }
export function markCredentialInvalid() { if (!invalid) { invalid = true; emit(); } }
export function clearCredentialInvalid() { if (invalid) { invalid = false; emit(); } }
export function useCredentialInvalid() {
  return useSyncExternalStore(
    (l) => { listeners.add(l); return () => listeners.delete(l); },
    () => invalid,
    () => false,
  );
}
```
It stores a boolean flag and nothing else — never the token, never the email, never a session value.

**Extend `frontend/src/api/client.ts`** (additive; do not rewrite the existing body):
```ts
const SESSION_REASONS = new Set(['UNAUTHENTICATED', 'SESSION_EXPIRED', 'INVALID_SESSION']);
const REFRESH_PATH = '/api/auth/refresh';
let refreshInFlight: Promise<boolean> | null = null;

async function attemptRefresh(): Promise<boolean> {
  refreshInFlight ??= (async () => {
    try {
      await rawFetch(REFRESH_PATH, { method: 'POST' });
      return true;
    } catch {
      return false;
    } finally {
      refreshInFlight = null;
    }
  })();
  return refreshInFlight;
}
```
Extract plan 02's existing request body into a private `rawFetch` and make `apiFetch` wrap it:
1. Call `rawFetch(path, init)`.
2. On an `ApiError` whose `problem.reason` is in `SESSION_REASONS`, and only when `path !== REFRESH_PATH` and the call has not already been retried, `await attemptRefresh()`. If it resolves `true`, re-issue `rawFetch(path, init)` **once** and return its result; if `false`, rethrow.
3. On an `ApiError` whose `problem.reason === 'INVALID_CREDENTIALS'`, call `markCredentialInvalid()` and rethrow. This is the D-04 signal: the stored Jira credential is dead, which is a different situation from an expired app session and must not trigger a refresh attempt.
4. Rethrow everything else unchanged.

The single-flight `refreshInFlight` promise matters: several queries can 401 concurrently on the same expired access token, and without it each would fire its own refresh, rotating the cookie repeatedly. Once the absolute cap (plan 05) is reached, refresh returns 401 permanently and step 2 falls through to a rethrow — which is what sends the user back to sign-in rather than looping. Never inspect or attempt to read the session cookies here; they are httpOnly by design (D-08).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Injected script → page JavaScript | Any XSS-executed code runs with the SPA's privileges |
| Browser JS → `/api/auth/**` | State-changing sign-in, sign-out, refresh and replacement requests cross here |
| User keystrokes → application memory | A plaintext Jira API token exists in the DOM for the duration of one submit |
| Client → any client-side persistence | Nothing credential-shaped may cross this boundary |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-01 | Information Disclosure (XSS) | Injected script exfiltrating the session token — the reason the token never touches `localStorage`/`sessionStorage` | mitigate | The session lives only in httpOnly cookies written by the server; no client code names, reads or stores `access_token`/`refresh_token`. Grep-gated at 0 for `localStorage`, `sessionStorage` and both cookie names. XSS would still be able to *ride* the session, but it cannot extract a portable credential — which is exactly why D-08 chose cookies over `localStorage` |
| T-07-02 | Information Disclosure (XSS) | Server-supplied strings (`email`, `updatedBy`, `baseUrl`, `ProblemDetail.detail`) rendered as HTML | mitigate | React escapes interpolated text; `dangerouslySetInnerHTML` remains grep-gated at 0 from plan 02. All new failure text comes from the fixed `messageForReason` table, not from interpolating upstream content |
| T-07-03 | Tampering | CSRF against `POST /api/auth/login`, `/logout`, `/refresh` or `PUT /api/auth/credential` | mitigate | Every write goes through plan 02's single `apiFetch` boundary, which echoes the JS-readable `XSRF-TOKEN` cookie as `X-XSRF-TOKEN` on all non-GET requests; plan 05's `csrf.spa()` enforces it server-side with no endpoint exemptions. `AuthControllerIT` case 19 asserts a CSRF-less replacement is 403 |
| T-07-04 | Information Disclosure | The typed API token leaking into the console, a URL, a query key, an error report or React state that outlives the submit | mitigate | `console.*` is grep-gated at 0 across `frontend/src`; the token is never a query key or route search param; the input is cleared on success. Mutation variables are not logged anywhere |
| T-07-05 | Information Disclosure | The stored token being retrieved or displayed — masked, truncated or revealed | mitigate | No API returns it (plan 06 `SessionResponse` and this plan's 204 replacement both carry no token field), and the settings screen renders no representation of it; mask characters, `lastFour`, and reveal affordances are grep-gated at 0 (D-13) |
| T-07-06 | Spoofing | A revoked Jira credential being mistaken for a transient network failure, so the release manager retries forever instead of replacing the token | mitigate | Branching is on the machine-readable `reason` property with a distinct message per value (asserted pairwise-distinct in `auth.test.ts` case 6) and a `data-reason` attribute on every rendered failure. `INVALID_CREDENTIALS` additionally raises the visually distinct `CredentialAlert` banner with a direct link to replacement — grep-gated against message-text matching (D-04) |
| T-07-07 | Denial of Service | Refresh loops — concurrent 401s each firing a refresh, or a refresh 401 recursing into itself | mitigate | Single-flight `refreshInFlight` promise; the retry is attempted at most once per request; `path !== REFRESH_PATH` prevents recursion; `INVALID_CREDENTIALS` never triggers a refresh. `auto.test.ts` cases 2, 3 and 5 lock all three in |
| T-07-08 | Elevation of Privilege | Replacing one Jira account's stored credential with a token belonging to a different account | mitigate | The server compares the validated `identity.accountId()` against the JWT subject and returns 409 `ACCOUNT_MISMATCH`; the client cannot choose whose credential it replaces because the account is taken from the session, never from the request body |
| T-07-09 | Spoofing | Client-side route guarding treated as an access control | accept | `beforeLoad` is a navigation convenience only; every `/api/**` read and write is independently authorised by plan 05's filter chain, so bypassing the guard in the browser grants nothing. The guard exists so a deep link renders the sign-in screen instead of a broken page |
| T-07-10 | Information Disclosure | The browser's password manager persisting the Jira API token | mitigate | `autoComplete="off"` on every `apiToken` input, in both the sign-in and the replacement form; `autoComplete="username"` remains on the email field only |
| T-07-11 | Elevation of Privilege | A stolen session remaining usable with no way to force sign-out on the server | accept | D-09's recorded consequence of statelessness. Sign-out clears the cookies and the client cache; the residual window is bounded by the 30-minute idle window and the 8-hour absolute cap from plan 05 |
