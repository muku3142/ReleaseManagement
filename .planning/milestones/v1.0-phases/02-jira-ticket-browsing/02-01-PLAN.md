<decisions>

**D-PLAN-01-A — `JiraTicketReadException extends JiraAuthenticationException` (resolves the
open question PATTERNS.md flagged for the planner).**

Chosen: **extend**, not a sibling type.

Reasoning:
1. RESEARCH.md is explicit that `JiraAuthFailureReason` is the shared taxonomy and that a
   parallel error scheme must not be invented. A sibling exception would need its own
   `@ExceptionHandler` duplicating all eight switch arms, and duplicated switches drift.
2. Spring resolves `@ExceptionHandler` by most-specific type. A subclass with no handler of
   its own routes to the superclass handler automatically — **zero new wiring in
   `GlobalExceptionHandler` beyond the one new `case`**.
3. `JiraAccessContextService.currentContext()` already throws `JiraAuthenticationException`
   from inside every ticket-read call path. With a sibling hierarchy, callers and tests would
   need two catch types for one logical failure.
4. Accepted cost: the name `JiraAuthenticationException` becomes broader than "authentication".
   That is a naming imperfection, not a structural one, and it is cheaper than nine
   duplicated switch arms.

**D-PLAN-01-B — `RESULT_SET_TOO_LARGE` maps to HTTP 422 Unprocessable Entity.**

PATTERNS.md suggested 413. Rejected: RFC 9110 defines 413 as *request content* too large, and
the request here is tiny — it is the *result set* that exceeds what the server will load. 422
("the request was well formed but the server was unable to process the contained
instructions") is the honest fit: the filter is syntactically fine, the server just cannot
process it within its bounds. 400 is already occupied by `VALIDATION_FAILED`. Clients branch on
`reason`, not status, so this changes nothing for the SPA.

**D-PLAN-01-C — `JiraTicketReadException` exposes only `JiraTicketReadException(JiraAuthFailureReason)`.**
No message-carrying overload, because adding one would require widening
`JiraAuthenticationException`'s constructor set for a diagnostic string nothing currently
logs. Callers that need diagnosis (field-name collision in plan 03) log locally before
throwing.

</decisions>

`public final class`, **no Spring annotations, no Spring imports**, instantiable with `new`.
The only third-party import is `tools.jackson.databind.JsonNode` (Jackson 3 — NOT

Public API — exactly one method:
```java
public String flatten(JsonNode adfDoc)
```

Behaviour:
- `null`, missing, or non-object input returns `""`.
- Output is plain text with lightweight Markdown markers, so the same string is usable both in
  the browse UI and (Phase 5) in generated documents.

Node handling (D-02-04 in-scope set):
| `type` | Emitted |
|---|---|
| `doc` | children, no extra decoration |
| `paragraph` | children then `"\n"` |
| `text` | its `text` value with marks applied (see below) |
| `hardBreak` | `"\n"` |
| `bulletList` | children at `listDepth + 1` |
| `orderedList` | children at `listDepth + 1` |
| `listItem` | `"  ".repeat(Math.max(0, listDepth - 1))` + `"- "` then children |
| `codeBlock` | `"```\n"` then children then `"```\n"` |
| anything else | **degrade, never throw, never drop**: append `node.path("text").asText("")` if the node has a `text` field, then walk its children |

Mark handling on a `text` node, applied in the order the `marks` array lists them:
| mark `type` | Result |
|---|---|
| `strong` | `"**" + text + "**"` |
| `em` | `"*" + text + "*"` |
| `code` | `` "`" + text + "`" `` |
| `link` | `text + " (" + mark.path("attrs").path("href").asText("") + ")"` |
| anything else | `text` unchanged (drop the decoration, keep the content) |

Bounds (the "no unbounded traversal of untrusted structures" posture from RESEARCH.md's
Security Domain):
- `private static final int MAX_NODES = 5000;`
- `private static final int MAX_DEPTH = 50;`
- Track a visited-node counter across the whole walk. When either bound is hit, stop
  descending, append exactly `"\n[content truncated]"` **once**, and return normally. Never
  throw — a bounds hit must be visible in the output, not silent and not an exception.
- Carry the depth as a method parameter; do not use a mutable field for it.

Add exactly one comment, on the `default ->` arm, explaining the degrade-to-text rule (that is
the non-obvious WHY; nothing else in the class needs narration). Do not write class-level
Javadoc blocks.
