<objective>
Build the two backend mechanisms JIRA-03 and JIRA-04 exist for: cursor pagination to
exhaustion against `POST /rest/api/3/search/jql`, and field-name-to-id resolution through
`GET /rest/api/3/field`.

Purpose: this is the highest-cost-if-wrong work in the phase. The legacy `/search` endpoint
already returns 410 on this tenant, `/search/jql` carries **no `total`**, and community reports
say its `isLast` flag never flips true — so the loop must terminate on the **absence of
`nextPageToken`** and must carry a hard page ceiling so a token-chaining bug fails loudly
rather than pinning a thread forever.

Output: `JiraFieldMetadataPort` + adapter + `FieldMetadataService` (cached, collision-safe),
and `JiraTicketPort` + `JiraRestTicketAdapter` (paginating, ADF-flattening, error-mapping),
each covered by WireMock/unit tests.

No user-visible change lands in this plan; plan 05 wires it to an endpoint and plan 06 to the
screen. This is deliberate: the pagination contract is the single riskiest thing in the phase
and it gets a plan whose whole context budget is spent proving it.
</objective>

<decisions>

**D-PLAN-03-A — Requested fields are a `TicketField` enum, not raw strings.**
JIRA-04/D-02-03 require every field to be addressed by an id resolved from metadata. An enum
carrying the Jira **display name** gives the service a type-safe key to resolve and gives the
adapter a type-safe key to read the resolved id back out — with no field-id literal anywhere in
the codebase. Raw `Map<String,String>` keyed on display-name strings would put the same strings
in three files.

**D-PLAN-03-B — Collision detection is per-resolution, not per-cache-build.**
A real Jira instance may well contain duplicate display names among custom fields nobody in
this project ever requests. Failing the whole cache build on any duplicate would be a false
alarm. The cache therefore stores `name → List<id>`, and only a **requested** name whose list
has more than one entry throws (RESEARCH.md Pitfall 4: fail loud, never guess).

**D-PLAN-03-C — One `TicketDetail` record, no separate `TicketSummary`.**
PATTERNS.md sketched both. Nothing in this phase or the UI-SPEC ever needs the ticket without
its rich-text fields — the table and the expand panel come from one fetch. Two records for one
shape is the speculative abstraction the project rules forbid.

**D-PLAN-03-D — Comment truncation is reported, not hidden.**
Jira embeds only the first page of comments inside a search result, with a sibling `total`.
Fetching the rest would be one extra request per ticket, which no requirement asks for. But
silently showing 20 of 60 comments is exactly the silent-truncation failure JIRA-03 exists to
prevent, so `TicketDetail` carries `commentTotal` alongside the flattened bodies and plan 07
surfaces the discrepancy in the UI.

</decisions>

```java
List<TicketDetail> results = new ArrayList<>();
String pageToken = null;
int pagesFetched = 0;
do {
    JqlSearchPage page = restClient.post()
            .uri(access.siteBaseUrl() + "/rest/api/3/search/jql")
            .header(HttpHeaders.AUTHORIZATION, "Basic " + basic)
            .header(HttpHeaders.ACCEPT, MediaType.APPLICATION_JSON_VALUE)
            .contentType(MediaType.APPLICATION_JSON)
            .body(new JqlSearchRequest(jql, requestedIds, pageSize, pageToken))
            .retrieve()
            .body(JqlSearchPage.class);
    if (page == null) {
        throw new JiraTicketReadException(JiraAuthFailureReason.JIRA_ERROR);
    }
    if (page.issues() != null) {
        for (JsonNode issue : page.issues()) {
            results.add(toTicketDetail(issue, fieldIds));
        }
    }
    // Terminate on the ABSENCE of nextPageToken, never on isLast: community reports across
    // 2026 describe isLast never flipping true on this endpoint. isLast is informational only.
    pageToken = page.nextPageToken();
    if (++pagesFetched >= maxPages && pageToken != null && !pageToken.isBlank()) {
        throw new JiraTicketReadException(JiraAuthFailureReason.RESULT_SET_TOO_LARGE);
    }
} while (pageToken != null && !pageToken.isBlank());
return results;
```

     `/search/approximate-count` from inside this loop. **Never** assume the returned page size
     equals `pageSize`.
