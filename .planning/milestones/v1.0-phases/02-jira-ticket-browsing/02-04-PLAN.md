into three durable artefacts: a findings document Phase 6 can be scoped from, a redacted
WireMock contract fixture, and a thin provider-boundary adapter.

<decisions>

**D-PLAN-04-A — The capture is a blocking human-action checkpoint, and it comes first.**
The two calls need a live Jira API token for this tenant. The application's own stored
credential is AES-256-GCM encrypted with a key held only in the environment and is deliberately
unreachable outside `JiraAccessContextService`, so there is no way for the executor to obtain
one. Everything the executor *can* automate — the exact commands, the id extraction, the output
paths — is written out in the checkpoint so the human step is a copy-paste, not a research task.
The checkpoint is Task 1 so no implementation is thrown away if the capture surprises us.

**D-PLAN-04-B — Capture raw and verbatim before any normalising.**
02-CONTEXT.md is explicit: "Capture the raw response verbatim first — the point is to learn the
actual shape, so do not normalise or reshape it before recording what came back." The adapter in
Task 2 is written **against what came back**, not against RESEARCH.md's MEDIUM-confidence sketch.

**D-PLAN-04-C — The adapter returns `JsonNode`, not a typed model.**
Atlassian says this endpoint may change without notice, and Phase 6 has not been scoped yet.
Modelling a typed hierarchy now would be guessing at a contract that does not exist and that
nothing yet consumes. The spike adapter's job is to prove the two-call mechanism and pin the
shape in a fixture. Phase 6 defines the domain model once it knows what it needs.

</decisions>

**1. Resolve CNV-2896 to its numeric internal id.** `dev-status` will not accept the issue key
— passing the key returns something that looks like "no ADO link" rather than an error, which
is exactly the trap this step avoids:
```bash
curl -sS -u "$JIRA_EMAIL:$JIRA_TOKEN" -H "Accept: application/json" \
  "$JIRA_SITE/rest/api/3/issue/CNV-2896?fields=id" \
  | tee .planning/phases/02-jira-ticket-browsing/spike-capture/issue-id.json
```
Read the `"id"` value from that output and export it:
```bash
export ISSUE_ID="<the numeric id, e.g. 123456>"
```

**2. Ask dev-status which application types actually carry data.** The summary endpoint needs
no `applicationType`, so it is the right first probe — it tells you which types exist before
you guess at one:
```bash
curl -sS -u "$JIRA_EMAIL:$JIRA_TOKEN" -H "Accept: application/json" \
  "$JIRA_SITE/rest/dev-status/1.0/issue/summary?issueId=$ISSUE_ID" \
  > .planning/phases/02-jira-ticket-browsing/spike-capture/summary.json
cat .planning/phases/02-jira-ticket-browsing/spike-capture/summary.json
```

**3. Pull the detail for each `dataType`.** Try `applicationType=azure` first; if a response
comes back with an empty `detail` array, retry the same command with
`applicationType=AzureDevOpsGit` and then with the `_instance`/application type name the
summary response in step 2 revealed. Capture **every** attempt — a negative result is a
finding:
