# Phase 02 — UI Design Contract: Jira Ticket Browsing

> Visual and interaction contract for JIRA-02..JIRA-06 (project → fix version → ticket table
> with checkbox selection, JQL escape hatch, rich-text ticket detail, error/empty/loading
> states). Generated by gsd-ui-researcher, verified by gsd-ui-checker. Extends the Phase 1
> design language — no new visual system introduced.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — Phase 1 shipped hand-rolled Tailwind utility classes with no component library installed (`frontend/package.json` has no shadcn/Radix/Mantine dependency, no `components.json`). This phase continues that pattern rather than introducing shadcn mid-project; re-litigating the component-library choice is out of scope per the researcher brief. |

Accent reserved for: the "Load tickets" primary CTA button, the "Advanced: edit as JQL" disclosure toggle and "Try again" retry link, the live "N selected" selection counter, and focus-visible rings on the project/fix-version selects and row checkboxes. Not used for table row hover backgrounds (use plain `gray-50` hover, matching neutral row-hover convention) or for status/resolution text (those render as plain gray text this phase — no color-coded status pills, since Jira status values are instance-configurable free text and color-coding them would require a mapping this phase has no requirement to build).

Destructive is declared for consistency with the project palette but **has no live use in this phase** — see Copywriting Contract below (Phase 2 has no destructive actions).

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | **"Load tickets"** — enabled once a project and fix version are chosen (primary path) or non-empty JQL is entered (advanced path); disabled while a search is in flight. Do not auto-fetch on picker change — the fetch can take several seconds (JIRA-03 pages to exhaustion), so the release manager explicitly triggers it rather than being surprised by a slow request every time they change the fix-version dropdown. |
| Empty state heading | **"No tickets found"** |
| Empty state body | **"No tickets matched {project} / {fixVersion}. Try a different fix version, or use Advanced: edit as JQL to widen the filter."** (JQL path variant: "No tickets matched your JQL. Try a broader query.") Rendered in neutral `gray-600`, no `role="alert"`, no icon — visually calm, distinct from the error state below. |
| Error state | `messageForReason(problem)` (existing table in `frontend/src/api/auth.ts` — already covers all six reason codes this phase needs: `JIRA_UNREACHABLE`, `JIRA_RATE_LIMITED`, `INVALID_CREDENTIALS`, `JIRA_FORBIDDEN`, `JIRA_ERROR`, `SITE_NOT_CONFIGURED` — **zero new table entries required**) rendered `role="alert"` `data-reason={reason}` in `red-600`, plus a **"Try again"** button that re-runs the exact last search (same project/fixVersion/JQL) rather than forcing the release manager to re-pick filters. Exception: if the backend's pagination safety-ceiling (RESEARCH.md Pattern 1) trips, it currently classifies as generic `JIRA_ERROR` ("Jira returned an unexpected error. Try again shortly.") — that copy is **not actionable enough** for this specific case per JIRA-06's "clear, actionable" bar. Recommend the backend add a dedicated reason (e.g. `RESULT_SET_TOO_LARGE`) so the UI can render "This query matched too many tickets to load. Narrow your fix version or JQL filter." If the backend planner declines a new reason code, the executor must still special-case this condition client-side (e.g. via `problem.detail` text matching) rather than shipping the generic message for it — flagging this as a planning input, not resolving the backend enum decision here. |
| Destructive confirmation | **None** — Phase 2 has no destructive actions. Ticket selection (checkboxes) is non-destructive, entirely client-side, and freely reversible; no confirmation dialog is needed for checking/unchecking or clearing selection. |

## Screen Layout & States

**Route:** new `/tickets` route, nested under the existing `authenticated` layout route (inherits the session guard and `AppShell`/`CredentialAlert` for free, same pattern `router.tsx` already establishes for `/` and `/settings`).

### 1. Filter bar (top of page, `white` surface, `p-6` matching `AppShell`'s `<main>` padding)

- **Primary path (default, visible):** two `<select>` pickers side by side — "Project" then "Fix version" (disabled until a project is chosen, populated via `GET /rest/api/3/project/{key}/versions` on project change), each styled identically to `SettingsRoute`'s `baseUrl` input (`rounded border border-gray-300 px-3 py-2 text-sm`). "Load tickets" button (`bg-blue-600 ... text-white`, matching existing Save/Sign-in buttons) to the right, disabled while `projectKey`/`fixVersionId` are unset or a search is in flight.
- **Advanced path (collapsed by default):** a text toggle **"Advanced: edit as JQL"** (`text-blue-600 underline text-sm`, matching existing link styling) that reveals a `<textarea>` for raw JQL plus its own "Load tickets" trigger. Choosing to use the JQL textarea and clicking "Load tickets" ignores/ clears the project+fixVersion selects for that search (mutually exclusive per request, per D-02-01 — one shared query mechanism, two entry UIs). Collapsed state is the default on page load — this keeps the fix-version-first flow visually primary, matching D-02-01's "demoted from primary, not dropped."

### 2. Loading state (replaces the table area only; filter bar stays visible but its inputs/button are disabled)

- This is the phase's most-seen state (JIRA-03's pages-to-exhaustion fetch can take several seconds on a large fix version) and must not be an afterthought placeholder spinner alone.
- Copy: **"Loading tickets… this can take a few seconds for large fix versions."** in `gray-600 text-sm`, with a simple CSS spinner (border-spin, no icon library) to its left.
- If an advisory count is fetched (`POST /search/approximate-count`), append **" (~{n} tickets)"** — the tilde is mandatory in the copy since the count is explicitly approximate (research: never treat it as authoritative); never render it as "Showing X of Y" phrasing, which would imply a known exact total mid-load.
- Filter controls (project/fixVersion selects, JQL textarea, "Load tickets" button) are disabled for the duration — prevents overlapping/duplicate fetches from rapid re-clicking.

### 3. Ticket table (once loaded, non-empty)

Columns, in order: `[select-all checkbox]` · Key · Summary · Type · Status · Resolution · Assignee · Reporter · `[expand toggle]`.

- Table wrapped in an `overflow-x-auto` container (7 text columns + checkbox + toggle is wide; horizontal scroll on narrow viewports rather than column-hiding, since no column is optional per D-02-02's fixed field set).
- Header row: a checkbox that selects/deselects every currently loaded row (valid because the full matching set is already client-side per the research's Pattern 4 — there is no "select all across pages" ambiguity to solve). Renders `indeterminate` when some but not all rows are checked.
- Row height: compact, `text-sm`, `py-2` per cell — matches the density of Phase 1's existing forms rather than a spacious card-per-ticket layout, because a fix version can hold "tens to low hundreds" of tickets (RESEARCH.md) and a release manager needs to scan many rows at once.
- **Key** renders as plain `text-sm font-semibold` (not a hyperlink to Jira this phase — no requirement calls for linking out).
- **Summary** truncates with `overflow-hidden text-ellipsis whitespace-nowrap` plus a `title` attribute carrying the full text (native tooltip) — never silently drops characters from the underlying data, only from the visual truncation.
- **Status** / **Resolution** / **Type** render as plain `text-sm text-gray-700` — no color-coded pills this phase (see Color section rationale: Jira status values are instance-specific free text with no fixed vocabulary to map colors against).
- **Assignee** / **Reporter** render as plain display-name text, no avatar images (no requirement calls for avatars; keeps the fetch/render surface to exactly D-02-02's field set).
- Row expand toggle (rightmost column, a real `<button>` with `▸`/`▾` glyph and an `aria-expanded` attribute — keyboard/screen-reader accessible, not a `div onClick`) reveals an inline panel below the row: **Description** first, then **Comments** (each ADF-flattened per D-02-04), inside a `bg-gray-50 border border-gray-200 rounded p-4` panel. The panel has `max-h-80 overflow-y-auto` — bounded height with internal scroll, **never a truncated/ellipsis cutoff of the actual text**, since a release manager reading a ticket's full description for later document generation must never have content silently hidden.
- A live **"{n} selected"** indicator (`text-sm font-semibold text-blue-600`) sits directly above the table, updating as checkboxes change. No further action button exists yet for the selected set this phase — Phase 3 (Release Assembly) is what consumes a selection; Phase 2's scope ends at "browse, filter, and check tickets," and the spec deliberately does not invent a premature "Create release" button here.

### 4. Empty state (valid filter, zero matching tickets — a successful response with `issues: []`)

Replaces the table area with a centered, neutral message (see Copywriting Contract) — `gray-600`, no alert role, no red, no icon. Visually calm and unmistakably different from state 5.

### 5. Error state (any non-2xx `ProblemDetail`)

Replaces the table area with `role="alert" data-reason={reason}` red-600 text (see Copywriting Contract) plus a "Try again" button. The empty vs. error visual contrast (neutral gray vs. alert red, no role vs. `role="alert"`) is the concrete mechanism satisfying JIRA-06's "distinguishable from 'no results'" requirement — a screen reader announces the error state and stays silent on the empty state, and a sighted user sees red only on genuine failure.

## Drag-and-Drop Assessment (UX-01)

**Not applicable to this phase.** UX-01 requires drag-and-drop "wherever ordering or moving is the natural gesture." Phase 2 is pure browse-and-select: tickets have no order relative to each other (the table is not reorderable — Jira's own return order is preserved), and checkbox selection is a boolean per-row toggle, not a move-between-groups operation. Nothing in JIRA-02..06 or D-02-01..05 involves reordering or moving items. Do not invent a drag interaction here (e.g. drag-to-select rows) — checkbox click/keyboard-space is the correct, already-accessible interaction. UX-01 becomes concretely relevant starting Phase 3 (REL-08's manual items) and later Phase 4 (template section reordering) — revisit there, not here.

## Checker follow-ups — BINDING, not optional

Recorded here rather than left as executor notes, because accessibility items passed along
informally are the ones that get dropped. **UX-01 mandates keyboard accessibility**, so items
2 and 3 are requirements, not polish.

1. **Primary visual anchor (Dimension 2 FLAG).** The **ticket table is the primary visual
   anchor** of the `/tickets` screen. The project and fix-version pickers are subordinate
   controls that feed it. Stated explicitly so the executor does not have to infer hierarchy
   from colour and spacing alone.

2. **Row-expand button needs an accessible name (Dimension 2 FLAG).** The `▸`/`▾` expand
   toggle is icon-only, so `aria-expanded` alone leaves it unnamed for screen-reader users.
   It MUST carry `aria-label="Expand ticket details"` / `"Collapse ticket details"`, toggling
   in step with `aria-expanded`. A glyph is not an accessible name.

3. **Selection counter must be announced (phase-specific check 7).** The live `{n} selected`
   indicator MUST sit in an `aria-live="polite"` region (or carry `role="status"`). Without it
   a keyboard or screen-reader user gets no feedback at all when checking rows, while a sighted
   user sees the count change — the exact asymmetry UX-01 exists to prevent. This is a defect,
   not a nicety.

4. **Spacing exception (Dimension 5 FLAG) — no action.** The 12px (`gap-3`/`space-y-3`) value
   is grid-aligned (a multiple of 4) and carried forward from Phase 1's existing `AppShell` and
   `LoginRoute` rather than newly introduced. Left as-is deliberately; fold it into the named
   scale in a later phase only if it recurs enough to be load-bearing.

## Planning input — new reason code required

The pagination **safety-ceiling breach** (token-chaining hits its hard page limit) currently
falls back to the generic `JIRA_ERROR` copy. That is a materially different situation from
"Jira returned an error", and the generic message would send the release manager looking in the
wrong place entirely.

The planner should add a dedicated `reason` code for it — extending `JiraAuthFailureReason` and
the `messageForReason` table, per the Phase 1 error contract — with copy that says the result
set was too large to load completely and suggests narrowing the filter. Every other
`JIRA-06` reason code already exists verbatim from Phase 1 and needs no new entry.
