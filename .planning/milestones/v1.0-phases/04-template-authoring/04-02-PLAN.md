Create `src/main/resources/db/migration/V4__template_authoring.sql`. Open with a header comment in
V3's style, then exactly these two tables:

```sql
-- Document templates: many named templates per document type with exactly one active (D-04-12).
-- "Exactly one active" is a partial unique index rather than a service-layer check, because a
-- convention that only lives in Java is one concurrent request away from being false.
-- Templates are freely editable and freely deletable with no guard and no soft-delete (D-04-13):
-- Phase 5's document snapshot stores rendered content, so deleting a template destroys nothing
-- readable. Chrome fields (D-04-15) sit on the row; the logo (D-04-16) lives in its own table so
-- that listing templates never reads image bytes.

CREATE TABLE template (
    id                   UUID PRIMARY KEY,
    name                 VARCHAR(200) NOT NULL,
    document_type        VARCHAR(32)  NOT NULL
                         CHECK (document_type IN ('RELEASE_NOTES', 'RUNBOOK', 'APPROVAL')),
    body                 TEXT         NOT NULL,
    active               BOOLEAN      NOT NULL DEFAULT false,
    cover_enabled        BOOLEAN      NOT NULL DEFAULT false,
    cover_title          VARCHAR(500) NOT NULL DEFAULT '',
    cover_subtitle       VARCHAR(500) NOT NULL DEFAULT '',
    header_text          VARCHAR(500) NOT NULL DEFAULT '',
    footer_text          VARCHAR(500) NOT NULL DEFAULT '',
    page_numbers_enabled BOOLEAN      NOT NULL DEFAULT false,
    warnings             TEXT         NOT NULL DEFAULT '[]',
    created_at           TIMESTAMPTZ  NOT NULL DEFAULT now(),
    created_by           VARCHAR(255) NOT NULL,
    updated_at           TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_by           VARCHAR(255) NOT NULL,
    CONSTRAINT template_type_name_unique UNIQUE (document_type, name)
);

CREATE UNIQUE INDEX template_one_active_per_type_idx ON template (document_type) WHERE active;

CREATE TABLE template_logo (
    template_id  UUID PRIMARY KEY REFERENCES template (id) ON DELETE CASCADE,
    bytes        BYTEA        NOT NULL,
    content_type VARCHAR(64)  NOT NULL CHECK (content_type IN ('image/png', 'image/jpeg')),
    filename     VARCHAR(255) NOT NULL,
    byte_size    INTEGER      NOT NULL,
    width        INTEGER      NOT NULL,
    height       INTEGER      NOT NULL,
    uploaded_at  TIMESTAMPTZ  NOT NULL DEFAULT now()
);
```

The partial unique index is new syntax for this codebase — V1 to V3 have only plain `UNIQUE`
constraints. It permits *zero* active rows per type, which is deliberate: D-04-13 allows deleting
the active template and the UI warns rather than blocks (UI-SPEC planning input #3).

Method notes (everything else is a straight copy of `ReleaseRepositoryAdapter`'s shape):

- `create` and `update`: wrap `jpa.saveAndFlush(...)` in
  `try { ... } catch (DataIntegrityViolationException e) { throw new TemplateDuplicateException(); }`
  — the `(document_type, name)` unique constraint is genuinely exercised because the duplicate flow
  in plan 04-04 names a copy "{name} copy".
- `update` must first `jpa.findById(id).orElseThrow(TemplateNotFoundException::new)`, then copy
  name, body, the six chrome fields, warnings, `updatedAt` and `updatedBy` onto the managed entity.
  It must NOT copy `active`, `createdAt` or `createdBy`.
- `setActive(UUID)` is `@Transactional` and does exactly two steps, in this order:
  1. `jpa.findByDocumentTypeAndActiveTrue(type).ifPresent(e -> e.setActive(false));` then
     `jpa.flush();` — the flush is required, otherwise Hibernate may order the INSERT-side update
     first and the partial unique index rejects the transaction.
  2. set `active = true` on the target entity and flush.
  Look the target up first with `jpa.findById(templateId).orElseThrow(TemplateNotFoundException::new)`
  to learn its document type.
- `delete(UUID)` calls `jpa.deleteById(templateId)` with no existence check and no active check
  (D-04-13). The `template_logo` row goes with it via `ON DELETE CASCADE`.
- `saveLogo` writes/overwrites the `TemplateLogoEntity` row keyed by the template id and returns the
  reloaded `Template`; `deleteLogo` calls `logoJpa.deleteById(templateId)` only if it exists;
  `findLogo` maps the entity to `LogoImage`.
- `toDomain(TemplateEntity)` builds `Template` with `logo = null` unless the caller separately loaded
  it. To keep `LogoMetadata` on the aggregate without loading bytes, have the adapter's `load(id)`
  and `findAll()` call a projection: add
  `@Query("SELECT new com.evision.releasemgmt.domain.template.LogoMetadata(l.contentType, l.filename, l.byteSize, l.width, l.height, l.uploadedAt) FROM TemplateLogoEntity l WHERE l.templateId = :id")
   Optional<LogoMetadata> findMetadata(@Param("id") UUID id);`
  to `TemplateLogoJpaRepository`, and for `findAll()` a second method returning
  `List<TemplateLogoEntity>`'s ids only is unnecessary — instead add
  `@Query("SELECT l.templateId FROM TemplateLogoEntity l") List<UUID> findAllTemplateIdsWithLogo();`
  and populate `LogoMetadata` lazily only in `findById`. For `findAll()`, set `logo` to a
  non-null `LogoMetadata` only when the id appears in that list, using a metadata fetch per such id
  (there are at most three templates per type; this is not a hot path).
  If the JPQL constructor expression proves awkward, the acceptable alternative is a second entity
  projection interface — but selecting `bytes` in any list query is not acceptable.
