**Validator.** Create `src/main/java/com/evision/releasemgmt/application/LogoValidator.java` as a
`@Service` constructor-injecting the three caps via `@Value`. One public method:
```java
public LogoImage validate(byte[] bytes, String filename)
```
which returns a `LogoImage` carrying the sniffed content type and the read dimensions, or throws
`LogoRejectedException`. Steps, in this exact order:

1. `if (bytes == null || bytes.length == 0) throw new LogoRejectedException(INVALID_TYPE);`
2. `if (bytes.length > maxBytes) throw new LogoRejectedException(TOO_LARGE);` — the size check comes
   before anything that touches the content, so an oversized file costs nothing to reject.
3. Sniff the magic bytes. PNG is the 8-byte signature
   `0x89 0x50 0x4E 0x47 0x0D 0x0A 0x1A 0x0A`; JPEG is `0xFF 0xD8 0xFF`. Anything else throws
   `INVALID_TYPE`. Write the comment that says why:
   ```java
   // TMPL-09 / REQUIREMENTS.md:234: the type is decided by content, never by the filename or the
   // browser-supplied Content-Type. SVG is the case this exists for - it is XML, it can carry script
   // and external entity references, and openhtmltopdf would process it in Phase 5. A file named
   // logo.png whose first bytes are "<?xml" is refused here.
   ```
4. Read the dimensions from the header only, without decompressing the image:
   ```java
   try (ImageInputStream in = ImageIO.createImageInputStream(new ByteArrayInputStream(bytes))) {
       Iterator<ImageReader> readers = ImageIO.getImageReaders(in);
       if (!readers.hasNext()) throw new LogoRejectedException(LogoRejectionReason.INVALID_TYPE);
       ImageReader reader = readers.next();
       try {
           reader.setInput(in);
           int width = reader.getWidth(0);
           int height = reader.getHeight(0);
           ...
       } finally {
           reader.dispose();
       }
   } catch (IOException e) {
       throw new LogoRejectedException(LogoRejectionReason.INVALID_TYPE);
   }
   ```
   Add the comment explaining why this is `getWidth`/`getHeight` rather than `ImageIO.read`:
   ```java
   // getWidth/getHeight read the header only. ImageIO.read would allocate the full raster, which is
   // exactly the decompression-bomb the dimension cap exists to stop - a small file declaring
   // 30000x30000 pixels. Reject on the declared dimensions, before any raster is allocated.
   ```
5. Cross-check `reader.getFormatName()` against the sniffed type (`"png"` / `"jpeg"` or `"JPEG"`,
   case-insensitive); a mismatch is `INVALID_TYPE`.
6. `if (width > maxWidth || height > maxHeight) throw new LogoRejectedException(DIMENSIONS_EXCEEDED);`
7. Build and return `new LogoImage(bytes, new LogoMetadata(contentType, safeFilename(filename),
   bytes.length, width, height, Instant.now()))` where `safeFilename` takes only the base name (strip
   anything up to and including the last `/` or `\`), truncates to 255 characters, and falls back to
   `"logo"` when blank — the filename is only ever echoed back to the SPA as display text, but a path
   fragment has no business being stored.

@PostMapping(path = "/{templateId}/logo", consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
public TemplateResponse uploadLogo(@PathVariable UUID templateId,
                                   @RequestParam("file") MultipartFile file,
                                   Principal principal) throws IOException {
    return toResponse(service.uploadLogo(templateId, file.getBytes(),
            file.getOriginalFilename(), principal.getName()));
}

@DeleteMapping("/{templateId}/logo")
public TemplateResponse removeLogo(@PathVariable UUID templateId) {
    return toResponse(service.removeLogo(templateId));
}

@GetMapping("/{templateId}/logo")
public ResponseEntity<byte[]> downloadLogo(@PathVariable UUID templateId) {
    LogoImage image = service.getLogo(templateId);
    return ResponseEntity.ok()
            // The stored type is one of two values enforced by both the sniffing validator and a
            // CHECK constraint, and nosniff stops a browser from re-interpreting the bytes as
            // anything else. User-uploaded content served from our own origin gets both belts.
            .header(HttpHeaders.CONTENT_TYPE, image.metadata().contentType())
            .header(HttpHeaders.X_CONTENT_TYPE_OPTIONS, "nosniff")
            .header(HttpHeaders.CONTENT_DISPOSITION,
                    "inline; filename=\"" + image.metadata().filename() + "\"")
            .header(HttpHeaders.CACHE_CONTROL, "no-store")
            .body(image.bytes());
}
```
(If `HttpHeaders.X_CONTENT_TYPE_OPTIONS` does not exist on this Spring version, use the literal
header name `"X-Content-Type-Options"` — do not skip the header.)

The frontend renders the thumbnail with `<img src="/api/templates/{id}/logo">`; that request carries
the `SameSite=Strict` access-token cookie same-origin, so no security configuration change is needed.

@ExceptionHandler(LogoRejectedException.class)
public ProblemDetail handleLogoRejected(LogoRejectedException ex) {
    return switch (ex.reason()) {
        case INVALID_TYPE -> problem(HttpStatus.UNSUPPORTED_MEDIA_TYPE, "Logo rejected",
                "This file isn't a supported image. Upload a PNG or JPEG — SVG and other formats aren't accepted.",
                "LOGO_INVALID_TYPE");
        case TOO_LARGE -> problem(HttpStatus.PAYLOAD_TOO_LARGE, "Logo rejected",
                "This image is too large for the configured byte limit.", "LOGO_TOO_LARGE");
        case DIMENSIONS_EXCEEDED -> problem(HttpStatus.UNPROCESSABLE_ENTITY, "Logo rejected",
                "This image exceeds the configured maximum pixel dimensions.",
                "LOGO_DIMENSIONS_EXCEEDED");
    };
}

// Spring rejects anything above spring.servlet.multipart.max-file-size before our validator sees a
// byte. Without this the SPA would get a bare 500 for the very case it has specific copy for.
@ExceptionHandler(MaxUploadSizeExceededException.class)
public ProblemDetail handleMaxUploadSize(MaxUploadSizeExceededException ex) {
    return problem(HttpStatus.PAYLOAD_TOO_LARGE, "Logo rejected",
            "This image is too large for the configured byte limit.", "LOGO_TOO_LARGE");
}
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → multipart upload | Arbitrary binary content, with an attacker-chosen filename and Content-Type header |
| stored bytes → browser `<img>` | Bytes served back from our own origin, where a mis-typed response would execute in our security context |
| uploaded bytes → Phase 5 PDF renderer | openhtmltopdf will embed whatever is stored here |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-24 | Elevation of Privilege | An SVG upload carrying `<script>` or an external entity reference, later processed by openhtmltopdf | mitigate | `LogoValidator` sniffs magic bytes and accepts only the PNG 8-byte signature and the JPEG SOI marker; a `.png`-named SVG is refused, asserted by `LogoValidatorTest`. A `CHECK (content_type IN ('image/png','image/jpeg'))` constraint on `template_logo` is the second belt |
| T-04-25 | Denial of Service | A decompression bomb — a small file declaring enormous pixel dimensions | mitigate | Dimensions are read from the header via `ImageReader.getWidth(0)`/`getHeight(0)` and checked against `app.template.logo.max-width`/`max-height` before any raster is allocated; `ImageIO.read` is never called, asserted by grep |
| T-04-26 | Denial of Service | A multi-megabyte upload filling the database or heap | mitigate | `bytes.length > maxBytes` is checked first, before any content inspection, and `spring.servlet.multipart.max-file-size: 4MB` stops anything larger at the container with `MaxUploadSizeExceededException` mapped to `LOGO_TOO_LARGE` rather than a 500 |
| T-04-27 | Elevation of Privilege | Stored XSS by serving uploaded bytes as `text/html` | mitigate | `GET /{id}/logo` sets `Content-Type` from the stored, whitelisted value and adds `X-Content-Type-Options: nosniff` plus `Content-Disposition: inline`, so a browser cannot re-interpret the bytes |
| T-04-28 | Tampering | Path traversal through the supplied filename | mitigate | `safeFilename` keeps only the base name and truncates to 255 characters; the filename is never used as a path — the bytes live in a `BYTEA` column, not on a filesystem (D-04-16) |
| T-04-29 | Information Disclosure | An unauthenticated caller reading another install's logo | accept | `/api/**` is `authenticated()` and this deployment has a single release-manager role; per-template authorisation has nothing to distinguish (`REQUIREMENTS.md` §Out of Scope, single user role in v1) |
</threat_model>
