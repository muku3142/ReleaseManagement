**Client-side pre-check** in `handleFile`, before calling the mutation, using the backend-declared
limits from `props.limits`:
- `file.type` is neither `image/png` nor `image/jpeg`, or the name ends in `.svg` → set the
  invalid-type message locally and do not send the request.
- `file.size > limits.maxBytes` → set the too-large message locally and do not send.
This is a latency optimisation only. The server re-validates by content regardless (plan 04-05), and
the pre-check is deliberately weaker than the server's — a `.svg` renamed to `.png` will pass here
and be refused there, which is exactly why the two paths must produce the same sentence.

**Rejection copy** — one `rejection` state string rendered as
`<p className="mt-2 text-sm text-red-600" role="alert" data-reason={rejectionReason}>{rejection}</p>`,
set either by the pre-check or from the mutation's `ApiError.problem.reason`, using these exact
sentences:
- `LOGO_INVALID_TYPE` → `This file isn't a supported image. Upload a PNG or JPEG — SVG and other formats aren't accepted.`
- `LOGO_TOO_LARGE` → `` `This image is too large. Upload a file under ${formatMaxSize(limits.maxBytes)}.` ``
- `LOGO_DIMENSIONS_EXCEEDED` → `` `This image is too large. Maximum dimensions are ${limits.maxWidth}×${limits.maxHeight}px.` ``

The numbers are interpolated from `props.limits`, which came from `GET /api/templates/catalog`. **No
byte count and no pixel count may be written as a literal in this file** — that is UI-SPEC planning
input #2's whole point, and an acceptance criterion greps for it. If `props.limits` is undefined
(catalog still loading), fall back to the generic `This image is too large.` sentence.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| local file → multipart upload | The author selects arbitrary binary content from their own machine |
| stored logo bytes → `<img>` in our origin | The uploaded image is rendered back inside the application |
