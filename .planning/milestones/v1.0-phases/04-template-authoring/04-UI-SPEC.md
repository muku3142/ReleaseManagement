# Phase 04 — UI Design Contract: Template Authoring

> Visual and interaction contract for TMPL-01, TMPL-02, TMPL-03, TMPL-04, TMPL-05, TMPL-06,
> TMPL-08, TMPL-09 (template management, two-pane authoring screen, placeholder catalog drawer,
> validation feedback, live preview, structured document chrome, logo upload). Generated by
> gsd-ui-researcher, verified by gsd-ui-checker. Extends the Phase 2/3 design language — no new
> visual system introduced. The genuinely new interaction primitives this phase adds are a
> non-modal slide-in drawer (placeholder catalog) and a scoped Markdown typography exception for
> the rendered preview (see Design System below); everything else — buttons, badges, `<dialog>`
> confirmations, banners, error/empty states — reuses Phase 2/3 patterns verbatim.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — continues Phase 1-3's hand-rolled Tailwind pattern. No `components.json`, no component-library dependency. Re-litigating that choice is out of scope, per Phase 2/3 precedent. |
| Preset | not applicable |
| Component library | none — native HTML elements throughout (`<textarea>`, `<input>`, `<select>`, `<dialog>`, real `<button>`s). **New this phase:** a non-modal slide-in drawer for the placeholder catalog (D-04-21) — an absolutely-positioned panel, not a `<dialog>`, because the editor underneath must stay visible and interactive while the catalog is open (see Placeholder Catalog Drawer below). This is a layout pattern built from existing primitives, not a new dependency. |
| CSS plugin | **New this phase:** `@tailwindcss/typography` (the `prose` utility class family) — added specifically so the rendered Markdown preview reads as a document rather than more app chrome (focus area: preview pane). This is a CSS-only Tailwind plugin: zero JS, zero interactive components, does not compromise the "no component library" line. Its `prose` classes define their own internal heading/paragraph/list/code type scale for rendered content — see the declared exception in Typography below. |
| Icon library | none — continues Phase 2/3's plain-glyph rule. Reuses the existing `×` "Dismiss" glyph (Phase 3) for the placeholder-catalog drawer's close control. No new icon dependency. |
| Font | system default (Tailwind's default `sans` stack), unchanged — **plus** `font-mono` (Tailwind's default monospace stack) for the source `<textarea>` only. See Typography. |

**Client-side rendering libraries (not a design-system choice).** D-04-09 allots this phase exactly
two new frontend *runtime* dependencies: a Mustache-spec-conformant JS implementation and a
CommonMark-conformant Markdown renderer, used only for the live preview. Package selection is a
planner/implementation decision, not researched here. This spec's binding requirement on whichever
libraries are chosen: raw-HTML parsing must be disabled (mirrors D-04-05) and unresolved keys must
render through the `[[unknown: token]]` marker (D-04-08), never silently blank. If the chosen
Markdown library cannot suppress raw HTML parsing, that is a blocking library-selection defect, not
a UI detail to work around later.

## Typography

Reuses Phase 2/3's declared four-role scale exactly for all **app chrome** — toolbar, forms, lists,
badges, buttons, banners. **One declared, scoped exception**, stated explicitly so the checker does
not flag it as scale drift:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`text-sm`) | 400 regular | 1.5 |
| Label | 14px (`text-sm`) | 600 semibold | 1.5 |
| Heading | 16px (`text-base`) | 600 semibold | 1.2 |
| Display | 18px (`text-lg`) | 600 semibold | 1.2 |

**Source editor exception:** the body `<textarea>` uses `font-mono` at 14px, line-height 1.6 (not
1.5) — monospace and slightly taller line-height are standard for editing raw markup so `{{`/`}}`
pairs and section braces are easy to scan. This changes font-family and line-height only, not size
or weight, so it does not add a fifth size or third weight to the app scale.

**Rendered preview exception:** the live preview's rendered Markdown body is **exempt from the
four-role app scale** and instead uses `@tailwindcss/typography`'s `prose prose-gray max-w-none`
classes, which define their own internal heading (h1–h6), paragraph, list, blockquote, and code
scale appropriate for document-like content. This is deliberate and scoped to exactly the rendered
`<div>` the Markdown-to-HTML output is injected into — it must **not** leak into any surrounding
app chrome (toolbar, tabs, banners, drawer). The reason: focus area 4 requires the preview to "read
as a document, not as app chrome," which is structurally impossible inside a 4-size/2-weight UI
scale built for buttons and labels. Cover title/subtitle in the preview's cover block (see Document
Chrome & Logo below) also use `prose`-scale sizing (title ≈ `text-2xl font-semibold`, subtitle ≈
`text-base text-gray-600`), not the app's Heading/Display tokens, for the same reason.

Chrome form fields (cover title, cover subtitle, header text, footer text) are plain single-line
`<input type="text">` elements at the standard Body/Label size (14px) — **not** monospace. They are
short strings entered the same way every other text input in the app is (Settings' `baseUrl`,
Release name), unlike the body textarea, which is a large source-editing surface.

## Color

Reuses Phase 2/3's dominant/secondary/accent/destructive values exactly. **One new semantic color
is added this phase** — amber, for the warning class of validation feedback that red cannot
honestly represent (see reasoning below).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `gray-50` (`bg-gray-50`) | Page canvas (unchanged `AppShell`), empty-state panels |
| Secondary (30%) | `white` | Header bars, table/list surfaces, editor and preview pane surfaces, drawer surface |
| Accent (10%) | `blue-600` | See reserved-for list below |
| Destructive/Error | `red-600` | Blocking failures only — see reserved-for list |
| **Warning (new)** | `amber-600` (text/border), `amber-50`/`amber-100` (backgrounds) | Non-blocking validation feedback only — see reserved-for list |

**Why a second semantic color, not a shade of red or blue.** Focus area 3 requires three validation
states — malformed (blocks save), unknown placeholder (warns, saves), clean — to be **visually
separable at a glance**, not merely distinguishable on close reading. Reusing red at two different
shades for "blocks your work" and "saved fine, but look at this" risks exactly the ambiguity the
requirement exists to prevent, and blue is already fully committed to the accent/primary-action
role. Amber is the conventional, widely legible "caution, non-blocking" signal and is used
**nowhere else** in the app, so its appearance is always meaningful.

Accent (`blue-600`) reserved for: "New template" button, "Save template" button, "Create template" button in
the new-template dialog, "Make active" text action, the release picker's focus ring, the
Placeholders drawer toggle button's active/open state, and the clean-save confirmation banner
(`bg-blue-50 border-blue-200 text-blue-900`, matching Phase 3's add-result banner exactly).

Destructive (`red-600`) reserved for: "Delete template" button + confirmation, malformed-Mustache
save-rejection banner, render-bound-breach save-rejection banner, logo upload rejection text, the
"Discard changes" button in the unsaved-changes-on-navigate confirmation.

Warning (`amber-600`/`amber-50`) reserved for: the save-succeeded-with-warnings banner, the
unknown-placeholder count/detail disclosure, the in-preview `[[unknown: token]]` marker chip, the
per-template "has warnings" list-row indicator, and the placeholder catalog's "always empty until
Phase 6" tag on `commits`/`pullRequests` entries. Not used for anything else — in particular, not
for the preview's "this is approximate" or "release picker" notices, which are informational, not
cautionary, and stay in the existing blue-50 informational tone or plain gray, per below.

Active-template badge and Open/Frozen-style status pills reuse Phase 3's neutral-gray badge
convention (`bg-gray-800 text-white` for "Active" — the darkest neutral signals "this is the one in
force," same reasoning Phase 3 used for `FROZEN`). No accent or warning color is used for badges,
consistent with the standing "accent/warning is not for status text" rule carried from Phase 2/3.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA (template list) | **"+ New template"** — per document-type section; opens a small dialog collecting only a name (document type is fixed by the section it's in). |
| Primary CTA (authoring screen) | **"Save template"** — always enabled except while a save request is in flight (`"Saving…"`, same border-spin pattern as `/tickets`/release-detail). |
| Empty state (template list, a document type has zero templates — reachable only after deleting every template of that type; never on first run per D-04-14) | Heading: **"No {DocumentType} templates yet."** Body: **"Create one to get started."** with the section's own "+ New template" action directly below — no separate link needed. |
| Empty state (authoring screen, body is blank) | In the **preview pane's body area only** (not a page-level empty state): **"This template's body is empty."** — `text-gray-500 italic text-sm`, replacing where rendered content would go. Chrome (cover/header/footer), if configured, still renders normally around it. |
| Empty state (no releases exist to preview against) | Release picker shows a disabled placeholder option **"No releases available"**; preview pane shows a neutral panel: **"Create a release first to preview this template against real data."** with a **"Go to releases"** link to `/releases`. |
| Save succeeded, clean | `role="status"`, `bg-blue-50 border border-blue-200 text-blue-900`: **"Template saved."** |
| Save succeeded, with warnings | `role="status"`, `bg-amber-50 border border-amber-200 text-amber-900`: **"Template saved with {n} unknown placeholder warning(s)."** with a **"Show details"** disclosure listing each unresolved token (e.g. `ticket.compnent` — body; `cover.title` — chrome). Never phrased as an error — the save genuinely succeeded (D-04-07). |
| Save blocked, malformed | `role="alert"`, `red-600`, rendered inline above the editor toolbar (same `fieldErrors`-adjacent convention as `SettingsRoute`/release-create, since the specific defect text is backend-generated and dynamic): **"Template not saved — {backend detail text, e.g. 'Unclosed section: {{#items}} has no matching {{/items}}.'}"** Identifies which field (Body / Cover title / Cover subtitle / Header text / Footer text) when the defect is in a chrome field. |
| Save blocked, render bound exceeded | `role="alert"`, `red-600`: **"Template not saved — validation took too long or produced too much content to render safely. Simplify the template (fewer nested sections or shorter loops) and try again."** |
| Live preview, syntax cannot parse (before save, as-you-type) | Preview pane body area shows a neutral panel (not `role="alert"` — this is expected mid-typing, not a failure): **"Preview unavailable — check your template syntax (e.g., every {{#x}} needs a matching {{/x}})."** `bg-gray-50 text-gray-600 text-sm p-4`. |
| In-preview unknown placeholder marker | `[[unknown: {token}]]` rendered inline, `font-mono text-xs bg-amber-100 text-amber-900 px-1 py-0.5 rounded` — conspicuous, never a silent blank (D-04-08). |
| Preview, client-side collection cap exceeded | `bg-blue-50 border border-blue-200 text-blue-900 text-xs px-3 py-2` informational strip above the rendered content: **"Preview truncated — this release has {n} items; showing the first {cap}. Generated documents are bounded separately when produced."** Non-blocking, informational tone (blue, not amber) — this is a preview practicality, not a defect in the author's template. |
| Preview, standing approximation notice (always visible, non-dismissible) | `bg-gray-100 text-gray-600 text-xs px-3 py-1.5 border-b border-gray-200`, pinned above the preview content: **"Preview approximation — actual page breaks, headers, and footers are determined when the document is generated."** |
| Page-numbering literal placeholder in preview | **"Page X of Y"**, `italic text-gray-400`, rendered wherever the page-numbering toggle is on, inside the header or footer strip. |
| Template delete confirmation | Title: **"Delete {template name}?"** Body (non-active template): **"This permanently deletes the template. Documents already generated from it are not affected. This cannot be undone."** Body (active template — same dialog, one extra sentence): **"This is the active {DocumentType} template. Deleting it will leave no active template for this document type until you mark another one active."** Buttons: **"Cancel"** / **"Delete template"** (`bg-red-600 text-white`). |
| Discard-unsaved-changes confirmation (navigating away, dirty template) | Title: **"Discard unsaved changes?"** Body: **"You have unsaved edits to '{template name}'. Leaving now will discard them."** Buttons: **"Keep editing"** (`border-gray-300 text-gray-700`) / **"Discard changes"** (`text-red-600 border border-red-600`). |
| Logo upload rejection — wrong type | `red-600` inline text below the drop zone: **"This file isn't a supported image. Upload a PNG or JPEG — SVG and other formats aren't accepted."** Identical copy whether caught client-side (extension/MIME pre-check) or server-side (content-sniffing per D-04-16) — the user-facing guidance is the same either way. |
| Logo upload rejection — too large | **"This image is too large. Upload a file under {maxSizeLabel}."** `{maxSizeLabel}` is sourced from the backend-declared limit, never hardcoded in the frontend. |
| Logo upload rejection — dimensions exceeded | **"This image is too large. Maximum dimensions are {maxWidth}×{maxHeight}px."** Same backend-sourced templating. |
| Logo remove | Plain **"Remove"** text button, `text-gray-600 hover:text-gray-900` — **no confirmation**, matching Phase 3's precedent for reversible, low-stakes actions (re-uploading is trivial). |
| Make-active | Plain **"Make active"** text button, `text-gray-600 hover:text-gray-900` — **no confirmation**; reversible, matching Phase 3's non-destructive-toggle precedent. |

## Screen Layout & States

### 0. `/templates` — template management surface (new route)

Route nested under `authenticatedRoute`, same pattern as `/tickets`/`/releases`. **AppShell nav:**
add a **"Templates"** link between "Releases" and "Settings" (same `Link` styling/`activeProps`
pattern).

- Header row (`white`, `p-6`): page heading "Templates" (Heading, 16px/600). No search/filter —
  template counts per type are small (a handful of named templates each), unlike the release
  library's search need.
- Three stacked sections, one per document type, in fixed order **Release Notes → Runbook →
  Approval** (matches the enum's natural generation order): each a `white` card
  (`border border-gray-200 rounded p-4`) with:
  - Section heading (Heading, 16px/600): **"Release Notes templates"** / **"Runbook templates"** /
    **"Approval templates"**.
  - A list of rows, one per template, sorted alphabetically by name: template name (`Link` to
    `/templates/$templateId`, `text-blue-600 font-semibold hover:underline`) · **"Active"** badge
    (`bg-gray-800 text-white` pill) when active, otherwise no badge · a small `amber-600` dot
    (`aria-label="Has unresolved placeholder warnings"`) when the template's last save recorded
    warnings · row actions: **"Make active"** (non-active rows only) · **"Duplicate"** · **"Delete"**
    (all plain `text-gray-600 hover:text-gray-900 text-sm` text buttons except Delete, which stays
    plain gray too — the confirmation dialog, not the trigger button, is what carries the weight,
    consistent with Phase 3's "Delete release" trigger only turning red on the confirming action;
    **correction for consistency with Phase 3**: keep "Delete" as `text-red-600` here to match Phase
    3's `/releases/$releaseId` row-action precedent for a genuinely destructive action-with-cost).
  - Empty state (that type has zero templates): see Copywriting Contract.
  - "+ New template" action at the bottom of each section's list — opens the new-template dialog
    (native `<dialog>`, single **Name** input, **Cancel**/**Create template** buttons) scoped to that
    section's document type; on success, navigates to `/templates/$newId`.
- **Duplicate** is an immediate action (no dialog): POST duplicates the template body/chrome/logo,
  names it "{name} copy" (backend disambiguates collisions), and navigates directly to the new
  copy's authoring screen so the manager can rename and edit right away.
- **Loading**: `gray-600 text-sm` "Loading templates…" + spinner glyph, replacing the three
  sections.
- **Error**: `role="alert" data-reason={reason}` red-600 + "Try again", replacing the three
  sections.

### 1. `/templates/$templateId` — two-pane authoring screen

**Toolbar row** (`white`, `p-6`, `flex items-center justify-between`):
- Left: template name (Heading, 16px/600) + a **"Rename"** text button (`text-blue-600 underline
  text-sm`) that swaps the name into an inline `<input>` on click, saving independently of the
  body/chrome Save action on blur/Enter · document type subtitle (`text-sm text-gray-600`, e.g.
  "Release Notes template") · Active badge / **"Make active"** action, same visual language as the
  list.
- Right: **"Placeholders"** toggle button (`border-gray-300 text-gray-700`, `bg-blue-50
  border-blue-300 text-blue-700` when the drawer is open — the one place accent tints a
  non-primary control, signaling "currently open" state) · dirty indicator text **"Unsaved
  changes"** (`text-sm text-gray-600`, present only when body/chrome differs from last save) ·
  **"Save template"** button.

**Tab switcher** (below toolbar, governs the **left (editor) pane only** — the right (preview)
pane always renders the full document regardless of active tab, since chrome affects the whole
document's appearance and the manager needs to see that while editing either half):
- **"Body"** (default) and **"Chrome & Logo"** — plain text tabs, active tab `border-b-2
  border-blue-600 text-gray-900 font-semibold`, inactive `text-gray-600`.

**Two-pane region** (below tabs): `flex flex-col lg:flex-row`, fixed height
(`h-[calc(100vh-260px)] min-h-[420px]`), each pane **independently scrolling**
(`overflow-y-auto`) so scrolling the preview never moves the editor or vice versa. Below the `lg`
breakpoint (1024px), panes stack vertically — editor first (the active task), preview second —
each taking full width with its own internal scroll rather than page-level scroll. **Not
resizable** — a fixed `lg:basis-[45%]` (editor) / `lg:basis-[55%]` (preview) split, deliberately
simple (no drag-handle component to build/maintain) since D-04-21 already establishes the preview
should get the larger, permanent share of space.

**Left pane — "Body" tab active:**
- Plain `<textarea>` (`font-mono text-sm leading-relaxed`, full pane height, `resize-none` — the
  pane itself scrolls, the textarea does not need its own resize handle), placeholder text
  **"Write Markdown + {{ }} placeholders…"** when empty.
- Tracks `selectionStart`/`selectionEnd` on every `blur`/`select` event into component state, so
  the last cursor position survives focus moving to the Placeholders drawer (see Placeholder
  Catalog Drawer below).

**Left pane — "Chrome & Logo" tab active:**
- Plain form, top to bottom, standard 14px inputs/labels (not monospace):
  1. **"Show cover page"** — native `<input type="checkbox">` + label.
  2. **Cover title** — `<input type="text">`, hint text below: "Accepts {{ }} placeholders, e.g.
     {{release.name}}."
  3. **Cover subtitle** — same pattern.
  4. **Header text** — `<input type="text">`, hint: "Shown as a strip at the top of every page."
  5. **Footer text** — `<input type="text">`, hint: "Shown as a strip at the bottom of every
     page."
  6. **"Show page numbers"** — checkbox + label, note beneath (`text-xs text-gray-500`): "Preview
     shows a literal placeholder — actual page numbers are calculated when the document is
     generated."
  7. **Logo** — see Document Chrome & Logo below.
- All six chrome fields are always editable regardless of the cover/page-number toggle states (no
  disabled/dimmed styling) — the toggles govern whether the *preview and future generation* use
  them, not whether they can be filled in ahead of time. Each field validates and warns exactly
  like the body (unknown placeholders warn, malformed constructs block save), aggregated into the
  same save-time banner.
- Each field tracks its own last cursor position the same way the body textarea does, so the
  Placeholders drawer can insert into whichever field — body or any chrome input — was last
  focused.

**Right pane — preview (always full document, regardless of left tab):**
- Top strip 1 (always visible, non-dismissible): the standing approximation notice (see
  Copywriting Contract).
- Top strip 2: release picker — `<select aria-label="Preview against">`, label text "Preview
  against:" — populated from the manager's releases, defaulting to the most recently created one.
  Disabled with the "No releases available" placeholder when none exist.
- Cover block (rendered only when "Show cover page" is on): `bg-white border border-gray-300
  shadow-sm rounded p-8 mb-6 text-center` — logo thumbnail (if uploaded, centered, `max-h-20`) →
  cover title (`text-2xl font-semibold`) → cover subtitle (`text-base text-gray-600 mt-2`),
  resolved against the selected release.
- Header strip (rendered whenever header text is non-empty): `bg-gray-100 text-gray-700 text-xs
  px-4 py-2 border-b border-gray-300`.
- Body content: `prose prose-gray max-w-none` container, the Mustache+Markdown render of the body
  textarea against the selected release. Unknown-placeholder markers and the "preview unavailable"
  / "body is empty" / "collection truncated" states render inside this container per Copywriting
  Contract.
- Footer strip (rendered whenever footer text is non-empty): same styling as header,
  `border-t` instead of `border-b`, placed at the very end.
- Page-number placeholder text renders inside whichever of header/footer strips is present, when
  "Show page numbers" is on.

### 2. Placeholder Catalog Drawer (D-04-21, D-04-20)

- Trigger: the toolbar's **"Placeholders"** button (state above). Toggles open/closed; a second
  click, clicking outside the drawer, or Escape (while the drawer has focus) closes it.
- **Non-modal.** No backdrop dimming the rest of the page — the editor/chrome form underneath must
  stay visible and directly interactive, since inserting a placeholder is meant to feel like
  continuing to write, not leaving the editor.
- Desktop (`lg` and above): absolutely positioned panel, `w-[380px] h-full`, `bg-white
  shadow-lg border-l border-gray-300`, anchored to the right edge of the two-pane region — it
  overlays the **preview pane** (which the author is not actively typing into), never the editor.
- Narrow (`<lg`): expands to full viewport width and slides up from the bottom instead
  (`inset-x-0 bottom-0 max-h-[70vh]`), so it stays usable when the two panes are stacked.
- Drawer header: title "Placeholders" (Heading) + a `×` close button (`aria-label="Close
  placeholder catalog"`, reusing Phase 3's dismiss glyph) + a text filter input
  (`placeholder="Filter placeholders…"`, client-side substring match — D-04-06's fixed vocabulary
  is small enough that this never needs a network request).
- Content: three collapsible sections — **Release fields** (root), **Item fields** (valid inside
  `{{#items}}` and `{{#groups}}{{#items}}`), **Group fields** (valid inside `{{#groups}}`) — each
  a list of real `<button>` rows (not `<li>`/`<div>`, so every entry is independently focusable
  and Enter/Space-activatable). Each row shows:
  - The token in `font-mono text-sm` (e.g. `release.name`, `items.status`).
  - A one-line prose description (`text-sm text-gray-700`) — properly written sentences per
    D-04-20, not annotation-style fragments.
  - Scope/eligibility tags, `text-xs px-1.5 py-0.5 rounded`, neutral gray
    (`bg-gray-100 text-gray-700`) for informational tags, **amber**
    (`bg-amber-100 text-amber-800`) only for the genuinely load-bearing caution tag: **"Always
    empty until Phase 6"** on `commits`/`pullRequests`. Other tags stay neutral gray: "Chrome +
    Body" / "Body only", "Ticket only", "Manual only".
- **Representative catalog contents** (illustrative, not exhaustive — the actual constant is
  D-04-20's concern, this establishes the pattern and grouping the researcher expects):

  | Group | Token | Description (example) | Tags |
  |---|---|---|---|
  | Release | `release.name` | The release's name. | Chrome + Body |
  | Release | `release.version` | The release's version string. | Chrome + Body |
  | Release | `release.status` | `OPEN` or `FROZEN`. | Chrome + Body |
  | Release | `release.jiraProjectKey` | The advisory Jira project key, empty if none was set. | Chrome + Body |
  | Release | `release.createdAt` / `frozenAt` / `lastRefreshedAt` | Release lifecycle timestamps; `frozenAt`/`lastRefreshedAt` empty if not yet frozen/refreshed. | Chrome + Body |
  | Item | `items` | Loop over every release item, ticket-backed and manual, in one unified collection. | Body only |
  | Item | `items.title` | The ticket summary or manual item title. | Body only |
  | Item | `items.isManual` | Section/inverted-section flag — true for manual items. Use `{{#isManual}}…{{/isManual}}` or `{{^isManual}}…{{/isManual}}` to branch. | Body only |
  | Item | `items.key`, `.issueType`, `.status`, `.resolution`, `.assignee`, `.reporter`, `.description`, `.comments` | Ticket fields. **Empty for manual items** — described explicitly, per D-04-01. | Body only · Ticket only |
  | Item | `items.category` | The manual item's category. **Empty for ticket items.** | Body only · Manual only |
  | Item | `items.commits`, `items.pullRequests` | Linked code detail. **Always empty until Phase 6** — see D-04-18. | Body only · Ticket only · Always empty until Phase 6 |
  | Group | `groups` | Items pre-grouped by issue type (tickets) or category (manual items, which have no issue type). | Body only |
  | Group | `groups.groupName` | The group's label. | Body only |
  | Group | `groups.items` | The item collection within this group — same fields as the root `items` above. | Body only |

- **Insert-at-cursor mechanism (mouse and keyboard identical):** clicking or Enter/Space-activating
  a catalog row inserts that token, wrapped as `{{token}}`, at the **last recorded cursor
  position** of whichever field (body textarea or a chrome input) was last focused before focus
  moved to the drawer — never the field's live DOM selection, since focus has already left it
  either way. After insertion, focus programmatically returns to that field with the cursor placed
  immediately after the inserted text, and an `aria-live="polite"` region announces "Inserted
  {{token}}" for screen-reader users who did not visually track the focus jump. The drawer **stays
  open** after an insert (multi-insert is the common case); the author closes it explicitly via
  `×`, the toggle button, Escape, or clicking outside.
- If no field has ever been focused yet when an insert is attempted, insert at the end of the body
  textarea and switch the tab to "Body" if "Chrome & Logo" was active — a sensible default rather
  than a dead click.

### 3. Document Chrome & Logo — logo upload control

Lives inside the "Chrome & Logo" tab (state 1), below the six structured fields.

- **No logo uploaded:** dashed drop zone, `border-2 border-dashed border-gray-300 rounded p-6
  text-center`: "Drag and drop a PNG or JPEG, or" + **"Choose file"** button
  (`border-gray-300 text-gray-700`) triggering a hidden `<input type="file"
  accept="image/png,image/jpeg">`.
- **Logo uploaded:** thumbnail (`max-h-40 max-w-full object-contain border border-gray-200
  rounded p-2 bg-white`) + metadata line (`text-sm text-gray-600`, e.g. "logo.png · 420×140px ·
  38KB") + **"Replace"** (`text-gray-600`, reopens the file picker) and **"Remove"**
  (`text-gray-600`, no confirmation — see Copywriting Contract) text actions.
- **Upload/remove take effect immediately**, via their own request — **not** part of the
  body/chrome unsaved-changes tracker the "Save template" button governs. This is a deliberate
  simplification: holding a pending `File` object across the Save button adds real state-management
  complexity for no material benefit, since a logo change has no meaningful "undo before save"
  need the way a half-typed body edit does.
- In flight: drop zone/thumbnail area shows the same border-spin + "Uploading…" pattern used
  elsewhere in the app (no bespoke progress bar for a single small image).
- Rejection states: inline `red-600` text directly below the control — see Copywriting Contract
  for the three specific messages (wrong type, too large, dimensions exceeded). Identical copy
  whether the rejection originates from a fast client-side pre-check or the server's
  content-sniffing validation (D-04-16), so the author never sees two different messages for what
  reads as the same problem.

### 4. Validation feedback — summary of the three states

Concrete, separable at a glance, per focus area 3:

| State | Trigger | Visual | Blocks save? |
|---|---|---|---|
| Clean | Save succeeds, sample-context render finds no unknown tokens | `blue-50`/`blue-200`/`blue-900` banner, "Template saved." | No — succeeded |
| Warning | Save succeeds, sample-context render finds ≥1 unknown token | `amber-50`/`amber-200`/`amber-900` banner + count + disclosure; amber marker chip in preview; amber dot on list row | **No** — D-04-07 deliberately does not block |
| Error (malformed) | Save-time backend rejects a construct outside D-04-06's subset (partials, lambdas, custom delimiters, unclosed section) | `role="alert"` red-600 banner, backend detail text, field identified | **Yes** |
| Error (bound exceeded) | Save-time render breaches the timeout or collection cap | `role="alert"` red-600 banner, fixed copy | **Yes** |

Live-preview-only, pre-save: a syntax the client renderer cannot parse at all shows the neutral
gray "Preview unavailable" panel (not red, not amber — this is expected mid-typing, and the
authoritative gate is the Save button, not the live preview).

### 5. Unsaved-changes handling

- Any router navigation away from `/templates/$templateId` while body/chrome differs from last
  save (in-app link click, browser back/forward, or the "Templates" nav link) triggers the
  discard-confirmation `<dialog>` (see Copywriting Contract) via a TanStack Router navigation
  blocker. A `beforeunload` listener covers tab close/reload with the browser's native prompt.
  Logo changes never trigger this (they already persisted immediately, per state 3).
- The "Unsaved changes" toolbar text is the only in-page dirty signal — no color change on the
  Save button itself, kept deliberately simple.

### Primary visual anchor (Dimension 2)

Every screen in this phase declares one focal point. Nothing else on the screen may compete with it
for visual weight.

- **`/templates`** — the **three document-type section cards**. The eye should land on "which
  templates exist, and which one is active per type." The `bg-gray-800` Active pill is the strongest
  mark on the screen and is what the anchor resolves to; row actions stay plain text so they never
  compete with it. There is deliberately no search, no filter bar and no toolbar above the sections
  to pull attention away.
- **`/templates/$templateId`** — the **rendered preview pane**. This is the whole reason D-04-21
  chose two panes over three and gave the preview the larger 55% share: the author's question is
  "what does this produce," and the preview is the only thing that answers it. Consequences that
  follow and are binding: the source textarea stays visually quiet (mono, no highlighting, no
  chrome of its own); the catalog drawer overlays the **preview** rather than the editor only
  because the drawer is transient and the editor is where the cursor lives — but the drawer must be
  dismissible in one gesture precisely because it occludes the anchor; and no persistent banner,
  toolbar or panel may be added above the preview that would push it below the fold at the
  `lg` breakpoint.

## Planning input — items the planner/backend must resolve

Recorded here rather than silently assumed, matching Phase 2/3's convention of surfacing
backend-facing gaps discovered while designing the UI:

1. **New `ProblemDetail` reason codes needed**, extending the Phase 1 taxonomy — do not invent a
   parallel scheme: `TEMPLATE_MALFORMED` (with a human-readable `detail` describing the specific
   defect and which field it's in), `RENDER_BOUND_EXCEEDED` (timeout or collection cap breached
   during save-time validation), and a logo-upload family (`LOGO_INVALID_TYPE`,
   `LOGO_TOO_LARGE`, `LOGO_DIMENSIONS_EXCEEDED`, or one `LOGO_REJECTED` with a machine-readable
   sub-reason — planner's choice, but the three distinct user-facing messages in the Copywriting
   Contract must map to something specific enough to select the right string).
2. **Backend-declared logo limits must be fetchable**, not hardcoded in the frontend — the
   rejection copy for size/dimensions templates `{maxSizeLabel}`/`{maxWidth}×{maxHeight}` from a
   config or catalog endpoint, consistent with D-04-16 keeping the bound a single source of truth.
3. **Deleting the active template is permitted by D-04-13** and leaves its document type with zero
   active templates. The UI warns (see confirmation copy) but does not block it, per the locked
   decision's "no delete guard." The backend and Phase 5's generation path must tolerate a document
   type having no active template — this is out of Phase 4's build scope but must not be an
   unhandled state when Phase 5 starts.
4. **Manual-item grouping inside `{{#groups}}`** is described in the catalog table above as "by
   category, since manual items have no issue type" — this is the researcher's inference from
   D-04-02's planner note, not a confirmed backend design. Verify against the actual view-model
   assembler and correct the catalog description if the grouping key differs.
5. **`@tailwindcss/typography` is recommended, not mandated** — it is the natural fit for the
   "reads as a document" requirement and adds no JS runtime, but if the planner has a reason to
   hand-roll the prose styles instead, the binding constraint is the *outcome* (a document-like
   internal type scale, scoped to the rendered container only), not the specific plugin.
