<objective>
Extend the existing Phase 4 render pipeline with the three things every downstream Phase 5 plan
needs, and fix one correctness defect Phase 4 already shipped.

Purpose:
1. **Correctness fix (shipped defect).** `pom.xml` carries `com.vladsch.flexmark:flexmark` (core
   only). GFM pipe tables are an opt-in flexmark extension, so the backend currently renders
   `| Service | Service |` as a literal paragraph, while the client `markdown-it` preview renders a
   real table. `src/main/resources/templates/starter-approval.md` already contains a pipe table, and
   the reference customer document (`docs/templates/orchstro-release-notes.md`) depends on one. This
   divergence is invisible in the authoring preview and only shows up in a generated document.
2. **Shared-AST hand-off.** `parseMarkdown` is already package-private for exactly this phase
   (D-04-04). The PDF adapter also needs the *existing* `HtmlRenderer` applied to that same
   `Document`, so a package-private `renderHtml(Document)` sibling is added rather than each new
   adapter building its own renderer (which would reintroduce the divergence this plan is fixing).
3. **Plain-text chrome resolution.** A running header is one line of text (TMPL-08), not a Markdown
   document. Generation must store *resolved* chrome, so the render port needs a Mustache-only
   `resolve` alongside `render`, and `RenderService` needs a bounded wrapper for it.
4. **Dependency + boundary setup for both renderers.** Adding openhtmltopdf and docx4j here (with
   the ArchUnit confinement rule extended in the same commit) means plans 05-05 and 05-06 can run in
   parallel without both editing `pom.xml` and `ArchitectureBoundaryTest.java`.

Output: three new Maven dependencies, an extended render adapter/port/service, an extended ArchUnit
rule, and tests proving the table gap is closed.
</objective>
