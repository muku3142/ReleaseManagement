<objective>
Render a stored document snapshot's Markdown to a PDF with its cover page, running header, footer
and page numbering (DOC-05, and the PDF half of DOC-08).

Purpose: openhtmltopdf gets the body almost for free — plan 05-01 exposed `parseMarkdown` and
`renderHtml` so this adapter reuses the *same* parser and *same* HTML renderer the authoring preview
and save-time validation already use. That reuse is the whole of D-05-07's parity argument for the
body. The genuinely new code is the **chrome shell**: a full XHTML document with `@page` margin
boxes, `counter(page)`/`counter(pages)`, a `position: running()` header element, and a cover page.
There is no analog for that shell anywhere in this codebase (05-PATTERNS.md "No Analog Found") — build
it from RESEARCH.md Pattern 3, not from a local file.

**Export does not re-enter `RenderService`.** The snapshot already holds resolved Markdown and
resolved chrome. Re-running Mustache here would resolve against *today's* release data and destroy
the immutability DOC-07 promises. This adapter takes strings and bytes, not a release.

Output: a one-method port, the adapter, and a test that opens the produced PDF and asserts on it.
</objective>

```css
@page { size: A4; margin: 2.5cm 2cm;
  @top-center { content: element(runningHeader); }
  @bottom-center { content: FOOTER_CONTENT; } }
body { font-family: sans-serif; font-size: 11pt; line-height: 1.45; }
#running-header { position: running(runningHeader); font-size: 9pt; color: #444; }
.cover { page-break-after: always; text-align: center; padding-top: 6cm; }
.cover img { max-height: 3cm; }
.cover h1 { font-size: 24pt; margin: 0.6cm 0 0 0; }
.cover p { font-size: 13pt; color: #555; }
h1, h2, h3 { page-break-after: avoid; }

```

A4 is the default page size, resolving RESEARCH.md Open Question #2: the tenant is
`evisionegypt.atlassian.net` and it is a one-line constant to change.

`FOOTER_CONTENT` is built in Java, not templated by the caller:
- footer text set, page numbers on → `"<escaped footer> \2022 Page " counter(page) " of " counter(pages)`
- footer text set, page numbers off → `"<escaped footer>"`
- footer text empty, page numbers on → `"Page " counter(page) " of " counter(pages)`
- both empty → `none`

**Emit the `@page :first` override only when `chrome.coverEnabled()` is true**, suppressing both
margin boxes on the cover:
```css
@page :first { @top-center { content: none; } @bottom-center { content: none; } }
```
If there is no cover page, page 1 is body content and must keep its chrome — suppressing it there
would be a bug, not a nicety.

Body of the XHTML, in order:
1. `<div class="cover">` — only when `coverEnabled`. Contains the logo `<img>` (only when `logo != null`),
   an `<h1>` with the resolved cover title and a `<p>` with the resolved cover subtitle.
2. `<div id="running-header">` — only when the resolved header text is non-blank. This element must
   exist in the flow exactly once for `position: running()` to work.
3. `<div class="body">` + `bodyHtml`.

**Two escaping rules, both mandatory and both tested in Task 2:**
- Chrome text placed in **HTML** (cover title, cover subtitle, running header) is HTML-escaped:
  `&` → `&amp;`, `<` → `&lt;`, `>` → `&gt;`, `"` → `&quot;`. Chrome fields are Mustache-resolved
  user text and can carry `<script>`; the body's protection (`neutralizeRawHtml`) does not cover
  them because they never pass through flexmark.
- Chrome text placed in a **CSS string** (the footer) is CSS-escaped: `\` → `\\`, `"` → `\"`, and
  CR/LF/`}`/`<` are stripped. An unescaped `"` in a footer closes the CSS string and lets the
  remainder of the footer become CSS declarations.

Logo: embed as `data:<storedContentType>;base64,<bytes>` using
`logo.metadata().contentType()` — **never** a type derived from `logo.metadata().filename()`. The
content type was established by content sniffing at upload (TMPL-09); re-deriving it from a filename
would undo that.

Render with a **fresh** builder per call into an in-memory buffer (RESEARCH.md Patterns 2 and 6 —
`PdfRendererBuilder` accumulates per-document state and is not safe to share; `StreamingResponseBody`
is not warranted at this document scale):
```java
ByteArrayOutputStream out = new ByteArrayOutputStream();
PdfRendererBuilder builder = new PdfRendererBuilder();
builder.useFastMode();
builder.withHtmlContent(xhtml, null);   // null base URI: no external resource resolution
builder.toStream(out);
builder.run();
return out.toByteArray();
```
Passing `null` as the base URI is a security control, not an omission: with no base URI the renderer
cannot resolve a relative `src`/`href` against a local path. Register no fonts (RESEARCH.md Pitfall 3
— PDFBox cannot embed `.otf`, and the typography contract is the system sans stack). Do not reach
for the lower-level `PdfBoxRenderer` (Pitfall 4).

Wrap any exception from `run()` in `UncheckedIOException` — plan 05-08 converts it to
`EXPORT_FAILED`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| stored template content (untrusted author) → openhtmltopdf | Markdown body and the four chrome strings originate as untrusted template text |
| stored logo bytes → PDF image embedding | Content-validated at upload (TMPL-09), re-embedded here |
| PDF renderer → local filesystem / network | openhtmltopdf resolves `src`/`href` against a base URI if given one |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-21 | Tampering (markup injection via chrome) | cover title/subtitle/header in the XHTML shell | mitigate | Chrome text never passes through flexmark, so `neutralizeRawHtml` does not protect it. HTML-escape `& < > "` before interpolation; asserted by `htmlInChromeTextIsEscapedNotRendered`. |
| T-05-22 | Tampering (CSS injection via footer) | `@bottom-center { content: "…" }` | mitigate | Footer text is interpolated into a CSS string literal. Escape `\` and `"`, strip CR/LF/`}`/`<`; asserted by `quoteInFooterTextDoesNotBreakTheStylesheet`. Without this, a footer containing `"` closes the string and the remainder becomes CSS. |
| T-05-23 | Information Disclosure (SSRF / local file read via resource resolution) | `PdfRendererBuilder.withHtmlContent(xhtml, baseUri)` | mitigate | Base URI is passed as `null`, so relative `src`/`href` cannot resolve. Body markup cannot contain raw HTML at all (`neutralizeRawHtml`, D-04-05), and the only image emitted is the logo as an inline `data:` URI. |
| T-05-24 | Spoofing (content-type confusion on the embedded logo) | logo data URI | mitigate | The MIME type comes from `logo.metadata().contentType()` — the content-sniffed value stored at upload — never from the filename. Grep criterion asserts `metadata().filename()` appears nowhere in the adapter. |
| T-05-25 | Denial of Service (unbounded PDF layout) | openhtmltopdf layout pass | accept | RESEARCH.md Pitfall 5 and A3: the stored Markdown was itself produced under `RenderService`'s collection cap at generation time, so pathological input is not reachable through the normal generate→export path. Adding a second timeout wrapper is recorded as an explicit non-goal. Revisit if measured export times at the cap's upper bound prove otherwise. |
| T-05-26 | Denial of Service (renderer state corruption under concurrency) | `PdfRendererBuilder` reuse | mitigate | A fresh builder is constructed inside the export method on every call (RESEARCH.md Pattern 2 — the builder accumulates per-document state; sharing it across concurrent requests corrupts output). Grep criterion asserts it is not a field. |
| T-05-27 | Information Disclosure (resource leak) | PDFBox temp/font resources | mitigate | The one-shot `PdfRendererBuilder(...).toStream(...).run()` API manages its own lifecycle; the lower-level `PdfBoxRenderer`, which requires explicit `cleanup()` on every path including exceptions, is explicitly not used (RESEARCH.md Pitfall 4). |
</threat_model>
