| Question | Decision | Why |
|---|---|---|
| Control shape | A labelled `type="number"` input with `min={5} max={120} step={1}`, followed by the file's standard `text-xs text-gray-500` hint. Label: **"Cover logo height (mm)"**. | `ChromeFieldsForm.tsx`'s four text inputs are the structural analog (label above, input, hint below, identical `className`). No `type="number"` exists anywhere in `frontend/src` today, so this establishes it — following the text inputs' structure exactly, only the `type` and the constraint attributes differ. The unit goes in the label so the number needs no suffix decoration. |
| Does the browser also constrain the input | **Yes, `min`/`max`/`step` as HTML5 attributes — advisory only.** No JS clamping, no local validation state, no disabled Save. | `min`/`max` on a number input are free and give the author spinner bounds. They are not a guarantee (typing works around them), which is fine: `@Min(5) @Max(120)` on `ChromeFieldsRequest` is the authority, and an out-of-range save already surfaces through `TemplateDetailRoute.tsx`'s existing catch-all `saveProblem` banner (lines 392-396) with no new error path. |
| Must the field join `ChromeFieldName` | **No.** | `ChromeFieldName` exists solely to drive placeholder-caret tracking for the four fields that accept `{{ }}`. Placeholders make no sense in a number. Concretely: `TemplateDetailRoute.chromeFieldElement` (line 204) locates chrome inputs positionally with `querySelectorAll('input[type="text"]')`, so a `type="number"` input is invisible to that lookup and `CHROME_FIELD_ORDER`'s indexing stays correct. The new input therefore also gets **no** `onBlur`/`onSelect`/`trackSelection`. |

One deliberate deviation from a file convention, worth the one-line comment the action below specifies:
`RenderedDocument.tsx` is `className`-only today, but Tailwind's `max-h-*` scale is fixed steps with no
`mm` unit and no arbitrary-value variant in use anywhere in this codebase. An inline
`style={{ maxHeight: '...mm' }}` is simpler and more honest than synthesising a dynamic class string.
</decisions_resolved>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| author's keystrokes → `chrome.logoRenderHeightMm` in React state | Free-form input; a number input still accepts arbitrary typed text and yields whatever `Number()` produces |
| React state → inline `style` on the cover `<img>` | A value crosses into a CSS declaration, in the one component that renders both the authoring preview and the document viewer |
| React state → `PUT /api/templates/{id}/content` body | The value leaves the browser and becomes a server-side persistence request |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05.1-06 | Injection (a value reaching a CSS declaration) | `RenderedDocument.tsx` inline `style={{ maxHeight: ... }}` | mitigate | React's `style` prop takes an object, not a CSS string: the value is set through the CSSOM, which parses `${n}mm` as a single declaration and cannot be escaped into a second one. `Number(e.target.value)` guarantees a `number` or `NaN` reaches state — never a string — so no `escapeCss`-style control is applicable or needed. Contrast the footer text (`PdfExportAdapter.escapeCss`), which genuinely is an author-supplied *string* entering a CSS string literal. |
| T-05.1-07 | Tampering (a browser bypassing `min`/`max` to persist an out-of-range height) | the `type="number"` input | mitigate (server-side) | Explicitly accepted as unenforceable in the browser: HTML5 `min`/`max` are advisory and DevTools defeats them. Plan 01's `@Min(5) @Max(120)` on `ChromeFieldsRequest` plus V6's `CHECK ... BETWEEN 5 AND 120` on both tables are the authority. The rejection already surfaces to the user through `TemplateDetailRoute.tsx`'s existing catch-all `saveProblem` banner (lines 392-396) — no new error path is added. |
| T-05.1-08 | Denial of Service (a cleared or non-numeric input yielding `NaN`, breaking the preview) | `Number(e.target.value)` | accept | `Number('')` is `0`, which the preview renders as `maxHeight: 0mm` (an invisible logo, visibly wrong to the author in the live preview) and which the server then rejects on save with `VALIDATION_FAILED` through the existing banner. `type="number"` prevents non-numeric text from reaching `onChange` at all in every current browser. Adding client-side clamping or local validation state to pre-empt a self-evident, immediately-visible, server-rejected typo would be error handling for a case the existing surfaces already answer. |
| T-05.1-09 | Information Disclosure (the logo image URL) | `props.logoUrl` | accept | Unchanged by this plan. The `src` value, its authentication and its `no-store` handling are untouched; only the element's `max-height` changed. |
</threat_model>
