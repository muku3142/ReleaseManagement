<objective>
Close the actual defect. `PdfExportAdapter.buildCss` hard-codes `max-height: 3cm` and
`DocxExportAdapter.logoParagraph` applies **no cap at all** — it multiplies the logo's native pixel
dimensions by `EMU_PER_PIXEL`, so a 2000×2000 upload is ~20.8in tall on an 11.7in A4 page. Both now read
the height off the snapshot's chrome, and both scale proportionally, downward only.

Purpose: DOC-08's parity requirement, plus ROADMAP criteria 3, 4 and 5. And D-05.1-07: this defect
survived a 552-test suite and a passing phase verification because `PdfExportAdapterTest` and
`DocxExportAdapterTest` each assert their own side of a seam that no test crosses. Fixing the two
adapters without adding the crossing test would leave the mechanism that let this ship fully intact.

Output: two adapter edits, plus three tests in `GenerateThenExportSeamTest` that generate **one**
snapshot with an oversized logo and assert the rendered dimension in **both** formats — and a required
sanity check proving those tests fail against the pre-fix adapters.

**Why the seam test uses 15mm, not the 30mm default:** at 30mm the PDF's pre-fix hard-coded `3cm`
happens to produce the right answer, so a PDF assertion at the default would pass against broken code.
15mm makes the pre-fix PDF wrong (85pt instead of 43pt) **and** the pre-fix DOCX wrong (135mm instead of
15mm), so one test proves both defect sites are fixed *and* that the per-template value is genuinely
threaded template → snapshot → both exporters.

    private P logoParagraph(WordprocessingMLPackage pkg, ChromeFields chrome, LogoImage logo) throws Exception {
        // T-05-31: width/height come from the stored, content-sniffed LogoMetadata, never from a
        // filename - docx4j itself also determines the embedded content type from the image
        // bytes' own signature, not from any filename string.
        BinaryPartAbstractImage imagePart = BinaryPartAbstractImage.createImagePart(pkg, logo.bytes());
        long widthEmu = (long) logo.metadata().width() * EMU_PER_PIXEL;
        long heightEmu = (long) logo.metadata().height() * EMU_PER_PIXEL;
        // D-05.1-05, THE DEFECT: createImageInline takes explicit EMU dimensions, so unlike the PDF's
        // CSS max-height and the browser's, nothing here clamps on our behalf. Without this block a
        // 2000x2000 upload renders ~20.8in tall on an 11.7in A4 page - wider than the page and nearly
        // two pages long - while the same logo is 1.2in in the PDF.
        //
        // Scale WIDTH by the same ratio (D-05.1-06): a letterboxed or stretched logo is worse than an
        // oversized one. Only ever DOWN - the `if` is what makes this a maximum rather than a target,
        // matching how max-height already behaves in the other two renderers.
        long maxHeightEmu = chrome.logoRenderHeightMm() * EMU_PER_MM;
        if (heightEmu > maxHeightEmu) {
            double ratio = (double) maxHeightEmu / heightEmu;
            widthEmu = Math.round(widthEmu * ratio);
            heightEmu = maxHeightEmu;
        }
        Inline inline = imagePart.createImageInline("logo", "Logo", 0, 1, widthEmu, heightEmu, false);
        Drawing drawing = new Drawing();
        drawing.getAnchorOrInline().add(inline);
        R run = factory.createR();
        run.getContent().add(drawing);
        P p = centeredParagraph();
        p.getContent().add(run);
        return p;

**4. Add the four helpers** at the bottom of the class, after `unwrap`:

```java
    private static LogoImage logo(int width, int height) throws IOException {
        ByteArrayOutputStream out = new ByteArrayOutputStream();
        ImageIO.write(new BufferedImage(width, height, BufferedImage.TYPE_INT_RGB), "png", out);
        byte[] bytes = out.toByteArray();
        return new LogoImage(bytes, new LogoMetadata("image/png", "logo.png", bytes.length, width,
                height, Instant.now()));
    }

    // Reads the extent back off REOPENED bytes, matching DocxExportAdapterTest's stated convention:
    // walk the OOXML tree, never trust the writer's own intent. Note the flatten() walker above stops
    // at Drawing - Drawing exposes getAnchorOrInline(), not getContent(), so it is not a
    // ContentAccessor and the walker cannot descend into it. Hence the explicit last hop.
    private static Inline firstInline(byte[] docx) throws Exception {
        Drawing drawing = flatten(load(docx).getMainDocumentPart()).stream()
                .filter(o -> o instanceof Drawing).map(o -> (Drawing) o).findFirst()
                .orElseThrow(() -> new AssertionError("no Drawing in the exported DOCX"));
        return (Inline) unwrap(drawing.getAnchorOrInline().get(0));
    }

    // {renderedWidthPt, renderedHeightPt} of the first image drawn on page 1. PDF maps an image XObject
    // onto the unit square, so the CTM in force at that image's `Do` operator IS its rendered box in
    // points - which is the only signal that reflects what openhtmltopdf's CSS actually computed.
    // PDFBox 2.0.24 has no higher-level API for this, and PdfExportAdapterTest's countImageXObjects
    // proves only that an image is present.
    private static float[] firstImageSizePt(byte[] pdf) throws Exception {
        try (PDDocument document = PDDocument.load(pdf)) {
            ImageSizeCollector collector = new ImageSizeCollector();
            collector.processPage(document.getPage(0));
            assertThat(collector.sizes).as("no image drawn on the cover page").isNotEmpty();
            return collector.sizes.get(0);
        }
    }

    private static class ImageSizeCollector extends PDFStreamEngine {

        private final List<float[]> sizes = new ArrayList<>();

        @Override
        protected void processOperator(Operator operator, List<COSBase> operands) throws IOException {
            if ("Do".equals(operator.getName()) && operands.get(0) instanceof COSName name
                    && getResources().getXObject(name) instanceof PDImageXObject) {
                Matrix ctm = getGraphicsState().getCurrentTransformationMatrix();
                sizes.add(new float[]{ctm.getScalingFactorX(), ctm.getScalingFactorY()});
                return;
            }
            // Form XObjects and every other operator must still reach the base engine, or nested
            // content streams (and the graphics state they set) are never processed.
            super.processOperator(operator, operands);
        }
    }
```

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `document_snapshot.logo_render_height_mm` → a CSS declaration | A stored, author-originated number is interpolated into the stylesheet `openhtmltopdf` parses |
| the same value → EMU integer arithmetic | The same number drives explicit width/height computation for an embedded OOXML image |
| the same value → the printable page area | A rendered dimension large enough to displace content makes the document itself unusable |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05.1-10 | Injection (breaking out of a CSS declaration into arbitrary rules) | `PdfExportAdapter.buildCss` | mitigate | Already mitigated by type: `chrome.logoRenderHeightMm()` is a Java `int`, so `StringBuilder.append(int)` can only emit digits (or a leading `-`) and cannot emit `;`, `}`, `<` or a quote. `escapeCss` — which exists in this very file for the footer, an author-supplied *String* entering a CSS string literal — is neither needed nor applicable, and an acceptance criterion pins its call count at 4 so nobody adds a fifth. Independently, values outside 5..120 cannot reach here at all: `@Min(5) @Max(120)` on `ChromeFieldsRequest` and `CHECK ... BETWEEN 5 AND 120` on both V6 columns (plan 01). |
| T-05.1-11 | Denial of Service / integer overflow in EMU arithmetic | `DocxExportAdapter.logoParagraph` | mitigate | `EMU_PER_MM` is declared `long`, so `int mm * EMU_PER_MM` widens before multiplying and cannot overflow for any `int` mm at all, let alone a bounded one. Worst permitted case is `120 × 36000 = 4,320,000` — five orders of magnitude below `Long.MAX_VALUE`. The pre-existing `(long) width * EMU_PER_PIXEL` casts are kept unchanged. `ratio` is a `double` in `(0, 1)` and is applied only inside the `heightEmu > maxHeightEmu` branch, so `Math.round(widthEmu * ratio)` can only shrink. |
