## Decisions Made

**Task 1 was recovered and verified, not re-executed.** The plan's Task 1 was authored and self-verified by a prior executor session that was killed by a session limit before it could commit. The orchestrator confirmed the on-disk state against every Task 1 acceptance criterion (grep checks on both adapter files, `mvn clean test` at 558/0/0/0) and committed it as `437e479` before spawning this session. This session read but did not modify `PdfExportAdapter.java` or `DocxExportAdapter.java`, except transiently during the mandatory RED check (see below), after which both were restored via `git checkout --` to exactly `437e479`'s content.

**The PDF dimension assertion reads the image XObject's CTM scaling factors, not a rasterized bitmap measurement.** PDFBox always maps an image XObject onto the unit square before the content-stream's `cm`/`Do` pair positions and scales it; the CTM in force at that `Do` operator IS the image's rendered box in PDF points - the same signal openhtmltopdf's CSS `max-height` computation produced. This needed a `PDFStreamEngine` subclass overriding `processOperator` to intercept `Do` and read `getGraphicsState().getCurrentTransformationMatrix()`, since no existing helper in the codebase reads rendered (as opposed to native pixel) image dimensions - `PdfExportAdapterTest.countImageXObjects` only proves presence.

**The DOCX dimension assertion reuses the existing `flatten()`/`unwrap()` walker with one explicit extra hop.** `flatten()` already surfaces every unwrapped `JAXBElement` node in the document tree, including `Drawing` - but `Drawing` exposes `getAnchorOrInline()`, not `getContent()`, so it is not a `ContentAccessor` and the walker cannot descend into it on its own. `firstInline()` filters `flatten()`'s output for the first `Drawing`, then makes the one explicit `unwrap(drawing.getAnchorOrInline().get(0))` hop to reach the `Inline` and read `.getExtent().getCx()`/`.getCy()` - the exact EMU values `logoParagraph` set at construction, read back off reopened bytes per the file's stated "never trust the writer's own intent" convention.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `ImageSizeCollector` needed explicit operator registration to read a real CTM**

- **Found during:** Task 2, first run of the new seam tests (green suite, but the PDF assertion failed: `pdfSizePt[1]` was `1.0f` instead of ~`42.52f`).
- **Issue:** `PDFStreamEngine` (unlike its subclass `PDFTextStripper`, which registers dozens of operators in its own constructor) registers **zero** operators by default. The plan's mandated `ImageSizeCollector` code overrides `processOperator` only for `Do` and otherwise delegates to `super.processOperator(operator, operands)` for every other operator, including `cm` (concatenate matrix), `q` (save graphics state) and `Q` (restore). Without a registered `OperatorProcessor` for `cm`, the base class's fallthrough is a no-op - the graphics state's CTM never leaves identity, and `getCurrentTransformationMatrix().getScalingFactorX/Y()` always reports `1.0` regardless of what the page actually draws. This is a correctness bug in the mandated test code, not a design question: the class as written could never assert a real rendered dimension.
- **Fix:** Added a no-arg constructor to `ImageSizeCollector` that calls `addOperator(new Concatenate())`, `addOperator(new Save())`, `addOperator(new Restore())` from `org.apache.pdfbox.contentstream.operator.state` - the minimum set needed for the CTM this test reads to reflect the page's actual `cm`/`q`/`Q` sequence.
- **Files modified:** `src/test/java/com/evision/releasemgmt/application/GenerateThenExportSeamTest.java`
- **Verification:** Re-ran `mvn clean test -Dtest=GenerateThenExportSeamTest` - `pdfSizePt[1]` read `42.52f` (matching the predicted 15mm-in-points value) and all 7 tests passed.
- **Committed in:** `c41d74f` (Task 2 commit)
