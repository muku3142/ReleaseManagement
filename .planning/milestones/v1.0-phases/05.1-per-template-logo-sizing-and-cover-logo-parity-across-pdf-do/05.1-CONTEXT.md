# Phase 05.1: Per-Template Logo Sizing - Context

**Gathered:** 2026-08-11
**Status:** Ready for planning
**Source:** Direct decision capture (the direction was settled with the user immediately after Phase 5
closed, in the same session that found the defect). No `/gsd-discuss-phase` run — the user chose this
path over re-asking a decision they had just made.

<domain>
## Phase Boundary

**In scope:** making the cover logo's rendered height a per-template setting, and making all four
renderers honour it identically.

**Out of scope, explicitly:**
- Logo *upload* validation. `LogoValidator`'s byte cap (2 MB) and pixel cap (2000×2000) are about
  what may be stored and are a decompression-bomb control (`TMPL-09`). This phase is about *rendered*
  size. Do not touch `LogoValidator`, `app.template.logo.max-bytes`, `max-width` or `max-height`.
- Logo *position* (it stays centred on the cover), logo in the running header, or more than one logo.
- Any other chrome field's behaviour.
- The two tracked todos in `.planning/todos/pending/` (AdfFlattener paragraph separation, no-op
  staleness stamping on remove paths).
- Re-rendering or repairing existing snapshots. They are append-only by design.

**The defect this phase closes.** The cover logo is sized in three independent places and only two of
them cap it:

| Surface | Current sizing | A 512×512 logo renders at |
|---------|----------------|---------------------------|
| PDF | `PdfExportAdapter.java:97` — `.cover img { max-height: 3cm }` | ~1.2 in |
| Browser preview + viewer | `RenderedDocument.tsx:62` — `max-h-20` (5rem / 80px) | 80 px |
| DOCX | `DocxExportAdapter.java:204-205` — native px × `EMU_PER_PIXEL` (9525), **no clamp** | 5.3 in |

Uploads are accepted up to 2000×2000, so the DOCX worst case is ~20.8 in tall on an 11.7-in A4 page —
wider than the page and nearly two pages long. This is the `DOC-08` parity class that `D-05-07`
deliberately left to a human eyeball check, and that check only catches it when the logo happens to be
large enough to notice. Phase 5's parity check passed because the logo used was small.
</domain>

<decisions>
## Implementation Decisions

### D-05.1-01 — Per-template setting, not global configuration
The rendered height is authored per template, alongside the other chrome fields. Rejected alternatives,
both considered and declined by the user: a single `app.template.logo.render-max-height` in
`application.yml` (one value for every template, needs a restart to change, and an existing document
would silently re-render at whatever the current value is), and a clamp-only bug fix with no setting
at all.

### D-05.1-02 — It lives on `ChromeFields`
`TMPL-08`/`D-04-15` already establish `ChromeFields` as the structured, non-free-form home for
cover/header/footer presentation. Logo height is exactly that kind of setting, so it belongs there
rather than in a new aggregate, a new table, or a JSON blob.

**Blast radius the planner must account for:** `ChromeFields` is a Java record, so adding a component
breaks every construction site. There are **10 in `src/main`** —
`DocumentSnapshotRepositoryAdapter:127`, `TemplateRepositoryAdapter:183`, `TemplateController:121`,
`DocumentGenerationService:73`, three in `TemplateSeeder` (73, 78, 83), `ChromeFields.empty():10`, and
`Template.create` via `empty()` — and **13 test files**: `DocumentSnapshotPersistenceIT`,
`TemplatePersistenceIT`, `DocxExportAdapterTest`, `PdfExportAdapterTest`, `DocumentControllerTest`,
`DocumentExportControllerTest`, `TemplateControllerTest`, `TemplateLifecycleIT`,
`TemplateLogoControllerTest`, `DocumentExportServiceTest`, `DocumentGenerationServiceTest`,
`GenerateThenExportSeamTest`, `TemplateServiceTest`. This is a mechanical-but-wide change; plan for it
rather than discovering it.

### D-05.1-03 — Stored on the snapshot, so a generated document keeps its size
The value is copied into `document_snapshot` at generation time, exactly as the four resolved chrome
strings and the logo bytes already are. Re-exporting an old revision must reproduce the size it was
generated with, not today's template setting. This follows the same reasoning that made
`DocumentGenerationService` copy `templateBody` and the logo bytes rather than reference them: the
snapshot is the immutable audit record (`DOC-07`, and Phase 7's `AUDIT-02` rests on it).

### D-05.1-04 — Existing rows get a default equal to today's PDF behaviour
The V6 migration defaults both new columns to the current effective PDF size (`3cm` = `30mm`), so no
existing template or snapshot changes appearance. The one intentional visible change is DOCX, which
was rendering at native pixel size and is being brought into line. Do **not** backfill anything else,
and do **not** add an update path to `DocumentSnapshotRepository` — it exposes `create` plus reads and
no update at all (`D-05-06`), which is the guarantee this project depends on.

### D-05.1-05 — The DOCX clamp is required regardless of the setting
Even if the per-template value were dropped from scope, `DocxExportAdapter.logoParagraph` must clamp.
It is the defect. It must scale **proportionally** — compute the constrained height, then scale width
by the same ratio — never letterbox or stretch. `createImageInline` takes explicit width and height in
EMU, so the arithmetic is the adapter's own responsibility.

### D-05.1-06 — Aspect ratio is preserved in every renderer, and the constraint is a maximum
A logo smaller than the configured height renders at its natural size; it is never scaled *up*. This
matches how `max-height` already behaves in the PDF and the browser, so the DOCX clamp is what has to
be written to match them, not the reverse.

### D-05.1-07 — Parity is asserted, not left to a human this time
`D-05-07` declined automated cross-format parity and that stands as a general rule — but the specific
invariant "the logo is no taller than N in both formats" is mechanically checkable, and its absence is
what let this ship. The phase must include a test that asserts the clamp in both export paths from a
single generated snapshot, in the spirit of `GenerateThenExportSeamTest` (which exists precisely
because unit tests on either side of a seam cannot catch a contract mismatch). A human still eyeballs
overall visual parity; that is unchanged.

### Claude's Discretion

- **Unit.** `mm` is the strong steer: the output is a printed document, `openhtmltopdf` accepts `mm`
  natively in the `@page` CSS context, `1mm = 36000 EMU` exactly for docx4j, and CSS `mm` works in the
  browser — so one stored integer serves all three with no lossy conversion. `px` would be the odd
  choice for print. Settle it once and use it everywhere; do not store one unit and display another.
- **Default and bounds.** Default must be 30mm per `D-05.1-04`. The upper bound has to satisfy
  criterion 5: A4 is 297mm tall and `PdfExportAdapter` sets `2.5cm 2cm` margins, leaving 247mm of
  printable height, and the cover already has `padding-top: 6cm`. Pick a bound that cannot overflow
  the cover page and state the arithmetic. A lower bound above 0 avoids an invisible logo.
- **Control shape.** `ChromeFieldsForm.tsx` is the analog and its existing pattern is a labelled
  input with a `text-xs text-gray-500` hint below. A number input is the obvious fit. Note the form's
  `ChromeFieldName` union type currently covers only the four *text* fields because it drives
  placeholder-insertion caret tracking — a numeric field must not be added to that union, since
  `{{ }}` placeholders make no sense in it.
- **Validation placement.** Bean Validation on `ChromeFieldsRequest` is the established boundary
  (`SaveTemplateContentRequest` already uses `@NotNull @Valid`). Decide whether the browser also
  constrains the input, but the server is the authority.
- **Whether `ChromeFields.empty()` returns the default or zero.** `empty()` feeds
  `Template.create`, so a new template's initial value comes from here. Choose deliberately and say why.
</decisions>

<specifics>
## Specific Ideas

- **The seam test is the model to copy.** `GenerateThenExportSeamTest` drives content from a real
  `DocumentGenerationService.generate` call through a real `DocumentExportService` in both formats,
  with no hand-written fixture on either side. A logo-clamp assertion belongs in that same shape:
  generate once with an oversized logo, export both ways, assert the rendered dimension in each. Unit
  tests on `PdfExportAdapter` and `DocxExportAdapter` separately are what missed this defect class.
- **PDFBox and docx4j can both be inspected for image size.** The existing
  `PdfExportAdapterTest`/`DocxExportAdapterTest` helpers already open exported bytes; the DOCX side can
  read the `Inline` extent back off the drawing, which is the most direct assertion available.
- **Verify with an actually-oversized logo.** A 512×512 or larger PNG is needed to exercise the clamp;
  a small logo passes trivially under every implementation, including a broken one. Whatever fixture
  is used must be big enough that the pre-fix code visibly fails.
- **Check the Java version trap.** `export JAVA_HOME="$HOME/.jdks/jdk-25"` before every Maven call;
  the machine default is 17. And `mvn clean test` (not bare `mvn test`) after changing the record —
  incremental compilation will otherwise pass while tests still reference the 6-arg constructor.
- **Baselines that must not regress:** backend 556 tests, frontend 183 tests, `tsc -b` clean on a
  second consecutive run.
</specifics>

<deferred>
## Deferred Ideas

- Logo width control, or independent width/height. Height plus preserved aspect ratio covers the real
  need; two axes invite distortion.
- Logo placement options (left/centre/right, or in the running header rather than the cover).
- A second logo, or per-document-type logos beyond what per-template already gives.
- Repairing or re-rendering pre-existing snapshots — precluded by append-only (`D-05-06`), and the
  remedy is Regenerate, exactly as decided for the Phase 5 content-type fix.
- Automated *visual* parity (golden images) between PDF and DOCX. Still declined per `D-05-07`;
  `D-05.1-07` adds a dimensional assertion only, which is a different and mechanically checkable thing.
</deferred>
