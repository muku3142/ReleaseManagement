## Pattern Assignments

### Focus 1 — The ALTER TABLE precedent (there IS one; V6 is not the first)

**Analog:** `src/main/resources/db/migration/V5__document_generation.sql` lines 15-21, and
`V2__session_invalidation.sql` line 1-5 (the project's very first ALTER, for comparison).

V4 and V5 both do exclusively `CREATE TABLE` for the two tables this phase alters (`template` at
`V4__template_authoring.sql:9`, `document_snapshot` at `V5__document_generation.sql:37`), so neither of
those files is the analog for the ALTER itself — V5's own later lines are.

**The exact style to mirror** (`V5__document_generation.sql:17-21`):
```sql
-- D-05-04: the grouping dimension is a per-template setting. ISSUE_TYPE is the default precisely so
-- every template authored in Phase 4 keeps rendering {{#groups}} exactly as it did - the section
-- shape and {{groupName}} do not change, only which field keys the grouping.
ALTER TABLE template ADD COLUMN grouping_dimension VARCHAR(16) NOT NULL DEFAULT 'ISSUE_TYPE'
    CHECK (grouping_dimension IN ('ISSUE_TYPE', 'COMPONENT'));
```
This is `NOT NULL DEFAULT <value>` in one statement, with a comment above citing the decision ID and
explaining *why this default* — the exact style D-05.1-04 asks for on `template.logo_render_height_mm`.

**Contrast, from the same file** (`V5__document_generation.sql:7` and `:15`), showing the *nullable, no
default, no backfill* variant used when a column must NOT silently apply new behaviour to old rows:
```sql
ALTER TABLE release_ticket_item ADD COLUMN component VARCHAR(255);
...
ALTER TABLE release ADD COLUMN items_changed_at TIMESTAMPTZ;
```
**Do not use this second style for either V6 column** — D-05.1-04 explicitly wants both new columns
defaulted to `30` (mm), not nullable, because every renderer's `chrome.logoRenderHeightMm()` call must
always get a real int, never null-check it.

**What V6 needs, concretely** (two ALTERs, not one, matching D-05.1-03's "stored on both `template` and
`document_snapshot`"):
```sql
ALTER TABLE template ADD COLUMN logo_render_height_mm INTEGER NOT NULL DEFAULT 30
    CHECK (logo_render_height_mm BETWEEN <lower> AND <upper>);

ALTER TABLE document_snapshot ADD COLUMN logo_render_height_mm INTEGER NOT NULL DEFAULT 30;
```
Note the asymmetry that already exists between `template`'s chrome columns (`NOT NULL DEFAULT ''`-style,
`V4__template_authoring.sql:16-21`) and `document_snapshot`'s (`NOT NULL`, **no** default,
`V5__document_generation.sql:47-52`, "because generation always supplies them" per the canonical_refs
note) — CONTEXT.md's D-05.1-04 overrides that asymmetry specifically for this column, defaulting
*both* tables to `30`, because existing snapshot rows (generated before this phase) also need a value
that reproduces "today's PDF behaviour" for old documents. This is a deliberate, stated exception to the
V5 convention — the planner should say so in the migration comment, the way every other comment in these
files cites its decision ID.

The `CHECK` constraint syntax itself is the same convention as `document_type IN (...)` — a numeric
`BETWEEN` is new to this codebase's CHECK usage (every existing CHECK is an `IN` enum list), but it is
standard Postgres and needs no new pattern, just the bound values Claude's Discretion asks for (worked
arithmetic: 247mm printable height, 6cm/60mm cover padding-top already consumes room before the logo).

### Focus 3 — A numeric Bean Validation example: none exists

Searched all of `src/main/java` for `@Min`, `@Max`, `@Positive`, `@DecimalMin`, `@DecimalMax`, `@Digits`
— zero matches. Every existing Bean Validation annotation in this codebase is `@NotNull`, `@Size`, or
`@Pattern` (`SaveTemplateContentRequest.java:13-15`, `ChromeFieldsRequest.java:6-9`). This phase's
`logoRenderHeightMm` field on `ChromeFieldsRequest` is **the first numeric-bound validation in the
project.**

**What to establish, following the existing `@Size` convention's placement style exactly**
(`ChromeFieldsRequest.java`):
```java
import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.Size;

public record ChromeFieldsRequest(boolean coverEnabled,
                                  @Size(max = 500) String coverTitle,
                                  @Size(max = 500) String coverSubtitle,
                                  @Size(max = 500) String headerText,
                                  @Size(max = 500) String footerText,
                                  boolean pageNumbersEnabled,
                                  @Min(<lower>) @Max(<upper>) int logoRenderHeightMm) {
}
```
Use the same bound values as the V6 migration's `CHECK (logo_render_height_mm BETWEEN <lower> AND
<upper>)` — server-side Bean Validation and the DB CHECK are the two independent belts this codebase
already pairs everywhere else (e.g. `template_one_active_per_type_idx` is the DB-level enforcement of
D-04-12, with a service-layer comment at `TemplateService`'s call sites explaining why the DB check
exists in addition to any application check). Existing `GlobalExceptionHandler` already maps
`MethodArgumentNotValidException`/`@Valid` failures to `VALIDATION_FAILED` generically — no new
exception handler is needed for this.

### Focus 4 — Reading image dimensions back out of exported bytes, and the seam-test wiring

**PDFBox helper (`PdfExportAdapterTest.java`, lines 174-207):**
```java
private static byte[] onePixelPng() throws IOException {
    BufferedImage image = new BufferedImage(1, 1, BufferedImage.TYPE_INT_RGB);
    image.setRGB(0, 0, 0xFFFFFF);
    ByteArrayOutputStream out = new ByteArrayOutputStream();
    ImageIO.write(image, "png", out);
    return out.toByteArray();
}

private static int countImageXObjects(PDDocument document) throws IOException {
    int count = 0;
    for (PDPage page : document.getPages()) {
        PDResources resources = page.getResources();
        if (resources == null) continue;
        for (COSName name : resources.getXObjectNames()) {
            if (resources.isImageXObject(name)) count++;
        }
    }
    return count;
}
```
This existing helper counts image XObjects but **does not read their rendered dimensions** — nothing
in this codebase currently asks PDFBox "how tall did this image actually render." The direct way (not
present, but the natural extension of the existing `PDResources`/`COSName` walk above) is to fetch the
`PDImageXObject` itself and read the **placement**, not the pixel data: openhtmltopdf renders the
`<img>` at its CSS-computed box size, so the most reliable in-PDF signal is the image's transformation
matrix scale on the content stream, or — simpler and sufficient for this phase's "no taller than N mm"
assertion — decode the page at high DPI with `PDFRenderer` and measure the rendered logo's pixel
bounding box against the page's known DPI-to-mm conversion. Either approach is new engineering; the
existing `countImageXObjects` only proves presence/absence, which is what phase 5 needed and all this
phase needs to extend.

**docx4j helper — the `flatten`/`unwrap` walker (`DocxExportAdapterTest.java`, mirrored verbatim in
`GenerateThenExportSeamTest.java` lines 168-189):**
```java
private static List<Object> flatten(Object root) {
    List<Object> all = new ArrayList<>();
    flattenInto(root, all);
    return all;
}

private static void flattenInto(Object node, List<Object> all) {
    Object o = unwrap(node);
    if (o == null) return;
    all.add(o);
    if (o instanceof ContentAccessor ca) {
        for (Object child : ca.getContent()) {
            flattenInto(child, all);
        }
    }
}

private static Object unwrap(Object o) {
    return o instanceof JAXBElement<?> el ? el.getValue() : o;
}
```
This walker is reused identically in three test files already (`DocxExportAdapterTest`,
`DocxAstWalkerTest`-family, `GenerateThenExportSeamTest`) — copy it verbatim rather than writing a new
one. `logoBecomesAnImagePartWhenPresent` (`DocxExportAdapterTest.java:262-279`) currently only counts
`BinaryPartAbstractImage` parts:
```java
long imagePartsWithLogo = pkgWithLogo.getParts().getParts().values().stream()
        .filter(p -> p instanceof BinaryPartAbstractImage).count();
```
**It does not read the `Inline` extent** — no existing test does. CONTEXT.md's own suggestion ("read
the `Inline` extent back off the drawing") is the right approach but has no precedent to copy; the
concrete path is: `flatten(mainPart)` already collects every unwrapped JAXBElement including the
`Drawing`/`Inline` nodes the `logoParagraph` method builds (`DocxExportAdapter.java:206-208`,
`Inline inline = imagePart.createImageInline(...)`), so filter `flatten(...)` for
`o instanceof org.docx4j.wml.Inline` and read `.getExtent().getCx()`/`.getCy()` (EMU) directly off it —
these are the exact same EMU values `logoParagraph` set at construction, so this is a genuine
round-trip assertion, not trusting the writer's own intent (matching this test file's own stated
comment convention, `DocxExportAdapterTest.java:288`: "reopen bytes, walk the OOXML tree, never trust
the writer's own intent").
