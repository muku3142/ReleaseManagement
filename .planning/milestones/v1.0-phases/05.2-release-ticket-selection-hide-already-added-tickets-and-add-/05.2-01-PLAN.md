<objective>
Make `POST /api/tickets/search` able to hide the tickets a named release already holds, server-side,
after Jira has answered — and prove with one test that the release scope actually travels the whole
way from the request body to the filtered result.

Purpose: ROADMAP success criteria 1 and 2. When a release manager browses while assembling release X,
the candidate list must not re-offer tickets X already contains; browsing with no release in mind must
behave exactly as it does today.

**This is not a correctness fix.** `ReleaseService.addTickets` already de-duplicates and already
reports an `alreadyPresent` count, and `D-03-13` deliberately treats a wholly-redundant selection as
success rather than a 409. That behaviour stays exactly as it is. Do not "harden" the add path — this
plan removes avoidable scrolling, it does not repair anything.

Output: an optional `releaseId` on the search request, a second parameter on
`TicketSearchService.search`, a post-filter over the complete list the Jira port returns, and the
tests that cross the seam.
</objective>

<decisions_already_made>
These are settled. Implement them; do not re-litigate them in code or comments.

- **D-05.2-02 — the filter is server-side, after the Jira call, and never in JQL.** Jira has no
  knowledge of our releases and no JQL clause can express membership. The filter is a plain
  post-filter on the list `JiraTicketPort.searchAll` returns.
- **D-05.2-02, enforcement** — the release scope is threaded as a **separate parameter**,
  `search(criteria, releaseScope)`, and is **never** added as a fifth component of
  `TicketSearchCriteria`. A record with no such field makes `toJql()` *structurally incapable* of
  seeing it; a comment saying "don't use this field" would only make it forbidden.
- **D-05.2-03 — there is no pagination here and none may be introduced.** `searchAll` already
  exhausts Jira's cursor pagination inside the adapter (`JIRA-03`) and returns a complete
  `List<TicketDetail>`. No cursor, page token or page size reaches the client. Do not add a
  "top up the page after filtering" step, a filtered-count-vs-total reconciliation, or a total count
  field. There is no page to top up.
- **D-05.2-04 — reuse `ReleaseRepository.findTicketKeys(releaseId)`.** It already exists and is
  already used by `ReleaseService.addTickets:70`. Do not add a second query, a projection, a
  `countByRelease`, or a dedicated membership endpoint.
- **D-05.2-05 — absence of a release scope is today's behaviour.** No scope means no filter and no
  membership query at all.
</decisions_already_made>

<where_the_filter_lives_and_why>
The discretion item "where does the filter execute" is **resolved here — implement this, do not
re-decide it.**

`TicketSearchService` gains an optional `ReleaseRepository` collaborator and runs the filter itself.

Reasoning, so it is on the record: the alternative was composing in `TicketController` (fetch the
membership set there, filter the service's result). Both are legal — `ArchitectureBoundaryTest`'s only
application-layer rule bans `application -> adapters.{jira,persistence,web,render}` and says nothing
about `application -> ports` or `application -> application`. The tie-break is precedent.
`ReleaseService` already holds exactly this shape: a repository port (`ReleaseRepository`) plus a
cross-domain application service (`TicketSearchService`), and it already runs the "diff against
`findTicketKeys`" idiom this filter needs. Meanwhile **no controller in this codebase depends on a
repository port** — every controller takes exactly one application service. Giving `TicketController`
a `ReleaseRepository` would be the first controller-to-port dependency in the app; giving
`TicketSearchService` an optional `ReleaseRepository` is the first ticket-to-release dependency. Of
those two firsts, the second is the smaller deviation, keeps the filter next to the data it filters
(the full Jira list is already in hand inside `search`), and leaves `TicketController` thin.

No Spring bean cycle results: `ReleaseService -> TicketSearchService -> ReleaseRepository ->
ReleaseRepositoryAdapter`, and `ReleaseRepositoryAdapter` depends only on JPA repositories and domain
types.
</where_the_filter_lives_and_why>

<known_edges_state_them_do_not_fix_them>
- **The moved-issue case.** `addTickets` de-duplicates against the keys *Jira returned*, not the keys
  requested, because an issue that moved projects is requested as `OLD-1` and comes back as `NEW-5`
  (`ReleaseService:81-83`). A filter keyed on the release's stored `ticket_key` therefore will not
  hide a ticket whose key has since changed — it will show up under its new key and, if selected, be
  added a second time under that new key. This is acceptable and probably correct: the release
  genuinely does not contain `NEW-5`. **Pin it with a test so it is a documented property rather than
  a future surprise. Do not add key-remapping logic.**
- **An unknown `releaseId`.** `findTicketKeys` on an id that does not exist returns an empty list, so
  nothing is filtered and the search behaves exactly as an unscoped one. That is consistent with
  `D-05.2-05` and needs no code. **Do not add a release-existence check or a 404 path** — the only
  client sends an id it already routed to, and error handling for a case that cannot happen is
  prohibited by this project's CLAUDE.md.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client JSON body -> `TicketSearchRequest` | `releaseId` is caller-supplied and is used to key a database lookup |
| release membership -> JQL string sent to Jira | Our internal data would be leaving the system if it reached the query |
| `TicketSearchService` -> `ReleaseRepository` | First ticket-domain-to-release-domain dependency in the application layer |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05.2-01 | Information Disclosure (a caller supplies an arbitrary `releaseId` and infers which tickets that release holds, by diffing a scoped search against an unscoped one) | `TicketSearchRequest.releaseId` -> `findTicketKeys` | accept | Real, and accepted with a stated reason rather than papered over. This is a single-release-manager internal tool: every `/api/**` path is `authenticated()` in `SecurityConfig`, there is no per-release authorisation model anywhere in the product, and any authenticated caller can already read the same release outright via `GET /api/releases/{id}`. The inference channel therefore discloses nothing the direct endpoint does not. Introducing an ownership check here alone would be a control this product does not have anywhere else, giving false assurance. **If a multi-user model is ever added, this endpoint must be revisited alongside `GET /api/releases/{id}` — it is not a separate hole, it is the same one.** |
| T-05.2-02 | Information Disclosure (release membership leaking into a query sent to a third party) | `TicketSearchCriteria.toJql()` | mitigate | Structural, not conventional: the scope is a parameter of `TicketSearchService.search`, and `TicketSearchCriteria` has no field for it, so `toJql()` cannot read it. Two gates enforce this — `grep -c 'UUID' TicketSearchCriteria.java` returns 0, and the record file is asserted untouched by `git diff`. Two tests assert the composed JQL is identical with and without a scope (`theSameSearchOmitsATicketWithAReleaseScopeAndReturnsItWithout`, `releaseScopedSearchHidesMembersWithoutChangingTheQuerySentToJira`) and one asserts the id does not appear in the query string at all. |
| T-05.2-03 | Tampering (SQL injection through `releaseId`) | `findTicketKeys` | mitigate | Already mitigated and unchanged: the field is typed `UUID`, so anything that is not a UUID is rejected by Jackson before the controller body runs, and `findTicketKeys` is a Spring Data JPA query with a bound parameter. No new sink is introduced. |
