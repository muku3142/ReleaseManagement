# Phase 05.2 Plan 03: Release-scoped ticket search and the add-tickets dialog Summary

**Threaded an optional `releaseId` through `POST /api/tickets/search` from `TicketBrowser`, built `AddTicketsToReleaseDialog` as a new sibling of `AddToReleaseDialog` (release fixed, tickets chosen — the mirror image, not a second mode), and wired the release page's "Add tickets" button so it exists only on an OPEN release. Frontend tests: 197 → 210 (13 new, 0 regressions).**

## Accomplishments

- **`frontend/src/api/tickets.ts`** — `toSearchBody` and `useTicketSearch` both accept an optional `releaseId`, spread into the request body only when present (`D-05.2-05`: absence is today's unfiltered behaviour). `TicketSearchCriteria` itself is untouched, so `toJql()` remains structurally incapable of seeing the release scope.
- **`frontend/src/components/TicketBrowser.tsx`** — one new optional `releaseId` prop threaded straight into `useTicketSearch(props.releaseId)`, with no client-side row exclusion anywhere (`grep -cE '\.filter\(.*(alreadyOn|present|excluded)'` returns 0). Two additive UI changes, both gated on `props.releaseId !== undefined`: a persistent note ("Tickets already on this release are hidden.") and an extra clause on the project-mode empty-state hint. The shared filter row's classes were left untouched.
- **`frontend/src/components/AddTicketsToReleaseDialog.tsx`** (new, 87 lines) — the release is fixed via props, `TicketBrowser` is mounted only while the dialog is open (scoped by `props.releaseId`), and a successful add calls `props.onAdded(result)` then `props.onClose()`. Failures render through the same `role="alert" data-reason` / `messageForReason` idiom as every other mutation error in the app, and the dialog stays open on failure so the server's `RELEASE_FROZEN` refusal (the race-safety-net behind the UI gate) is visible rather than swallowed.
- **`frontend/src/routes/ReleaseDetailRoute.tsx`** — four narrow, additive edits: two pieces of state (`addOpen`, `addOutcome`), one "Add tickets" button as the first item in the existing `isOpen`-gated action row, one permanent mount of the new dialog, and one outcome banner block (kept structurally separate from the existing `showBanner` block so its narrowing is undisturbed). `addResultMessage` is reused verbatim — no new copy was written, including for the all-already-present success case.

## Decisions Made

See `key-decisions` in the frontmatter for the full reasoning; in short:
- `AddToReleaseDialog` was deliberately not extended or touched (`D-05.2-07`) — verified by an empty `git diff --name-only` on that file across all three commits.
- The new dialog's `TicketBrowser` child is mounted only while `props.open` is true, so every reopen starts from a fresh, unsearched state without any manual reset effect — the dialog element itself stays permanently mounted for `showModal()`/`close()`.
- The frozen-release gate is exactly the pre-existing `isOpen` boolean already wrapping the action row; no new gating logic was needed or added, per `D-05.2-08`.
- The shared filter-row classes inside `TicketBrowser` were left untouched; the narrower-dialog layout problem was solved entirely on the `<dialog>` element (`w-[min(90vw,72rem)] max-w-none`) and its wrapper (`max-h-[70vh] overflow-y-auto`), so `/tickets` is unaffected.
- Outcome copy reuses `addResultMessage` verbatim, including the `D-03-13` all-already-present success phrasing.

### Auto-fixed Issues

**1. [Rule 3 - blocking issue] Test fixture type mismatch under `tsc -b`**
- **Found during:** Task 3 verification (second `npx tsc -b` run)
- **Issue:** `RELEASE` in `ReleaseDetailRoute.test.tsx` was an untyped object literal; TypeScript inferred `frozenAt`/`frozenBy` as `null` literal types and `status` as `string`. Spreading it into a new `frozen` fixture with `status: 'FROZEN'` failed to satisfy `Release`.
- **Fix:** Explicitly typed `RELEASE: Release` (imported from `../../src/api/releases`) and explicitly typed the derived `frozen` fixture the same way, rather than loosening any production type.
- **Files modified:** `frontend/tests/components/ReleaseDetailRoute.test.tsx`
- **Commit:** `707cb93`

**2. [Rule 1 - bug] Wrong assertion target in the outcome-banner test**
- **Found during:** Task 3, first test run
- **Issue:** `container.querySelector('[role="status"]')?.textContent` included the dismiss button's "×" glyph, so the assertion against `addResultMessage(...)` failed on an exact string match by one trailing character.
- **Fix:** Narrowed the selector to `'[role="status"] p'`, matching only the message paragraph, not the whole banner including its dismiss button.
- **Files modified:** `frontend/tests/components/ReleaseDetailRoute.test.tsx`
- **Commit:** `707cb93`
