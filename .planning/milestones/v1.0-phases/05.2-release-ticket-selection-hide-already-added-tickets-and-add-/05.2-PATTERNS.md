**Correction to the phase brief's framing — the "stale-selection reconciliation" at line 58 is NOT a `useEffect`.** It is inline in `runSearch`'s `onSuccess` callback (lines 55-64):
```typescript
function runSearch() {
  const usingJql = jqlOpen && jql.trim() !== '';
  const criteria: TicketSearchCriteria = usingJql
    ? { mode: 'jql', jql: jql.trim() }
    : { mode: 'project', projectId, sprintId: sprintId || null, statusCategories };

}
```

### 4. The search request path — five hops

**Hop 1 — `TicketSearchRequest.java` (whole file, DTO):**
```java
public record TicketSearchRequest(
        @Pattern(regexp = "^[0-9]+$", message = "must be a numeric Jira project id")
        String projectId,
        @Pattern(regexp = "^[0-9]+$", message = "must be a numeric Jira sprint id")
        String sprintId,
        @Size(max = 2000, message = "must be at most 2000 characters")
        String jql,
        Set<StatusCategory> statusCategories) {

    @AssertTrue(message = "supply either projectId (sprintId optional), or jql - not both")
    public boolean isExactlyOneFilterMode() { ... }
}
```
An optional release-scope field (e.g. `releaseId`) is added here as a plain nullable field with no validation annotation forcing its presence — it must NOT participate in `isExactlyOneFilterMode()`, since it is an orthogonal concern (D-05.2-05: absence means unfiltered).

**Hop 2 — `TicketController.search` (lines 25-33), which builds the domain criteria:**
```java
@PostMapping("/search")
public TicketSearchResponse search(@Valid @RequestBody TicketSearchRequest request) {
    TicketSearchCriteria criteria = request.jql() != null && !request.jql().isBlank()
            ? TicketSearchCriteria.byJql(request.jql())
            : TicketSearchCriteria.byProject(request.projectId(), request.sprintId(),
                    request.statusCategories());
    return new TicketSearchResponse(
            service.search(criteria).stream().map(TicketController::toResponse).toList());
}
```
This is the hop where `request.releaseId()` must be read and passed to `service.search(...)` **as a separate argument, not folded into `TicketSearchCriteria`** — see the hard constraint below.

**Hop 3 — `TicketSearchCriteria.toJql()` (whole file, 47 lines) — the constraint boundary:**
```java
public record TicketSearchCriteria(String projectId, String sprintId, String jql,
                                   Set<StatusCategory> statusCategories) {
    public static TicketSearchCriteria byProject(...) { ... }
    public static TicketSearchCriteria byJql(String jql) { ... }
    public String toJql() {
        if (jql != null) return jql;
        String sprintClause = ...;
        String statusClause = ...;
        return "project = " + projectId + sprintClause + statusClause + " ORDER BY key ASC";
    }
}
```
**D-05.2-02's hard constraint, concretely enforced:** `TicketSearchCriteria` has exactly four fields (`projectId`, `sprintId`, `jql`, `statusCategories`) and `toJql()` reads only them. If a release-scope value were added as a fifth field on this record, it would technically compile and `toJql()` would just ignore it — but that is fragile and invites a future edit to accidentally reference it. **The safe shape is to keep the release scope entirely outside `TicketSearchCriteria`** — thread it as a second parameter to `TicketSearchService.search(TicketSearchCriteria criteria, UUID releaseId)` (or an `Optional<UUID>`), never added to the record. This makes "`toJql()` cannot see it" true by construction (the type it's called on has no such field), not just true by convention.

**Hop 4 — `TicketSearchService.search` (lines 34-38), the filter's home:**
```java
public List<TicketDetail> search(TicketSearchCriteria criteria) {
    JiraAccessContext access = accessContextService.currentContext();
    Map<TicketField, String> fieldIds = fieldMetadataService.resolve(FIELDS);
    return ticketPort.searchAll(access, criteria.toJql(), fieldIds);
}
```
The post-filter is one `.filter(...)` added after `ticketPort.searchAll(...)` returns, using the existing `findTicketKeys`-diff idiom already established in `ReleaseService.addTickets` (see §5 below) — filter OUT tickets whose key is in the release's present set, not IN.

**Hop 5 — `JiraTicketPort.searchAll` (whole file, 14 lines) — the complete-list contract (D-05.2-03):**
```java
public interface JiraTicketPort {
    List<TicketDetail> searchAll(JiraAccessContext access, String jql, Map<TicketField, String> fieldIds);
}
```
Returns a complete `List<TicketDetail>`, already pagination-exhausted (`JIRA-03`). This interface itself needs no change — the filter is a pure post-processing step on its output, never a parameter to it.

### 5. Does an existing application service depend on both a Jira-side and a release-side collaborator?

**Yes — `ReleaseService` (whole file), and this is the load-bearing precedent for where the filter should live.**

```java
private final ReleaseRepository repository;              // release-side port
private final TicketSearchService ticketSearchService;   // Jira-side application service

public ReleaseService(ReleaseRepository repository, TicketSearchService ticketSearchService) {
    this.repository = repository;
    this.ticketSearchService = ticketSearchService;
}
```
And it already runs the exact "diff requested against `findTicketKeys`" idiom the new filter needs, in `addTickets` (lines 65-92):
```java
List<String> requested = distinct(ticketKeys);
Set<String> present = Set.copyOf(repository.findTicketKeys(releaseId));
List<String> toFetch = requested.stream().filter(key -> !present.contains(key)).toList();
```

**But `TicketSearchService` itself currently depends on Jira-side collaborators only** (`JiraAccessContextService`, `FieldMetadataService`, `JiraTicketPort` — see the whole file above). The existing dependency direction in this codebase is **release → ticket** (`ReleaseService` reaches into `TicketSearchService`), never the reverse. Making `TicketSearchService` depend on `ReleaseRepository` would introduce the first ticket → release dependency in the app, coupling a would-be-generic ticket-search capability to release membership for what is, per D-05.2-05, an optional/absent-by-default concern.

**`ArchitectureBoundaryTest` (whole file, 4 rules) does not forbid this either way:** its only application-layer rule (`applicationDoesNotDependOnAdapters`, lines 37-52) restricts `application` → `adapters.{jira,persistence,web,render}`, not `application` → `ports` or `application` → `application`. So both options are legal under the test; the decision is a design-quality one, not a compile-time-enforced one.

**Recommendation, following the codebase's own precedent exactly:** compose at the same layer `ReleaseService` already composes at — give `TicketSearchService.search` a second, optional parameter for the release scope, and have it call `ReleaseRepository.findTicketKeys` itself when that scope is present. This mirrors `ReleaseService`'s existing shape (one service class holding both a same-domain repository port and a cross-domain application-service reference) rather than pushing composition into `TicketController`, where **no controller in this codebase currently depends on a repository port directly** — every controller (`ReleaseController`, `TicketController`) depends on exactly one `application`-layer service (see `ReleaseController` and `TicketController`, both single-collaborator constructors). Adding a `ReleaseRepository` dependency to `TicketController` would be the first controller-to-port dependency in the app; adding it to `TicketSearchService` is the first ticket-to-release dependency. Of the two "firsts," giving `TicketSearchService` an *optional* `ReleaseRepository` collaborator (unused unless a release scope is supplied) is the smaller deviation, keeps the filter next to the data it filters (the full Jira result list is already in hand inside `search`), and keeps `TicketController` a thin single-service controller like every other controller in the app. State this reasoning in the plan rather than leaving it implicit, per the discretion note.

## Explicit Gaps (per the phase brief's request)

- **No existing frontend component takes a "scope" or "filter out these keys" style prop today.** Every list-rendering component in the app (`TicketsRoute`'s table, `ReleaseDetailRoute`'s ticket/manual-item tables) renders exactly what its query returned, with no client-side exclusion prop anywhere in `frontend/src/components/` or `frontend/src/routes/`. The extracted `TicketBrowser` introducing an (optional) `releaseId` prop that changes what the server returns — never a client-side filter prop — will be the first of its kind, consistent with D-05.2-02 (filtering happens server-side).
- **No existing test asserts a component renders identically before and after a refactor**, in the sense of a snapshot/byte-comparison test written *for* a refactor.
