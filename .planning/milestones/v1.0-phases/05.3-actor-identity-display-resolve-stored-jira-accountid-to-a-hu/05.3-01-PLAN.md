<objective>
Build the read-only actor lookup: a narrow port, a JPQL scalar projection that never hydrates
`JiraCredentialEntity`, and an application service that batches and de-duplicates the lookup and
degrades an unresolvable accountId to itself.

Purpose: this is the load-bearing half of the phase. Decryption of `encrypted_token` is triggered by
JPA hydrating `JiraCredentialEntity.token` (`@Convert(converter = EncryptedTokenConverter.class)`), so
the risk attaches to the **entity type**, not to any particular query text. Every display path in plan
02 will go through what this plan builds, so this plan's job is to make the token literally
unreachable from a display path — in the type system, not in a comment.

Output: `ActorDirectory` port, `ActorDirectoryAdapter`, a projection query on
`JiraCredentialJpaRepository`, `ActorResolutionService` + `ResolvedActors`, one unit test class and
new tests on the existing `JiraCredentialPersistenceIT`.
</objective>

```java
package com.evision.releasemgmt.application;

import com.evision.releasemgmt.ports.ActorDirectory;
import org.springframework.stereotype.Service;

import java.util.Arrays;
import java.util.Map;
import java.util.Objects;
import java.util.Set;
import java.util.stream.Collectors;

@Service
public class ActorResolutionService {

    private final ActorDirectory directory;

    public ActorResolutionService(ActorDirectory directory) {
        this.directory = directory;
    }

    /**
     * D-05.3-05: one call for a whole response, not one per row. Varargs because seven of the nine
     * call sites resolve one or two ids inline; a list site passes {@code toArray(String[]::new)},
     * which — unlike {@code List.of} — tolerates the null a release that was never frozen carries.
     */
    public ResolvedActors resolve(String... accountIds) {
        Set<String> distinct = Arrays.stream(accountIds)
                .filter(Objects::nonNull)
                .collect(Collectors.toSet());
        return new ResolvedActors(distinct.isEmpty() ? Map.of()
                : directory.findEmailsByAccountId(distinct));
    }
}
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `jira_credential` row → application layer | The email being read sits in the same row as `encrypted_token`. Anything that widens the read surface here widens exposure of a secret. |
| `RM_CREDENTIAL_KEY` → decryption on a read path | Any JPA read returning a hydrated `JiraCredentialEntity` runs `EncryptedTokenConverter` and can throw. Whether a code path crosses this boundary is decided by its **return type**. |
| caller-supplied accountId collection → SQL | The `IN` clause is bound from values that will, in plan 02, originate in stored rows rather than request parameters. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05.3-01 | Denial of Service (a superseded `RM_CREDENTIAL_KEY` making an unrelated screen throw) | `ActorDirectory` / `ActorDirectoryAdapter` | mitigate | The port declares one method returning `Map<String,String>`; no declaration on it can carry a token, so no implementation can hydrate the entity without changing the port. Backed by a JPQL scalar projection copied from `findSessionsInvalidatedAt`, and proved end-to-end against a genuinely undecryptable Postgres row in Task 3 with an anti-vacuity `assertThatThrownBy` on `findByAccountId`. This is not hypothetical: a key rotation once locked every user out of the sign-in that would have replaced the unreadable token. |
| T-05.3-02 | Information Disclosure (the stored API token reaching a caller) | `ActorDirectory` | mitigate | Structural: the only method's return type is `Map<String,String>` of account id → email, the JPQL selects exactly `jiraAccountId` and `jiraEmail`, and the adapter holds no reference to `JiraCredentialRepository`. Acceptance criterion 5 of Task 1 greps for zero occurrences. The response-level assertion (`AUTH-03`/`D-13`, D-05.3-06) is made in plan 03. |
| T-05.3-03 | Information Disclosure (an accountId → email enumeration oracle) | `ActorResolutionService` | accept | No endpoint accepts an accountId from the client. `resolve(...)` is only ever called in plan 02 with ids already stored on rows the caller is authorised to read, and every `/api/**` path is `authenticated()` in `SecurityConfig`. If a future endpoint ever took an accountId parameter this disposition must be revisited — recorded here rather than left implicit. |
| T-05.3-04 | Tampering (SQL injection through the `IN` list) | `findEmailsByAccountIdIn` | mitigate | JPQL with a named `:accountIds` parameter binding, not string concatenation. Already the house pattern. |
| T-05.3-05 | Denial of Service (an unbounded `IN` list) | `ActorResolutionService` | accept | The collection is de-duplicated to a `Set` and its size is bounded by the number of distinct actors in one response — realistically one or two in a single-release-manager tool, and bounded above by the page of releases already loaded.
