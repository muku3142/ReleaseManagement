# Phase 05.3 Plan 01: Actor Resolution Lookup Summary

**Projection-only ActorDirectory port plus a batching ActorResolutionService, proven end-to-end against a Postgres row this JVM's active key cannot decrypt.**

## Accomplishments
- `ActorDirectory` port: one method, `Map<String,String>` return type, no declaration on it can carry a token
- `JiraCredentialJpaRepository.findEmailsByAccountIdIn`: JPQL scalar projection with `WHERE ... IN`, modelled on `findSessionsInvalidatedAt`
- `ActorResolutionService.resolve(String...)`: filters null, de-dupes to a `Set`, and skips the query entirely when nothing is resolvable
- `ResolvedActors.display`: degrades an unknown accountId to itself (D-05.3-04), never blank/null/"Unknown"
- Proved against a real Postgres row whose ciphertext the active `RM_CREDENTIAL_KEY` cannot decrypt: `findByAccountId` throws, `ActorDirectory.findEmailsByAccountId` still resolves the email

- `ActorResolutionService.resolve` uses varargs rather than `List<String>` per plan's stated rationale (inline call sites vs. one list call site tolerating a null entry).

- Reused the existing `JiraCredentialPersistenceIT` class for the decryption-survival tests rather than a new IT class, per the plan's instruction (one Testcontainers Postgres container is cheaper than two).
