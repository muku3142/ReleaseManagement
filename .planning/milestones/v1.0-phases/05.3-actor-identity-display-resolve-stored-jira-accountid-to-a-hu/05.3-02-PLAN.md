<objective>
Wire the resolution service into the four controllers that map actor-bearing responses, so the eight
actor fields across six DTOs carry an email instead of an opaque Jira account id.

Purpose: this is the visible half of the phase. It is a read-time mapping change only — no stored
value, no column, no migration, no write path (D-05.3-02), which is exactly why already-recorded
history (including append-only `document_snapshot` rows, DOC-07) starts displaying correctly with no
regeneration.

Output: four modified controllers and six updated `@WebMvcTest` slice tests.
</objective>

<decisions_resolved_here>
Every remaining "Claude's Discretion" item from 05.3-CONTEXT.md, settled so the executor does not
have to weigh anything:

- **API field shape: the existing field's *content* changes; no sibling field is added.**
  `generatedBy`, `createdBy`, `frozenBy` and `updatedBy` start carrying the email. Reason: adding
  `*Email` siblings would widen 6 DTOs by 8 fields, widen 4 frontend type files and require new render
  code, to surface an opaque id nobody asked to see. Nothing external consumes this API, so there is
  no compatibility constraint. When an account has no credential row the field carries the raw id
  anyway (D-05.3-04), so the id is not lost where it is actually informative.

- **Consequence: no frontend change is required by this phase, and none is to be made.** The three
  render sites (`DocumentsSection.tsx:96,101,229`, `ReleaseDetailRoute.tsx:187,191`,
  `SettingsRoute.tsx:77`) interpolate the value as a plain string and the TypeScript types stay
  `string` / `string | null`. Do **not** add a `title` attribute showing the raw id: the id is not sent
  any more, so there would be nothing to show. Do **not** open `ReleaseDetailRoute.tsx` — phase 05.2
  is editing that file.

- **De-static only where the helper must resolve for itself.** `ReleaseController.toResponse(Release)`,
  `ReleaseController.toAddResult` and `TemplateController.toResponse(Template)` become instance
  methods (matching `JiraSiteConfigController`'s already-instance helper).
  `ReleaseController.toSummaryResponse` stays `static` and takes a `ResolvedActors` parameter instead,
  because a list row must not resolve for itself — that would be the N+1 (D-05.3-05).
  `DocumentController.toResponse` is *already* an instance method (line 148); it needs no de-staticing.

- **Templates have no list-level N+1.** `TemplateSummaryResponse` carries no actor field
  (`TemplateController.java:209-213`), so `TemplateController.list()` and
  `TemplateController::toSummaryResponse` are untouched. PATTERNS.md item 3 records the same finding.
  The only true multi-row sites in the whole phase are `ReleaseController.list()` and
  `DocumentController.revisions()`.

- **No short-circuit on the signed-in user's own `CLAIM_EMAIL`** — settled in plan 05.3-01; do not
  reintroduce it here.
</decisions_resolved_here>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `jira_credential.jira_email` → HTTP response body | An email is PII. Before this plan the API returned an opaque account id in these eight fields; after it, it returns a person's address. |
| stored accountId → resolution lookup | The ids fed into the lookup come from stored rows, not from request parameters. |
| `encrypted_token` → any read on the display path | The email being returned lives in the same row as the encrypted token. |
