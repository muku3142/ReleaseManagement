### Acceptance-criteria reinterpretation (per `<plan_criteria_warning>`)

**Task 1, criterion 2** (`revisions()` resolves ONCE, outside the per-row map — the plan's own `awk` script):
```
awk '/actorResolution.resolve/{r=NR} /\.map\(s -> new DocumentRevisionResponse/{m=NR} END{print (r>0 && m>r) ? "OK" : "FAIL"}' DocumentController.java
```
prints `FAIL`, not `OK`. The underlying property genuinely holds: `grep -n` shows `actorResolution.resolve` at line 79 (inside `revisions()`, before the `.map(` at line 82) and a second, unrelated `actorResolution.resolve` at line 164 (inside `toResponse()`, a single-actor lookup for the single-document GET path). The awk script has no arrays — it overwrites `r` on every match rather than tracking the specific call inside `revisions()` — so once a second, legitimate `resolve()` call exists elsewhere in the file (which the plan's own Task 1 action requires: one call in `revisions()`, a separate one in `toResponse()`), `r` ends up pointing at whichever call is textually last in the file, not the one paired with the map it's checking. Verified directly with `grep -n` that the real ordering (`revisions()`'s resolve at line 79, its map at line 82) satisfies the stated property. This is the exact brittle-criterion shape the plan's `<plan_criteria_warning>` and prior-project memory (`gsd-plan-grep-criteria-are-brittle`) describe: the check counts/orders textual matches rather than asserting the property per-method.

All other acceptance criteria (Tasks 1, 2, 3) passed as written, including the `mvn clean test` runs scoped to each task's slice tests.
