# Phase 05.3: Actor Identity Display - Context

**Gathered:** 2026-08-11
**Status:** Ready for planning
**Source:** Direct decision capture. The user reported seeing
`"generatedBy": "5f5f5f58aba9660071082b49"` on a document revision and chose between the three
approaches in the same session. No `/gsd-discuss-phase` run.

<domain>
## Phase Boundary

**In scope:** turning the stored actor identifier into something a person recognises, everywhere the
API returns one.

**Out of scope, explicitly:**
- Changing what is *stored*. No migration, no write-path change, no backfill. See `D-05.3-02`.
- The JWT's contents, the login flow, token refresh, or session invalidation.
- Adding a user store, display names, avatars, or any Jira `/myself` call at read time. The email is
  already in the database; do not reach out to Jira to render a list.
- Reading, decrypting or returning the stored API token in any form. This is the hard constraint —
  see `D-05.3-03`.
- The two tracked todos in `.planning/todos/pending/`.

**The defect.** `AuthenticationService.java:58` issues the session as
`jwtTokenService.issue(identity.accountId(), email)`: the JWT **subject** is the Jira accountId, and
the email rides along as a separate `CLAIM_EMAIL` claim (`JwtTokenService.java:121`). Every controller
then records `principal.getName()`, which is the subject. So the accountId — not a person — is what
lands in the database and comes back out of the API.

It is worth being precise, because the first reading of a value like `5f5f5f58aba9660071082b49` is
"that's a session id". It is not. It is a Jira Cloud accountId: stable across logins, unique per user,
and a perfectly good *identifier*. The problem is purely that it is not a *label*.

**Nine capture sites, five controllers:**

| Site | Field |
|------|-------|
| `DocumentController:56` | `generatedBy` |
| `ReleaseController:54` | release `createdBy` |
| `ReleaseController:86` | `frozenBy` |
| `TemplateController:80, 114, 131, 136, 142` | template `createdBy` / `updatedBy` |
| `JiraSiteConfigController:35` | site config `updatedBy` |

**Eight response DTOs carry an actor field:** `DocumentResponse:12`, `DocumentRevisionResponse:6`,
`JiraSiteConfigResponse:5`, `ReleaseResponse:8-9`, `ReleaseSummaryResponse:7-8`, `TemplateResponse:10`.
`ReleaseResponse` and `ReleaseSummaryResponse` each carry two (`createdBy` and `frozenBy`).
</domain>

<decisions>
## Implementation Decisions

### D-05.3-01 — Resolve for display; keep storing the accountId
The accountId stays exactly as it is in every table. Resolution to an email happens when a response is
built.

Two alternatives were considered with the user and rejected:
- **Store the email going forward** (change the 9 sites to use the `CLAIM_EMAIL` claim). Simplest, but
  every existing row stays opaque forever — `document_snapshot` is append-only (`D-05-06`/`DOC-07`) so
  those rows can never be corrected — and it discards a stable identifier in favour of a mutable label.
- **Store both.** Best for a permanent audit trail, but it is a schema change across `release`,
  `template`, `document_snapshot` and `jira_site_config`, and it *still* leaves existing rows opaque.

Read-time resolution is the only one of the three that fixes already-recorded history.

### D-05.3-02 — Nothing stored changes, and no migration is written
This phase adds no column, alters none, and rewrites no row. If a plan proposes a migration, the plan
is wrong. The append-only guarantee that `DOC-07` and Phase 7's `AUDIT-02` rest on is untouched
precisely because nothing is written.

### D-05.3-03 — The resolution query MUST NOT load the credential entity
**This is the most important constraint in the phase.**

`JiraCredentialRepository.findByAccountId` returns a `JiraCredential`, whose record includes
`apiToken`. Loading that entity **decrypts `encrypted_token`**. The adapter already avoids this
deliberately: `upsert`, `findSessionsInvalidatedAt` and `markSessionsInvalidated` all use JPQL rather
than `findById` + `save`, and the comment at `JiraCredentialRepositoryAdapter.java:33` records why —
a rotated `RM_CREDENTIAL_KEY` throws on stale ciphertext, and when that happened it locked every user
out of the very sign-in that would have replaced the unreadable token.

**Mechanism confirmed by pattern mapping (2026-08-11), not inferred:** decryption is triggered purely by
JPA hydrating `JiraCredentialEntity.token`, which carries
`@Convert(converter = EncryptedTokenConverter.class)`. So the risk attaches to the **entity type**, not
to any particular query text: *any* query whose return type is `JiraCredentialEntity` can throw on a
superseded key. Only a JPQL projection selecting scalar columns avoids it. This is the single fact the
whole phase turns on — verify it still holds before building.

If a display path calls `findByAccountId`, then a single unreadable credential row turns into a failure
on the document list, the releases list, and the template list — screens that have nothing to do with
credentials. A cosmetic improvement would become an outage.

So: add a **projection-only** lookup that selects `account_id` and `email` and nothing else, modelled
on `findSessionsInvalidatedAt`. Do not widen `JiraCredential`. Do not add a "lightweight" flag to
`findByAccountId`. A separate, narrow port method whose return type cannot carry a token is the point —
the type system should make the mistake impossible, not a comment.

### D-05.3-04 — An unresolvable actor degrades to the accountId
If no credential row exists for an accountId (the user's credential was deleted, or the row predates
something), the response carries the accountId, exactly as today. Never blank, never null, never an
error, never a placeholder like "Unknown". The raw id is strictly more useful than any of those,
because it is still traceable in Jira.

### D-05.3-05 — Batch the lookup; no query per row
A releases list or a revision history renders many actors at once. Resolution must not issue one query
per row — this is the N+1 the project's own instructions call out by name. Collect the distinct
accountIds for a response and resolve them in one call.

Note the realistic cardinality: this is a single-release-manager tool, so most responses will contain
one or two distinct actors. The batching requirement is about not writing the N+1 shape, not about
optimising a measured bottleneck — do not build a cache for it.

### D-05.3-06 — The token is never read on this path
`AUTH-03`/`D-13`: the stored token is never returned to the client in any form. This phase reads an
email from the same table that holds the encrypted token, so the plans must be explicit that the token
column is neither selected nor decrypted, and a test should assert it.

### Claude's Discretion

- **Field naming in the API.** Whether `generatedBy` starts carrying an email, or a sibling field
  (`generatedByEmail`) is added alongside the id. Adding a field is more informative and lets the UI
  show the id on hover, but it widens 8 DTOs and the frontend types. Changing the existing field's
  content is smaller and the frontend needs no type change. Decide and state the reasoning; note that
  nothing external consumes this API, so backwards compatibility is not a constraint.
- **Where resolution happens.** A small application-layer service the controllers call while mapping
  to DTOs is the obvious shape. Consider whether it belongs behind a port; note that
  `TicketSearchService` and friends show the house style for application services with a repository
  dependency.
- **Whether the signed-in user's own email short-circuits the lookup.** It is already on the JWT as
  `CLAIM_EMAIL`, so the common case could avoid a query entirely. Judge whether that is a worthwhile
  special case or an unnecessary branch — the project's instructions favour the latter absent a
  measured need.
- **How the frontend displays it.** Whether the raw id remains visible anywhere (a `title` attribute,
  say) or is replaced entirely.
- ~~Test strategy for criterion 4.~~ **Largely resolved by pattern mapping — a precedent exists.**
  `JiraCredentialPersistenceIT.upsertOverwritesARowEncryptedUnderASupersededKey` already constructs an
  undecryptable row via a direct `JdbcTemplate` UPDATE, bypassing the entity and its converter. Reuse
  that technique: build such a row, then load a document/release response and assert it renders with the
  email resolved. That is the strong form of the claim — asserting the projection query's shape in
  isolation would pass even if some caller used `findByAccountId` anyway. What remains discretionary is
  only which response(s) to exercise.
- **Three of the four `toResponse` helpers are `private static`.** `ReleaseController`,
  `TemplateController` and `DocumentController` all use static mapping helpers; only
  `JiraSiteConfigController`'s is already an instance method. Injecting a resolution service forces
  de-staticing the other three. Decide whether that is acceptable (it is the smallest change) or whether
  resolution happens before mapping.
- **`ReleaseController.list()` and `TemplateController.list()` are the real N+1 sites**, at up to two
  actor lookups per row. `JiraSiteConfigController` has no list endpoint at all.
</decisions>

<specifics>
## Specific Ideas

- **The decryption test is the one worth building.** Criterion 4 is the criterion that stops this phase
  from creating a worse bug than it fixes. A test that stores a credential row whose `encrypted_token`
  is unreadable under the current key, then loads a document response and asserts it renders with the
  email resolved, proves the projection genuinely avoids the entity. That is the seam-crossing shape
  Phase 5 learned to value: asserting the projection query in isolation would pass even if a caller
  used `findByAccountId` anyway.
- **Verify against real data.** The user has documents generated with accountIds already stored. After
  the change, an existing revision's `generatedBy` should show their email with no regeneration — that
  is criterion 2, and it is the whole reason read-time resolution was chosen.
- **`RM_CREDENTIAL_KEY` rotation is a real scenario here, not a hypothetical.** It has already caused a
  lockout in this project once. Treat it as a live risk.
- **Environment:** `export JAVA_HOME="$HOME/.jdks/jdk-25"` before every Maven call; the machine default
  is 17. `src/test/resources/application.yml` SHADOWS main's rather than merging, so any new config
  property must be added to both or full-context ITs fail on unresolved placeholders.
- **Baselines:** read the current test counts rather than trusting a number written here — phases 05.1
  and 05.2 are both queued ahead of this one and will raise them. At the time of writing: backend 556,
  frontend 183, `tsc -b` clean.
</specifics>

<deferred>
## Deferred Ideas

- Display names rather than emails. Jira's `/myself` returns a `displayName` and `JiraIdentity` already
  carries it, but it is not persisted. Storing it would be a schema change and an email is
  unambiguous, which is what an audit trail wants.
- Avatars.
- A real user store, or any notion of a user independent of a Jira credential. The project explicitly
  has none.
- Backfilling stored actor values, or adding an email column to the four actor-bearing tables. Both
  rejected by `D-05.3-01`/`D-05.3-02`.
- Changing the JWT subject to the email. That would make every *future* row a label rather than an
  identifier, which is the opposite of the direction chosen, and it would break
  `findSessionsInvalidatedAt`-style lookups keyed on accountId.
</deferred>
