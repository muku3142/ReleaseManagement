## Pattern Assignments

### 1. The projection-query pattern this phase must copy exactly

**Analog:** `src/main/java/com/evision/releasemgmt/adapters/persistence/JiraCredentialRepositoryAdapter.java`

Full adapter (69 lines) — the two methods that matter, verbatim:

```java
// lines 26-30 — the method the new lookup must NOT resemble: loads the whole entity,
// which decrypts encrypted_token via the JPA converter as a side effect of hydration.
@Override
public Optional<JiraCredential> findByAccountId(String accountId) {
    return jpa.findById(accountId)
            .map(e -> new JiraCredential(e.getJiraAccountId(), e.getJiraEmail(), e.getToken(), e.getKeyVersion(), e.getUpdatedAt()));
}

// lines 59-62 — the shape the new lookup MUST copy: delegates straight to a JPQL
// projection method on the Spring Data interface, no entity hydration at all.
@Override
public Optional<Instant> findSessionsInvalidatedAt(String accountId) {
    return jpa.findSessionsInvalidatedAt(accountId);
}
```

The comment at lines 32-41 (verbatim, this is the "why" the new method must carry forward in its own
Javadoc or a comment on the port):

```java
/**
 * Updates via JPQL rather than findById + save. Loading the entity would decrypt the
 * stored token, so a row encrypted under a superseded key would make this throw — and
 * this is exactly the call that replaces an unreadable token, so a key rotation would
 * lock every user out with no way back in.
 *
 * <p>Clearing sessions_invalidated_at is intentional: a fresh sign-in supersedes any
 * earlier logout, so the new pair is accepted without depending on second-precision
 * ordering between the token's iat and the previous invalidation instant.
 */
```

The JPQL it delegates to — `src/main/java/com/evision/releasemgmt/adapters/persistence/repository/JiraCredentialJpaRepository.java`:

```java
// lines 12-17 — the interface-level comment, also worth carrying forward in spirit for
// the new batch method:
/**
 * The write and metadata operations here deliberately avoid loading the entity. Loading it
 * decrypts {@code encrypted_token} through EncryptedTokenConverter, so any operation that
 * did a findById would fail on a row encrypted under a superseded key — including the login
 * that is trying to replace that very token.
 */
public interface JiraCredentialJpaRepository extends JpaRepository<JiraCredentialEntity, String> {

    // lines 36-37 — the exact single-column projection pattern to copy, widened to two
    // columns and a WHERE...IN for the batch case (see item 2):
    @Query("select e.sessionsInvalidatedAt from JiraCredentialEntity e where e.jiraAccountId = :accountId")
    Optional<Instant> findSessionsInvalidatedAt(@Param("accountId") String accountId);
}
```

**Decryption mechanism, confirmed precisely** (per the focus request): decryption is **not** a
separate step anywhere — it is triggered automatically by Hibernate/JPA whenever it hydrates a
`JiraCredentialEntity.token` field, because that field carries:

```java
// src/main/java/com/evision/releasemgmt/adapters/persistence/entity/JiraCredentialEntity.java:23-25
@Column(name = "encrypted_token", nullable = false)
@Convert(converter = EncryptedTokenConverter.class)
private String token;
```

`EncryptedTokenConverter` (`src/main/java/com/evision/releasemgmt/adapters/persistence/crypto/EncryptedTokenConverter.java`)
implements `jakarta.persistence.AttributeConverter<String, String>`; its `convertToEntityAttribute`
(lines 72-96) does the AES-256-GCM decrypt and throws `IllegalStateException` on a superseded-key or
truncated envelope. **Any** JPA read path that returns a hydrated `JiraCredentialEntity` — `findById`,
`findAll`, a derived-query method returning the entity type, a JPQL `select e from ...` — runs this
converter and can throw. Only a JPQL projection that selects specific scalar columns (`select
e.jiraEmail, ...`) avoids touching the `token` field's getter/converter entirely, because Hibernate
never materialises that column into an entity instance. This is exactly why `findSessionsInvalidatedAt`
projects a single column instead of returning a partial entity — the same discipline the new
`(account_id, email)` lookup must follow.

### 2. Batch / multi-key lookup precedent

**Explicit gap: none exists.** Grepped the whole `src/main/java` tree for `findAllBy...In`,
`WHERE ... IN :`, and any repository method returning `Map<...>` — the only `findAllBy*` hit is
`TemplateJpaRepository.findAllByOrderByDocumentTypeAscNameAsc()` (unfiltered, not keyed), and the only
`Map<String,...>`-returning code (`ReleaseViewAssembler`, `RenderContextMapper`, `FieldMetadataService`,
`RenderService`) all build in-memory `Map`s from data already loaded, not from a repository query. **No
file in this codebase currently issues a `WHERE x IN (:keys)` query or returns a keyed `Map` from a
repository.** The planner is establishing this pattern, not following one. The nearest structural model
is still the JPQL-projection style above — a new interface method such as:

```java
@Query("select e.jiraAccountId as accountId, e.jiraEmail as email from JiraCredentialEntity e where e.jiraAccountId in :accountIds")
List<AccountEmailProjection> findEmailsByAccountIdIn(@Param("accountIds") Collection<String> accountIds);
```

(interface-projection or a DTO constructor-expression JPQL — either is idiomatic Spring Data; nothing
in this codebase precedes either choice, so pick the interface-projection form since it needs no new
class and cannot accidentally widen to include `token`).

### 3. The controller `toResponse`-style seam, one per controller

@GetMapping("/revisions")

                                               @PathVariable TemplateDocumentType documentType) {

**`JiraSiteConfigController.java`** — the simplest case: single row, no list, and note the

mapping helpers; only `JiraSiteConfigController`'s is already an instance method. Injecting a
resolution-service dependency into `ReleaseController`/`TemplateController`/`DocumentController` means
either de-staticing those helpers (consistent with `JiraSiteConfigController`'s existing shape) or
passing a resolved-emails map as an extra parameter into the static helpers. De-staticing is the smaller
diff and matches the one controller that already isn't static.

### 5. Precedent for constructing an unreadable/wrong-key credential row in a test

**This exists, and it is the strongest possible precedent.** `JiraCredentialPersistenceIT.java`
(`src/test/java/com/evision/releasemgmt/adapters/persistence/JiraCredentialPersistenceIT.java`),
method `upsertOverwritesARowEncryptedUnderASupersededKey` (lines 55-70):

```java
/**
 * A row encrypted under a superseded key must not block the sign-in that replaces it.
 * upsert previously did findById + save, which decrypted the stored token first, so
 * rotating RM_CREDENTIAL_KEY threw on login and locked every existing user out with no
 * recovery path — re-entering the token went through the same failing read.
 *
 * <p>Simulating rotation by writing ciphertext this key cannot decrypt is equivalent to
 * the key having changed under an existing row, and avoids rebuilding the context with a
 * different key.
 */
@Test
void upsertOverwritesARowEncryptedUnderASupersededKey() {
    repository.upsert("557058:rotated", "rm@acme.com", "token-under-old-key");
    // key version 1, a valid-looking IV, then bytes that will fail the GCM tag check
    byte[] undecryptable = new byte[1 + 12 + 32];
    undecryptable[0] = 1;
    jdbcTemplate.update(
            "UPDATE jira_credential SET encrypted_token = ? WHERE jira_account_id = ?",
            Base64.getEncoder().encodeToString(undecryptable), "557058:rotated");

    repository.upsert("557058:rotated", "rm@acme.com", "token-under-new-key");
    ...
}
```

The technique — `upsert` a real row via the port, then use `@Autowired JdbcTemplate` to overwrite
`encrypted_token` directly with bytes that fail the GCM tag check, bypassing the entity/converter
entirely on the write side — is exactly how to build the fixture for this phase's decryption test. A
sibling test in the same file, `sessionInvalidationDoesNotRequireDecryptingTheStoredToken` (lines
72-85), is the closer structural match to what's needed here: it proves a *different* JPQL-projection
operation (`markSessionsInvalidated`/`findSessionsInvalidatedAt`) succeeds against an undecryptable row.
The new test for this phase should follow that second test's shape but drive it through the actual
display path (a controller endpoint or the new resolution service), per the CONTEXT.md guidance that
the stronger claim is "exercise a row whose ciphertext is unreadable and show the screen still
renders" rather than asserting the projection query's SQL shape in isolation.

`EncryptedTokenConverterTest.java` (`src/test/java/com/evision/releasemgmt/adapters/persistence/crypto/EncryptedTokenConverterTest.java`)
exists as a unit test of the converter itself but does not exercise the repository/entity layer — it is
a secondary reference, not the primary precedent.

## Shared Patterns

### JPQL projection to avoid entity hydration (the phase's central constraint)
**Source:** `JiraCredentialJpaRepository.findSessionsInvalidatedAt` (line 36) +
`JiraCredentialRepositoryAdapter.findSessionsInvalidatedAt` (lines 59-62)
**Apply to:** the new `(account_id, email)` batch lookup port method — this is the only acceptable
shape; `findById`/`findByAccountId`/any entity-returning query must not appear on this path.

### `@Service` with one port/repository dependency and one narrow public method
**Source:** `application/TicketSearchService.java` (full file, 40 lines)
**Apply to:** the new resolution/enrichment application service. Constructor injection, no field
injection, package `application`, `@Service` annotation — matches every other application service in
the codebase (`JiraAccessContextService`, `JiraSiteConfigService`, etc.).

### Controller `private (static) toResponse(...)` mapping helper
**Source:** all four controllers, excerpted above
**Apply to:** every one of the 9 capture sites. Note the static/instance inconsistency flagged above —
`JiraSiteConfigController`'s already-instance helper is the shape the other three will need to converge
toward once they take a resolution-service dependency.

### Degrade-to-raw-value on missing data (already an established idiom, not new to this phase)
**Source:** `DocumentController.java` lines 165-173 — `downloadLogo` returns a plain 404 rather than a
misleading reason when data is simply absent; `WR-04`'s comment there is conceptually the same "don't
manufacture a placeholder" discipline `D-05.3-04` asks for (though that specific code path is a 404, not
an id-degrades-to-itself — cited only as evidence the "no synthetic placeholder" instinct is already
house style, not a new invention for this phase).
