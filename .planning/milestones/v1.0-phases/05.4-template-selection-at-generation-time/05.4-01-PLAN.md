<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller -> TemplateRepository.setUserDefault | accountId and templateId arrive from upper layers; templateId originates from a URL path |
| application -> PostgreSQL | native upsert SQL with bound parameters |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05.4-01 | Tampering | template_user_default rows | mitigate | Row's document_type is copied from the template row inside `INSERT ... SELECT` (upsertFromTemplate); no API exists that writes a caller-chosen type, so a cross-type default is unrepresentable (D-05.4-04). Proven by the RUNBOOK-row IT test. |
| T-05.4-02 | Tampering | native upsert query | mitigate | `:accountId`/`:templateId` are JPA-bound parameters, never concatenated; no SQL string building. |
| T-05.4-03 | Elevation of privilege | per-user default rows | mitigate | Every port method is keyed by an explicit accountId; clearUserDefault deletes only `WHERE account_id = :accountId`, so one account cannot clear another's row through this port. Upper layers pass `principal.getName()` (plan 04). |
| T-05.4-04 | Denial of service | deleting a template that is someone's default | accept | ON DELETE CASCADE drops the default and the user falls back to the active template (D-05.4-04); deletion is never blocked, matching D-04-13. |
| T-05.4-05 | Information disclosure | account_id column | accept | Stores the same Jira accountId every existing actor column stores (D-05.3-01); no new PII. |
</threat_model>
