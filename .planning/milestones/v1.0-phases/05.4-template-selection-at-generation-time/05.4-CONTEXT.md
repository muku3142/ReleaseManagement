# Phase 05.4: Template Selection At Generation Time - Context

**Gathered:** 2026-10-07
**Status:** Ready for planning
**Source:** Direct decision capture. D-05.4-01 and D-05.4-02 were decided 2026-08-12 when the phase was
inserted (recorded in the ROADMAP section). D-05.4-03 to D-05.4-06 were decided 2026-10-07 at planning
time, after the user added: "make sure the user can set a default template, this will be different for
each user". No `/gsd-discuss-phase` run.

<domain>
## Phase Boundary

**In scope:**
- Choosing, at generation time, which template of the slot's document type produces the document.
- A **per-user default template per document type**, set from the Templates screen, used to preselect
  the picker and to resolve generation when no explicit choice is sent.
- Readiness no longer depends on the global active template (see D-05.4-06).

**Out of scope, explicitly:**
- Removing the global `active` concept. It survives as the org-wide fallback (D-05.4-03).
- Changing what a snapshot stores. `DocumentSnapshot.create(...)` already copies `template.id()`,
  `template.name()` and `template.body()` (DOC-07), so which template produced a revision is already
  recorded.
- Any user profile/preferences store beyond the one table this phase needs. No user entity exists, and
  this phase does not create one.
- A "remember as my default" control in the generate picker. The user chose the Templates screen only.

**The defect being fixed.** `DocumentGenerationService.java:51` resolves the template as
`templateRepository.findActive(documentType).orElseThrow(NoActiveTemplateException::new)`, and
`TemplateRepositoryAdapter.setActive()` keeps exactly one active template per type. Generating with a
different template means activating it globally, which silently changes what every other release, and
every other user, generates next.

<decisions>
## Implementation Decisions

### D-05.4-01: The choice is an optional override (decided 2026-08-12, extended by D-05.4-03)
`generate()` accepts an optional `templateId`. When it is absent, the server resolves the default
(D-05.4-03). Removing `active` outright was offered and rejected on 2026-08-12, and was offered again on
2026-10-07 as "replace global active with per-user defaults" and rejected again.

### D-05.4-02: Type-filtered picker, server-enforced (decided 2026-08-12)
The picker lists only templates whose `documentType` equals the slot's. The server rejects a `templateId`
whose type does not match the path's `documentType` and does not trust the client. An unknown
`templateId` is also a rejection, not a silent fallback to the default. Per-type readiness, revision
numbering and export filenames all key off document type, so a cross-type template would make the
snapshot's own `documentType` dishonest. Both rejections need distinct ProblemDetail reason codes,
following the existing `GlobalExceptionHandler` pattern.

### D-05.4-03: Per-user default, layered over the global active template (decided 2026-10-07)
Resolution order when generating, as implemented in the application service:
1. explicit `templateId` from the request (validated per D-05.4-02)
2. the **requesting user's default** for this document type
3. the **global active** template for this document type (`findActive`, unchanged)
4. otherwise: rejection (no template resolvable)

The picker preselects using the same order (2, then 3). With neither, it has no preselection and the
user must pick.

A user's default is **personal**. Setting it changes nothing for any other user and does not touch
`template.active`. Success criterion 5 ("does not change what any other release generates next") holds
for *other users*; for the same user, changing their own default is intended to change their next
generation.

### D-05.4-04: Storage is one new table (decided 2026-10-07)
This **reverses the ROADMAP's "no schema change" note**: that note held for D-05.4-01/02 alone.
`V7` adds a table keyed by `(account_id, document_type)` (primary key), holding `template_id` as a FK to
`template(id)` with **`ON DELETE CASCADE`**, so deleting a template silently drops any defaults pointing
at it and those users fall back to the global active template. Deletion is not blocked.

`account_id` is the Jira accountId from `principal.getName()`, the same identifier every actor column
already stores (D-05.3-01). There is no FK on it, because no user table exists.

Set/clear is an upsert/delete on that key. The repository-level invariant: a stored default's template
must have the same `document_type` as the row. The set endpoint enforces it, since the table cannot
express it without denormalising.

### D-05.4-05: Default is set from the Templates screen only (decided 2026-10-07)
Each template gets a "Set as my default" action beside the existing Activate action. The template marked
as the user's default shows a "My default" badge, which is visually distinct from the existing
global-active badge, because both can apply to different templates of the same type. The user can also
clear their default. The template list/detail response gains a per-requester boolean (e.g.
`myDefault`), computed for the authenticated user. `active` stays as-is.

REST shape is the planner's call, following `TemplateController` conventions. The obvious fit is
`PUT /api/templates/{templateId}/my-default` and `DELETE /api/templates/{templateId}/my-default`, or a
per-type resource. The generate picker does **not** offer "remember as default".

### D-05.4-06: Readiness stops depending on the active template (decided 2026-10-07)
Readiness must be the same for every viewer, so it cannot depend on per-user defaults. The blocking
state now means "**no template of this document type exists at all**", not "no active template". With
templates present but none active and no personal default, generation is still possible via an explicit
pick.

Rename the state and its error code from `NO_ACTIVE_TEMPLATE` to `NO_TEMPLATE` end to end: the enum,
`DocumentReadinessService`, the ProblemDetail code, `api/documents.ts`, `api/auth.ts`, and the
`DocumentsSection.tsx` branches. No compatibility alias (project rule: no backwards-compatibility shims).
`NoActiveTemplateException` is renamed to match. Its copy no longer says "Activate one from Templates";
it says to create one.

`DocumentReadinessService.all()` replaces its per-type `findActive` call with an existence check. Keep
it one query per type or better; do not add a per-release query.

### Claude's Discretion
- Exact ProblemDetail reason-code names for mismatch, unknown template, and no-resolvable-template.
- Request body shape for generate (`{ "templateId": "..." }` optional body, or a query param). Prefer an
  optional JSON body, since the endpoint is a POST.
- Whether default resolution lives in `DocumentGenerationService` or a small collaborator. Keep it in
  the service unless it is reused by the picker-preselection read path.
- How the picker obtains its preselection: the frontend can compute it from the type-filtered template
  list (`myDefault`, then `active`) with no extra endpoint. Prefer that.
- Picker UX inside `DocumentsSection.tsx`: a select beside each slot's Generate button, reusing existing
  component patterns. No UI-SPEC was produced; the user chose to skip it.
</decisions>

<specifics>
## Specific Ideas

- Success criterion 5 needs a test with **two principals**: user A sets a default, and user B's
  generation and picker preselection are unaffected.
- A test proves `ON DELETE CASCADE`: delete the template that is A's default, and A's next generation
  falls back to the global active template.
- A test proves a cross-type `templateId` is rejected, both at generate and at set-default.
- The snapshot's `templateId`/`templateName` reflect the template actually used in each resolution path
  (explicit, personal default, global active).
</specifics>
