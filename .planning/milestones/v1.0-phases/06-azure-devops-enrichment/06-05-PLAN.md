`@Service public class EnrichmentService` (SLF4J logger as in `FieldMetadataService`). Fields:
`private final ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor();`, `private final Semaphore permits;`
(service-wide, so concurrent runs share one cap, which also protects the shared ADO budget later), `Duration deadline`,
`int maxCommitsPerTicket`, `JiraAccessContextService accessContextService`, `JiraDevStatusPort devStatusPort`, `ReleaseRepository releaseRepository`.
Constructor takes those plus `@Value("${app.enrichment.max-concurrent}") int maxConcurrent`, `@Value("${app.enrichment.deadline}") Duration deadline`,
`@Value("${app.enrichment.max-commits-per-ticket}") int maxCommitsPerTicket`.

```java
/**
 * D-06-01/D-06-04: discovers and stores code links for the given tickets of one release. Per-item failures become
 * FAILED items and never escape; only the final write can throw (ReleaseFrozenException, ReleaseNotFoundException).
 */
public void enrich(UUID releaseId, List<TicketDetail> tickets)
```
Steps:
1. Return immediately when `tickets` is empty.
2. `JiraAccessContext access = accessContextService.currentContext();` on the calling thread (Pattern 1: virtual workers do not inherit
   the SecurityContext).
3. `Map<String, CodeLinks> previous` = from `releaseRepository.findById(releaseId)` items, keyed by ticket key (request thread; workers never touch the DB).
4. For each ticket with non-null `jiraIssueId`, submit a task: `permits.acquire(); try { return enrichOne(access, ticket, previousOrNotAttempted); } finally { permits.release(); }`
   (InterruptedException -> restore interrupt and return `previous.failed(TIMEOUT, now, previous.history())`).
5. Collect with one shared deadline (`deadlineNanos = System.nanoTime() + deadline.toNanos()`); for each future
   `get(max(0, remaining), NANOSECONDS)`; on `TimeoutException`: `future.cancel(true)` and record `previous.failed(EnrichmentReason.TIMEOUT, Instant.now(), previous.history())`;
   on `ExecutionException` (should not happen, enrichOne catches) record `DEV_STATUS_ERROR`.
6. `releaseRepository.saveEnrichment(releaseId, results);` once.

`CodeLinks enrichOne(JiraAccessContext access, TicketDetail ticket, CodeLinks previous)` (package-private for tests), wrapping everything in
`try { ... } catch (DevStatusUnrecognisedException e) {...} catch (JiraTicketReadException e) {...} catch (RuntimeException e) { log.warn("Enrichment of {} failed", ticket.key(), e); ... }`
(Pitfall 7: nothing escapes a worker). Success path:
```java
DevStatusLinks links = devStatusPort.fetchLinks(access, ticket.jiraIssueId(), ticket.key());
List<LinkedCommit> commits = links.keyTaggedCommits();
boolean capped = commits.size() > maxCommitsPerTicket;
if (capped) commits = newest maxCommitsPerTicket by authoredAt;
EnrichmentStatus status = links.hasDisplayableLinks() ? LINKED : NO_LINK;   // D-06-10
return new CodeLinks(status, capped ? COMMIT_LIMIT : null, capped, Instant.now(), CommitsSource.KEY_TAGGED,
        links.pullRequests(), commits, links.branches(), previous.history());
```
Comments: KEY_TAGGED is the D-06-09 Jira-only source; the cap keeps any item under the template render collection limit (ADO-02).
Failure paths use `previous.failed(reason, Instant.now(), previous.history())` (D-06-12). Map `JiraTicketReadException.reason()`:
INVALID_CREDENTIALS, JIRA_FORBIDDEN -> JIRA_UNAUTHORIZED; JIRA_RATE_LIMITED -> JIRA_RATE_LIMITED; JIRA_UNREACHABLE -> JIRA_UNREACHABLE; others -> DEV_STATUS_ERROR.
Never log the access context or tokens.

Add a `@PreDestroy void shutdown() { executor.shutdownNow(); }` only if RenderService does the same; otherwise match RenderService.

## Trust Boundaries

| Boundary | Description |

| browser -> POST code-links/refresh | Optional `ticketKey` query parameter is untrusted |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-21 | Tampering (JQL injection) | refreshCodeLinks | mitigate | Key must already be on the release, and `fetchTickets` filters every key through `TICKET_KEY` before composing JQL |
| T-06-22 | Denial of service | EnrichmentService | mitigate | Service-wide `Semaphore(max-concurrent=6)`, per-run deadline PT45S with `cancel(true)`, commit cap 400 per ticket |
| T-06-23 | Elevation of privilege | EnrichmentService | mitigate | `JiraAccessContext` resolved once from the caller's own principal; workers receive the value and cannot reach another user's credential |
| T-06-24 | Tampering | refresh/create/add | mitigate | Enrichment errors are caught and logged; the release write already committed is untouched (D-06-04) |
| T-06-25 | Information disclosure | logs | mitigate | Logs carry ticket key and release id only, never the access context or tokens |
</threat_model>
