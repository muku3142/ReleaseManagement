<objective>
Add corrections end to end: a correction supersedes an entry without editing it, can void an entry that should never have
existed, and shows in the history with the original marked as superseded.

Phase user story: **As a** release manager, **I want to** record each promotion of a frozen release through the environment ladder
and review its complete append-only history, **so that** I always know where every release sits and how it got there.

Purpose: AUDIT-03 / ROADMAP criterion 5 - history is append-only and a correction adds a new entry. Reuses the 07-03 port unchanged
(`appendUnderLock` takes a decide function), so no persistence change is needed.
Output: domain `correct`, service + endpoint, correction UI, tests.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-24 | Elevation / Tampering (IDOR) | correcting another release's entry via this release's URL | mitigate | `correct` looks the original up only among the path release's entries (PromotionNotFoundException); composite FK `(supersedes_id, release_id)` backstop; IT covers it |
| T-07-25 | Tampering / Repudiation | silent history rewrite | mitigate | Correction is an INSERT with `supersedes_id` and a required reason (`@NotBlank` + DB CHECK); originals stay visible; trigger blocks UPDATE/DELETE |
| T-07-26 | Tampering | double correction race | mitigate | Release row lock serialises corrections; `promotion_superseded_once` unique index is the backstop |
| T-07-27 | Spoofing | correction actor | mitigate | Actor from `principal.getName()`; request has no actor field |
| T-07-28 | Tampering (stored XSS) | reason/note display | mitigate | React text only; `@Size(max = 2000)` server-side |
</threat_model>
