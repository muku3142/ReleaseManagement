## Milestone v1.1 Requirements — Release Assistant

Defined 2026-10-13. A read-only assistant that answers plain-language questions from this system's own data, using a self-hosted Ollama model (no data egress). Research: `.planning/research/v1.1/SUMMARY.md`. Phase numbering continues at 9.

### RAG Service — Index

- [x] **RAG-01**: An internal app with its own API key can create collections and push, replace or delete documents (text, title, URL, metadata) by its own ids, and sees only its own collections
- [x] **RAG-02**: Pushed documents become searchable by meaning through a self-hosted embedding model; unchanged content is not re-embedded and deleted content never appears
- [x] **RAG-03**: Ingestion is asynchronous and survives model-server outages — pushes are accepted while Ollama is down and indexed when it returns
- [x] **RAG-04**: An app can re-index a collection and see each collection's indexing status and last-indexed time
- [x] **RAG-05**: An app can search a collection with optional metadata filters and get ranked passages with their source references

### RAG Service — Chat

- [x] **RAG-06**: An app can ask a question over one or more collections and receive a streamed (SSE) answer
- [x] **RAG-07**: Answers cite sources built by the service from passage metadata and tool-result sources, never from model text
- [x] **RAG-08**: An app can supply tool definitions; the service returns tool calls, the app runs them and returns results, and the service answers with them — the service never calls into apps
- [x] **RAG-09**: The service says it does not know when the sources do not support an answer
- [x] **RAG-10**: The service API is published as an OpenAPI contract any internal app can integrate against
- [x] **RAG-11**: An app can send text with an instruction and receive the transformed text streamed back, with no retrieval involved (generic summarize/clean/rewrite)

### RAG Service — Safety

- [x] **SAFE-01**: Every request is bounded — tool-round cap, deadline, and per-client concurrency limit
- [x] **SAFE-02**: Document text is treated as data, never instructions, and answers are plain text; the residual prompt-injection risk is accepted and documented
- [x] **SAFE-03**: Ollama is the only outbound call (no data leaves the machine), and logs record metadata only, never question or answer text
- [x] **SAFE-04**: Answer quality and the model choice are measured through the API on 30-50 representative questions (3 runs each, including injection and not-in-the-data cases) before v1.1 ships

### ReleaseManagement Assistant

- [x] **ASST-01**: Ticket text, manual items, the latest generated documents and code-link text are pushed to the RAG service and kept current, without slowing v1 actions or breaking them when the service is down
- [x] **ASST-02**: The release manager asks questions on an Assistant screen behind ReleaseManagement's existing login and sees answers stream in; the browser never holds the service API key
- [x] **ASST-03**: Exact facts — stage, dates, counts, readiness, deployments, churn — come from ReleaseManagement's own read-only tools, which ReleaseManagement runs
- [x] **ASST-04**: ReleaseManagement's assistant tools are read-only, enforced by architecture tests
- [x] **ASST-05**: "Ask about this release" opens the assistant scoped to that release
- [x] **ASST-06**: A "how I answered" panel shows the tools and sources behind each answer
- [x] **ASST-07**: An empty chat offers starter questions, and follow-ups use the current session's turns only
- [x] **ASST-08**: The screen shows clear offline, busy and model-missing states, plus when the index was last updated
- [x] **ASST-09**: The release manager can send any generated document (release notes, runbook, approval) to the model to clean it up, summarize it, or apply a custom instruction, and sees the result stream in beside the original for comparison
- [x] **ASST-10**: The release manager can edit the AI result and save it as a new revision marked AI-assisted, with the instruction recorded; the original revision is never changed

### v1.1 decisions (2026-10-13)

- **Scoping: shared, like v1.** Local data already has no per-user filter, so the assistant answers from everything the app holds. It must never claim to honour per-user Jira permissions. A `project_key` is stored on each index chunk so filtering can be added later without re-indexing.
- **Production hardware: unknown.** Build and test on the 4 GB dev GPU (`qwen3:4b`); the model is a config property; re-measure on the real host before shipping.
- **Postgres: the compose Postgres.** The image switches to pgvector and the extension is created by migration.
- **Phase order: service first** (9 RAG service foundation and index, 10 chat and citations, 11 tool-call protocol, 12 ReleaseManagement as first client, 13 assistant screen and quality gate).
- **No saved conversations** in v1.1. **Index only what the screens show.** **Prompt-injection residual risk accepted.**
- **Architecture: standalone reusable RAG service** (approved 2026-10-13) — see PROJECT.md Key Decisions; ReleaseManagement is the first client

### v1.1 Out of Scope

| Feature | Reason |
|---------|--------|
| Filtering answers by each user's Jira permissions | Decided shared like v1; `project_key` stored so it can be added later |
| Saved conversations, feedback thumbs, admin re-index screen | Deferred — no stated need; a re-index endpoint covers ops |
| Write or action tools | The assistant is advisory and read-only (ASST-04) |
| Cloud LLM fallback | No data egress |
| Agent frameworks, free-text-to-SQL | Over-engineering; a bounded loop over existing services is enough |
| Service calling into client apps (callbacks/MCP) | Callers run their own tools; the service holds no app credentials |
