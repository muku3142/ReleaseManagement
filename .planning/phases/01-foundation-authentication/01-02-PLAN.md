**`frontend/src/api/client.ts`** — the single HTTP boundary for the whole SPA:
```ts
function readCookie(name: string): string | null {
  const match = document.cookie.match(new RegExp('(^|; )' + name + '=([^;]*)'));
  return match ? decodeURIComponent(match[2]) : null;
}

export async function apiFetch<T>(path: string, init: RequestInit = {}): Promise<T> {
  const method = (init.method ?? 'GET').toUpperCase();
  const headers = new Headers(init.headers);
  if (init.body !== undefined) headers.set('Content-Type', 'application/json');
  if (method !== 'GET' && method !== 'HEAD') {
    const csrf = readCookie('XSRF-TOKEN');
    if (csrf) headers.set('X-XSRF-TOKEN', csrf);
  }
  const response = await fetch(path, { ...init, headers, credentials: 'same-origin' });
  if (response.status === 204) return undefined as T;
  if (!response.ok) {
    const problem = await response.json().catch(() => ({ status: response.status, reason: 'UNKNOWN' }));
    throw new ApiError({ ...problem, status: response.status, reason: problem.reason ?? 'UNKNOWN' });
  }
  return (await response.json()) as T;
}
```
`credentials: 'same-origin'` is required for the httpOnly JWT cookies plan 05 introduces. Read `XSRF-TOKEN` and echo it as `X-XSRF-TOKEN` on every non-GET — that is exactly what Spring Security 7.1's `csrf.spa()` expects (D-08). Never read, store or send a JWT from JavaScript; the cookies are httpOnly and invisible here by design.

```ts
export type JiraSiteConfig = { baseUrl: string; updatedAt: string; updatedBy: string };
export const jiraSiteQueryKey = ['jira-site'] as const;

export function useJiraSite() {
  return useQuery({ queryKey: jiraSiteQueryKey, queryFn: () => apiFetch<JiraSiteConfig>('/api/settings/jira-site') });
}

export function useUpdateJiraSite() {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: (baseUrl: string) =>
      apiFetch<JiraSiteConfig>('/api/settings/jira-site', { method: 'PUT', body: JSON.stringify({ baseUrl }) }),
    onSuccess: (config) => queryClient.setQueryData(jiraSiteQueryKey, config),
  });
}
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Server-rendered HTML/JS → browser DOM | Any server data rendered into the SPA crosses here |
| Browser JS → `/api/**` | State-changing requests must carry a CSRF token |
| Build output → jar | Anything in `frontend/dist` ships to every client |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Tampering | State-changing `PUT /api/settings/jira-site` issued from the browser without a CSRF token | mitigate | `apiFetch` reads the JS-readable `XSRF-TOKEN` cookie and echoes it as `X-XSRF-TOKEN` on every non-GET/HEAD request — the contract Spring Security 7.1 `csrf.spa()` enforces once plan 05 lands (D-08) |
| T-02-02 | Information Disclosure | A future contributor storing a session token in `localStorage`, re-opening the XSS exposure D-08 exists to close | mitigate | No token is ever handled in JS; the JWT cookies are httpOnly and unreadable here. Enforced by the grep gate `localStorage|sessionStorage` == 0 in this plan's acceptance criteria |
| T-02-03 | Tampering (XSS) | Server-supplied `baseUrl` / `updatedBy` rendered into the DOM | mitigate | React escapes interpolated text by default and `dangerouslySetInnerHTML` is grep-gated to 0. No HTML rendering of server strings anywhere in Phase 1 |
| T-02-04 | Information Disclosure | Secrets baked into the client bundle | mitigate | No `import.meta.env` secret is introduced; the SPA needs no configuration beyond same-origin relative paths. `RM_*` secrets live only in the backend process |
| T-02-05 | Spoofing | Cookies scoped to the wrong origin during local development, causing the auth flow to silently fail or be sent cross-origin | mitigate | Vite dev proxy with `changeOrigin: false` keeps SPA and API same-origin on `localhost` (RESEARCH.md Pitfall 4); production is one jar, one origin |
| T-02-06 | Denial of Service | Retry storms against a failing backend from the query layer | accept | `retry: false` on the `QueryClient` — a single-user internal tool does not need retry, and surfacing the `reason` immediately is the D-04 requirement |
</threat_model>
