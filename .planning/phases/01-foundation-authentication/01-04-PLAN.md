<objective>
Build the encrypted credential vault: the Jira API token is stored as an AES-256-GCM envelope in a single column, keyed by Jira `accountId`, with the key supplied from the environment at startup — and it can be replaced without disturbing anything else.

Purpose: AUTH-03 requires that a database connection alone does not expose plaintext tokens, and AUTH-04 requires token replacement without losing existing data. Both are properties of the storage design, so they are settled here — before plan 06 wires the sign-in flow that writes through this vault.
Output: `EncryptedTokenConverter`, the `jira_credential` mapping, the persistence port and adapter, a framework-free crypto unit test, and a Testcontainers test that reads the raw column with native SQL to prove it is not plaintext.
</objective>

Create `adapters/persistence/crypto/EncryptedTokenConverter.java` as `@Component @Converter implements AttributeConverter<String, String>`, following RESEARCH.md Pattern 3 exactly:

```java
private static final int IV_LENGTH = 12;      // GCM standard nonce length
private static final int TAG_BITS = 128;
private static final int KEY_BYTES = 32;      // AES-256

private final SecretKey key;
private final byte keyVersion;

public EncryptedTokenConverter(@Value("${app.credential.key}") String base64Key,
                               @Value("${app.credential.key-version}") int keyVersion) {
    byte[] raw = Base64.getDecoder().decode(base64Key);
    if (raw.length != KEY_BYTES) {
        throw new IllegalStateException(
            "RM_CREDENTIAL_KEY must decode to exactly 32 bytes for AES-256; got " + raw.length);
    }
    if (keyVersion < 1 || keyVersion > 127) {
        throw new IllegalStateException("app.credential.key-version must be between 1 and 127");
    }
    this.key = new SecretKeySpec(raw, "AES");
    this.keyVersion = (byte) keyVersion;
}
```
The length check is a fail-fast startup control, not defensive padding: a short key would otherwise silently produce AES-128 or a runtime error on first sign-in. The exception message must state the observed length but must never include the key value.

`convertToDatabaseColumn(String plainToken)`: return `null` for `null`; generate a fresh `byte[12]` IV from a `SecureRandom` **on every call** (an IV reused under the same key destroys GCM's guarantees — RESEARCH.md's threat table lists this explicitly); `Cipher.getInstance("AES/GCM/NoPadding")` in `ENCRYPT_MODE` with `new GCMParameterSpec(TAG_BITS, iv)`; assemble `ByteBuffer.allocate(1 + IV_LENGTH + ciphertext.length).put(keyVersion).put(iv).put(ciphertext)`; return `Base64.getEncoder().encodeToString(buffer.array())`.

`convertToEntityAttribute(String stored)`: return `null` for `null`; base64-decode; read and discard the version byte (v1 has exactly one active key, so the version is metadata for a future rotation batch, not a key selector — D-11); read the 12-byte IV; treat the remainder as ciphertext+tag; decrypt with the same parameters; return the UTF-8 string.

Hold a single `SecureRandom` instance as a field rather than constructing one per call. Wrap the checked `javax.crypto` exceptions in an unchecked `IllegalStateException` with a fixed message that never contains the token, the ciphertext or the key. Let `AEADBadTagException` propagate as that `IllegalStateException` — a failed tag check means the stored row was tampered with or the wrong key is configured, and both must be loud failures, not silent nulls.

**`EncryptedTokenConverterTest.java`** — plain JUnit, no Spring context, constructing the converter directly with the 32-byte fixture key and version `1`:
1. Round-trip: `convertToEntityAttribute(convertToDatabaseColumn("ATATT3xFfGF0-secret-token"))` equals the input.
2. Ciphertext is not plaintext: the encrypted value does not contain `ATATT3xFfGF0` and is not equal to the input.
3. Two encryptions of the same plaintext produce **different** stored values (proves a fresh IV per write).
4. Envelope layout: base64-decoding the stored value yields a first byte equal to `1` and a total length of `1 + 12 + plaintextLength + 16`.
5. `null` in → `null` out, both directions.
6. Tampering: flip the last byte of the base64-decoded ciphertext, re-encode, and assert `convertToEntityAttribute` throws (GCM tag check fails).
7. A key that decodes to 16 bytes makes the constructor throw `IllegalStateException` whose message contains `32 bytes`.
8. A different 32-byte key cannot decrypt a value produced by the fixture key (throws).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Application → PostgreSQL | The Jira API token crosses here and must be ciphertext on the far side |
| Operating environment → application | `RM_CREDENTIAL_KEY` crosses here at startup |
| Persistence layer → everything above it | The decrypted token must not travel further than the code that makes a Jira call |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-01 | Information Disclosure | An attacker with a database connection or a stolen backup reading plaintext Jira tokens | mitigate | Column-level AES-256-GCM via `EncryptedTokenConverter`; the DB never sees plaintext. | T-04-05 | Information Disclosure | The key or the token appearing in logs, exception messages or stack traces | mitigate | No logging statements at all in the converter (grep-gated); exception messages carry only the observed key length and fixed strings |
