<objective>
Issue and validate the session: a stateless HS256 JWT pair in httpOnly cookies, with the algorithm pinned on the decoder, a rolling idle window via a refresh token, an immutable absolute cap, CSRF for the same-origin SPA, and a stateless Spring Security filter chain that reads the token from a cookie rather than the `Authorization` header.

Purpose: this is the security substrate every authenticated endpoint in the project sits on. It is deliberately separated from the login endpoint (plan 06) so the token mechanics, the cap-preservation rule and the authorization matrix are correct and independently tested before any flow depends on them.
Output: `JwtConfig`, `JwtTokenService`, cookie writer and resolver, `SecurityConfig`, and tests that assert an alg-confusion attempt, a cross-type token replay and a refresh-past-the-cap all fail.

**`config/JwtConfig.java`** — decode the secret once and build one encoder plus two decoders:
```java
private static final int MIN_SECRET_BYTES = 32;   // HS256 requires a >= 256-bit key

@Bean
SecretKey jwtSigningKey(@Value("${app.jwt.secret}") String base64Secret) {
    byte[] raw = Base64.getDecoder().decode(base64Secret);
    if (raw.length < MIN_SECRET_BYTES) {
        throw new IllegalStateException(
            "RM_JWT_SECRET must decode to at least 32 bytes for HS256; got " + raw.length);
    }
    return new SecretKeySpec(raw, "HmacSHA256");
}

@Bean
JwtEncoder jwtEncoder(SecretKey jwtSigningKey) {
    return new NimbusJwtEncoder(new ImmutableSecret<>(jwtSigningKey));
}

@Bean
@Primary
JwtDecoder accessTokenDecoder(SecretKey jwtSigningKey) {
    return decoder(jwtSigningKey, JwtTokenService.TYPE_ACCESS);
}

@Bean
JwtDecoder refreshTokenDecoder(SecretKey jwtSigningKey) {
    return decoder(jwtSigningKey, JwtTokenService.TYPE_REFRESH);
}

private JwtDecoder decoder(SecretKey key, String expectedType) {
    NimbusJwtDecoder decoder = NimbusJwtDecoder.withSecretKey(key)
            .macAlgorithm(MacAlgorithm.HS256)
            .build();
    decoder.setJwtValidator(new DelegatingOAuth2TokenValidator<>(
            JwtValidators.createDefault(),
            new TokenTypeValidator(expectedType),
            new AbsoluteExpiryValidator()));
    return decoder;
}
```
`.macAlgorithm(MacAlgorithm.HS256)` is the alg-confusion control and is mandatory: it makes the decoder reject any token whose header advertises a different algorithm (including `none`) instead of trusting the token's own `alg`. Two decoders — rather than one plus ad-hoc claim checks at call sites — mean an access token presented at `/api/auth/refresh` and a refresh token presented as an access token are both rejected by the decoder itself, before any application code runs.

**`TokenTypeValidator`** implements `OAuth2TokenValidator<Jwt>`: returns `OAuth2TokenValidatorResult.failure(new OAuth2Error("invalid_token", "Unexpected token_type", null))` unless `expectedType.equals(jwt.getClaimAsString("token_type"))`.

**`AbsoluteExpiryValidator`** implements `OAuth2TokenValidator<Jwt>`: reads `absolute_exp` as a long (fail if absent), and fails when `Instant.now().isAfter(Instant.ofEpochSecond(absoluteExp))`. This is what makes the 8-hour cap enforced on *every* request, not only at refresh time.

**`TokenPair`** — the record from `<interfaces>`.

**`JwtTokenService.java`** — `@Component`, constructor-injects `JwtEncoder`, `@Qualifier("refreshTokenDecoder") JwtDecoder`, and the three TTLs via `@Value("${app.jwt.access-ttl}") Duration` etc.
- `issue(jiraAccountId, email)`: `Instant now = Instant.now()`, `Instant absoluteExpiry = now.plus(absoluteTtl)`, then encode two tokens via a private `encode(...)`.
- `encode(String subject, String email, Instant issuedAt, Instant expiresAt, String tokenType, Instant absoluteExpiry)`: build `JwtClaimsSet.builder().subject(subject).issuedAt(issuedAt).expiresAt(expiresAt).id(UUID.randomUUID().toString()).claim(CLAIM_TOKEN_TYPE, tokenType).claim(CLAIM_EMAIL, email).claim(CLAIM_ABSOLUTE_EXP, absoluteExpiry.getEpochSecond()).build()` and return `jwtEncoder.encode(JwtEncoderParameters.from(claims)).getTokenValue()`.
- `refresh(String refreshTokenValue)`:
  1. decode with the **refresh** decoder; a `JwtException` becomes `SessionRefreshException(INVALID_SESSION)`, except that an expiry/absolute-cap validation failure becomes `SESSION_EXPIRED` (inspect the `OAuth2Error` description or check the claim directly before mapping).
  2. read `absolute_exp` from the decoded token and, if `Instant.now()` is after it, throw `SessionRefreshException(SESSION_EXPIRED)`.
  3. issue a **new** pair whose access and refresh expiries are `now + ttl` but whose `absolute_exp` claim is the value **copied from the incoming refresh token, never recomputed**. Do not call `issue(...)` here — that would mint a fresh cap. Add a private `issueWithCap(subject, email, absoluteExpiry)` used by both paths so there is exactly one encoding path.
- There is no persistence, no lookup and no revocation list anywhere in this class. Storing a refresh token server-side would silently reintroduce the session state D-05 and D-09 explicitly reject.
- Never log a token value, the secret, or a claim set.

**`ProblemDetailAuthenticationEntryPoint.java`** — `@Component`, implements both `AuthenticationEntryPoint` and `AccessDeniedHandler`. **`SecurityConfig.java`** — one `SecurityFilterChain` bean:
```java
http
  .csrf(csrf -> csrf.spa())
  .sessionManagement(sm -> sm.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
  .oauth2ResourceServer(oauth2 -> oauth2
      .bearerTokenResolver(cookieBearerTokenResolver)

  .exceptionHandling(ex -> ex

      .accessDeniedHandler(problemDetailEntryPoint))
  .authorizeHttpRequests(auth -> auth
      .requestMatchers("/api/auth/login", "/api/auth/refresh", "/api/auth/logout").permitAll()
      .requestMatchers(HttpMethod.GET, "/api/settings/jira-site").permitAll()
```

- `POST /api/auth/login` — nobody is authenticated yet by definition.

- `POST /api/auth/logout` — idempotent cookie clearing.
- `GET /api/settings/jira-site` — D-16 requires a fresh environment to be usable, and the sign-in screen must show which site it will authenticate against, before anyone is signed in.
