**The five criteria under test, verbatim from ROADMAP.md §"Phase 1: Foundation & Authentication":**
1. Release manager can configure which Jira Cloud site the system reads from, and see it in the UI.
2. Release manager can sign in by supplying their Jira email and API token, which the system validates live against that site before granting access.
3. Signing in with an invalid, expired, or revoked token is rejected with a clear error, not a silent failure or generic crash.
4. Stored Jira credentials are encrypted at rest and never appear in any API response after being saved.
5. Release manager can replace an expired or revoked Jira token from a settings screen without losing any existing releases, templates, or history.

**Everything under test already exists** from plans 01-07: the single-jar build, `GET|PUT /api/settings/jira-site`, the live `JiraRestAuthAdapter` (active whenever the `stub-jira` profile is **not** enabled), the AES-256-GCM credential column, the cookie-borne JWT pair, `POST /api/auth/login|refresh|logout`, `GET /api/auth/session`, `PUT /api/auth/credential`, and the SPA's sign-in, guard, sign-out, credential-invalid banner and token-replacement surfaces.

**Criterion 5's scope, stated honestly:** no releases, templates or documents exist yet — those arrive in Phases 3, 4 and 5. Per CONTEXT.md §"Specific Ideas", the testable assertion available now is that replacing the token preserves the credential row's identity and `created_at`, leaves `jira_site_config` untouched, and does not cascade into deleting anything. Record it that way rather than overclaiming.
