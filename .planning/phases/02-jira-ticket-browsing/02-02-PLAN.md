<decisions>

**D-PLAN-02-A — Ports take `JiraAccessContext`, not three loose strings.**
`JiraAuthPort.validate(siteBaseUrl, email, apiToken)` uses three args because login happens
*before* any context exists. Every port added in this phase runs *after* sign-in, so it takes
the `JiraAccessContext` record directly. It is a framework-free `domain/auth` record, so
ArchUnit's ports rule is satisfied.

**D-PLAN-02-B — `JiraProjectSummary(id, key, name)`; `JiraVersion(id, name)`.**
`id` is carried because JQL must be composed from Jira **ids**, never from interpolated display
names (RESEARCH.md Security Domain / anti-patterns). `key` and `name` are for display. Version
`released` / `archived` / `releaseDate` are deliberately **not** modelled — no requirement reads
them, and adding fields "because Jira returns them" is the over-fetching this project's rules
forbid.

**D-PLAN-02-C — Endpoints are `/api/jira/projects` and `/api/jira/projects/{projectId}/versions`.**
Both are plain authenticated `GET`s under the existing `/api/**` rule. `SecurityConfig` is not
touched — the only permitAll carve-out is `GET /api/settings/jira-site`, which these paths do
not match.

</decisions>

   `@Component`, implements `JiraProjectPort`, constructor-injects `RestClient jiraRestClient`.
   **No `@Profile`** — unlike auth, there is no stub variant; ticket browsing has no
   sign-in-without-Jira requirement.

   `listProjects(JiraAccessContext access)`:
   - Classic **offset** pagination — `/project/search` was not part of the `/search`
     deprecation, so do **not** apply the cursor pattern here.
   - Loop: `GET {access.siteBaseUrl()}/rest/api/3/project/search?startAt={startAt}&maxResults=50`
     with `Authorization: Basic {base64(email + ":" + apiToken)}` and `Accept: application/json`.
     Build the Basic header inline with
     `Base64.getEncoder().encodeToString((access.email() + ":" + access.apiToken()).getBytes(StandardCharsets.UTF_8))`
     — the same two lines as `JiraRestAuthAdapter`; do **not** extract a shared header builder
     for two adapters.
   - Accumulate `page.values()` into the result list; advance `startAt += page.values().size()`.
   - Terminate when `values` is empty, OR `Boolean.TRUE.equals(page.isLast())`, OR
     `page.total() != null && accumulated >= page.total()`.
   - Hard ceiling: 50 iterations, then `throw new JiraTicketReadException(JiraAuthFailureReason.RESULT_SET_TOO_LARGE)`.
   - Map each `JiraProjectPayload` to `JiraProjectSummary`.

   `listVersions(JiraAccessContext access, String projectId)`:
   - Single call, no pagination: `GET {siteBaseUrl}/rest/api/3/project/{projectId}/versions`,
     same two headers. Deserialize with `.body(JiraVersionPayload[].class)` (Jira returns a bare
     JSON array). A `null` body yields an empty list.
   - Map to `JiraVersion`. Preserve Jira's returned order — do not sort.

   Wrap the body of both methods in the **six-branch catch cascade copied verbatim** from
   `JiraRestAuthAdapter` lines 44-56, substituting `JiraTicketReadException` for
   `JiraAuthenticationException`. Add one comment above the `listProjects` loop stating that
   `/project/search` is offset-paginated and deliberately not cursor-paginated.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-02-01 | Elevation of Privilege | `JiraProjectService` | mitigate | Every method calls `accessContextService.currentContext()`, which is keyed strictly on `CurrentUserPort.currentAccountId()`. No accountId-taking overload exists, so results can never exceed what the caller can see in Jira (AUTH-02) |
| T-02-02-02 | Information Disclosure | `GET /api/jira/projects` | mitigate | Falls under `SecurityConfig`'s `/api/**` authenticated rule; the only public GET carve-out is the literal path `/api/settings/jira-site`. Proven by the controller test asserting `401` + `UNAUTHENTICATED` for an anonymous caller |
| T-02-02-03 | Tampering | `projectId` → outbound Jira URL | mitigate | `projectId` values only ever originate from the `/api/jira/projects` response the same user just received.
