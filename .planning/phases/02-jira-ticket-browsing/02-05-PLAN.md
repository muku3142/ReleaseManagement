<objective>
Wire the wave-2 machinery into a single REST endpoint the SPA can call:
`POST /api/tickets/search`, taking either a project + fix-version selection or raw JQL, and
returning the **complete** matching ticket set in one response.

Purpose: this is where JIRA-02's three filter dimensions, JIRA-03's exhaustive paging,
JIRA-04's field resolution and AUTH-02's credential scoping meet. RESEARCH.md Pattern 4 is the
governing shape — the backend pages to exhaustion once and hands the SPA the whole array,
because cursor pagination cannot support page-jumping and the frontend does client-side
selection over an already-loaded list.

Output: `TicketSearchCriteria`, `TicketSearchService`, `TicketController`, three DTOs, and the
tests including the `SecurityFilterChainIT` authorization assertions.
</objective>

<decisions>

**D-PLAN-05-A — `POST /api/tickets/search`, not `GET /api/tickets?...`.**
PATTERNS.md sketched a GET with query parameters. Rejected for three reasons:
1. The advanced-JQL escape hatch (D-02-01) has no length bound from the release manager, and
   URL-length limits are a silent failure mode. RESEARCH.md makes exactly this argument for the
   Jira-facing call; it applies identically to our own.
2. A request body gets `@Valid` + the **already-overridden** `handleMethodArgumentNotValid`,
   so the cross-field XOR rule and the numeric-id format rule both surface as
   `VALIDATION_FAILED` with a `fieldErrors` map for free. Query parameters would raise
   `BindException`, which `GlobalExceptionHandler` does not override, producing a ProblemDetail
   with **no `reason` property** — a silent break of the project's error contract.
3. The SPA triggers this manually from a "Load tickets" click, which PATTERNS.md already
   directs to be a `useMutation`, not an auto-fetching `useQuery`. A POST fits that shape
   exactly.
It is a search, not a resource creation — POST-for-search is the standard pragmatic answer when
the query does not fit a URL, and the response is not cacheable anyway (it is per-user and
credential-scoped).

**D-PLAN-05-B — Primary-path JQL is composed from numeric ids only.**
`project = 10023 AND fixVersion = 10891 ORDER BY key ASC`. Both values are validated against
`^[0-9]+$` at the DTO boundary, so there is no quoting, no escaping and no string that could
break out of a clause (RESEARCH.md Security Domain: JQL clause injection via display names).
Display names never touch the composed query.

**D-PLAN-05-C — `ORDER BY key ASC` on the composed path, nothing appended on the JQL path.**
Cursor pagination over an unordered result set is not guaranteed stable, so the path this
project controls gets an explicit deterministic order. The escape hatch is forwarded verbatim —
appending to a user's JQL would break any query that already has its own `ORDER BY`, and the
release manager who reaches for raw JQL owns their ordering. Recorded as a known limitation in
the summary.

**D-PLAN-05-D — No `/search/approximate-count` call.**
UI-SPEC makes the "(~n tickets)" hint conditional ("If an advisory count is fetched"). It costs
an extra Jira round-trip on every search for a number the spec itself forbids treating as
authoritative. Not built. The loading copy stands on its own.

**D-PLAN-05-E — Response is `{"tickets": [...]}`, not a bare array.**
An object leaves room for an additive field later (an advisory count, a truncation flag)
without a breaking change for the SPA.

</decisions>

public record TicketSearchCriteria(String projectId, String fixVersionId, String jql) {

package com.evision.releasemgmt.adapters.web.dto;

import jakarta.validation.constraints.AssertTrue;
import jakarta.validation.constraints.Pattern;
import jakarta.validation.constraints.Size;

public record TicketSearchRequest(
        @Pattern(regexp = "^[0-9]+$", message = "must be a numeric Jira project id")
        String projectId,

        @Pattern(regexp = "^[0-9]+$", message = "must be a numeric Jira version id")

}

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → `POST /api/tickets/search` | Untrusted request body containing filter ids and, on the advanced path, raw JQL |
| Composed JQL → Jira | A query string this service builds and sends upstream |
| `TicketDetail` → HTTP response | Jira-sourced content, including flattened rich text, crossing back to the browser |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-05-01 | Tampering | JQL clause injection via `projectId` / `fixVersionId` | mitigate | Both are `@Pattern("^[0-9]+$")`-validated at the DTO boundary before `toJql()` runs; a value that could carry a quote or an `AND` never reaches the composer. Proven by controller test 5 |
| T-02-05-02 | Elevation of Privilege | Advanced-JQL escape hatch widening the caller's reach | accept | Raw JQL is forwarded verbatim, but it executes **as the signed-in user's own Jira credential** via `currentContext()`. | T-02-05-03 | Elevation of Privilege | Unauthenticated ticket read | mitigate | `/api/tickets/**` falls under `SecurityConfig`'s `/api/**` authenticated rule with no carve-out; asserted at the slice level (test 11) **and** through the full filter chain in `SecurityFilterChainIT` |
| T-02-05-04 | Denial of Service | A JQL matching the entire instance | mitigate | The ceiling from plan 03 fires and surfaces as `RESULT_SET_TOO_LARGE` (422) with actionable copy, rather than a thread pinned against an unbounded upstream |
| T-02-05-05 | Information Disclosure | Validation failure detail | mitigate | `handleMethodArgumentNotValid` emits fixed Bean Validation messages and field names only; it never echoes the submitted JQL back to the client |
| T-02-05-06 | Spoofing | CSRF on the new POST | accept | Inherits the documented Phase 1 posture: `oauth2ResourceServer()` exempts cookie-bearer requests from CSRF, mitigated by `SameSite=Strict` on `access_token`. `SecurityConfig` is unchanged, so no new exposure is introduced. Recorded in `01-05-SUMMARY.md` threat flags |
