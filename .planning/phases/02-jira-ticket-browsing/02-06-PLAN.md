<decisions>

**D-PLAN-06-A — The search is a `useMutation`, not a `useQuery`.**
UI-SPEC is explicit that the fetch must not auto-run on picker change, because paging to
exhaustion can take seconds. A mutation gives an unambiguous manual trigger, `isPending` for
the disabled state, and a `mutate()` re-invocation for **Try again** with no cache-key
gymnastics. The underlying call is a POST anyway (plan 05, D-PLAN-05-A).

**D-PLAN-06-B — Selection is a `Set<string>` of ticket keys held in `useState`.**
The whole matching set is client-side (RESEARCH.md Pattern 4), so there is no
"select all across pages" ambiguity and no need for a store. Loading a new result set clears
the selection — a checkbox referring to a ticket no longer on screen would be a lie.

**D-PLAN-06-C — No client-side pagination or virtualisation.**
RESEARCH.md sizes a fix version at "tens to low hundreds" of tickets, and the backend ceiling
bounds the worst case. Rendering a few hundred rows is not a measured problem, and this project
does not optimise unmeasured ones. Revisit only if a real fix version proves slow at UAT.

**D-PLAN-06-D — No advisory "(~n tickets)" count.**
Plan 05 deliberately does not call `/search/approximate-count`, and UI-SPEC makes that copy
conditional on the count being fetched. The loading copy stands alone.

</decisions>

```typescript
import { useMutation } from '@tanstack/react-query';
import { apiFetch } from './client';

export type Ticket = {
  key: string;
  summary: string;
  issueType: string;
  status: string;
  resolution: string | null;
  assignee: string | null;
  reporter: string;
  fixVersions: string[];
  description: string;
  comments: string[];
  commentTotal: number;
};

export type TicketSearchCriteria =
  | { mode: 'fixVersion'; projectId: string; fixVersionId: string }
  | { mode: 'jql'; jql: string };

export type TicketSearchResponse = { tickets: Ticket[] };

// The backend rejects a body carrying both filter modes, so the discriminated union is
// narrowed to exactly one shape here rather than sending optional fields and hoping.
export function toSearchBody(criteria: TicketSearchCriteria): Record<string, string> {
  return criteria.mode === 'jql'
    ? { jql: criteria.jql }
    : { projectId: criteria.projectId, fixVersionId: criteria.fixVersionId };
}

export function useTicketSearch() {
  return useMutation({
    mutationFn: (criteria: TicketSearchCriteria) =>
      apiFetch<TicketSearchResponse>('/api/tickets/search', {
        method: 'POST',
        body: JSON.stringify(toSearchBody(criteria)),
      }),
  });
}
```
   `toSearchBody` is exported specifically so it is unit-testable without rendering anything.
   Never call `fetch` directly — `apiFetch` carries the CSRF echo and the silent-refresh retry.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `/api/tickets/search` response → DOM | Jira-sourced summaries, statuses, display names and flattened rich text are rendered |
| Selection state | Client-only, non-persisted, non-authoritative |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-06-01 | Tampering (XSS) | Rendering Jira-sourced text | mitigate | Every value is rendered as a React text child (`{ticket.summary}`), never via `dangerouslySetInnerHTML`. React escapes text children, so a summary containing markup is displayed literally. Acceptance criteria for plan 07 grep for the absence of `dangerouslySetInnerHTML` across the route |
| T-02-06-02 | Information Disclosure | Error rendering | mitigate | Copy comes only from `messageForReason(problem)` keyed on the machine-readable reason; the raw upstream body is never rendered |
| T-02-06-03 | Denial of Service | Overlapping searches from rapid clicking | mitigate | Both selects and the button carry `disabled={search.isPending}`, so a second exhaustive multi-page fetch cannot be started while one is running |
| T-02-06-04 | Repudiation | Selection state | accept | Selection is transient, client-only and consumed by nothing in this phase. Phase 3 records the release-assembly action with an actor when a selection is actually committed |
