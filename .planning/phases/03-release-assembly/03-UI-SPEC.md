# Phase 03 — UI Design Contract: Release Assembly

> Visual and interaction contract for REL-01, REL-02, REL-03, REL-04, REL-05, REL-08 (push
> tickets from `/tickets` into a release, freeze, release library, release detail with per-ticket
> detail and manual items). Generated by gsd-ui-researcher, verified by gsd-ui-checker. Extends
> the Phase 2 design language — no new visual system introduced; the one new interaction
> primitive is a native `<dialog>` modal (see Design System below), needed because this is the
> first phase with a create/confirm flow that must interrupt the current screen.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — continues Phase 1/2's hand-rolled Tailwind pattern. No `components.json`, no component-library dependency exists in `frontend/package.json`; re-litigating that choice is out of scope, per Phase 2's own precedent. |
| Preset | not applicable |
| Component library | none — native HTML elements, matching `TicketsRoute.tsx`/`SettingsRoute.tsx`. **New this phase:** the native `<dialog>` element (`showModal()` / `close()`), used for the Add-to-release picker and the freeze/delete confirmation prompts. This is a browser primitive, not a library — it ships focus trap, Escape-to-close and a backdrop for free, keeping the "no component library" line intact while giving Phase 3's first interrupting flows correct baseline accessibility. |
| Icon library | none — continues Phase 2's rule of plain glyphs over SVG icons. This phase introduces exactly one new glyph: `×` for the dismissible add-result banner's close control, styled as a real `<button aria-label="Dismiss">`, not a decorative icon. |
| Font | system default (Tailwind's default `sans` stack) — unchanged |

## Typography

Reuses Phase 2's declared type scale exactly — no new sizes, no third weight.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`text-sm`) | 400 regular | 1.5 |
| Label | 14px (`text-sm`) | 600 semibold | 1.5 |
| Heading | 16px (`text-base`) | 600 semibold | 1.2 |
| Display | 18px (`text-lg`) | 600 semibold | 1.2 |

All net-new Phase 3 elements (release name/version headers, status badges, modal titles, table headers, button labels) use exactly these four size/weight pairs. Release name in the detail header and the library table's clickable name cell both use **Heading** (16px/600) — never a new "page hero" size. Modal titles also use Heading, matching an in-page section heading rather than inventing a dialog-specific type scale.

## Color

Reuses Phase 2's dominant/secondary/accent/destructive values exactly. This phase extends *where* accent and destructive are used — it does not add a hue.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `gray-50` (`bg-gray-50`) | Page canvas (unchanged `AppShell`), empty-state panels |
| Secondary (30%) | `white` | Header bars, table surfaces, modal surface, release detail card |
| Accent (10%) | `blue-600` | See reserved-for list below |
| Destructive | `red-600` | Error text/alerts (unchanged) **plus, new this phase, the "Delete release" action and its confirmation** |

Accent (`blue-600`) reserved for: the **"Add to release"** button on `/tickets`, the **"New release…"** disclosure toggle inside the picker, the **"Create & add"** submit button, the **"Refresh from Jira"** and **"Freeze release"** buttons on release detail, the **"+ Add manual item"** disclosure toggle, the release library's clickable release-name links, the "Browse tickets" empty-state link, and focus-visible rings on all new inputs. Not used for: table row hover (plain `gray-50`), status/category text (plain gray, see below), or the "Remove"/"Edit" row actions (plain gray — these are reversible, low-stakes actions and stay visually quiet, matching Phase 2's reasoning for the non-destructive checkbox toggle).

Destructive (`red-600`) reserved for: error alerts (unchanged), the **"Delete release"** button and its confirmation dialog's confirm button. This is the first phase where destructive color has a live target — Phase 2 declared it with no use yet.

**New neutral pattern — release status badge.** `OPEN` and `FROZEN` are a small, system-owned, exactly-two-value enum (not arbitrary Jira free text like ticket status), so unlike Phase 2's ticket-status columns, a badge is justified here. Kept inside the existing neutral gray family — no new hue is introduced:
- `OPEN`: `bg-gray-100 text-gray-700` pill, label "Open"
- `FROZEN`: `bg-gray-800 text-white` pill, label "Frozen" — deliberately the darkest neutral in the palette, signaling permanence/weight without borrowing red or introducing a new color

Manual-item categories (`CONFIG_CHANGE`/`DATABASE_SCRIPT`/`INFRASTRUCTURE`/`OTHER`) render as **plain `text-gray-700` text**, not colored badges — four categories with no urgency semantics do not warrant four new colors, consistent with Phase 2's "no color-coding without a real signal" rule.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | **"Add to release"** — appears on `/tickets` only when `selected.size > 0`, next to the existing "{n} selected" indicator. This is the phase's core action: it opens the Add-to-release picker. Disabled state does not apply — the button is simply absent at zero selection, matching Phase 2's pattern of not inventing a premature button. |
| Empty state heading (release library, no releases exist) | **"No releases yet"** |
| Empty state body (release library, no releases exist) | **"Releases are created from the ticket browser. Browse tickets, select the ones you want, and choose 'Add to release' → 'New release…'."** with an inline **"Browse tickets"** link (`text-blue-600 underline`) to `/tickets`. |
| Empty state (release library, search yields nothing) | Heading: **"No releases match '{query}'"**. Body: **"Try a different name or version."** No "Browse tickets" link here — the release-set is not actually empty, only the filtered view is. |
| Empty state (release detail, zero items, OPEN) | Heading: **"No items yet"**. Body: **"Add tickets from the ticket browser, or add a manual item below."** (Reachable when a release is created via "New release…" with a selection that turned out to be 100% duplicates elsewhere, or after removing every item.) |
| Empty state (release detail, zero items, FROZEN) | **"This release has no items."** Plain text, no call-to-action — nothing can be added to a frozen release. |
| Error state (any screen, non-2xx `ProblemDetail`) | `messageForReason(problem)` per the existing Phase 1 table, rendered `role="alert" data-reason={reason}` in `red-600`, with a **"Try again"** button re-running the exact last action — same convention as Phase 2. **New reason codes needed this phase** (see Planning Input below): `RELEASE_NOT_FOUND`, `RELEASE_FROZEN`, `RELEASE_DUPLICATE`. |
| Error state (release detail, release not found / deleted) | `RELEASE_NOT_FOUND` → **"This release doesn't exist or has been deleted."** with a **"Back to releases"** link to `/releases` instead of "Try again" (retrying a 404 on the same id cannot succeed). |
| Error state (create-and-add, duplicate name+version) | `RELEASE_DUPLICATE` → **"A release named '{name}' version '{version}' already exists. Choose a different name or version."** Rendered inline inside the picker's "New release…" form, next to the fields, same `fieldErrors`-adjacent placement `SettingsRoute` already uses for `VALIDATION_FAILED`. |
| Error state (mutating a frozen release — defensive only, UI should make this unreachable) | `RELEASE_FROZEN` → **"This release is frozen and can no longer be changed."** |
| Add-result feedback (D-03-13 — must never read as an error) | Dismissible banner (`bg-blue-50 border border-blue-200 text-blue-900`, `role="status"`) at the top of the release detail screen after landing from the picker: all-new → **"{n} ticket(s) added to {name} {version}."**; partial overlap → **"{added} added, {alreadyPresent} already on this release."**; all-duplicate → **"All {n} selected tickets were already on this release."** Never phrased as a warning or error — a duplicate add is explicitly a success per D-03-13, not a partial failure. |
| Freeze confirmation | Modal title: **"Freeze {name} {version}?"** Body: **"Freezing locks the ticket set and manual items exactly as they are now. You cannot add, remove, or refresh items afterward, and there is no way to unfreeze. If scope changes later, create a new release."** Buttons: **"Cancel"** (`border-gray-300 text-gray-700`, closes with no change) / **"Freeze release"** (`bg-blue-600 text-white` — a lifecycle lock, not a data-destroying action, so it stays on the accent color, not destructive red; its irreversibility is carried entirely by the modal copy and the explicit two-step confirm, not by borrowing red). |
| Delete confirmation | Modal title: **"Delete {name} {version}?"** Body: **"This permanently deletes the release and its items. This cannot be undone."** Buttons: **"Cancel"** / **"Delete release"** (`bg-red-600 text-white` — genuinely destroys data, so this one *does* use destructive red). Only ever reachable on an `OPEN` release — the button does not render on a `FROZEN` one (D-03-11), so there is no "why is this disabled" state to design for. |
| Remove ticket / remove manual item (release detail, OPEN only) | **No confirmation dialog.** A removed ticket can be re-added from `/tickets` at any time while the release stays open (D-03-13's idempotent add means re-adding is always safe), and a removed manual item can simply be re-entered — both reversible in practice, so this stays a plain **"Remove"** text button, matching Phase 2's reasoning for the non-destructive checkbox toggle. |

## Screen Layout & States

### 0. `/tickets` — addendum (existing screen, minimal change)

`frontend/src/routes/TicketsRoute.tsx:259-263` currently renders `{selected.size} selected` in a `role="status" aria-live="polite"` `<p>` whenever `loaded !== null && loaded.length > 0`. This phase changes that block to a flex row:

- Left: the existing `{n} selected` text, unchanged (still inside the same `aria-live="polite"` region — do not regress the Phase 2 accessibility follow-up).
- Right (new): the **"Add to release"** button (`bg-blue-600 text-white text-sm font-semibold px-4 py-2 rounded`), rendered **only when `selected.size > 0`** — absent, not disabled, at zero selection. Opens the Add-to-release picker (state 1 below) with the current `selected` set and the currently browsed `projectId`'s Jira project key (for D-03-05's advisory default) passed in.
- No other change to `/tickets`. The multi-select, table, filter bar, loading/empty/error states are all unchanged from `02-UI-SPEC.md`.

**AppShell nav (`frontend/src/components/AppShell.tsx`):** add a **"Releases"** link between "Tickets" and "Settings", same `Link` styling (`text-gray-600 hover:text-gray-900`, `activeProps` bold) pointing to `/releases`.

### 1. Add-to-release picker (native `<dialog>` modal, opened from state 0)

- Title (Heading, 16px/600): **"Add {n} ticket(s) to a release"**.
- Body, in order:
  1. **Open releases list** — one row per `OPEN` release: name (font-semibold) + version + an **"Add"** button (`border-gray-300 text-sm px-3 py-1.5 rounded`, not accent — the modal's one accent action is reserved for "Create & add" below, keeping a single visual primary per screen). Sorted by `created_at` descending (most recently created release is the most likely target of the current push). If more than 8 open releases exist, a plain text filter input (`placeholder="Filter by name or version…"`) appears above the list — client-side substring match, not a network request.
  2. **Loading** (fetching open releases): `gray-600 text-sm` "Loading releases…" with the same border-spin glyph used on `/tickets`.
  3. **Error** (list fetch failed): `role="alert" data-reason={reason}` red-600 `messageForReason` text + "Try again".
  4. **Zero open releases**: skip the list section entirely (nothing to show) and auto-expand the "New release…" form below rather than rendering an empty list with a separate toggle to find.
  5. **"New release…"** disclosure toggle (`text-blue-600 underline text-sm`, same visual pattern as Phase 2's "Advanced: edit as JQL") — collapsed by default when at least one open release exists; auto-expanded when none do. Reveals:
     - **Name** (`<input type="text" required>`, label "Release name")
     - **Version** (`<input type="text" required>`, label "Version")
     - No project-key field — `jira_project_key` is set automatically from the project being browsed on `/tickets` (D-03-05), never a form input.
     - **"Create & add"** submit button (`bg-blue-600 text-white text-sm font-semibold px-4 py-2 rounded`) — the modal's one accent CTA. Disabled while the request is in flight or while either field is empty.
     - Inline validation error area directly below the fields for `VALIDATION_FAILED`/`RELEASE_DUPLICATE` (see Copywriting Contract) — same `fieldErrors`-adjacent placement as `SettingsRoute`'s Jira-site form.
- Footer: **"Cancel"** (`border-gray-300 text-gray-700`) closes the dialog with no side effect.
- On success (either "Add" on an existing release, or "Create & add"): close the dialog and navigate to `/releases/$releaseId` for the target release, carrying the add-result counts (added/alreadyPresent) so state 4's banner (below) can render immediately — no extra round trip to compute it client-side.

### 2. Release library — `/releases`

- Route nested under `authenticatedRoute`, same pattern as `/tickets`/`/settings`.
- Header row (`white`, `p-6`): page heading "Releases" (Heading, 16px/600) + a search input (`placeholder="Search by name or version…"`, `aria-label="Search releases"`) — debounced 300ms, re-queries the backend list endpoint with the current text (cheap local-DB search, unlike Phase 2's expensive Jira search, so live-as-you-type is appropriate here and does not need an explicit trigger button).
- **Loading**: `gray-600 text-sm` "Loading releases…" + spinner glyph, replacing the table area only (search input stays enabled).
- **Empty, no releases exist at all**: centered panel (`bg-gray-50 p-6 rounded`, no alert role) — see Copywriting Contract.
- **Empty, search yields nothing**: same panel styling, different copy (no "Browse tickets" link — see Copywriting Contract).
- **Error**: `role="alert" data-reason={reason}` red-600 + "Try again", replacing the table area.
- **Loaded, non-empty**: table, columns in order: Name (clickable `Link` to `/releases/$id`, `text-blue-600 font-semibold hover:underline` — deliberately a link here, unlike Phase 2's non-linking ticket Key cell, because opening a release is this table's entire purpose) · Version · Status (badge, see Color) · Project (`jira_project_key` or "—" if absent) · Items (count) · Last refreshed (`toLocaleString()` or "—" if never refreshed). Row height and cell padding match Phase 2's ticket table (`text-sm`, `py-2` per cell).

### 3. Release detail — `/releases/$releaseId`

**Header (`white`, `p-6`):**
- Row 1: release name (Heading, 16px/600) + version (`text-gray-600 text-sm`, inline after name) + status badge (see Color).
- Row 2 (meta, `text-sm text-gray-600`, `space-x-4`): "Project: {jira_project_key}" (omitted entirely if null, not shown as "—" — an absent advisory field is not worth a placeholder) · "Created by {createdBy} on {createdAt}" · "Frozen by {frozenBy} on {frozenAt}" (only when `FROZEN`) · "Last refreshed: {lastRefreshedAt}" (only when at least one refresh has happened; omitted, not "—", if never refreshed).
- Row 3 (actions, **OPEN only** — entirely absent when `FROZEN`, not disabled-and-visible): **"Refresh from Jira"** (`border-gray-300 text-gray-700`, secondary — re-pulls current field values for ticket-backed items; shows the same border-spin + "Refreshing…" pattern as `/tickets`' loading state while in flight, and disables itself plus Freeze/Delete for the duration) · **"Freeze release"** (`bg-blue-600 text-white`, opens the freeze confirmation modal) · **"Delete release"** (`text-red-600 border border-red-600`, opens the delete confirmation modal).
- **Frozen banner** (`FROZEN` only, replaces row 3): `bg-gray-100 text-gray-700 text-sm rounded p-3` — **"This release is frozen. Its ticket set is locked and cannot be changed."**

**Add-result banner** (only present immediately after landing from the picker, dismissible): see Copywriting Contract. Sits between the header and the item sections.

**Item sections** (D-03-04's deterministic order rendered as two labeled groups, not one interleaved table — clearer to scan and does not contradict the ordering rule, which governs generated-document order in Phase 5, not this screen's layout):

- **"Tickets ({n})"** — reuses Phase 2's ticket table columns exactly: Key · Summary · Type · Status · Resolution · Assignee · Reporter · expand toggle (`▸`/`▾`, `aria-expanded`, `aria-label="Expand ticket details"`/`"Collapse ticket details"` — same accessible-name requirement Phase 2's checker flagged as binding). Sorted by ticket key ascending. **New column, OPEN only:** a trailing "Remove" text button (`text-gray-600 hover:text-gray-900 text-sm`) per row. The expand panel reuses Phase 2's exact pattern: `bg-gray-50 border border-gray-200 rounded p-4`, `max-h-80 overflow-y-auto`, Description then Comments, never truncated. Because D-03-06 means this data is a stored snapshot, not a live Jira fetch, no loading state applies here beyond the page's own initial load.
- **"Manual items ({n})"** below the tickets section — columns: Title · Category (plain text, see Color) · Description (truncated one line with `title` tooltip, plus the same expand-toggle pattern if descriptions can be long) · **OPEN only:** "Edit" / "Remove" text buttons per row. Sorted by title ascending.
- **"+ Add manual item"** disclosure toggle (`text-blue-600 underline text-sm`, **OPEN only** — absent when `FROZEN`), same collapsed-by-default pattern as the JQL toggle. Reveals: Title (`<input required>`), Description (`<textarea>`), Category (`<select>` with the 4 fixed options: "Config change" / "Database script" / "Infrastructure" / "Other"), **"Add item"** submit (`bg-blue-600 text-white text-sm font-semibold px-4 py-2 rounded`). Clicking "Edit" on an existing manual item opens the same field set inline, pre-filled, with the submit button reading **"Save changes"** instead.
- **Empty items** (both sections empty): see Copywriting Contract, OPEN vs. FROZEN variants.

**Loading** (initial page load): `gray-600 text-sm` "Loading release…" + spinner glyph, replacing the entire content area below `AppShell`'s header.

**Error, not found**: see Copywriting Contract — replaces the entire content area with the `RELEASE_NOT_FOUND` message and a "Back to releases" link, no "Try again" (retrying a 404 on a fixed id cannot succeed).

**Error, generic load failure**: `role="alert" data-reason={reason}` red-600 + "Try again", replacing the entire content area.

### 4. Freeze / Delete confirmation (native `<dialog>` modals, opened from release detail row 3)

Both follow the same shape: title (Heading), body (Body, 14px/400), two buttons (Cancel + the named action). See Copywriting Contract for exact copy and per-action color. Both close on Escape and on backdrop click, equivalent to Cancel — no accidental confirm path exists (confirm requires an explicit click on the named button, never Enter-to-submit on a bare focus state, since freeze and delete are exactly the two truly irreversible/destructive actions this phase has).

## Drag-and-Drop Assessment (UX-01)

**Not applicable to this phase**, by explicit decision (D-03-04). Release items carry no user-controlled order in v1 — no `position` column, no reorder endpoint — so there is nothing to drag. The two item sections (Tickets, Manual items) each render in a fixed, deterministic sort (ticket key ascending / title ascending) that the release manager cannot change from this screen. UX-01's "moving items into or between groupings on a release" is explicitly deferred to Phase 5, where template-driven grouping at generation time is the actual consumer of ordering. Do not invent a drag interaction here.

## Planning input — new reason codes required

Extending `JiraAuthFailureReason`-equivalent taxonomy for release-specific failures (per Phase 1's `ProblemDetail`/`reason` error contract — do not invent a parallel scheme):

- **`RELEASE_NOT_FOUND`** — release id does not exist or was deleted. UI: "This release doesn't exist or has been deleted." + "Back to releases" link, no retry.
- **`RELEASE_FROZEN`** — a write attempted against a `FROZEN` release (add/remove/refresh/freeze-again/delete). UI-unreachable in the happy path since the relevant buttons are absent when frozen, but the backend must still reject it and the frontend must still handle the response defensively. UI: "This release is frozen and can no longer be changed."
- **`RELEASE_DUPLICATE`** — `UNIQUE (name, version)` violation on create. UI: inline in the picker's "New release…" form, "A release named '{name}' version '{version}' already exists. Choose a different name or version."

All three need entries added to the frontend's `messageForReason` table (`frontend/src/api/auth.ts`) alongside the existing six from Phase 1/2 — zero of the existing entries are reused for these cases, since none of them describe a release-lifecycle failure.
