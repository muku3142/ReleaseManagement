<objective>
Render a stored document snapshot's Markdown to a `.docx` with cover page, running header, footer
and page numbering (DOC-06, and the DOCX half of DOC-08).

Purpose: this is the one genuinely new piece of engineering in the phase. RESEARCH.md's highest-risk
finding resolved to **do not use `flexmark-docx-converter`** — it is pinned to docx4j 11.4.9, and
docx4j 17.0.0 (this project's locked version) *removed* the methods its bytecode calls
(`getEGBlockLevelElts`, `getParagraphContent`, `getRunContent`, the four `ArrayList*` classes). It
also drags in Log4j 2 and ten unused flexmark extensions. So the AST is hand-walked.

That is not the "don't hand-roll a hard problem" trap: the node vocabulary is **closed and small**,
fixed by what `AdfFlattener` emits plus what a template author can write. Nothing outside the table
in Task 1 can reach this walker, so nothing outside it needs handling.

**Export does not re-enter `RenderService`.** Input is already-resolved Markdown and already-resolved
chrome from a stored snapshot (D-05-05).

Output: a one-method port, a walker, the package-assembling adapter, and a test that reopens the
produced `.docx` with docx4j and asserts on its OOXML.
</objective>

Handle exactly this vocabulary, and nothing else:

| flexmark node | OOXML target |
|---|---|
| `Heading` (1-6) | `P` with `PPr.pStyle` = `Heading1`..`Heading6` |
| `Paragraph` | `P` with inline runs |
| `BulletList` / `OrderedList` / `ListItem` | `P` per item with `PPr.numPr` (ilvl from nesting depth, numId 1 = bullet, 2 = decimal) |
| `FencedCodeBlock` / `IndentedCodeBlock` | one `P` per line, monospace `RPr.rFonts`, no `numPr` |
| `TableBlock`/`TableHead`/`TableBody`/`TableRow`/`TableCell` | `Tbl` / `Tr` / `Tc`, header cells bold |
| `ThematicBreak` | an empty `P` (a horizontal rule has no cheap OOXML analog and dropping it silently would lose a visual separator) |
| `BlockQuote` | `P` with a left indent |
| `StrongEmphasis` | `RPr.b` |
| `Emphasis` | `RPr.i` |
| `Code` (inline) | `RPr.rFonts` monospace |
| `Link` | the link's **text** runs only |
| `SoftLineBreak` | a space |
| `HardLineBreak` | `Br` |
| `Text` | plain `R`/`Text` |

`ThematicBreak` and `BlockQuote` are included beyond RESEARCH.md's list because a template author can
type `---` or `>` and RESEARCH.md's A2 explicitly flags its own list as inference, not a substitute
for checking. `Link` renders text only and creates **no** hyperlink relationship — see the threat
model; a stored document is a record, not a navigation surface.

**Unknown node fallback, mandatory:** any node type not in the table becomes a plain `Text` run
carrying `node.getChars().toString()`. Never drop it, never emit it as markup. Add a comment stating
this is the same posture `neutralizeRawHtml` takes: degrade to literal, readable text.

`Text` content is set through docx4j's `Text` object, which JAXB escapes on marshal — do **not**
hand-build XML strings anywhere in this class.

Use `org.docx4j.jaxb.Context.getWmlObjectFactory()` for every object, and docx4j 17's
`getContent()`-based navigation throughout (17.0.0 removed `getEGBlockLevelElts()`,
`getParagraphContent()` and `getRunContent()`).

Order of assembly:

1. **Numbering part.** Add a `NumberingDefinitionsPart` with a minimal numbering XML defining

   walker emits. Verify the docx4j 17.0.2 idiom for creating this part (`new

   permitted, because it is a fixed, project-authored constant containing no user data — say so in a
   comment.

2. **Cover page**, only when `chrome.coverEnabled()`:
   - logo, when `logo != null`: `BinaryPartAbstractImage.createImagePart(pkg, logo.bytes())` then
     `createImageInline(...)` — width derived from `logo.metadata().width()`/`height()`, never from
     the filename, and the image part's content type comes from the stored, content-sniffed
     `logo.metadata().contentType()`.
   - a centred `P` with the resolved cover title at a large size, a centred `P` with the resolved
     cover subtitle, then a **page break** so the body starts on page 2.
   The cover title/subtitle go through docx4j `Text` objects — JAXB escapes them. Do not
   HTML-escape them (that is the PDF path's problem, and doing it here would show literal `&amp;`).

3. **Body**: `walker.appendBody(renderAdapter.parseMarkdown(resolvedMarkdown), pkg.getMainDocumentPart())`.
   Use the shared AST — do not build a local `Parser`.

4. **Chrome parts.** On the section's `SectPr`:
   - `sectPr.setTitlePg(new BooleanDefaultTrue())` **only when `coverEnabled`** — `titlePg` is what
     gives page 1 its own header/footer, and without a cover page there is nothing to differentiate.
   - a `HeaderPart` referenced as `HdrFtrRef.DEFAULT` containing the resolved header text (skip
     entirely when the header text is blank), and, when `coverEnabled`, an **empty** `HeaderPart`
     referenced as `HdrFtrRef.FIRST` so the cover shows no running header.
   - a `FooterPart` referenced as `HdrFtrRef.DEFAULT` whose paragraph is: the resolved footer text
     run (when non-blank), then — when `chrome.pageNumbersEnabled()` — a literal `" • Page "` run, a
     `CTSimpleField` with instruction `" PAGE \\* MERGEFORMAT "`, a literal `" of "` run, and a
     `CTSimpleField` with `" NUMPAGES \\* MERGEFORMAT "`. Plus, when `coverEnabled`, an empty
     `FooterPart` as `HdrFtrRef.FIRST`.
   Prefer `CTSimpleField` over hand-built `fldChar` begin/separate/end run triplets (RESEARCH.md
   §Don't Hand-Roll). If `CTSimpleField` proves unusable in 17.0.2, fall back to the `fldChar`
   triplet and record why in the summary — do not drop page numbering.

5. Wrap any failure in `UncheckedIOException`; plan 05-08 converts it to `EXPORT_FAILED`.

Do **not** build a shared "chrome renderer" abstraction with the PDF adapter. CSS margin boxes and
OOXML section parts have nothing in common below the `ChromeFields` record itself, and forcing an
abstraction over them is the unnecessary-indirection CLAUDE.md rules out (RESEARCH.md Pattern 3).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| stored template content (untrusted author) → docx4j writer | Markdown body and chrome strings originate as untrusted template text |
| stored logo bytes → OOXML image part | Content-validated at upload (TMPL-09), re-embedded here |
| generated `.docx` → whoever opens it in Word | The output is a document this system authors on a user's behalf |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-28 | Tampering (bypassing Phase 4's raw-HTML control) | `DocxAstWalker` | mitigate | Phase 4 neutralises raw HTML **post-parse**, in the AST, so no `HtmlBlock`/`HtmlInline` node survives to reach this walker — the tags are already `Text` nodes. The walker emits every text value through docx4j `Text` objects (JAXB-escaped on marshal) and builds no XML strings. Asserted by `rawHtmlIsLiteralTextNotMarkup`. |
| T-05-29 | Tampering (OOXML injection via hand-built XML) | `DocxAstWalker`, `DocxExportAdapter` | mitigate | No user data is ever concatenated into an XML string. Every element is built through `Context.getWmlObjectFactory()`. The single raw XML string permitted (the numbering definitions part) is a fixed project constant containing no user data, and a grep criterion confirms the walker itself contains none. |
| T-05-30 | Tampering / Information Disclosure (external relationship injection) | `Link` node handling | mitigate | Markdown links render as text runs only; no `Hyperlink` element and no external relationship target is created. A stored document is an audit record, not a navigation surface, and an OOXML external relationship pointing at an attacker-chosen URL is a phishing primitive inside a document that looks like it came from us. Grep criterion asserts no `Hyperlink`. |
| T-05-31 | Spoofing (content-type confusion on the embedded logo) | `BinaryPartAbstractImage.createImagePart` | mitigate | Image content type and dimensions come from the stored, content-sniffed `LogoMetadata`, never from the filename. Grep criterion asserts `metadata().filename()` appears nowhere in the adapter. |
| T-05-32 | Information Disclosure (XXE on the DOCX path) | docx4j | accept | docx4j is used purely as a **writer** here. No untrusted `.docx` or XML is ever parsed by this project — a "import a DOCX template" feature is explicitly out of scope, and TMPL-08 uses structured chrome fields specifically to avoid that class of feature (RESEARCH.md §Security Domain). The test's `WordprocessingMLPackage.load` reads only bytes this code just produced. |
| T-05-33 | Denial of Service (renderer state corruption under concurrency) | `WordprocessingMLPackage` reuse | mitigate | A fresh package is created inside the export method on every call (RESEARCH.md Pattern 2 — the package *is* the document). Grep criterion asserts it is not a field. |
| T-05-34 | Denial of Service (unbounded OOXML tree construction) | `DocxAstWalker` | accept | Same reasoning as the PDF path (RESEARCH.md Pitfall 5): the stored Markdown was bounded by `RenderService`'s collection cap when the snapshot was generated, so pathological input is unreachable through the normal generate→export path. A second timeout wrapper is an explicit non-goal absent measured evidence. |
| T-05-35 | Tampering (stale transitive docx4j) | build classpath | mitigate | Plan 05-01 ran `mvn dependency:tree -Dincludes=org.docx4j` and asserted exactly one version resolves. The removed-in-17 methods fail at **runtime**, not compile time, so a grep criterion here additionally forbids naming any of them. |
