<interfaces>
The `fixVersions` block in `JiraRestTicketAdapter.toTicketDetail` (lines 110-116) is the exact
analog — `components` is the same shape, an array of `{id, name}` objects:
```java
        List<String> fixVersions = new ArrayList<>();
        for (JsonNode version : field(fields, fieldIds, TicketField.FIX_VERSIONS)) {
            String name = version.path("name").asText(null);
            if (name != null) {
                fixVersions.add(name);
            }
        }
```

`TicketSearchService` requests `EnumSet.allOf(TicketField.class)`, so adding the enum constant is
what puts the field on the wire — there is no second list to update:
```java
    private static final Set<TicketField> FIELDS = EnumSet.allOf(TicketField.class);
    ...
    Map<TicketField, String> fieldIds = fieldMetadataService.resolve(FIELDS);
```

`FieldMetadataService.resolve` looks each field up by lower-cased `displayName()` and **throws
`JiraTicketReadException(JIRA_ERROR)` if any field cannot be resolved** — so `COMPONENT`'s display
name must be exactly what Jira calls the field, or every ticket search breaks.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|

| `TicketDetail` → `release_ticket_item` | Materialised audit copy of external data (D-03-06) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-36 | Tampering (schema drift crashing the fetch) | `toTicketDetail` component mapping | mitigate | Guarded with `isArray()` and `isEmpty()` before indexing, and `path("name").asText(null)`, so a missing field, a non-array, an empty array or a nameless object all yield `null` rather than throwing. This mirrors the defensive posture the file's existing comment demands for permission-hidden fields. |
| T-05-37 | Denial of Service (breaking every ticket search) | `TicketField.COMPONENT` display name | mitigate | `FieldMetadataService.resolve` throws `JIRA_ERROR` if **any** requested field name is unresolvable, so a wrong display name breaks all searching, not just component. Task 1 requires verifying `"Components"` against the live tenant's `/rest/api/3/field` and recording the confirmed value. |
| T-05-38 | Tampering (wrong field silently selected) | custom field shadowing "Components" | mitigate | Inherited unchanged from JIRA-04: `disambiguate` prefers the **system** field when a custom field shadows the name, and refuses to guess between multiple custom fields. No hardcoded `customfield_NNNNN` is introduced — a grep criterion asserts this. |
| T-05-39 | Tampering (mutating a frozen audit record) | V5 `component` column | mitigate | The column was created nullable with no `DEFAULT` and no backfill (plan 05-03), and this plan writes it only through `overwriteSnapshot`, which is only reachable from create/add/refresh paths that already enforce `requireOpen()`. `existingRowsKeepNullComponentAfterMigration` asserts the no-backfill guarantee. |
| T-05-40 | Tampering (stored XSS via a Jira component name) | component text reaching the SPA and the renderers | mitigate | Component is a plain string carried like `issueType` and `status`. React escapes it on render; the server-side path escapes it through flexmark's `Text` nodes (D-04-05) and, in plan 05-06, through docx4j `Text` objects. No new sink. |
</threat_model>
