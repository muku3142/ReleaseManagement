<objective>
Expose PDF and DOCX download endpoints for any stored revision (DOC-05, DOC-06), and introduce the
one genuinely new security control this phase needs.

Purpose: plans 05-05 and 05-06 built two renderers that take strings and bytes. This plan wires them
to stored snapshots and to HTTP. Two things make it more than plumbing:

- **Export must not re-enter `RenderService`.** The snapshot already holds resolved Markdown and
  resolved chrome. Re-running Mustache at export time would resolve against *today's* release data,
  so a document downloaded next month would not match the one approved this month — destroying the
  immutability DOC-07 promises and the audit value D-05-06 exists for.
- **`Content-Disposition` filename injection is new exposure.** RESEARCH.md flags this explicitly:
  export filenames are the **first** place this codebase builds an HTTP header value from free text.
  Release name and version are unvalidated free text (D-03-08). `TemplateController.downloadLogo` is
  the header-shape analog but is **not** a safe copy for the filename line — its filename comes from
  validated upload metadata.

Output: an export service, a sanitiser with its own test class, two endpoints, one new reason code.
</objective>

Create `adapters/web/ExportFilename` — a final class with a private constructor and one static
method, in the style of `RenderContextMapper`:

```java
    /**
     * Builds a safe Content-Disposition filename from free-text release data.
     *
     * <p>This is the first place in this codebase that interpolates user-supplied free text into an
     * HTTP header value. Release name and version are unvalidated (D-03-08), so an ALLOWLIST is used
     * rather than a denylist: every character outside [A-Za-z0-9 ._-] is replaced. That single rule
     * closes header injection (no CR/LF/quote survives), path traversal (no slash or backslash
     * survives) and encoding ambiguity (no non-ASCII survives) at once.
     *
     * <p>TemplateController.downloadLogo is NOT a safe copy for this: its filename comes from a
     * validated upload's own metadata, not from free text.
     */
    public static String sanitize(String releaseName, String version, TemplateDocumentType type,
                                  int revision, String extension)
```

Algorithm, in this order:
1. Compose the raw candidate: `releaseName + " " + version + " " + label(type) + " r" + revision`,
   where `label` is `Release Notes` / `Runbook` / `Approval` (matching the UI's document-type labels).
2. Replace every character not in `[A-Za-z0-9 ._-]` with `_`. Use an explicit allowlist character
   check, not a regex denylist.
3. Collapse runs of `_` to one, collapse runs of spaces to one, then strip leading/trailing `_`,
   space and `.` (a leading `.` would make a hidden file; a trailing `.` is invalid on Windows).
4. If the result is empty, use `document`.
5. Truncate to `120 - extension.length() - 1` characters, then strip trailing `_`/space/`.` again.
6. Return `result + "." + extension`.

Also add a helper that returns the whole header value, so no caller ever concatenates it by hand:
```java
    public static String attachment(String filename) {
        return "attachment; filename=\"" + filename + "\"";
    }
```
No `filename*=UTF-8''…` variant is emitted: the sanitiser folds to ASCII deliberately, so there is
nothing a UTF-8 form would add except a second, differently-escaped copy of the same value to keep
correct. Record that as a comment.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| release name/version (free text, D-03-08) → HTTP response header | **New exposure this phase.** The first header value this codebase builds from unvalidated free text |
| stored snapshot content → renderer → browser download | Untrusted-origin template content becomes a file the user opens locally |
| renderer library failure → HTTP response | Third-party failure crossing back to the client |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-41 | Tampering (HTTP response header injection) | `Content-Disposition` on both export endpoints | mitigate | `ExportFilename.sanitize` replaces every character outside `[A-Za-z0-9 ._-]`, so CR, LF and `"` cannot survive into the header. Enforced at the helper (`noOutputContainsAHeaderTerminator`, full 0..0x7F sweep) and end-to-end (`hostileReleaseNameCannotEscapeTheContentDispositionHeader`, which also asserts no injected header appears). A grep criterion forbids the endpoints building the header value by hand. |
| T-05-42 | Tampering (path traversal via the download filename) | saved filename on the client | mitigate | The same allowlist removes `/`, `\` and, after the collapse/strip step, any `..` sequence, so a name of `../../etc/passwd` cannot direct where a browser writes the file. Asserted in `ExportFilenameTest`. |
| T-05-43 | Spoofing (content-type confusion / in-origin rendering) | export responses | mitigate | `Content-Type` is set explicitly to `application/pdf` or the OOXML wordprocessing type, `X-Content-Type-Options: nosniff` blocks MIME sniffing, and `Content-Disposition: attachment` (not `inline`) prevents the browser rendering attacker-influenced content inside our own origin. |
| T-05-44 | Tampering (immutability breach via re-rendering) | `DocumentExportService` | mitigate | The service takes `snapshot.markdown()` and `snapshot.chrome()` and passes them straight to the port. It has no `RenderService` dependency — asserted by a grep criterion — and `pdfUsesTheStoredMarkdownAndStoredChrome` captures the port arguments to prove no transformation happens in between. |
| T-05-45 | Information Disclosure (leaking internals in an error) | `EXPORT_FAILED` handler | mitigate | The ProblemDetail carries a fixed, generic `detail` string and the machine-readable reason only. The renderer's exception is logged server-side via the existing `log.error` convention and never serialised to the client, matching the `handleUnexpected` precedent. |
| T-05-46 | Information Disclosure (cross-release document access) | both endpoints | mitigate | Snapshot lookup is keyed on `releaseId` **and** `documentType` **and** `revision`, so a revision number cannot address another release's document. `/api/**` is `authenticated()` in `SecurityConfig`. |
| T-05-47 | Denial of Service (unbounded export work) | renderer invocation per request | accept | RESEARCH.md Pitfall 5 and A3, recorded as an explicit non-goal: the stored Markdown was bounded by `RenderService`'s collection cap when the snapshot was generated, so pathological input is unreachable through the normal generate→export path. Buffering to `byte[]` rather than streaming is bounded by the same fact. Revisit with measured evidence, not speculatively. |
| T-05-48 | Denial of Service (memory) | `ResponseEntity<byte[]>` buffering | accept | Deliberate, per RESEARCH.md Pitfall 6 — documents are a few hundred KB to a few MB, the same class of bounded server-generated blob `downloadLogo` already buffers. `StreamingResponseBody` would forfeit the ability to set an HTTP status after the first flush, which is what makes the `EXPORT_FAILED` path above possible. |
</threat_model>
