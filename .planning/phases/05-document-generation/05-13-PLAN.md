<diagnosis_already_done>
The verification report's diagnosis was re-validated against the code before this plan was written.
Two of its three claims hold and one does not — build against this, not against the report:

1. **Body: genuinely broken.** `DocumentGenerationService.java:58` is
   `renderService.render(template.body(), view, "Body").html()`. `RenderService.render` runs Mustache
   **then flexmark** and returns HTML (`RenderService.java:62-69`). That HTML is stored at line 71 as
   the `markdown` component of `DocumentSnapshot`. `PdfExportAdapter.java:32` and `DocxExportAdapter`
   then call `renderAdapter.parseMarkdown(...)` on it, and
   `MustacheFlexmarkRenderAdapter.neutralizeRawHtml` (a required control under the untrusted-template
   constraint) replaces every HTML node with a `Text` node, which always renders escaped. Hence the
   visible tags.

2. **Chrome: NOT broken — the report is wrong here.** Lines 61-64 call
   `renderService.resolveText(...)`, which is `engine.resolve` = **Mustache only, no flexmark**
   (`RenderService.java:74-81`, `MustacheFlexmarkRenderAdapter.resolve`). The four chrome fields
   therefore already hold plain resolved text, exactly what both exporters consume. The only thing
   wrong with those four lines is that the accessor is spelled `.html()`. **Do not "fix" chrome
   behaviour — there is nothing wrong with it.** Changing it would break
   `storedChromeIsResolvedWhileBothBooleansAreCopiedUnchanged`.

3. **The ports are already correct and need no edit.** `PdfExportPort` and `DocxExportPort` both
   already carry javadoc saying the parameter is already-resolved Markdown from a stored snapshot.
   The contract was written down; generation just did not honour it.

**Root cause, stated precisely:** `RenderResult` has a single component named `html`, returned by two
methods that produce different things — `render()` returns HTML, `resolveText()` returns
Mustache-resolved text. Every call site reads `.html()` and looks correct. That is the trap, and it is
what Task 1 removes.

**Direction chosen: store MARKDOWN.** The snapshot is the immutable audit record, Markdown is the
authored source of truth, D-05-05 already says "post-Mustache, pre-flexmark Markdown", the record
component is already named `markdown`, both ports already document Markdown, and both exporters
already parse Markdown. Generation is the single place that disagrees. Storing HTML instead would
mean rewriting both exporters, the viewer plan 05-12, and D-05-05 — five changes to avoid one.
</diagnosis_already_done>

<existing_snapshots>
**Decided, not ignored: existing HTML-bodied snapshots are accepted as historical.**

`DocumentSnapshot` is append-only by design (D-05-06 — the port exposes `create` plus reads and no
update path at all), so rows written before this fix **cannot** be rewritten in place, and adding an
update path to repair them would destroy the exact immutability guarantee DOC-07 and Phase 7's
AUDIT-02 rest on.

Nor is read-time tolerance built: sniffing "does this body look like HTML?" in the exporters would be
a heuristic on an ambiguous input (a legitimate Markdown document may contain angle brackets), it
would live forever, and it would make the content type ambiguous again — the precise thing this plan
exists to end.

**The remedy already exists in the product: Regenerate.** It appends a correct revision, the affected
old revision stays visible and honestly labelled `(superseded)`, and the audit trail records both.
Nothing is deployed yet (Phase 5 of 8; snapshots exist only in local/dev databases), so the blast
radius is a handful of developer-machine rows.

Do **not** write a migration, a backfill, a repair endpoint or a sniffing branch. Record this decision
in the plan summary, and state it plainly to the user at the Task 3 checkpoint.
</existing_snapshots>

| stored snapshot body -> exported PDF/DOCX bytes | The persisted string is parsed and rendered by two document libraries |
