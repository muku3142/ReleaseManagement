# Phase 05 — UI Design Contract: Document Generation

> Visual and interaction contract for DOC-01..DOC-09 and UX-01 (generate/preview/export release
> notes, runbooks and approval documents; DOC-09 readiness columns on the release library; a
> human-verification surface for DOC-08 parity). Generated by gsd-ui-researcher, verified by
> gsd-ui-checker. Extends the Phase 2/3/4 design language — no new component library, no new icon
> library, no new CSS plugin. The genuinely new visual elements this phase adds are (1) a
> three-state readiness pill reused identically across two screens, (2) a "Success" green
> semantic color to make the fully-satisfied "frozen + generated" state read as genuinely done, and
> (3) a document viewer that reuses `TemplatePreview`'s exact chrome markup so a generated document
> looks pixel-identical to what the author saw while authoring. Everything else — tables, buttons,
> banners, disclosures, `<dialog>` confirmations, error/empty states — reuses Phase 2/3/4 patterns
> verbatim.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — continues Phase 1-4's hand-rolled Tailwind pattern. No `components.json`, no component-library dependency. Not reopened. |
| Preset | not applicable |
| Component library | none — native HTML elements throughout (`<table>`, `<select>`, `<button>`, disclosure `<button aria-expanded>`). **No new interaction primitive this phase** — every new control (readiness pill, revision picker, export buttons) is built from primitives Phase 1-4 already established (badge/pill pattern, native `<select>`, border-spin pending state, inline `role="alert"` error text). |
| CSS plugin | none new — reuses Phase 4's `@tailwindcss/typography` (`prose` utility family) for the document viewer's rendered body, exactly as `TemplatePreview.tsx` already uses it. Do not introduce a second typography treatment. |
| Icon library | none — continues the plain-glyph rule. Reuses the existing `▸`/`▾` expand glyph (release detail's ticket-expand pattern) for the revision-history disclosure, and the existing border-spin loading glyph for all new pending states. No new glyph is introduced. |
| Font | system default (Tailwind's default `sans` stack), unchanged. |

**Client-side rendering (not a design-system choice).** The document viewer (screen 2 below) renders
**already-Mustache-resolved** Markdown (D-05-05 stores post-Mustache, pre-flexmark Markdown), so it
needs only `markdown-it` — not `mustache` — client-side. **Do not add a fourth renderer.** Reuse the
exact `MarkdownIt` instance configuration `TemplatePreview.tsx` already declares (`html: false,
linkify: false, typographer: false`) so a generated document renders with the identical CommonMark
behavior the author previewed against. The recommended implementation shape is to extract
`TemplatePreview.tsx`'s cover/header/footer JSX and its `md` instance into a small shared module used
by both the authoring preview and the new document viewer — a planner/executor decision, not a new
design-system fact.

## Typography

Reuses Phase 2-4's declared four-role scale exactly for all app chrome. Reuses Phase 4's **scoped
prose exception** for the document viewer's rendered body — extended verbatim to this phase's new
route, not redefined:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`text-sm`) | 400 regular | 1.5 |
| Label | 14px (`text-sm`) | 600 semibold | 1.5 |
| Heading | 16px (`text-base`) | 600 semibold | 1.2 |

**Document viewer exception (reused from Phase 4, not new):** the rendered document body uses
`prose prose-gray max-w-none`, exactly as the authoring preview's body region does. The cover
title/subtitle inside the viewer's cover block also reuse Phase 4's exact sizing (`text-2xl

see Color and Screen Layout below for the full reasoning).

## Color

Reuses Phase 2-4's dominant/secondary/accent/destructive/warning values exactly. **One new
semantic color is added this phase — green, for "fully satisfied" document state**, plus amber's
reserved-for list is extended to cover the new "stale document" meaning.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `gray-50` (`bg-gray-50`) | Page canvas (unchanged `AppShell`), empty-state panels |
| Secondary (30%) | `white` | Header bars, table/card surfaces, document viewer surface |
| Accent (10%) | `blue-600` | See reserved-for list below |
| Destructive | `red-600` | Blocking failures only — see reserved-for list. **No destructive UI action exists in this phase** — see note below |
| Warning | `amber-600` (text/border), `amber-50` (background) | Non-blocking caution — extended this phase to the "Stale" document-readiness pill, in addition to Phase 4's validation-warning uses |
| **Success (new)** | `green-700` (text/border), `green-50` (background) | The "Up to date" document-readiness pill **only** — nothing else |

**Why a third small-footprint semantic color, not a shade of blue.** D-05-09 states that "frozen +
generated" is "the terminal, fully-satisfied state" and should "read as such." Blue is fully
committed to the accent/primary-action role (links, primary buttons) — using it for a passive status
pill would blur "click this" with "this is done," the same ambiguity Phase 4 avoided when it
introduced amber rather than overload red. Green is the conventional "complete, no action needed"
signal, is used **nowhere else** in the app, so its appearance is always meaningful, and it gives the
readiness grid the actual at-a-glance scanability the focus area asks for: a manager scanning the
`/releases` table for outstanding paperwork is looking for the **absence** of green, not the presence
of a particular gray shade among several similar gray shades.

**No destructive action this phase.** Generated documents are never deleted or overwritten (D-05-06
— "nothing is ever overwritten or pruned"); Regenerate always *appends*, it never destroys a prior
revision. There is therefore nothing in this phase's own surfaces for `red-600` to attach to beyond
the existing generic error-alert convention (`role="alert" text-red-600`, reused unchanged for
generation/export failures — see Copywriting Contract). Do not invent a delete-document action or a
destructive-styled button anywhere in this phase.

Accent (`blue-600`) reserved for, in addition to Phase 2-4's existing list: the **"Generate
{DocumentType}"** button (first generation, no prior revision exists), the **"Regenerate
{DocumentType}"** button **only while that document's state is Stale** (see Screen Layout — this is
the one case where regenerating is the thing to do, so it stays on-brand-urgent), the **"View
latest"** link inside the superseded-revision banner, and the document-viewer's **"Export PDF"** /
**"Export DOCX"** button labels' focus-visible ring (the buttons themselves are secondary/gray — see
below).

Destructive (`red-600`) reserved for, unchanged from Phase 2-4: existing error alerts. This phase
adds no new destructive-styled control.

Warning (`amber-600`/`amber-50`) reserved for, in addition to Phase 4's existing list: the **"Stale"**
readiness pill (both on `/releases` and on release detail's Documents section) and the **"Regenerate
{DocumentType}"** button while a document is Stale gets its urgency from being **blue**, not amber —
amber marks the *status*, blue marks the *available fix*, so the two colors never collide on the same
element.

Success (`green-700`/`green-50`) reserved for: the **"Up to date"** readiness pill, and **nothing
else** — not the Export buttons on success (those stay in their normal secondary-gray idle state; a
successful export is signaled by the file downloading, not by recoloring a button), not the Generate
button, not any banner.

Neutral gray (existing convention, unchanged) continues to carry: the **"No active template"** state
(italic `text-gray-400`) and the **"Not generated"** state (`text-gray-500`, non-italic) — see Screen
Layout for why these two stay plain text rather than pills, deliberately lower visual weight than the
two pill states.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA (Documents section, first generation) | **"Generate {DocumentType}"** — e.g. "Generate Release Notes." Always enabled once an active template exists for that type. |
| Primary CTA (Documents section, already generated) | **"Regenerate {DocumentType}"** — same action, appends a new revision (D-05-06). Never a confirmation dialog: regenerating is additive, not destructive. |
| Export CTAs | **"Export PDF"** / **"Export DOCX"** — present on every revision row (latest and every superseded one, per D-05-06's "all revisions remain exportable"). |
| Pending — generation | Button label swaps to **"Generating…"** with the standard border-spin glyph; button disabled; that document type's Export/View controls are disabled for the same duration to avoid acting on a revision that's mid-write. |
| Pending — export | Button label swaps to **"Exporting PDF…"** / **"Exporting DOCX…"** with the border-spin glyph; only the clicked button disables — the sibling format and other revisions stay usable, since D-05-05 makes each export an independent on-demand render with no shared lock. |
| Export success | No banner. The browser-native file download **is** the success signal (same convention as any file-download action — do not add a redundant "Export succeeded" toast). Button returns to its idle label. |
| Error — generation failed | `role="alert" data-reason={reason}` `text-red-600 text-sm`, inline directly below that document type's row: **"Couldn't generate {DocumentType} — {backend detail via messageForReason}. Try again."** The same button that triggered it remains the retry action — no separate "Try again" button. |
| Error — export failed | `role="alert" data-reason={reason}` `text-red-600 text-xs`, directly below the Export button pair: **"Couldn't export the {PDF/DOCX} — {backend detail via messageForReason}. Try again."** |
| Error — no active template (defensive, backend rejects a generate call the UI should have already prevented) | Same `messageForReason` convention: **"No active {DocumentType} template exists. Activate one from Templates before generating."** with a **"Go to templates"** link. |
| State — no active template | `text-gray-400 italic text-sm`: **"No active template"** in the pill position; row body text: **"No active {DocumentType} template — create or activate one to generate this document."** with a **"Go to templates"** link (`text-blue-600 underline`) to `/templates`. |
| State — never generated (active template exists) | `text-gray-500 text-sm`: **"Not generated"**; row body text: **"This document hasn't been generated yet."** |
| State — stale | Amber pill: **"Stale"**; row body text: **"Revision {n} of {n} · generated {date} by {actor}. The release has changed since this was generated."** |
| State — up to date | Green pill: **"Up to date"**; row body text: **"Revision {n} of {n} · generated {date} by {actor}."** (no extra caveat — this is the terminal, satisfied state) |
| Revision history disclosure | Collapsed trigger: **"Revision history ({n})"** with the `▸`/`▾` glyph, `aria-expanded`, `aria-label="Show revision history"`/`"Hide revision history"` — mirrors release detail's existing ticket-expand accessible-name pattern exactly. |
| Revision list row | **"Revision {n}"** + **"(latest)"** or **"(superseded)"** qualifier, `text-gray-600 text-xs` + generated date/actor + per-row **"View"** / **"Export PDF"** / **"Export DOCX"** actions. |
| Superseded-revision banner (document viewer, viewing anything but latest) | `bg-gray-100 text-gray-700 text-sm rounded p-3` (reuses release detail's Frozen-banner treatment): **"You're viewing Revision {n}, generated {date}. This has been superseded by Revision {latest}."** with a **"View latest"** link (`text-blue-600 underline`). |
| Template-deleted note (document viewer, source template no longer exists) | `text-xs text-gray-500 italic`, placed just below the toolbar: **"Generated from a template that has since been deleted. The content shown here is unaffected."** |
| Zero-item release, still generated (informational only — not a warning) | No special panel. A release with zero items still produces a valid document — `{{#items}}`/`{{#groups}}` sections simply render as empty, exactly as the authoring preview already shows for the sample context. This is expected template behavior, not a system state to call out. |
| Document-not-found (viewer route hit before first generation, or a bad revision number) | `role="alert" data-reason="DOCUMENT_NOT_FOUND"` `text-red-600 text-sm`: **"This document doesn't exist yet."** with a **"Back to release"** link (`text-blue-600 underline`) to `/releases/$releaseId` — no "Try again" (matches `RELEASE_NOT_FOUND`'s precedent: retrying a 404 on a fixed id cannot succeed). |
| Group-by control (template authoring addendum, D-05-04) | Label: **"Group by"**. Options: **"Issue type"** (default) / **"Component"**. Helper text (`text-xs text-gray-500`): **"Determines what {{groupName}} and {{#groups}} resolve to when this template renders."** |
| Human verification hint (document viewer, present once both PDF and DOCX have been exported at least once this session) | `bg-gray-50 text-gray-600 text-xs px-3 py-2 border border-gray-200 rounded`, non-dismissible while visible: **"Visual parity check — open the PDF and DOCX you just exported side by side and confirm the cover, header, footer and page numbers match. There's no automated check for this (see DOC-08 in the project's recorded decisions)."** See Human Verification Surface below for why this is informational only, not a recording feature. |

## Screen Layout & States

### Primary visual anchor — declared up front (Dimension 2)

- **`/releases`** — unchanged from Phase 3: **the release table** remains the anchor. The three new
  readiness columns are additional columns **within that same table**, not a second focal element.
  A manager's eye lands on the table as a whole; within it, the readiness pills are what pulls
  attention (color) while the plain-text states recede — that internal hierarchy is deliberate (see
  Color) but does not compete with the table itself as the page's one anchor.
- **`/releases/$releaseId`** — unchanged from Phase 3: **the item sections (Tickets, then Manual
  items)** remain the anchor; this was Phase 3's binding checker correction and still holds. The new
  **Documents section is subordinate**, placed *after* the item sections, using the same quiet card
  treatment Phase 4's template-list sections use (`border border-gray-200 rounded p-4`) rather than
  a heavier surface — deliberately so it reads as "also present here," not "the point of this page."
- **`/releases/$releaseId/documents/$documentType`** (new route) — **the rendered document** is the
  anchor, mirroring Phase 4's preview-pane precedent. The revision picker, superseded-revision
  banner and Export buttons are subordinate framing around it.

### 0. `/releases` — addendum: DOC-09 readiness columns

`frontend/src/routes/ReleasesRoute.tsx`'s existing table (Name · Version · Status · Project · Items ·
Last refreshed) gains **three new columns, appended at the end** in fixed order matching
`DOCUMENT_TYPES`: **Release Notes · Runbook · Approval**. Column order is additive — do not reorder
or remove the existing six.

Each cell renders exactly one of the four readiness states (see Color for exact classes), reused
verbatim from the shared readiness-pill treatment defined once and used identically here and on
release detail:

| State | Trigger | Visual | Clickable? |
|---|---|---|---|
| No active template | Zero active templates exist for that document type | `text-gray-400 italic text-xs whitespace-nowrap`, "No active template" | Yes — links to `/templates` (nothing to view on this release) |
| Not generated | Active template exists, never generated for this release | `text-gray-500 text-xs whitespace-nowrap`, "Not generated" | Yes — links to `/releases/$releaseId` (Documents section anchor) |
| Stale | ≥1 revision exists; release changed since the latest revision's `generated_at` (D-05-09) | Amber pill, "Stale" | Yes — links to `/releases/$releaseId/documents/$documentType` (the latest, stale revision) |
| Up to date | ≥1 revision exists; no release change since (or release is FROZEN, which can never go stale) | Green pill, "Up to date" | Yes — links to `/releases/$releaseId/documents/$documentType` (the latest revision) |

**Frozen vs. open behavior, stated explicitly (focus area requirement).** On an `OPEN` release, a
cell can transition Not generated → Up to date → Stale → Up to date (regenerated) → Stale (changed
again) indefinitely, following D-05-09's live comparison. On a `FROZEN` release, once a cell reaches
Up to date it **cannot** become Stale again — the ticket set is locked, so there is nothing left to
diverge from the generated snapshot. This needs no separate visual treatment (same green pill either
way) — the *behavior*, not the *appearance*, is what differs, and D-05-09 already guarantees it. Do
not add a "frozen" decoration to the pill; that would be a second signal for the same fact the
release's own Status column already carries.

**Loading/error/empty states are unchanged** from Phase 3's `/releases` (see `03-UI-SPEC.md`) — the
new columns render inside the same `releases.isPending`/`problem`/empty-state branches, nothing new
to design there.

### 1. `/releases/$releaseId` — addendum: Documents section

New card, placed **after** the Manual items table and the "+ Add manual item" form (i.e., at the very
end of the page), `id="documents"` so the DOC-09 grid's "Not generated"/"Stale"/"Up to date" links can
deep-link into it directly:

```
<section id="documents" class="mt-6 rounded border border-gray-200 bg-white p-4">
  <h3>Documents</h3>
  ... one row per document type, DOCUMENT_TYPES order ...
</section>
```

**Renders identically regardless of release status** — `OPEN` or `FROZEN`. Unlike the Refresh/
Freeze/Delete action row (Phase 3, `OPEN`-only), document generation is orthogonal to whether the
item set can still change; generating final paperwork right after freezing is a completely normal
sequence.

Per-document-type row (`border-b border-gray-100 py-3 last:border-b-0`):

- Row 1: document type name (Heading, e.g. "Release Notes") + the same readiness pill/text used on
  `/releases`, right-aligned on the same line (`flex items-center justify-between`).
- Row 2 (`text-sm text-gray-600`): the state's body text — see Copywriting Contract (varies by
  state: no-active-template guidance, never-generated notice, or "Revision {n} of {n} · generated
  {date} by {actor}" with the Stale caveat appended when applicable).
- Row 3 (actions, only when ≥1 revision exists): **"View"** (`text-blue-600 underline text-sm`, links
  to the document viewer at the latest revision) · **"Export PDF"** / **"Export DOCX"**
  (`border-gray-300 text-gray-700 text-sm px-3 py-1.5 rounded`, see pending/error states in
  Copywriting Contract) · **"Regenerate {DocumentType}"** (blue if Stale, gray-bordered secondary if
  Up to date — see Color).
- Row 3 (actions, zero revisions, active template exists): only **"Generate {DocumentType}"**
  (`bg-blue-600 text-white text-sm font-semibold px-4 py-2 rounded`).
- Row 3 (actions, no active template): only **"Go to templates"** link, no generate control shown at
  all — nothing to click that would work.
- Row 4 (only when ≥1 revision exists): the **"Revision history ({n})"** disclosure (see Copywriting
  Contract), collapsed by default. Expanded, it lists every revision oldest-to-newest-or-newest-
  first — **newest first**, matching the release library's own recency-first convention (D-03's
  general "most recent first" bias seen in the Add-to-release picker) — each with its own View /
  Export PDF / Export DOCX actions, so a superseded revision's paperwork is reachable without
  visiting the viewer first.

Generation/export error text (see Copywriting Contract) renders directly below the row it belongs to,
scoped per document type — a Release Notes generation failure never bleeds into the Runbook row's
error slot.

### 2. `/releases/$releaseId/documents/$documentType` — document viewer (new route)

New route, `validateSearch` carrying an optional `?revision={n}` (defaults to the latest revision
when absent, same pattern `releaseDetailRoute` already uses for its own search params).

**Toolbar** (`white p-6 flex items-center justify-between`):
- Left: **"← Back to release"** link (`text-gray-600 hover:text-gray-900 text-sm`) to
  `/releases/$releaseId#documents` · document type + release name/version as the page heading
  (Heading, 16px/600), e.g. **"Release Notes — Orchstro 4.2.0"** · the readiness pill, reused
  identically from screens 0/1.
- Right: revision picker — `<select aria-label="Revision">`, options **"Revision {n} (latest)"**
  down to **"Revision 1"**, defaulting to the URL's `?revision` param or latest. Changing it
  navigates (`?revision={selected}`), re-fetching that revision's stored content — a full page-data
  swap, not a client-side toggle, since each revision is an independent immutable snapshot.
- Export PDF / Export DOCX buttons for **the currently viewed revision** (not always the latest —
  D-05-06's "every revision stays exportable" requirement lives here).

**Superseded banner** (only rendered when the viewed revision is not the latest): see Copywriting
Contract, placed directly below the toolbar.

**Template-deleted note** (only rendered when the backend indicates the source template no longer
exists — see Planning Input for the field this needs): see Copywriting Contract, placed directly
below the toolbar (above the superseded banner if both apply, since "this document's source is gone"
is the more surprising fact of the two).

**Document body:** reuses `TemplatePreview.tsx`'s exact cover-block / header-strip / body / footer-
strip markup and classes, fed from the stored snapshot instead of a live template:
- Cover block (rendered when the snapshot's chrome recorded `coverEnabled: true`): same `bg-white
  border border-gray-300 shadow-sm rounded p-8 mb-6 text-center` treatment, logo (from the snapshot's
  copied logo reference — see Planning Input), cover title/subtitle already fully resolved (no
  Mustache pass needed client-side — D-05-05's snapshot is post-render).
- Header/footer strips: same `bg-gray-100 text-gray-700 text-xs px-4 py-2` treatment, resolved text
  from the snapshot, **actual page numbers** rendered as real digits here (not the authoring
  preview's italic "Page X of Y" placeholder) if the snapshot recorded a resolved value — otherwise
  fall back to the same placeholder text with the same styling if pagination genuinely cannot be
  known outside a paginated renderer (planner's call — see Planning Input).
- Body: `prose prose-gray max-w-none p-4`, `markdown-it`-rendered from the snapshot's stored
  Markdown. **No unknown-placeholder marker chip can appear here** — DOC generation only succeeds
  from a template that already passed TMPL-04's save-time validation, so there is nothing left
  unresolved by the time a snapshot exists. If the backend response is ever malformed enough that
  rendering throws, fall back to the same neutral "Preview unavailable" panel `TemplatePreview` uses,
  rather than a crash — defensive only, not an expected path.

**Human verification hint:** see Copywriting Contract — rendered directly below the Export buttons,
only after both formats have been exported at least once in the current session (client-side
`useState` flags, not persisted — see Human Verification Surface below).

**Loading:** `gray-600 text-sm` "Loading document…" + spinner, replacing the content area.
**Error, document not found:** see Copywriting Contract's `DOCUMENT_NOT_FOUND` entry.
**Error, generic load failure:** `role="alert" data-reason={reason}` red-600 + "Try again", same
convention as every other screen.

### 3. Human Verification Surface (DOC-08 parity)

D-05-07 explicitly declines building automated PDF/DOCX parity checks **and** declines building
golden-image comparison — the recorded mitigation is "a manual visual check once per phase," in the
shape of Phase 1's `01-08-UAT-RESULTS.md` and Phase 4's 04-11 live-tenant verification. Consistent
with that precedent and with the project's standing "no over-engineering" instruction, this UI
contract does **not** introduce a persisted "I verified this" record, a checkbox field on the
document/revision, or any new backend state — that would be building tracking infrastructure for a
check the locked decision explicitly chose not to formalize.

What this phase's UI *does* provide, and what satisfies the focus area's "how a person is meant to
compare the two exports" requirement:

1. **Both exports are one click away from the same screen** (the document viewer's toolbar), so the
   comparison is never more than two clicks and two downloads away.
2. **The informational hint strip** (Copywriting Contract) appears once both formats have been
   exported in the current viewing session, telling the release manager exactly what to compare
   (cover, header, footer, page numbers — precisely the parts D-05-07 identifies as the genuinely
   divergent area, since the shared AST already guarantees body-content parity by construction).
3. **The actual verification record is a plan-time artifact**, not a running-app feature: a
   `05-UAT-RESULTS.md`-style checklist produced once during this phase's execution/testing, mirroring
   `01-08-UAT-RESULTS.md`. This is a planner/executor deliverable, not something this UI-SPEC can
   create, and is called out again in Planning Input below so it isn't silently dropped.

### 4. Template authoring addendum — grouping dimension control (D-05-04)

Extends `frontend/src/routes/TemplateDetailRoute.tsx` (Phase 4's two-pane authoring screen). Adds one
new toolbar-level control, **not tab-scoped** (applies regardless of whether "Body" or "Chrome &
Logo" is active, same reasoning as the existing Active badge and dirty indicator):

- Placed in the toolbar's left cluster, after the document-type subtitle: **"Group by"** label
  (`text-sm text-gray-600`) + native `<select aria-label="Group by">` with two options, **"Issue
  type"** (default) and **"Component"**. Helper text directly beneath in the Chrome & Logo tab is not
  needed — the toolbar placement with the short helper text (Copywriting Contract) is sufficient
  since this is a single binary setting, not a multi-field form.
- Participates in the **same dirty-tracking and Save flow** as body/chrome — changing it marks
  "Unsaved changes" and is only persisted when "Save template" is clicked, exactly like a chrome
  field. It is a template property, not an instant-effect control like the logo (contrast with Logo
  Upload's deliberate instant-effect exception in `04-UI-SPEC.md`).
- **Placeholder Catalog Drawer copy update:** the `groups` entry's description changes from "Items
  pre-grouped by issue type." to **"Items pre-grouped by this template's chosen dimension (issue type
  or component)."** — the token shape (`{{#groups}}`, `{{groupName}}`, `{{#groups}}{{#items}}`) is
  unchanged per D-05-04, only the description text needs updating.
- **New catalog entry** (Item group, per D-05-02): `items.component` — description: **"The ticket's
  Jira component, or 'Uncategorised' if none is set. Empty for manual items."** Tags: "Body only ·
  Ticket only" (same tag family as `items.assignee`, `items.reporter`, etc.).

## Drag-and-Drop Assessment (UX-01)

**Recommendation: close UX-01 to v2 this phase, with reasoning recorded — do not defer silently a
third time.** This is a recommendation for the planner/user to formally confirm (D-05-11 flags this
as a plan-time decision, not one the UI researcher can make unilaterally), but the design analysis is
conclusive enough to state plainly:

- D-05-01 removed UX-01's last concretely-scoped consumer: runbook deploy steps are now static
  template text (D-05-01), so there is nothing structured to reorder there.
- The one remaining candidate — reordering items within a release/group — was already declined once
  by D-03-04 on the grounds that "the ordering that actually matters is the ordering inside a
  generated document, which is template-driven at generation time," and that reasoning is unchanged:
  grouping is now template-driven (D-05-04) and within-group order is deterministic (ticket key /
  title ascending, per `03-UI-SPEC.md`).
- Building a drag-and-drop reorder feature with **no requirement currently depending on its output**
  (nothing reads a stored item order — not the view-model, not any template, not any document) is
  exactly the class of speculative feature this project's engineering principles rule out ("solve the
  problem at hand, not hypothetical future problems").

**If the user overrides this recommendation and wants item reordering built anyway**, the smallest
correct shape (for the planner's reference, not built here): a `position` integer on
`release_ticket_item`/`release_manual_item`, a reorder endpoint, and on release detail's item tables
a per-row **"Move up" / "Move down"** button pair (`aria-label="Move {item} up"` /
`"Move {item} down"`) as the keyboard-native equivalent required alongside any drag handle — never a
drag-only control. That is out of scope for this spec unless the recommendation above is rejected.

**Keyboard accessibility for this phase's actual pointer interactions:** every new interactive
element introduced this phase — readiness-pill links, Generate/Regenerate/Export buttons, the
revision `<select>`, the revision-history disclosure `<button aria-expanded>` — is a native HTML
element, inherently operable by Tab, Enter/Space and arrow keys (for the `<select>`) with no custom
gesture layer. **No drag interaction exists anywhere in this phase's shipped surfaces**, so no
keyboard-equivalent work is owed beyond what these native elements already provide.

## Planning input — items the planner/backend must resolve

Recorded here rather than silently assumed, matching Phase 2-4's convention of surfacing
backend-facing gaps discovered while designing the UI:

1. **New `ProblemDetail` reason codes needed**, extending the existing taxonomy — do not invent a
   parallel scheme: `DOCUMENT_NOT_FOUND` (no snapshot exists for the requested release/type/
   revision), `NO_ACTIVE_TEMPLATE` (defensive — generate/regenerate attempted with zero active
   templates for that type; the UI already prevents reaching this in the happy path, mirroring how
   Phase 3 treated `RELEASE_FROZEN`), `EXPORT_FAILED` (PDF or DOCX render failed on demand — one code
   is enough since the UI already knows which format it requested and doesn't need the reason code to
   carry that). Reuse Phase 4's existing `RENDER_BOUND_EXCEEDED` if generation itself can breach the
   timeout/collection bound — do not create a second bound-exceeded code.
2. **Does the document snapshot need a `templateDeleted` (or equivalent) flag in its API response?**
   Screen 2's "Generated from a template that has since been deleted" note (D-04-13 permits deletion;
   D-05-05 says the snapshot survives) needs the backend to expose whether the original template row
   still exists, distinct from the snapshot's own copied name/body/chrome. If this is expensive or
   awkward to compute, the note can be dropped without breaking any locked decision — it is a
   nice-to-have transparency note, not a requirement.
3. **Does the stored logo survive template deletion, and does the document snapshot copy the logo
   bytes/reference or only a pointer to the (deletable) template's logo?** D-05-05 says the snapshot
   copies "name, body and chrome fields" but doesn't explicitly name the logo. If the logo is not
   copied, the document viewer's cover block (screen 2) needs a graceful "no logo" fallback for any
   snapshot whose source template's logo was later removed or whose template was deleted — the same
   cover-block layout already handles "no logo uploaded" for the authoring preview, so this is a
   reuse, not a new state, provided the backend confirms which case applies.
4. **Are resolved page numbers available to the client at all, or must the viewer's header/footer
   always show the authoring preview's italic "Page X of Y" placeholder even for a generated
   document?** Real page counts only exist once a renderer paginates (PDF/DOCX), and the stored
   snapshot is pre-pagination Markdown (D-05-05). If no resolved page count is ever available
   client-side, screen 2 should keep the placeholder styling unchanged from Phase 4's preview rather
   than implying a real number is shown — this spec defaults to that safer assumption unless the
   planner confirms otherwise.
5. **Revision numbering scope** — confirmed by D-05-06 as "numbered per (release, document type)."
   The revision picker and revision-history list (screens 1 and 2) assume this scope directly; flag
   here only so an implementer double-checks the API shape matches before wiring the UI to it.
6. **`05-UAT-RESULTS.md`-style manual verification artifact** (see Human Verification Surface, screen
   3) is a planning/execution deliverable this UI-SPEC assumes will exist but cannot create — carry it
   into the phase's plan as an explicit task, the same way Phase 1's plan 01-08 and Phase 4's plan
   04-11 did.
