## Critical Anti-Patterns

| Pattern | Description | Severity | Prevention Mechanism |
|---------|-------------|----------|---------------------|
| Vite dev server vs Maven `npm ci` | A Vite dev server left running from a previous checkpoint held open handles inside `frontend/node_modules`. Maven's frontend profile runs `npm ci`, which deletes and reinstalls that tree; the delete failed partway with Windows EPERM (-4048), leaving `node_modules` at 21 entries with `react` and `vitest` gone. `mvn clean test` then failed for reasons unrelated to any code change. | advisory | Never start `npm run dev` in an executor agent, and stop any dev server before running a Maven build. If EPERM -4048 appears, check ports 5173/8080 for a node process before touching anything else. Repair is: stop the server, `cd frontend && npm ci`. |
| Grep-count acceptance criteria | Plans repeatedly assert `grep -c 'X' file` returns `N` while the same plan mandates comment text containing `X`, so the count is wrong by construction. One criterion also predicted a baseline nobody had checked (expected 4, real 3), making it unsatisfiable. Five occurrences across phases 05 and 05.1. | advisory | Verify the current count before predicting a post-change one; avoid strings the plan's own comments contain; prefer robust properties (`returns 0`, `grep -q`) over exact counts. The 05.2/05.3 planner prompts carried this rule and produced zero brittle counts — reuse that wording. |
| Assuming a killed agent did nothing | The session usage limit killed three agents mid-flight. Every time, their work had already landed on disk (and sometimes in git) and was recoverable after verification. I once reported plan 05.2-02 as "never started" after checking only the working tree and file listing — its two code commits were already in `git log`. | advisory | Before concluding an interrupted agent failed, check **`git log`** as well as `git status` and the file listing. Verify against the plan's acceptance criteria, then commit the surviving work rather than redoing it. |

<decisions_made>

- Logo height is a **per-template `ChromeFields` field stored on the snapshot**, chosen over a global
  `application.yml` value and over a clamp-only bug fix. Storing on the snapshot means an existing
  document re-exports at the size it was generated with.
- **The seam test uses 15mm, not the 30mm default.** At 30mm the pre-fix PDF's hard-coded
  `max-height: 3cm` coincidentally produces the correct answer, so a default-height assertion would pass
  against broken code. At 15mm both pre-fix renderers are demonstrably wrong. Reverting the fix failed
  4 of 4 seam tests, observed `expected: 540000L but was: 2857500L`.
- `ChromeFieldsRequest.logoRenderHeightMm` is `Integer`, not `int` — a primitive deserialises an absent
  field to `0`, which `@Min(5)` then rejects, so every save from a cached SPA build would 400.
- Existing rows default to 30 so **nothing already generated changes appearance in the PDF**. DOCX is the
  one intentional visible change, since it previously had no cap at all.
</decisions_made>
