Every open question CONTEXT.md left to discretion is settled here. Do not re-open any of them.

| Question | Decision | Why |
|---|---|---|
| Unit | **integer millimetres**, component named `logoRenderHeightMm`, column `logo_render_height_mm` | The output is a printed page. `openhtmltopdf` accepts `mm` natively in CSS, `1mm = 36000 EMU` exactly for docx4j, and CSS `mm` works in the browser — one stored integer serves all three renderers with no lossy conversion. One unit, stored and displayed; no conversion anywhere. |
| Default | **30** | `= 3cm`, the PDF's current hard-coded `max-height`. D-05.1-04: nothing that already exists changes appearance. |
| Upper bound | **120** | A4 is 297mm tall; `PdfExportAdapter` sets `@page margin: 2.5cm 2cm`, leaving **247mm** printable. `.cover` already spends **60mm** on `padding-top: 6cm`. Below the logo, the cover title (24pt with a 0.6cm top margin) and subtitle (13pt) need about **26mm**. `60 + 120 + 26 = 206mm`, which is **41mm inside** the printable area — so no permitted value can push cover content off page 1 (ROADMAP criterion 5). DOCX is safer still: it has no 60mm padding, so `120 + ~16mm` of title/subtitle sits well inside its own 246mm printable height. |
| Lower bound | **5** | Above 0, so a logo can never be an invisible zero-height ghost. 5mm is ~14pt — small but visibly present. |
| Validation placement | `@Min(5) @Max(120)` on `ChromeFieldsRequest` **and** `CHECK (... BETWEEN 5 AND 120)` on both V6 columns | The request-layer + DB pairing this codebase already uses for `groupingDimension` (`@Pattern` + `CHECK ... IN (...)`). The server is the authority; plan 02's browser `min`/`max` is advisory only. |
| `ChromeFields.empty()` | returns **30**, via a new `public static final int DEFAULT_LOGO_RENDER_HEIGHT_MM = 30` | `empty()` feeds `Template.create`, so it sets a brand-new template's initial value. 0 would violate V6's CHECK on the very first insert **and** would mean an invisible logo the first time `coverEnabled` is switched on. 30 makes a new template start exactly where every migrated row now sits. The constant kills the only real duplication of `30` in Java (`empty()` and the controller's default). |
| Request DTO type | **`Integer`**, not `int` | An absent field on a primitive `int` deserialises to `0`, which `@Min(5)` then rejects with a bare `VALIDATION_FAILED` — a cached SPA build would fail every save with no explanation. `Integer` lets the controller default an absent value while `@Min`/`@Max` (which skip `null`) still reject an explicit out-of-range number. This is the identical disposition `TemplateController.saveContent` already takes for `groupingDimension` three lines below, with the same "older client's payload" reasoning. |
| Domain + response types | primitive **`int`** | `ChromeFields` strings are already never-null by contract; the record carries a real value always. `ChromeFieldsResponse` matches every other response record in this codebase: primitives, no annotations. |
| Record-level range validation | **none** | Two belts already exist (Bean Validation at the boundary, CHECK at the database). A third check inside the record would be error handling for a case that cannot reach it. |
</decisions_resolved>

**1. New file `src/main/resources/db/migration/V6__logo_render_height.sql`** — verbatim:

```sql
-- D-05.1-01/D-05.1-02: the cover logo's RENDERED height is a per-template chrome setting, not a global
-- config value and not a constant hard-coded separately into each renderer (which is exactly how the
-- three renderers came to disagree by up to 4.5x). Millimetres because the output is a printed page:
-- openhtmltopdf accepts mm natively in CSS, 1mm = 36000 EMU exactly for docx4j, and CSS mm works in
-- the browser - one stored integer serves all three renderers with no lossy conversion.
--
-- D-05.1-04: DEFAULT 30 (= the PDF's previous hard-coded `max-height: 3cm`) so no existing template
-- and no existing document changes appearance. The one intentional visible change is DOCX, which had
-- no clamp at all and rendered a 512x512 logo 5.3in tall.
--
-- Bounds 5..120, and they must stay identical to ChromeFieldsRequest's @Min/@Max. Upper: A4 is 297mm
-- tall, PdfExportAdapter sets `@page margin: 2.5cm 2cm` leaving 247mm printable, and `.cover` already
-- spends 60mm on padding-top; the cover title (24pt, 0.6cm top margin) and subtitle (13pt) need about
-- 26mm below the logo. 60 + 120 + 26 = 206mm, 41mm inside the printable area, so no permitted value
-- can push cover content off page 1. Lower: 5mm keeps a logo visible instead of a zero-height ghost.
ALTER TABLE template ADD COLUMN logo_render_height_mm INTEGER NOT NULL DEFAULT 30
    CHECK (logo_render_height_mm BETWEEN 5 AND 120);

-- D-05.1-03: copied onto the snapshot at generation time, exactly like the four resolved chrome strings
-- and the logo bytes already are, so re-exporting revision 1 reproduces the size it was generated with
-- rather than today's template setting (DOC-07, and Phase 7's AUDIT-02 rests on it).
--
-- Unlike V5's other document_snapshot chrome columns this one carries a DEFAULT. That is a deliberate
-- exception to the "no default, generation always supplies them" convention above: rows generated
-- before this migration also need a value, and it has to be the one that reproduces today's PDF
-- behaviour (D-05.1-04 permits this and forbids backfilling anything else). The CHECK is repeated here
-- on purpose - the snapshot is the immutable audit record, and repeating it makes a forgotten setter in
-- the persistence mapper fail loudly (an unset Java int is 0, which this rejects) rather than silently
-- writing 0 and rendering an invisible logo forever.
ALTER TABLE document_snapshot ADD COLUMN logo_render_height_mm INTEGER NOT NULL DEFAULT 30
    CHECK (logo_render_height_mm BETWEEN 5 AND 120);
```

**2. `ChromeFields.java`** — replace the whole file:

```java
package com.evision.releasemgmt.domain.template;

// TMPL-08 / D-04-15: structured fields, not a second free-form template. Each string accepts the
// same {{ }} placeholders as the body and resolves against the same view-model, so no new
// expression surface exists. Strings are never null - "" means "not set".
//
// D-05.1-02: logoRenderHeightMm is the cover logo's MAXIMUM rendered height in millimetres, honoured
// identically by PdfExportAdapter, DocxExportAdapter and the browser's RenderedDocument. It is a
// maximum and never a target (D-05.1-06): a logo shorter than it keeps its natural size and is never
// scaled up. It is NOT an upload limit - LogoValidator's 2000x2000/2MB caps are a separate,
// storage-side decompression-bomb control (TMPL-09).
public record ChromeFields(boolean coverEnabled, String coverTitle, String coverSubtitle,
                           String headerText, String footerText, boolean pageNumbersEnabled,
                           int logoRenderHeightMm) {

    // = the PDF's previous hard-coded `max-height: 3cm`, and V6's column default on both tables, so a
    // brand-new template starts exactly where every migrated row now sits. Deliberately not 0:
    // empty() feeds Template.create, and 0 would both violate V6's CHECK on the first insert and mean
    // an invisible logo the first time coverEnabled is switched on.
    public static final int DEFAULT_LOGO_RENDER_HEIGHT_MM = 30;

    public static ChromeFields empty() {
        return new ChromeFields(false, "", "", "", "", false, DEFAULT_LOGO_RENDER_HEIGHT_MM);
    }
}
```

| T-05.1-02 | Denial of Service (a value large enough to push cover content off the printable page, making the document itself unusable) | the upper bound `120` | mitigate | Bounded by arithmetic, not by guesswork: 247mm printable − 60mm `.cover` `padding-top` − ~26mm of title/subtitle leaves 161mm; the bound is 120, i.e. 41mm of slack.
