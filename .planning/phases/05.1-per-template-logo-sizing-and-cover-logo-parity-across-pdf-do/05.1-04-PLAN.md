<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the running application → a real Postgres holding pre-phase rows | The V6 migration executes against durable data that no test ever sees |
| an author-supplied logo file → three independent rendering engines | The same bytes and the same height cross into openhtmltopdf, docx4j and the browser, each with its own sizing mechanism |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05.1-15 | Tampering (a migration silently altering existing audit records) | V6 against the local database | mitigate | Verified rather than assumed: Task 1 step 3 records the row counts *before* the app starts, then queries `flyway_schema_history` and `SELECT DISTINCT logo_render_height_mm` afterwards. V6 contains only `ALTER TABLE ... ADD COLUMN`; there is no `UPDATE`, and `git diff` on the migration file proves it. The checkpoint's step 1 independently confirms a pre-phase document re-exports unchanged in the PDF. |
| T-05.1-16 | Denial of Service (a permitted height still producing an unusable document) | the upper bound at 120mm | mitigate | Checkpoint step 5 exercises the exact worst permitted case in both export formats and requires the logo, title and subtitle all to remain on page 1. This is the one criterion whose arithmetic (247mm printable − 60mm padding − ~26mm of title/subtitle) is checked against a real renderer rather than only on paper. |
| T-05.1-17 | Information Disclosure (a logo used during verification persisting in the repository or the audit trail) | `logo-600x300.png` | mitigate | The generated file is written to the working directory, is not added to git, and the checkpoint instructs deleting it. Its bytes do land in `template_logo` and `document_snapshot_logo` in the **local** database, which is correct and expected behaviour for a logo the user uploaded — and it is a local dev database, nothing is deployed. `git status --short` is an acceptance criterion for both tasks, so a stray file cannot be committed unnoticed. |
| T-05.1-18 | Spoofing (a verification "pass" that never actually exercised the clamp) | the logo fixture used by the human | mitigate | This is the exact failure mode of Phase 5's own parity check, which passed because the logo used was small. The checkpoint therefore mandates a logo at least 400px tall, explains why, and supplies a command to generate a 600×300 one — and step 4 states the specific pre-phase numbers so a "looks fine" answer from an unclamped build would be visibly inconsistent. |
| T-05.1-19 | Elevation of Privilege | none introduced | accept | This plan writes no code and adds no surface. The authentication, CSRF and credential paths are untouched by the entire phase. |
</threat_model>
