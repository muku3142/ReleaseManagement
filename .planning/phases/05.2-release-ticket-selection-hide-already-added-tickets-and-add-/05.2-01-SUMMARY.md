# Phase 05.2 Plan 01: Server-Side Release-Membership Filter for Ticket Search Summary

**`POST /api/tickets/search` now accepts an optional `releaseId` that hides tickets the named release already holds, via a post-Jira filter in `TicketSearchService` that keeps `TicketSearchCriteria.toJql()` structurally unable to see release membership.**

## Accomplishments
- `TicketSearchService.search(TicketSearchCriteria, UUID releaseScope)` filters Jira's full result list against `ReleaseRepository.findTicketKeys(releaseScope)`, excluding tickets the target release already holds; the existing one-argument `search(criteria)` overload delegates to it with `null` and is byte-for-byte today's behaviour.
- `POST /api/tickets/search` accepts an optional `releaseId` in the request body, threaded to the service as a **separate argument**, never folded into `TicketSearchCriteria` — `toJql()` has no field to read it from.
- Seam tests at both the service level (`TicketSearchServiceTest`) and the full HTTP-adapter level (`TicketSearchPathTest`, `TicketControllerTest`) prove the release scope changes the result without changing the JQL sent to Jira.
- The D-05.2-01 guard (`aTicketOnADifferentReleaseIsStillVisible`) pins that the filter is per-target-release, not global — a ticket held by release A stays visible when browsing scoped to release B.
- The moved-issue edge case (`aMovedIssueIsNotHiddenUnderItsNewKey`) is now a documented, tested property rather than a latent surprise.

## Decisions Made
- Filter placement: `TicketSearchService` over `TicketController`, following the existing `ReleaseService` precedent (see `key-decisions` above and the plan's `<where_the_filter_lives_and_why>` section, which this plan implemented verbatim).
- Kept the one-argument `search(criteria)` overload rather than migrating every caller to a two-argument call with an explicit `null` — reduces caller-side noise and keeps `ReleaseService` and its test suite untouched, as the plan required.
- No validation annotation on `TicketSearchRequest.releaseId` — Jackson rejects a malformed UUID before the controller runs, and the only client sends an id it already routed to (per the plan's stated edge-case guidance and this project's CLAUDE.md "no error handling for cases that cannot happen").
