<the_extraction_seam_resolved>
`05.2-PATTERNS.md` §1 leaves one thing open — whether the extracted component owns the destination
dialog or hands the selection upward. **Resolved here; implement this, do not re-decide it.**

The extracted component **hands the selection upward through props** and never imports
`AddToReleaseDialog`:

```tsx
export function TicketBrowser(props: {
  actionLabel: string;
  onAction: (ticketKeys: string[], jiraProjectKey: string | null) => void;
}) { ... }
```

Reason: the release-page caller (plan 05.2-03) needs a *different* destination — a fixed release,
reached through `useAddTicketsToRelease` — so a browser that owned `AddToReleaseDialog` internally
would have to grow a mode flag to serve it, which is exactly the shape `D-05.2-07` rejects. Passing the
selection out keeps the browser about browsing and leaves "what happens to the chosen tickets" with
whoever mounted it.

`jiraProjectKey` travels with the keys because `TicketsRoute` needs it for
`AddToReleaseDialog`'s `jiraProjectKey` prop (`D-03-05`'s advisory project key), and it is derived from
state that now lives inside the browser (`loadedMode` + the projects query). The release-page caller
ignores it.
</the_extraction_seam_resolved>

```tsx
import { useState } from 'react';
import { AddToReleaseDialog } from '../components/AddToReleaseDialog';
import { TicketBrowser } from '../components/TicketBrowser';

export function TicketsRoute() {
  // The keys are snapshotted when the trigger is pressed rather than tracked live: showModal() makes
  // the rest of the document inert, so the selection cannot change while the dialog is open.
  const [picker, setPicker] = useState<{
    ticketKeys: string[];
    jiraProjectKey: string | null;
  } | null>(null);

  return (
    // No max-width cap: the ticket table is the point of this screen and eight columns do not
    // fit in 5xl, which was cutting content off.
    <div className="w-full">
      <h2 className="text-base font-semibold text-gray-900">Browse tickets</h2>

      <TicketBrowser
        actionLabel="Add to release"
        onAction={(ticketKeys, jiraProjectKey) => setPicker({ ticketKeys, jiraProjectKey })}
      />

      <AddToReleaseDialog
        open={picker !== null}
        ticketKeys={picker?.ticketKeys ?? []}
        jiraProjectKey={picker?.jiraProjectKey ?? null}
        onClose={() => setPicker(null)}
      />
    </div>
  );
}
```

The dialog stays **permanently mounted** and gated only by `open`, exactly as today — never
`{picker && <AddToReleaseDialog .../>}`. `AddToReleaseDialog` resets its own state in its open-effect
precisely because it never unmounts (its comment at lines 34-36 says so), and conditional mounting
would make that reset dead code.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Jira ticket text (summary, description, comments) -> browser DOM | Server-supplied strings originating in an external system are rendered on screen |
| user-typed JQL -> `POST /api/tickets/search` | Free text crosses to the backend and onward to Jira |
| selected ticket keys -> the caller-supplied `onAction` | The extraction introduces a new call boundary between the browse surface and whatever consumes its selection |
