# Phase 05.2: Release Ticket Selection - Context

**Gathered:** 2026-08-11
**Status:** Ready for planning
**Source:** Direct decision capture. The user requested the two capabilities and chose between the
design alternatives for each in the same session. No `/gsd-discuss-phase` run.

<domain>
## Phase Boundary

**In scope:** two assembly frictions, and the one extraction needed to serve both honestly.

1. Tickets already on the release being assembled do not appear in the ticket browse table.
2. Tickets can be added to a release from the release page, with the same browsing power the
   `/tickets` screen has.

**Out of scope, explicitly:**
- Removing tickets from a release. That already exists and is untouched.
- Changing what a release *is*, or the OPEN→FROZEN lifecycle.
- Manual (non-Jira) release items. They have their own path and are not part of ticket browsing.
- Changing Jira search itself — the JQL builder, field metadata resolution, pagination, or
  `TicketSearchCriteria.toJql()`'s output for a given set of filters.
- Any change to `release_ticket_item_key_unique`. Multi-release membership stays possible; see
  `D-05.2-01`.
- The `generatedBy`/`createdBy` actor-identity question (actor fields currently store the Jira
  accountId rather than an email). Real, but a separate concern with its own blast radius across 9
  capture sites — not this phase.

**Neither requirement is a correctness fix.** The backend already tolerates both situations:
`ReleaseService.addTickets` de-duplicates against what the release already holds and returns an
`alreadyPresent` count (`D-03-13`, lines 74-78), treating a wholly-redundant selection as success
rather than a 409. This phase removes avoidable human work; it does not repair broken behaviour. State
that in the plans so no one "hardens" a path that is already correct.
</domain>

<decisions>
## Implementation Decisions

### D-05.2-01 — The filter is scoped to the target release, never global
Browsing while assembling release X hides only what X already contains. A ticket sitting in release Y
still appears.

Rejected: hiding any ticket that is in *any* release. It reads as simpler but it contradicts the
schema — `release_ticket_item_key_unique UNIQUE (release_id, ticket_key)` (`V3__release_assembly.sql`)
scopes uniqueness per release precisely so one ticket can ship in two releases, which is what a hotfix
landing in both a patch and the next minor actually looks like. A global filter would make that state
unreachable through the UI while leaving it reachable in the data, so the UI and the data model would
disagree.

Also rejected: showing already-added tickets with a badge and a disabled control. It hides nothing, so
it does not solve the stated problem (scrolling past tickets already taken).

### D-05.2-02 — Filtering happens server-side, after the Jira call, never in JQL
`TicketSearchCriteria.toJql()` must not learn about releases. Jira has no knowledge of our release
membership and no JQL clause can express it. The filter belongs in `TicketSearchService.search`, on the
list `JiraTicketPort.searchAll` returns.

Server-side rather than client-side so that any count the UI reports is the count of what it is
actually showing. A client-side filter would make the server's total a lie.

### D-05.2-03 — No pagination complexity exists here, and none may be introduced
`JiraTicketPort.searchAll` returns a complete `List<TicketDetail>`; it exhausts Jira's cursor
pagination inside the adapter (that is `JIRA-03`). No cursor, page token or page size reaches the
client. The filter is therefore a plain post-filter on a complete list.

Do not add pagination, "top up the page after filtering", or a filtered-count-vs-total reconciliation.
There is no page to top up.

### D-05.2-04 — Reuse the existing membership query
`ReleaseRepository.findTicketKeys(releaseId)` already exists and is already used by
`ReleaseService.addTickets:70` for its own de-duplication. The filter uses it. Do not add a second
query, a projection, or a count endpoint for this.

### D-05.2-05 — The `/tickets` screen outside a release context is unchanged
With no target release, nothing is filtered and the screen behaves exactly as it does today. The
release context is what switches filtering on, which means the new request parameter is optional and
its absence is the current behaviour.

### D-05.2-06 — The browse surface is extracted, not duplicated
`TicketsRoute.tsx` (416 lines) currently owns the project picker, sprint picker, status filter, JQL
panel, results table, row expansion and multi-select state directly in the route component (state at
lines 17-28, table from line 285). That surface is extracted into one reusable component consumed by
both the `/tickets` route and the new release-page dialog.

This is the same move plan 05-12 made with `RenderedDocument`, and it is made for the same reason:
Phase 5 shipped with three renderers that could drift, and closing that took a dedicated plan. A second
hand-rolled ticket table would be that mistake again, in a place where the two copies would diverge on
filter semantics rather than on styling.

**The extraction must be behaviour-preserving, and the existing `TicketsRoute` tests passing untouched
are the proof.** Structure it exactly as Task 1 of `05-12-PLAN.md` did: a pure move, no behaviour
change, no test edited in the same task.

### D-05.2-07 — `AddToReleaseDialog` is not extended; the new dialog is its mirror image
`frontend/src/components/AddToReleaseDialog.tsx` carries `D-03-01` in its own header: it "owns exactly
one job - choose a destination release for an already-chosen ticketKeys array. It contains no ticket
search, project picker, sprint picker or ticket table of its own."

The new dialog is the inverse: the release is fixed, the tickets are chosen. That is a sibling
component, not a mode flag on the existing one. Adding search and a table to `AddToReleaseDialog` would
directly contradict a recorded decision and turn a single-purpose component into a two-mode one.

### D-05.2-08 — A frozen release shows no add affordance
`ReleaseService.addTickets:67` calls `release.requireOpen()`, so the server already refuses. The UI must
not let a release manager open the dialog, filter, select tickets and only then discover the release is
frozen. Absent or disabled at the entry point, with the reason legible — not a 409 after the work.

### D-05.2-09 — Document staleness needs no new handling, and must not get any
`items_changed_at` is stamped by `ReleaseRepositoryAdapter` on every item mutation, below the service
layer (see the `D-05-09` comment in `V5__document_generation.sql:9-15` and
`domain/release/Release.java:7`). A new add entry point that goes through `ReleaseService.addTickets`
inherits stamping automatically.

Do not stamp it again from the new path. `ReleaseRepositoryAdapter:87` deliberately does *not* stamp
when every requested ticket was already present, and a second stamping site would break that.

### Claude's Discretion

- **How the release context reaches the search request.** An optional field on
  `TicketSearchRequest`/`TicketSearchCriteria` is the obvious shape, but the exact name and whether the
  domain criteria record carries it or the service takes it as a separate argument is open. Prefer
  whichever keeps `toJql()` provably unable to see it.
- **Where the filter executes.** `TicketSearchService.search` is the natural home. If it needs a
  release-membership port, note that `TicketSearchService` currently depends only on Jira-side
  collaborators — adding a release dependency crosses a seam, so consider whether the controller
  composes instead. Decide and state the reasoning; do not leave it to the executor.
- **The extracted component's name, props and file location.** `frontend/src/components/` is where the
  other shared components live.
- **How the dialog reports the outcome.** `AddTicketsResult` already carries added / alreadyPresent /
  (third count) — decide what the dialog says for each, following the copy conventions the existing
  dialog and `05-UI-SPEC.md` establish.
- **Whether the release page's ticket list refreshes optimistically or by invalidation.** Follow the
  existing TanStack Query patterns in `frontend/src/api/releases.ts`.
</decisions>

<specifics>
## Specific Ideas

- **The seam worth testing.** Phase 5's two defects were both contract mismatches that no single test
  crossed. The equivalent seam here is: a release containing ticket K, a Jira search whose results
  include K, and the assertion that the response omits K while a search with no release context
  includes it. Test it through the service (or controller) with a stubbed `JiraTicketPort`, not by
  asserting the filter helper in isolation — an isolated filter test would pass even if the release
  context never reached it, which is exactly the failure mode that shipped twice.
- **The moved-issue case is a real edge.** `addTickets` de-duplicates against keys Jira returned rather
  than keys requested, because an issue that moved projects comes back under a new key. A filter keyed
  on the release's stored `ticket_key` will not hide a ticket whose key has since changed. That is
  acceptable and probably correct, but note it rather than discovering it.
- **Frozen-release verification.** Assert the add affordance is absent for a FROZEN release at the UI
  level, since the server-side refusal is already covered by Phase 3's tests.
- **Environment:** `export JAVA_HOME="$HOME/.jdks/jdk-25"` before every Maven call (machine default is
  17). Frontend commands run from `frontend/`; `npx tsc -b` is incremental and can report a stale
  failure on the first run after a branch change, so run it twice before believing a failure.
- **Baselines that must not regress:** backend 556 tests, frontend 183 tests, `tsc -b` clean. Phase
  05.1 may land first and raise both numbers — read the current baseline rather than trusting these if
  05.1 has already merged.
</specifics>

<deferred>
## Deferred Ideas

- A lightweight "add by ticket key" input on the release page, for when the keys are already known.
  Considered and set aside in favour of the full browse dialog; it is additive later if typing keys
  turns out to be the faster path in practice.
- Any global "a ticket belongs to at most one release" model, and the schema tightening that would
  make it true. Explicitly rejected by `D-05.2-01`.
- Badging already-added tickets with the releases they belong to. Rejected as the primary answer
  because it hides nothing, but it is the natural design if multi-release membership ever needs to be
  visible.
- Bulk add from a saved filter or a pasted list.
- The actor-identity defect (`generatedBy` and every other actor field storing a Jira accountId rather
  than a human-readable email). Genuinely worth fixing, spans 9 capture sites across 5 controllers, and
  interacts with append-only snapshots the same way the Phase 5 content-type fix did. Its own phase.
</deferred>
