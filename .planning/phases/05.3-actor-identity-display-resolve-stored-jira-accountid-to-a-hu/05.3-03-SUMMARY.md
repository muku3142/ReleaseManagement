## Accomplishments
- `ActorDisplaySeamIT`: five tests driving the real `ReleaseController.list()` and `DocumentController.revisions()` beans against a real Postgres row whose `encrypted_token` is corrupted via direct `JdbcTemplate` UPDATE (the same technique as `JiraCredentialPersistenceIT`) - covers criterion 1 (resolves to email), criterion 2 (pre-stored account ids resolve without rewriting), criterion 3 (no credential row degrades to the account id), criterion 4/T-05.3-13/T-05.3-16 (a bad row doesn't break the batch or the page), and T-05.3-14 (no response, serialized with the app's own `ObjectMapper`, contains the plaintext token, the stored ciphertext, or the substring "token")
- Mutation check (Task 1 acceptance criterion 7): reverted `ActorDirectoryAdapter.findEmailsByAccountId` to `jpa.findAllById(...)` (entity hydration) and reran the seam test - `releaseListRendersTheEmailForARowWhoseTokenCannotBeDecrypted`, `documentRevisionHistoryRendersTheEmailForARowWhoseTokenCannotBeDecrypted` and `oneUnreadableCredentialDoesNotBreakADifferentUsersRow` all failed with `AEADBadTagException` surfacing through Hibernate/JPA, exactly as predicted; reverted with a clean `git diff`
- Two ArchUnit rules added to `ArchitectureBoundaryTest`: `theWebAdapterCannotReachTheTokenBearingCredentialPort` (bans any `..adapters.web..` class from depending on `JiraCredentialRepository`) and `actorResolutionResolvesThroughActorDirectoryOnly` (bans `ActorResolutionService` from the same port) - T-05.3-15
- Non-vacuity proven by hand for both rules: temporarily injecting an unused `JiraCredentialRepository` constructor parameter into `ReleaseController` failed only the first rule; temporarily swapping `ActorResolutionService`'s dependency to `JiraCredentialRepository` failed only the second rule (and required a matching temporary edit to `ActorResolutionServiceTest`, also reverted). Both reverted with a clean `git diff` before committing
