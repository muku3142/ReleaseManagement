## Pattern Assignments

### `V7__template_user_default.sql` (migration, CRUD)

**Analog:** `src/main/resources/db/migration/V4__template_authoring.sql` lines 7-45 (the `template_logo` table: child of `template` with `ON DELETE CASCADE`, header comment citing decision IDs and the reason the constraint lives in SQL).

**FK + cascade pattern** (V4 `template_logo`):
```sql
CREATE TABLE template_logo (
    template_id  UUID PRIMARY KEY REFERENCES template (id) ON DELETE CASCADE,
    ...
    uploaded_at  TIMESTAMPTZ  NOT NULL DEFAULT now()
);
```

**document_type CHECK** (V4 `template`, copy verbatim so values stay in lockstep):
```sql
document_type        VARCHAR(32)  NOT NULL
                     CHECK (document_type IN ('RELEASE_NOTES', 'RUNBOOK', 'APPROVAL')),
```

**Apply:** `account_id VARCHAR(255) NOT NULL` (same width as `created_by` in V4), `document_type VARCHAR(32) NOT NULL CHECK (...)`, `template_id UUID NOT NULL REFERENCES template (id) ON DELETE CASCADE`, `PRIMARY KEY (account_id, document_type)`. No FK on `account_id` (no user table, D-05.4-04). Start the file with a comment block in the V4/V5 style citing D-05.4-04 and why "same document_type as the template" is enforced by the set path and not by the table. Latest migration is `V6__logo_render_height.sql`; this is `V7`. Flyway files are plain SQL, no Java migration.

### `TemplateUserDefaultEntity.java` (entity) and `TemplateUserDefaultJpaRepository.java`

**Analog:** `B/adapters/persistence/entity/TemplateLogoEntity.java` and `repository/TemplateLogoJpaRepository.java`.

**Entity shape** (`TemplateLogoEntity.java:1-40`): plain `@Entity @Table(name = ...)`, `@Id @Column(name = ...)` field, explicit `@Column(name=..., nullable=false)` per field, public no-arg constructor, hand-written getters/setters (no Lombok).
```java
@Entity
@Table(name = "template_logo")
public class TemplateLogoEntity {
    @Id
    @Column(name = "template_id")
    private UUID templateId;
    ...
    @Column(name = "uploaded_at", nullable = false)
    private Instant uploadedAt;
```
Enum column pattern (from `TemplateEntity.java`):
```java
@Column(name = "document_type", nullable = false)
@Enumerated(EnumType.STRING)
private TemplateDocumentType documentType;
```

**No analog:** a composite primary key. `grep IdClass|EmbeddedId` in `src/main` returns nothing. The planner picks `@IdClass` (simplest, fields stay flat on the entity) or `@EmbeddedId`; both are standard Jakarta Persistence. Alternative that avoids it: a surrogate `id UUID` plus `UNIQUE (account_id, document_type)`, but that departs from the D-05.4-04 primary key and is not recommended.

**JPA repository** (`TemplateLogoJpaRepository.java:12-25`): `extends JpaRepository<Entity, KeyType>`, derived query methods or `@Query` with a JPQL projection. For this phase derived queries are enough:
```java
List<TemplateUserDefaultEntity> findByAccountId(String accountId);
Optional<TemplateUserDefaultEntity> findByAccountIdAndDocumentType(String accountId, TemplateDocumentType type);
```
(Style reference: `TemplateJpaRepository.findByDocumentTypeAndActiveTrue`.)

### `TemplateRepository` port + `TemplateRepositoryAdapter` (modify)

**Analog:** the existing methods in the same pair. Decision for the planner: add the per-user default methods to `TemplateRepository` rather than a new port (the project rules say no extra layers), unless the adapter grows unwieldy. Proposed port methods: `Optional<Template> findUserDefault(String accountId, TemplateDocumentType type)`, `Set<UUID> findUserDefaultTemplateIds(String accountId)` (one query for the list screen), `void setUserDefault(String accountId, UUID templateId)`, `void clearUserDefault(String accountId, UUID templateId)`, `boolean existsByDocumentType(TemplateDocumentType type)` (readiness).

**Port Javadoc style** (`B/ports/TemplateRepository.java:30-40`): one-line behaviour + `@throws ...TemplateNotFoundException when the id is unknown`.

**Upsert pattern** (adapter `saveLogo`, `TemplateRepositoryAdapter.java:~118-133`): load-or-new, set fields, `save`, inside `@Transactional`:
```java
@Override
@Transactional
public Template saveLogo(UUID templateId, LogoImage image) {
    TemplateLogoEntity entity = logoJpa.findById(templateId).orElseGet(TemplateLogoEntity::new);
    entity.setTemplateId(templateId);
    ...
    logoJpa.save(entity);
    return load(templateId);
}
```
Apply: `setUserDefault` loads the template with `jpa.findById(templateId).orElseThrow(TemplateNotFoundException::new)` (the `setActive` pattern, adapter line ~96) to get its `documentType`, then `findByAccountIdAndDocumentType(...).orElseGet(...)`, set `templateId`, save. That is where the same-type invariant (D-05.4-04) is satisfied, since the row's `document_type` is derived from the template rather than accepted from the client.

**Idempotent delete** (`deleteLogo`): `if (logoJpa.existsById(...)) logoJpa.deleteById(...)`. Copy for `clearUserDefault` (clear must be a no-op when no default is set, and should only delete when the stored default points at this `templateId`).

**Read path** (`findActive`, adapter ~line 70): `jpa.findBy...(...).map(e -> toDomain(e, logoJpa.findMetadata(e.getId()).orElse(null)))`. Reuse `findById(...)` for the template behind the default row rather than re-mapping.

**Cascade note:** `delete()` already relies on `ON DELETE CASCADE` ("no guard, no existence check", adapter ~line 108). The new table inherits this with zero Java; do not add a manual cleanup.
