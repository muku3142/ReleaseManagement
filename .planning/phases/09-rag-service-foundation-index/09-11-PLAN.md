    1. Identify how the live stack was created:
       `docker inspect releasemanagement-postgres-1 --format '{{index .Config.Labels "com.docker.compose.project.config_files"}}'` and
       the same for `releasemanagement-app-1`. Record both in the SUMMARY. If postgres was not created from `compose.app.yaml`, STOP and
       report it as a checkpoint. Applying compose.app.yaml would then create a second Postgres on a different volume.
    2. Secrets in `.env`, without printing them: if `RAG_ADMIN_KEY` is missing or empty, append `RAG_ADMIN_KEY=$(openssl rand -base64 32)`.
       If `RAG_DB_PASSWORD` is missing, append `RAG_DB_PASSWORD=$(openssl rand -hex 24)`. Use the substitute-don't-duplicate approach
       from `.env.example`'s header.
    3. Back up v1 data before changing the image:
       `mkdir -p "$HOME/releasemanagement-backups" && docker exec releasemanagement-postgres-1 pg_dump -U releasemgmt -Fc releasemgmt > "$HOME/releasemanagement-backups/releasemgmt-pre-pgvector-$(date +%Y%m%d%H%M).dump"`.
       Check that the file size is greater than 0. Record the path in the SUMMARY. Also record the baseline
       `docker exec releasemanagement-postgres-1 psql -U releasemgmt -d releasemgmt -tAc "select count(*) from flyway_schema_history"`.
    4. Recreate Postgres on the new image: `docker compose -f compose.app.yaml up -d postgres`. Wait until
       `docker inspect releasemanagement-postgres-1 --format '{{.State.Health.Status}}'` is `healthy`. Then verify:
       - `docker exec releasemanagement-postgres-1 psql -U releasemgmt -d releasemgmt -tAc "select count(*) from flyway_schema_history"`
         equals the baseline recorded in step 3.
       - the image is `pgvector/pgvector:0.8.7-pg18-trixie`.
    5. Run the one-off on the existing volume (D-09-14). With `RAG_DB_PASSWORD` read from `.env`:
       `MSYS_NO_PATHCONV=1 docker compose -f compose.app.yaml exec -e RAG_DB_PASSWORD="$RAG_DB_PASSWORD" postgres bash /docker-entrypoint-initdb.d/10-ragdb.sh`.
       Expect exit code 0. Then confirm `ragdb` exists and has `vector`. This validates RESEARCH assumption A1. If the exec form
       fails, use `docker exec` and correct `docs/docker.md` to match.
    6. Start the service: `docker compose -f compose.app.yaml up --build -d rag-service`. Wait until its health is `healthy`
       (readiness). Confirm `releasemanagement-app-1` is still running and healthy, and that the v1 app responds:
       `curl -s -o /dev/null -w '%{http_code}' http://localhost:${RM_PORT}/actuator/health`, using `RM_PORT` from `.env`, returns 200.
    7. End-to-end with real Ollama. Use `$ADMIN` (from `.env`) and `$KEY` (the client key returned by registration, never printed):
       a. `POST /v1/admin/clients {"name":"smoke-<timestamp>"}` returns 201. Keep the key in `$KEY`. Without auth, or with a wrong key,
          a client route returns 401.
       b. `PUT /v1/collections/smoke` returns 201 with `nomic-embed-text`.
       c. Push three documents with distinct topics (deployment runbook, database backup policy, holiday calendar), each with
          metadata `{"release_id":"R1"}` or `{"release_id":"R2"}`. Each returns 202.
       d. Poll `GET /v1/collections/smoke` until `indexed` = 3 (timeout 120 s). Record `lastIndexedAt`.
       e. `POST /v1/collections/smoke/search {"query":"how do we back up the database"}`: the backup document ranks first. Record its
          score, and check that each hit has documentId, title, url and metadata. The same search with `filter {"release_id":"R2"}`
          returns only R2 documents.
       f. Re-push the backup document unchanged: the response status is INDEXED, and `indexed_at` (from GET document) is unchanged.
       g. `POST /v1/collections/smoke/reindex` returns 202 with requeued 3. Poll until indexed = 3 again, and confirm `lastIndexedAt` has advanced.
       h. Delete the backup document (204), then repeat the search from e: the backup document is absent.
       i. Register a second client. Its key on `GET /v1/collections/smoke` returns 404.
       j. `GET http://localhost:8081/v3/api-docs` returns 200 and contains `/v1/collections/{collection}/search`.
    8. Outage drill (success criterion 4):
       - Stop Ollama: `taskkill //IM "ollama app.exe" //F; taskkill //IM ollama.exe //F`. Confirm with
         `curl -s -m 2 localhost:11434/api/version` that it fails.
       - Push a new document. It returns 202. `GET` shows PENDING, and `GET /v1/status` shows `"ollama":"DOWN"` and `pending` >= 1.
         Wait 20 s and check that it is still PENDING, not FAILED.
       - Restart Ollama with `powershell -NoProfile -Command "Start-Process \"$env:LOCALAPPDATA\Programs\Ollama\ollama app.exe\""`.
         Poll `localhost:11434/api/version` for up to 60 s. If it does not come back, STOP and report a checkpoint asking the user to
         start Ollama. Do not leave the user without Ollama silently.
       - Poll the document until INDEXED, with a timeout of 360 s because backoff caps at 5 min. Record how long recovery took.
         `GET /v1/status` returns to `"ollama":"UP"`.
    9. Logs carry metadata only: run `docker logs rag-service-container-name 2>&1` (use the name from `docker compose ps`). The output
       contains none of the smoke document texts or queries; grep for one distinctive phrase from each text and from the query.
    10. Clean up smoke data: revoke both smoke clients through the admin API. Leave the `smoke` collection, since there is no delete
        endpoint, and note it in the SUMMARY.
    Record every step's outcome in the SUMMARY, with HTTP codes and timings and no secrets.
