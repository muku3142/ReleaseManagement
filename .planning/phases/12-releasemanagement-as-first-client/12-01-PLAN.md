    Create `config/AssistantProperties` (per D-12-16, prefix `app.assistant`, NOT `rm.assistant`):
    ```java
    @ConfigurationProperties("app.assistant")
    public record AssistantProperties(boolean enabled, String baseUrl, String apiKey, String embeddingModel,
                                      Sweep sweep, Timeouts index, Timeouts chat, int maxRounds, int toolResultMaxChars) {
        public record Sweep(Duration initialDelay, Duration interval) {}
        public record Timeouts(Duration connectTimeout, Duration readTimeout) {}
        // compact ctor: if (enabled && (isBlank(baseUrl) || isBlank(apiKey))) throw new IllegalStateException(
        //   "app.assistant.enabled=true requires app.assistant.base-url and app.assistant.api-key");
        // toString(): same fields but apiKey rendered as "***" (or "<unset>" when blank)
    }
    ```
    Collection names are NOT configuration: they are fixed by D-12-01 and live as a domain enum in plan 12-04
    (discretion choice: they are part of the data contract Phase 13 links against; configurability adds nothing).
    Create `config/AssistantConfig`:
    ```java
    @Configuration
    @ConditionalOnProperty(prefix = "app.assistant", name = "enabled", havingValue = "true")
    @EnableConfigurationProperties(AssistantProperties.class)
    @EnableScheduling
    public class AssistantConfig { }
    ```
    Comment only the WHY: no TaskScheduler/Executor bean here because a user-defined one replaces Boot's
    auto-configured scheduler/executor. `@EnableScheduling` lives here so scheduling is active only with the switch on
    (the main app has no other `@EnableScheduling`). Application classes do NOT import `config` types; later plans read
    individual values with `@Value("${app.assistant....}")`, the house style.
    Write `AssistantPropertiesTest` (plain JUnit + AssertJ, `new AssistantProperties(...)`) for the behaviours above.
