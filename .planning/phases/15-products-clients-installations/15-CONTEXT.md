# Phase 15: Products, Clients & Installations - Context

**Gathered:** 2026-10-20
**Status:** Ready for planning

<domain>
## Phase Boundary

A release manager can maintain a product and client register (create, rename, archive, link clients to
several products), say which products a release covers, and record which clients installed a FROZEN
release, singly or in bulk, in an append-only, correctable ledger. Per client they can see the release
currently running for each product. Templates can print a release's product names. Promotion tracking
(`environment_stage`, `promotion`, `PromotionService`) is untouched. Requirements PORT-01..PORT-08.

Not in this phase: dashboard grouping by product, the client x product matrix, the behind-latest view and
assistant answers (Phase 16); per-client ladders (v2).

</domain>

<decisions>
## Implementation Decisions

### Carried forward (decided at milestone scoping, not re-asked)
- Client <-> product is many-to-many (`product_client`).
- An install requires the release to be FROZEN and to cover the product; if the release has not reached the
  Production stage, show a warning but allow it.
- `client_deployment` is its own ledger, a copy of the `promotion` pattern: trigger-enforced append-only,
  corrections via `supersedes_id`, composite FKs `(release_id, product_id) -> release_product` and
  `(product_id, client_id) -> product_client`, current state derived on read. It carries no stage.
- Flyway V14 (pre-assigned). Test it against a realistic v1.1 snapshot, not only an empty DB.
- Products and clients are archived, never deleted.

### Products on releases
- **D-15-01:** A release's products can be changed at any time, while OPEN and after FROZEN, so existing
  v1.1 releases (all frozen) can be tagged and receive installs. Guard: a product cannot be removed from a
  release once any install record exists for that release + product (the composite FK enforces this; the
  service returns a clear error first).
- **D-15-02 (revised 2026-10-21 after research, Option A):** Any product change, on OPEN or FROZEN
  releases alike, bumps `releases.items_changed_at` (only when the product set actually changed). The
  readiness rule D-05-09 is NOT changed: `DocumentReadinessService.state` keeps returning UP_TO_DATE for a
  frozen release with a generated document, so only OPEN releases show stale. Frozen documents can already
  be regenerated by hand. The UI staleness note on the products editor shows on OPEN releases only.
  Rejected Option B (frozen compares items_changed_at) because it would flip some existing frozen v1.1
  releases to STALE on deploy.
- **D-15-03 (revised 2026-10-21, superseded in part by D-15-18):** The create-release form gets a product
  picker; products are also editable on the release detail page. "Unassigned" remains only as a defensive
  display for a release with zero product rows (the schema cannot enforce at least one).

### Install record shape
- **D-15-04:** Outcomes mirror promotion: `SUCCESS | FAILED | ROLLED_BACK`, plus `VOIDED` only as a
  correction (same CHECK as `promotion_voided_only_by_correction`).
- **D-15-05:** "Currently runs" for (client, product) = the effective row (not superseded, not VOIDED) with
  outcome SUCCESS and the newest `installed_at`, tie-broken by `recorded_at`. FAILED and ROLLED_BACK rows
  never change what a client runs. Back-dating an older install never overrides a newer one. Keep the
  effective rule in one place (e.g. an `effective_client_deployment` view) because Phase 16 reads it too.
- **D-15-06:** Corrections work like promotion corrections: "Correct" opens a form prefilled from the
  original (release, installed time, outcome, note) with a required reason and writes a superseding row;
  "Void" writes a VOIDED superseding row. The original stays visible, shown as superseded.
- **D-15-07:** Archived products and clients keep all links and history (shown with an "archived" label) but
  cannot be newly assigned to a release or receive new installs. They can be unarchived.

### Where things live in the UI
- **D-15-08:** A new top-level "Portfolio" nav page with Products and Clients tabs handles create, rename,
  archive/unarchive and client <-> product links. Settings is not used for this. Phases 16 and 17 build on
  this page.
- **D-15-09:** Installs are recorded only from the release detail page, in a "Client installs" section shown
  for FROZEN releases: pick a product of the release, tick one or more of that product's active clients,
  and set the installed time (default now, back-datable), outcome and note. Ticking several clients is the
  bulk install (PORT-07). The not-in-Production warning appears in this form. The release's install history
  is listed in the same section.
- **D-15-10:** A bulk install is all or nothing: one transaction; if any selected client is invalid, nothing
  is saved and the response names the offending clients.

### Per-client "runs" view
- **D-15-11:** PORT-06 is a client detail view on the Portfolio page: each product linked to the client with
  its current release (name, version, installed date, not-in-Production marker), followed by the client's
  full install history including superseded rows. The cross-client matrix is Phase 16.
- **D-15-12:** A linked product with no effective SUCCESS install shows "Not installed" explicitly; it is not
  hidden.
- **D-15-13:** A client <-> product link cannot be removed once the client has install records for that
  product (the composite FK blocks it). The UI explains why and offers archiving the client instead. Links
  without installs can be removed.

### Settled after research (2026-10-21)
- **D-15-14:** Installed time has no lower bound (not tied to frozenAt, unlike promotions) but may not be in
  the future.
- **D-15-15:** Any ledger row for a release+product (including voided or superseded rows) permanently
  blocks removing that product from the release; likewise any row for client+product blocks unlinking.
  This is what the composite FKs enforce; the service pre-check counts all rows. Copy: "Can't remove:
  installs are recorded for this product on this release." The fix for a wrong product is to void its
  installs and leave the product on the release.
- **D-15-16:** D-15-05 confirmed: a ROLLED_BACK row does not change what a client runs; going back to an
  older release is recorded as a SUCCESS install of that release. The record dialog shows a one-line hint
  under the ROLLED_BACK outcome saying so.

### Existing releases and required products (2026-10-21, user request during execute)
- **D-15-17:** V14 backfills products for existing releases: one product per distinct non-null
  `release.jira_project_key`, named exactly the key (e.g. live data today: one release "Release 4.3",
  project CNV -> product "CNV"), and a `release_product` row linking each existing release to its project's
  product. Existing releases with a NULL `jira_project_key` (none live today) go to a single product named
  "Default", created only if such releases exist. The user renames products on the Portfolio page later.
  The backfill is pure SQL in V14 (no Java migration), idempotent by construction (runs once), and must not
  bump `items_changed_at` or touch promotions/documents. V14PortfolioMigrationIT asserts the backfill on the
  v1.1 snapshot (including a NULL-key release and two releases sharing a key).
- **D-15-18:** Products are required: creating a release requires at least one active product (server
  rejects an empty list with a dedicated reason; the create form's picker is required and, when no active
  products exist, says "Add a product on the Portfolio page first." with a link). The last product of a
  release cannot be removed (server rejects an empty product set with a dedicated reason; the editor keeps
  the last checked product locked with copy "A release needs at least one product."). Existing tests and
  fixtures that create releases without products must be updated to pass a product.

### Claude's Discretion
- Template placeholder shape for PORT-08 (e.g. `release.products` as a list of `{name}` in `ReleaseView`,
  additive, still within the safe-template allow-list rules).
- Name uniqueness (case-insensitive unique product names and client names), length limits, sort orders.
- Endpoint paths, DTO shapes, row-lock discipline (copy `PromotionService.appendUnderLock`).
- Whether a client-product link can be added to an archived product (keep consistent with D-15-07).
- Audit-trail entries for create/rename/archive/link/install, following the existing audit pattern.

</decisions>
