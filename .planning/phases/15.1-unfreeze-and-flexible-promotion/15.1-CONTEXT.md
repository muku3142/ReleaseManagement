# Phase 15.1: Unfreeze and Flexible Promotion - Context

**Gathered:** 2026-10-22 (captured directly in conversation, not via /gsd-discuss-phase)
**Status:** Ready for research and planning

<domain>
## Phase Boundary

The phase adds two changes to the release lifecycle:
- A frozen release that has not been deployed anywhere can be reopened so its tickets can change.
- A promotion can jump straight to any later stage of the ladder.

Not in scope:
- editing tickets on a frozen release without unfreezing it;
- unfreezing a deployed release;
- promoting to an earlier stage;
- changing the ladder editor (Settings).

</domain>

<decisions>
## Implementation Decisions

- **D-15.1-01:** Tickets change through **Unfreeze, then edit, then Freeze again**. An "Unfreeze" action returns a FROZEN release to OPEN, so tickets can be added or removed with the existing OPEN flows. Freezing again stamps a **new** `frozen_at`. A frozen release still never accepts ticket changes directly.
- **D-15.1-02:** Unfreeze is allowed **only while the release has no promotion entries and no client install records**. Every entry counts, including FAILED, VOIDED and superseded ones, consistent with D-15-15's "any ledger row" rule. Otherwise the server rejects it with a reason code the UI shows. This keeps promotion and install history truthful, because both are tied to the frozen ticket set. Requires D-07-06 to stay: only frozen releases are promoted.
- **D-15.1-03:** A promotion may target **any later active stage**, skipping stages (e.g. DEV straight to PROD), or redeploy the current stage. Promoting to an **earlier** stage is still rejected; ROLLED_BACK remains the way back. This **reverses D-07-07** ("target must be the next stage"). No reason field is required for a skip.
- **D-15.1-04:** Changing an existing release's tickets makes its documents stale. Refrozen releases behave like any other frozen release afterwards. Documents generated while OPEN, or before the unfreeze, are stale relative to the new ticket set until regenerated. Research must check how the D-05-09 "frozen never stale" rule interacts with a refreeze.

### Decided after research (2026-10-22)
- **D-15.1-05:** The document staleness rule changes for **all** frozen releases, with no migration. A frozen release's document is out of date if it was generated before `lastRefreshedAt`, or before `itemsChangedAt` when `itemsChangedAt` is not after `frozenAt`. Product edits after freezing still never mark documents stale, which preserves D-15-02's intent. This revises D-05-09 ("frozen never stale") and D-15-02 Option A. The user accepted the side effect: a few existing frozen releases whose documents predate their last open-time change turn amber. The `reopened_at` migration alternative was rejected. Unfreeze itself does not bump `items_changed_at`, so an unfreeze and refreeze with no edit leaves documents green. Phase 16's planned tooltip "frozen releases never go stale" must change accordingly (16-06 already has a conditional for this).
- **D-15.1-06:** Rename `PROMOTION_STAGE_SKIPPED` to **`PROMOTION_STAGE_EARLIER`**. The new copy covers "earlier stage" and "rollback must target the current stage". Update the enum, `GlobalExceptionHandler`, `frontend/src/api/auth.ts`, `PromotionControllerTest` and `PromotionHistoryTest`.

### Claude's Discretion
- Where the Unfreeze button sits on release detail, and its confirmation copy.
- Whether unfreeze/refreeze events are recorded (no audit table exists; Phase 15 recorded none for product/client edits).
- How the correction replay (D-07-14/15) and the Phase 8 metrics adapt to stage skips. "Created to frozen" uses the latest `frozen_at`. Research decides whether the original first freeze also matters.

</decisions>

<code_context>
## Existing Code Insights

- `PromotionRejection.PROMOTION_STAGE_SKIPPED` is raised in two places in `PromotionHistory` (record and correction replay). Both need the new "any later stage" rule.
- The deployed-at lower bound is `frozenAt` (L112). After a refreeze, it is the new `frozen_at`, which is safe because unfreeze requires no promotions.
- Phase 16 "behind" orders frozen releases by `frozen_at`, so a refreeze moves a release in that order (acceptable: it is undeployed and uninstalled).
