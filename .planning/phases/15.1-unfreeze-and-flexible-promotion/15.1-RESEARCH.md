## User Constraints (from CONTEXT.md)

### Locked Decisions
- **D-15.1-01:** Tickets change through **Unfreeze, then edit, then Freeze again**. An "Unfreeze" action returns a FROZEN release to OPEN, so tickets can be added or removed with the existing OPEN flows. Freezing again stamps a **new** `frozen_at`. A frozen release still never accepts ticket changes directly.
- **D-15.1-02:** Unfreeze is allowed **only while the release has no promotion entries and no client install records**. Every entry counts, including FAILED, VOIDED and superseded ones, consistent with D-15-15's "any ledger row" rule. Otherwise the server rejects it with a reason code the UI shows. This keeps promotion and install history truthful, because both are tied to the frozen ticket set. Requires D-07-06 to stay: only frozen releases are promoted.
- **D-15.1-03:** A promotion may target **any later active stage**, skipping stages (e.g. DEV straight to PROD), or redeploy the current stage. Promoting to an **earlier** stage is still rejected; ROLLED_BACK remains the way back. This **reverses D-07-07** ("target must be the next stage"). No reason field is required for a skip.
- **D-15.1-04:** Changing an existing release's tickets makes its documents stale. Refrozen releases behave like any other frozen release afterwards. Documents generated while OPEN, or before the unfreeze, are stale relative to the new ticket set until regenerated. Research must check how the D-05-09 "frozen never stale" rule interacts with a refreeze.

- How the correction replay (D-07-14/15) and the Phase 8 metrics adapt to stage skips. "Created to frozen" uses the latest `frozen_at`. Research decides whether the original first freeze also matters.

## Summary

The phase is a small, well-bounded change to three existing seams, and **no Flyway migration is needed**. `release.status` is a `CHECK IN ('OPEN','FROZEN')` and `frozen_at`/`frozen_by` are nullable (V3), so Unfreeze is a status flip plus nulling two columns. Both ledgers (`promotion`, `client_deployment`) already take `releaseJpa.findByIdForUpdate(releaseId)` before reading `frozen` and inserting, so an unfreeze that takes the same lock, counts rows under it, and flips status is race-free by construction. No new lock design is needed.

The promotion rule change is one predicate in `PromotionHistory.record` (`isNextOrCurrent` at L136, used at L82-84). Correction replay needs **no** change: `correct()` (L91-109) never applied sequence rules (D-07-14), so the CONTEXT claim that "PROMOTION_STAGE_SKIPPED is raised in correction replay" is inaccurate. The second occurrence at L131-133 is inside `checkRollback`, which `record` calls for ROLLED_BACK ("rollback of a non-current stage"), and it must stay.

The one non-obvious trap is documents. `DocumentReadinessService.state` returns UP_TO_DATE for any FROZEN release with a generated document, ignoring timestamps (D-05-09, re-affirmed by D-15-02 Option A). After unfreeze, edit, refreeze the release is FROZEN again, so old documents would show green even though the ticket set changed. That directly violates SC4/D-15.1-04. The FROZEN branch must start comparing timestamps. This reopens a decision D-15-02 explicitly made (it rejected "Option B" to avoid flipping existing frozen v1.1 releases), so one user confirmation is needed (A1) or a small migration (Option D).

**Primary recommendation:** Add `ReleaseService.unfreeze` / `ReleaseRepositoryAdapter.unfreeze` (lock, count both ledgers, flip, null `frozen_at/by`, publish `ReleaseIndexInvalidated`), relax `PromotionHistory.record` to `target.position >= currentPosition`, and make the FROZEN readiness branch stale-aware (ignoring post-freeze product bumps). No migration.

### Pattern 1: Unfreeze under the release lock (mirror of `freeze`)
**What:** Service pre-checks status on a snapshot (cheap, friendly 409); the adapter re-checks under `findByIdForUpdate` inside one transaction, exactly like `lockOpen` does for mutations (ReleaseRepositoryAdapter L319-329).
**Example:**
```java
// Source: pattern of ReleaseRepositoryAdapter.freeze (L251-261); new code
@Override
@Transactional
public Release unfreeze(UUID releaseId) {
    ReleaseEntity entity = jpa.findByIdForUpdate(releaseId).orElseThrow(ReleaseNotFoundException::new);
    if (entity.getStatus() != ReleaseStatus.FROZEN) {
        throw new UnfreezeRejectedException(UnfreezeRejection.UNFREEZE_RELEASE_NOT_FROZEN);
    }
    if (promotionJpa.existsByReleaseId(releaseId)) {
        throw new UnfreezeRejectedException(UnfreezeRejection.UNFREEZE_HAS_PROMOTIONS);
    }
    if (clientDeploymentJpa.existsByReleaseId(releaseId)) {
        throw new UnfreezeRejectedException(UnfreezeRejection.UNFREEZE_HAS_INSTALLS);
    }
    entity.setStatus(ReleaseStatus.OPEN);
    entity.setFrozenAt(null);
    entity.setFrozenBy(null);
    jpa.save(entity);
    publisher.publishEvent(new ReleaseIndexInvalidated(releaseId));
    return load(releaseId);
}
```
Why race-free: `PromotionRepositoryAdapter.appendUnderLock` (L40-48) and `ClientDeploymentRepositoryAdapter.appendUnderLock` (L45-55) both lock the same row *before* reading `frozen` and inserting. Either the insert commits first (unfreeze sees the row and rejects) or unfreeze commits first (insert sees OPEN and rejects with RELEASE_NOT_FROZEN / INSTALL_RELEASE_NOT_FROZEN). Existing reason codes already cover the loser of the race.

### Pattern 2: Relaxed stage rule in the domain record
**What:** Replace `isNextOrCurrent(target)` with "target is not before the current stage". Retired check already runs first (L77), so only active stages reach the predicate.
**Example:**
```java
// PromotionHistory.record, replacing L82-84 and L136-138
} else if (isBeforeCurrent(target)) {
    throw reject(PromotionRejection.PROMOTION_STAGE_EARLIER);
}

private boolean isBeforeCurrent(Stage target) {
    return currentStage().filter(current -> target.position() < current.position()).isPresent();
}
```
Semantics: no current stage -> any active stage (first entry may be PROD); current stage X -> X itself (redeploy) or any later active stage. Applies to SUCCESS and FAILED alike (existing test `failedFollowsTheSameSequenceRules` documents FAILED follows the same rule).
- `currentStage()` is the highest-position stage with a standing SUCCESS; with "never earlier" this equals the latest by time except where corrections created an inversion, which is acceptable (corrections bypass sequence rules, D-07-14).
- `nextStage()` stays: it feeds `PromotionHistoryResponse.nextStageId` (PromotionController L86), `ReleasesTool` (L98) and the dialog default. It becomes a "suggested default", not a rule.
- `checkRollback` (L124-134) is unchanged: rollback of a non-current stage remains rejected, rollback still needs a standing SUCCESS dated at or before it.

### Anti-Patterns to Avoid
- **Counting ledger rows from a separate read-only transaction before the lock.** The guard must be inside the locked transaction.
- **Counting only effective rows.** D-15.1-02 says every row including VOIDED/superseded; `existsByReleaseId` is correct, an "effective" filter would be wrong.
- **Re-deriving staleness client-side** (T-05-55). Keep the single comparison in `DocumentReadinessService`.
- **Adding a ticket-edit path for FROZEN releases.** `requireOpen`/`lockOpen` stay untouched.

## Findings by Investigation Area

### Release / freeze flow (Release.java, ReleaseService, ReleaseRepositoryAdapter)
- `Release.requireOpen()` throws `ReleaseFrozenException` (409 `RELEASE_FROZEN`). All of add/remove/refresh/refreshCodeLinks/freeze/delete/manual-item mutations call it in the service and `lockOpen` in the adapter. Unfreeze makes them all work again without touching them. [VERIFIED: ReleaseService.java, ReleaseRepositoryAdapter.java]
- `ReleaseService.freeze` does `get(id).requireOpen()` then `repository.freeze(id, actor, Instant.now())`; refreeze reuses it unchanged and stamps a new `frozen_at`/`frozen_by`.
- `ReleaseStatus` has only OPEN/FROZEN; no new status. Keep it that way (DB CHECK would otherwise need a migration).
- **frozen_at on unfreeze: set NULL (and frozen_by NULL).** Reasons: OPEN releases are created with null (`Release.create`); UI shows "Frozen by" only when frozen; dashboard `createdToFrozen` becomes null = "Not frozen yet" (DashboardService L108); `PromotionHistory` only reads `frozenAt` when `frozen` is true (record path rejects on `!frozen` first, L65), and `DashboardService` L77 constructs histories for OPEN releases with null already. No code NPEs on null for an OPEN release. [VERIFIED]
- **Original first freeze does not matter.** Consumers: dashboard created->frozen and frozen->production medians (use the final freeze, which is what the CONTEXT wants), `deployedAt >= frozenAt` bound (requires latest), Phase 16 ordering (latest). Nothing needs the first freeze, so no new column.
- A released that was unfrozen becomes OPEN and therefore deletable (D-03-11). That is acceptable: it has no promotions or installs, and the FK/CASCADE rationale in V14 ("only OPEN releases are deletable and installs need a FROZEN release") still holds because the guard forbids unfreezing with any install row.
- Products stay editable on both states (D-15-01); unfreeze does not interact.

### Promotion ledger (PromotionHistory)
- `record`: frozen check L65; deployedAt bound L111-115 uses `frozenAt` (non-null whenever frozen; after refreeze it is the new value, safe because no entries can exist); retired target L77; sequence L80-84; rollback L124-134.
- `correct`: field checks only. No change needed for skips (SC4 "correction replay accepts stage skips" is already true). Planner should add a regression test proving a correction to/from a skipped stage is accepted, not a code change.
- Retired stages: `nextStage()` skips retired stages; the new rule never targets a retired stage (retired check precedes). If the *current* stage later became retired, redeploy to it is rejected by PROMOTION_TARGET_RETIRED (existing behaviour), later active stages remain valid.
- Reason code: `PROMOTION_STAGE_SKIPPED` now means the opposite. **Recommendation: rename the constant to `PROMOTION_STAGE_EARLIER`** and update (a) `GlobalExceptionHandler` L182-184 message, (b) `frontend/src/api/auth.ts` L102, (c) `PromotionControllerTest` L172, (d) `PromotionHistoryTest` L180/187/195/245. The same code is still used by `checkRollback` for "rollback must target the current stage", so the copy must cover both: "A promotion can target the current stage or a later one. To go back, record a rollback on the current stage." Keeping the old name would ship a misleading code; the rename is mechanical.
- Tests asserting rejection that must be rewritten: `firstEntryMustTargetTheFirstStage`, `skippingAStageIsRejectedNextAndRedeployAreAccepted`, `failedFollowsTheSameSequenceRules` (they currently assert skip rejections). New cases: first entry to PROD accepted; DEV->PROD accepted; PROD current then DEV rejected (EARLIER); redeploy current accepted; skip then ROLLED_BACK PROD returns current to DEV; retired middle stage skipped over; FAILED to a later stage accepted.

### Unfreeze guard: which repos answer it
- Promotions: `PromotionJpaRepository` (table `promotion`, FK to release `ON DELETE RESTRICT`). Install rows: `ClientDeploymentJpaRepository` (table `client_deployment` per V14, FK `ON DELETE RESTRICT`). Both currently expose only `findByReleaseIdOrderByRecordedAtAsc`; add `boolean existsByReleaseId(UUID releaseId)` to each (Spring Data derived query, no `@Query` needed). [VERIFIED: repository files]
- Reason codes (409 each; ProblemDetail via `problem(HttpStatus.CONFLICT, ...)`):
  - `UNFREEZE_RELEASE_NOT_FROZEN` ("Only a frozen release can be unfrozen.")
  - `UNFREEZE_HAS_PROMOTIONS` ("Can't unfreeze: promotions are recorded for this release.")
  - `UNFREEZE_HAS_INSTALLS` ("Can't unfreeze: installs are recorded for this release.")
  Two ledger codes (not one) because the remedy differs (void/correct promotion vs install). Check order: promotions first, then installs. If both exist, the first match is reported; acceptable.
- Frontend: add all three to the reason map in `frontend/src/api/auth.ts` next to `RELEASE_FROZEN` (L80) and `RELEASE_NOT_FROZEN` (L101); `messageForReason` is the single lookup.
- Voiding does not unblock unfreeze (D-15.1-02: any row counts). The UI copy should say "history is permanent; create a new release" for the blocked case.

### Documents (D-05-09 interaction) -- the key trap
- `DocumentReadinessService.state` (L38-62): no template -> NO_TEMPLATE; not generated -> NOT_GENERATED; **FROZEN -> UP_TO_DATE unconditionally**; else compares `lastRefreshedAt` and `itemsChangedAt` to `generatedAt`.
- OPEN-side stamping already works for edits: `addItems`, `removeItem`, `replaceItemSnapshots`, manual-item add/update/remove, and meaningful `saveEnrichment` all call `stampItemsChanged` (ReleaseRepositoryAdapter). So after unfreeze, an edit makes the release show STALE while OPEN. The break happens at **refreeze**: status returns to FROZEN and the unconditional branch hides the staleness.
- Product edits on FROZEN releases also bump `items_changed_at` (`ReleaseProductRepositoryAdapter.replace` L87-90) but D-15-02 Option A deliberately keeps them invisible to readiness on FROZEN releases. Any new rule must preserve that.
- `DocumentSnapshot` stores post-Mustache markdown plus `templateBody`/chrome and `generatedAt`; it holds **no reference to the ticket set** that produced it, and AI revisions carry the source's `stalenessBasis`. Old revisions simply remain as history; "stale" is purely a timestamp comparison. Regenerating creates a new revision. No snapshot migration or invalidation is needed. [VERIFIED: DocumentSnapshot.java, DocumentReadinessService.all]
- **Recommended rule (Option B-restricted, no migration):** in the FROZEN branch, return STALE if `generatedAt` is before `lastRefreshedAt`, or before `itemsChangedAt` **when `itemsChangedAt` is not after `frozenAt`** (a post-freeze product bump is ignored per D-15-02). Needs `frozenAt` passed to `state(...)`; the only production caller path is `all()` where `ReleaseSummary` already carries `frozenAt` (and `DocumentsTool` consumes `ReadinessEntry`). Signature change touches `DocumentReadinessServiceTest` (L73-75 and L161-163 assert the old "frozen is always up to date" behaviour and must be rewritten).
- **Side effect to confirm (A1):** an existing frozen release whose document was generated *before* its last OPEN-time change and was frozen without regenerating will flip from green to amber. That doc genuinely lacks the change, but D-15-02 rejected exactly this flip for v1.1 releases. If the user does not accept it, **Option D**: add `release.reopened_at TIMESTAMPTZ NULL` (set at unfreeze, never cleared), keep the unconditional UP_TO_DATE for releases with `reopened_at IS NULL`, and use the stale-aware comparison only when it is set. That needs a Flyway migration (see Flyway section) and an extra `ReleaseSummary`/entity field.
- UI copy to fix: `ReadinessPill.tsx` comment, `DocumentsSection.tsx` comment ("Renders identically for OPEN and FROZEN"), and Phase 16 plans (16-CONTEXT L56) planning a tooltip "frozen releases never go stale (D-05-09)" -- that statement becomes false and must be changed in Phase 16's plans.

## Common Pitfalls

### Pitfall 1: Refrozen documents stay green
**What goes wrong:** Unfreeze, edit tickets, refreeze: readiness reports UP_TO_DATE because FROZEN short-circuits.
**Why it happens:** D-05-09 assumed a frozen ticket set can never change.
**How to avoid:** Make the FROZEN branch compare timestamps (A1/Option D); update the two `DocumentReadinessServiceTest` cases.
**Warning signs:** a test that unfreezes, adds a ticket, refreezes and asserts STALE fails.

### Pitfall 2: Guard outside the lock
**What goes wrong:** A promotion or install commits between the guard and the flip, leaving an OPEN release with ledger rows (and a later promote then fails; history references an unfrozen ticket set).
**How to avoid:** Count inside the locked adapter transaction only. Add an IT that holds the lock (or interleaves) as `PromotionPersistenceIT` does for freeze.

### Pitfall 3: Old reason code with new meaning
**What goes wrong:** `PROMOTION_STAGE_SKIPPED` copy says "next stage only" or the name contradicts the rule.
**How to avoid:** Rename to `PROMOTION_STAGE_EARLIER` in enum, handler, `auth.ts`, tests; keep rollback-non-current mapped to it with combined copy.

### Pitfall 4: Dropping the post-freeze product exemption
**What goes wrong:** Naively comparing `itemsChangedAt` on FROZEN releases makes product tagging (D-15-01) stale documents, contradicting D-15-02.
**How to avoid:** Only count `itemsChangedAt <= frozenAt` (or use Option D's `reopened_at`).

### Pitfall 5: Forgetting to clear `frozen_by`/`frozen_at`
**What goes wrong:** An OPEN release still shows "Frozen by X on Y" or sorts into Phase 16's frozen list.
**How to avoid:** Null both; assert in the persistence IT and the controller test (`frozenAt` null in JSON).

### Pitfall 6: Skipped stage and FAILED semantics
**What goes wrong:** Treating FAILED to a later stage as invalid, or allowing a FAILED to an earlier stage once a later stage succeeded.
**How to avoid:** Same predicate for SUCCESS and FAILED; FAILED never changes `currentStage()` (standing success only).

### Pitfall 7: Environment landmines (from project memory)
`JAVA_HOME` must be set per Maven call; Vite vs `npm ci` EPERM; CRLF from worktrees; incremental compilation can mask stale classes. Planner verification steps should use clean builds for the touched modules.

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Rewriting deployed history by unfreeze + edit | Tampering | Reject when any promotion/install row exists, under the same lock the ledgers use; FK `ON DELETE RESTRICT` as backstop |
| Race: promote/install concurrent with unfreeze | Tampering | Single row lock (`findByIdForUpdate`); loser gets existing 409 reasons |
| Unfreeze without trace | Repudiation | INFO log with actor (A4); persisted audit deferred (no audit table) |

| Stage id from client | Tampering | Server resolves via `findStage` (unknown -> StageNotFound); retired check retained |
