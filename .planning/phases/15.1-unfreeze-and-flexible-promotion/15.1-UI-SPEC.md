# Phase 15.1 — UI Design Contract: Unfreeze and Flexible Promotion

> Small delta on existing screens. Baseline: `15-UI-SPEC.md` (approved). No new dependency, no new type size, no new colour, no new component, no new route. Decisions D-15.1-01..04 in `15.1-CONTEXT.md` are locked and not reopened. Three touch points: (1) "Unfreeze" action on `ReleaseDetailRoute`, (2) what changes on screen after unfreeze and refreeze, (3) the Target stage picker in `RecordPromotionDialog`.

## Color

No new colour.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `gray-50` canvas, `white` panels | unchanged |
| Secondary (30%) | `white` cards `border-gray-200`; `gray-100` frozen banner | unchanged |
| Accent (10%) | `blue-600` | see list |
| Destructive | `red-600` | not used by this phase (unfreeze is reversible, see below) |

Accent (`blue-600`) reserved for: (1) the existing filled "Freeze release" button, which is the single filled button in the OPEN header row; (2) the blue confirm button of the Unfreeze `ConfirmDialog`; (3) focus rings `focus-visible:ring-2 focus-visible:ring-blue-600` on the new button; (4) the existing "Record promotion" filled button. **The "Unfreeze" button itself is gray-bordered, not accent-filled**: `rounded border border-gray-300 px-4 py-2 text-sm text-gray-700 disabled:opacity-50`. A FROZEN release has no other filled button in its header, but "Record promotion" below is the primary action, so Unfreeze must not compete with it.

Unfreeze is not destructive-styled: it deletes nothing, is only allowed when no history exists, and Freeze undoes it. Confirm button is blue, like Archive in Phase 15.

## Screen: Release detail, FROZEN state (`ReleaseDetailRoute`)

Current layout: header block holds meta line, `ProductsEditor`, the OPEN-only action row (`isOpen && ...`), `actionProblem`, and the FROZEN-only grey banner (`isFrozen && "This release is frozen..."`).

### Unfreeze action placement (discretion, decided)

Place the **"Unfreeze"** button in the header block of a FROZEN release, in a `mt-4 flex flex-wrap items-center gap-3` row located directly **above** the grey frozen banner (same row pattern and same position slot the OPEN action row uses, so the action lives in the same place in both states). Order inside the block, top to bottom:

```
meta line (Frozen by ... on ...)
ProductsEditor
[FROZEN only] action row: Unfreeze button (+ pending spinner)
[FROZEN only] blocked-reason helper line (only when Unfreeze is blocked)
actionProblem (role="alert")
frozen banner
```

Not placed in the Promotion section: unfreeze changes the ticket set, which belongs to the release header, not to the ledger.

### Enabled and blocked states

The server decides; the UI never recomputes the rule (consistent with 15-UI-SPEC assumption 7). The release payload must expose `unfreezeBlockedReason: null | 'HAS_PROMOTIONS' | 'HAS_INSTALLS'` (planner owns the exact field name; if the API only returns the rule on rejection, the UI falls back to the rejection path below). `HAS_PROMOTIONS` wins when both apply.

| State | Button | Helper line under the row |
|-------|--------|---------------------------|
| FROZEN, `unfreezeBlockedReason` null | enabled | none |
| FROZEN, `HAS_PROMOTIONS` | `aria-disabled="true"` + `opacity-50 cursor-not-allowed`, stays in Tab order, click does nothing | Small `text-xs text-amber-700`: **"Can't unfreeze: this release has promotion history. Create a new release to change scope."** |
| FROZEN, `HAS_INSTALLS` | same as above | **"Can't unfreeze: client installs are recorded for this release. Create a new release to change scope."** |
| mutation pending | `disabled` (existing `busy` rule) with spinner + **"Unfreezing…"** beside it | none |
| OPEN | button not rendered | none |

Blocked button uses `aria-disabled` plus `aria-describedby` pointing at the always-visible helper line (not `disabled`, not hover-only), same pattern as 15-UI-SPEC "Blocked actions". Helper line `id="unfreeze-blocked-reason"`. Voided, failed and superseded entries still count, so the copy says "history", not "successful".

Rejection fallback: if the server rejects (stale page, a promotion was recorded in another tab), the existing `actionProblem` paragraph (`role="alert"`, `data-reason`, `text-sm text-red-600`, via `messageForReason`) shows the server reason. Required `messageForReason` entries: `RELEASE_UNFREEZE_HAS_PROMOTIONS` -> **"Can't unfreeze: this release has promotion history. Create a new release to change scope."**, `RELEASE_UNFREEZE_HAS_INSTALLS` -> **"Can't unfreeze: client installs are recorded for this release. Create a new release to change scope."**, `RELEASE_NOT_FROZEN` -> **"This release is already open."** (reason code names are placeholders; planner aligns to the server's `PromotionRejection`/release rejection enum). After any rejection the release query is invalidated so the button reflects the new state.

### Unfreeze confirmation dialog

Existing `ConfirmDialog`, same props as the Freeze one.

- Title: **"Unfreeze {name} {version}?"**
- Body: **"Unfreezing reopens this release so you can add, remove, or refresh tickets. Nothing has been deployed or installed, so no history is affected. Documents generated so far will be marked out of date until you regenerate them. Freeze the release again when the ticket set is final."**
- Confirm label: **"Unfreeze release"**; confirm class `rounded bg-blue-600 px-4 py-2 text-sm font-semibold text-white disabled:opacity-50`; cancel **"Cancel"** (existing).
- `pending={unfreeze.isPending}`; `onConfirm` uses `onSettled` to close, with the same comment rationale as Freeze (inert backdrop hides `actionProblem`).
- No required reason field (no audit table; discretion decision: unfreeze and refreeze are **not recorded** as events, matching Phase 15's treatment of product/client edits).

### Freeze dialog copy change (required)

The existing Freeze body says "there is no way to unfreeze". That is now false. Replace the body with:

**"Freezing locks the ticket set and manual items exactly as they are now. You cannot add, remove, or refresh items while it is frozen. You can unfreeze it again until a promotion or client install is recorded; after that, create a new release if scope changes."**

Also replace the grey FROZEN banner text with (still `rounded bg-gray-100 p-3 text-sm text-gray-700`):

**"This release is frozen. Its ticket set is locked. Unfreeze it to change tickets, if nothing has been deployed or installed yet."** when `unfreezeBlockedReason` is null; and **"This release is frozen. Its ticket set is locked and cannot be changed."** when blocked (unchanged copy, so the blocked case does not suggest an option that is not available).

## Screen: after unfreeze and after refreeze

### After Unfreeze succeeds

- Release status badge flips to OPEN; `Frozen by ... on ...` meta line disappears (`frozenAt` is cleared to null in the UI since status is OPEN); the OPEN action row (Add tickets, Refresh from Jira, Refresh code links, Freeze release, Delete release) and the existing OPEN ticket editing flows appear. The Unfreeze button and its helper line disappear. No new components.
- Mutation invalidates: the release, release list, promotions, installs, documents readiness and dashboard queries (the same set Freeze invalidates, plus documents readiness for the staleness note).
- Polite status announcement (existing page-level live region): **"{name} {version} unfrozen. Tickets can be edited."**
- Focus moves to the "Add tickets" button (first control of the newly rendered OPEN row), since the Unfreeze button is removed from the DOM.
- `PromotionSection` follows its existing `isFrozen` rule: shows **"Freeze this release to record promotions."**; history area is empty by definition. `ClientInstallsSection` shows its existing OPEN copy **"Freeze this release to record client installs."**
- `DocumentsSection`: unchanged rendering; it displays whatever readiness the server returns. Per D-15.1-04 the server reports STALE for documents generated before the unfreeze, so the existing STALE pill and its existing "regenerate" affordance appear. No new document UI.

### While OPEN again (after an unfreeze)

Add one note in the header block, only when the release was frozen before and is now OPEN and has at least one generated document (derive from the server: `documents readiness` has any STALE; the UI does not compute staleness): Small `text-xs text-amber-700`, placed under the OPEN action row (`mt-2`):

**"This release was unfrozen. Its existing documents are out of date and will need regenerating after you freeze it again."**

This is the same note slot and Small amber style as the Phase 15 products-editor staleness note, so only one note style exists for "documents stale because inputs changed". If the server reports no stale documents (nothing was generated), the note is not shown.

### After refreeze

- Freezing again is the existing Freeze flow and dialog (updated copy above). The meta line shows **"Frozen by {user} on {new frozenAt}"** (new timestamp; the previous freeze time is not shown, discretion decision: only the latest `frozen_at` is displayed).
- Documents: the grey-pill state is whatever the server returns. Contract: documents generated before the unfreeze remain visible in `DocumentsSection` as **STALE** (existing pill) until regenerated; after refreeze the Generate action regenerates against the new ticket set and the document returns to UP_TO_DATE via the existing flow. Frozen "never stale" (D-05-09) applies to documents generated while frozen; the UI must not hide or override a server STALE state on a FROZEN release. The planner/research must confirm the server returns STALE in this case; the UI contract is only "render the server state".
- Because the stale pill can now appear on a FROZEN release, the existing `DocumentsSection` STALE copy (line 141) must not say anything like "release changed while open" that is wrong for frozen releases. If it does, reword to the neutral **"Tickets changed after this document was generated. Regenerate it to include the change."**
- Polite announcement on freeze success is unchanged.

## Screen: Record promotion dialog, Target stage picker (`RecordPromotionDialog`)

Today the select lists every stage; retired stages are `disabled` and suffixed " (retired)". New behaviour for **record mode** (not correct mode):

Let `current` = the stage whose id is `history.currentStageId` (may be none), and order = the ladder order of `history.stages`.

| Option | Offered? | Notes |
|--------|----------|-------|
| Stages after `current` in ladder order, active (not retired) | yes | Skipping allowed (D-15.1-03) |
| `current` itself | yes | Label suffix ` (redeploy)` |
| Stages before `current` | **no, not rendered** | Earlier stages are not offered at all, not merely disabled; ROLLED_BACK is the way back |
| Retired stages | not rendered in record mode | Retired stages cannot be promoted to; rendering them disabled adds noise now that the list is filtered. (Exception: if `current` is itself retired it is rendered, disabled, suffixed ` (retired)` and cannot be chosen; the server still rejects if it is submitted.) |
| No `current` (not deployed yet) | all active stages offered | First promotion may target any stage |

Option labels: `{stage.name}` for later stages; `{stage.name} (redeploy)` for the current stage. Option order is ladder order. No grouping, no helper text per option.

Defaults (unchanged behaviour, per `defaultStageId`): SUCCESS and FAILED preselect the **next** stage (`nextStageId`), falling back to current when the ladder is at the last stage; ROLLED_BACK preselects the **current** stage. The user may pick any later stage instead. Skipping requires no reason and shows no warning (D-15.1-03).

Helper line under the select (Small `text-xs text-gray-600`, `mt-1`, `id="promotionStageHelp"`, linked by `aria-describedby` on the select), shown in record mode when `current` exists:

- **"Choose the next stage or skip ahead. Pick {current name} to record a redeploy. Earlier stages aren't offered; record a rollback instead."**

When the user selects a stage that skips at least one active stage after `current` (compare selected index with `nextStageId`'s index in the already-loaded `history.stages`; pure presentation of ladder order, not business logic), append a second Small neutral line (`text-xs text-gray-600`, `role="status"` so it is announced): **"This skips {n} stage(s): {names}."** Neutral grey, not a warning, because skipping is allowed and needs no justification. Names are joined with ", ", capped at 3 then "and {n} more".

Last stage reached and nothing later: the list contains only `current` ("(redeploy)"), helper line still shown.

All stages retired after `current` and `current` retired: select is empty; the submit button stays disabled via the existing `stageId === ''` rule, and Small red `text-sm text-red-600` shows **"No active stage is available to promote to. Add or restore a stage in Settings."** (defensive; edge case).

**Correct mode** is unchanged: the full stage list with retired stages disabled (the correction replay on the server validates the new ladder rule; the UI does not pre-filter, because a correction can move an entry to a stage that is only valid relative to its neighbours). Server rejection renders through the existing error paragraph.

Error copy: `PROMOTION_STAGE_SKIPPED` is now reused only for earlier-stage targets (D-15.1-03 reverses D-07-07). Update its `messageForReason` entry to: **"Can't promote to an earlier stage. Choose {current name} or a later stage, or record a rollback."** (If the code is renamed server-side, same copy under the new code.) Defensive only, since the picker no longer offers earlier stages.

Dialog width, fields, buttons and other copy are unchanged ("Record promotion" title and button, "Cancel").

`LadderDots` is unchanged. A skipped stage simply has no entry; it renders as not reached, exactly as an unvisited stage does today.

## Interaction and Accessibility

- **Blocked Unfreeze** uses `aria-disabled="true"` + `aria-describedby` to the always-visible helper line; click handler is a no-op. Not hover-only, not colour-only (the text states the reason).
- **Button accessible name:** the visible text is "Unfreeze"; add `aria-label="Unfreeze {name} {version}"` only if two such buttons could exist on one page (they cannot, so visible text is the name; no aria-label).
- **Dialog:** native `<dialog>` via `ConfirmDialog` (focus trap, Escape cancels). On confirm success focus goes to "Add tickets" (button removed from DOM otherwise). On cancel, focus returns to the Unfreeze button.
- **Stage select:** `aria-describedby="promotionStageHelp"`; the skip note is `role="status"` so a change of selection is announced once. Option text carries "(redeploy)" so the meaning does not depend on position.
- **Live region:** reuse the page-level `role="status" aria-live="polite" aria-atomic="true"`.
- **Pending / double-submit:** Unfreeze and Freeze share the existing `busy` flag; all header buttons disable while any mutation is pending.
- **Plain-text safety:** release name, version, stage names render as React text children only.
- **Reduced motion:** spinner has `motion-reduce:animate-none`; label text always shown.
- **Contrast:** `amber-700` on white/`gray-100` and `red-600` on white meet 4.5:1; essential text is `gray-600` or darker.
- **Responsive:** header action row uses `flex-wrap`; no layout change.

## Assumptions recorded (not settled by CONTEXT)

1. The API supplies `unfreezeBlockedReason` (or equivalent) on the release payload so the disabled state and its reason render without a failed request; if not, the button is enabled and the rejection copy above is the fallback.
2. The server marks pre-unfreeze documents STALE and keeps that state after refreeze until regenerated; the UI renders the server state only (T-05-55 rule: never re-derive staleness client-side).
3. The "was unfrozen" note appears only while OPEN and only when the server reports at least one STALE document; it is not persisted client-side (no `localStorage`).
4. The picker uses ladder order from `history.stages` and `history.currentStageId` already in the dialog props; no new endpoint. The server remains the authority and still rejects an earlier-stage target.
5. Correct mode keeps its full stage list (server replay validates).
6. Unfreeze/refreeze are not logged as visible events; only the latest `frozen_at` is displayed.
7. Reason code names in the copy table are placeholders for the planner to align with the server enum.
