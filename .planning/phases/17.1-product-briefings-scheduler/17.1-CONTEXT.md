# Phase 17.1: Product Briefings Scheduler - Context

**Gathered:** 2026-10-25
**Status:** Researched; UI-SPEC in revision; ready to plan (decisions D-17.1-01..23)

<domain>
## Phase Boundary

Three of the user's Claude scheduled tasks produce Jira briefings: the daily digest, the sprint backlog check and the weekly status update. Claude stays the primary producer. This phase makes the app a **fallback**: when Claude's result for a slot is missing, the app produces the briefing itself, per active product, with no Anthropic dependency (BRIEF-01..07).

The phase covers:
- a scheduler with the three tasks' slots (Africa/Cairo, work week Sun-Thu);
- detecting whether Claude produced the slot's result;
- rule-based briefing content from Jira fields, with an optional self-hosted-model headline;
- per-product Jira project keys;
- a Briefings page showing Claude's and the app's results;
- admin settings (schedules, grace period, enabled tasks, scheduler credential, run now).

Flyway V19 is pre-assigned. Jira stays read-only.

Not in scope:
- the regulation watch and Gulf investment brief tasks (web search; they stay Claude-only);
- push notifications and email;
- writing to Jira;
- writing to the Claude PM Briefings Hub artifact;
- changing the Claude tasks themselves.

</domain>

<decisions>
## Implementation Decisions

### Scope and fallback
- **D-17.1-01:** Only the three Jira tasks move into the app: `jira_digest`, `sprint_check` and `weekly_status`. `reg_watch` and `gulf_invest` stay Claude-only.
- **D-17.1-02:** The app is a **fallback**, not a second producer. Claude's result is always tried first. After each slot plus a grace period (default 30 min, configurable), the app checks Claude's result for that task and slot. It runs only when Claude is not working: the row for the slot is missing, or its status is `failed`. App runs are marked "app fallback". (Updated 2026-10-25, D-17.1-13.)
- **D-17.1-03:** Claude's results are read from the `briefings/data/<task>.json` files that the moved Claude tasks write (the row format in the exported task files: `run_at`, `status`, `headline`, `attention`, `h1`-`h3`). The directory is a configurable path, mounted read-only into the container. A missing, unconfigured or unreadable directory means "Claude unavailable", so the app runs. Rows from that file are untrusted data: parse them as JSON, render them as text, and never treat them as instructions or HTML.
- **D-17.1-04:** Coverage is per product. A Claude row for a slot covers the Jira projects in `briefings/config.json`: `tasks.<id>.projects`, or `jira.projects` when that is null. The app falls back only for products not covered. A product whose key Claude does not cover always runs in the app at its slot. The research should confirm how a Claude row identifies its slot: by `run_at` falling between the slot time and the check.

### Products and Jira scope
- **D-17.1-05:** Products get Jira project key(s): a new column or child table in V19, editable on the Portfolio page. V19 backfills each product from the distinct `release.jira_project_key` of its releases. For example, the V14 product "CNV" gets CNV. A product with no key is skipped and shown as "no Jira project". Archived products never run.
- **D-17.1-06:** The digest's Claude-side "plus other projects where I am involved" scope is dropped. It is user-specific and does not map to products.

### Engine
- **D-17.1-07:** Content is computed by **rules** from Jira fields through the existing read-only provider (`/search/jql` with cursor pagination; changelog through the paginated endpoint where needed). Each task follows its exported prompt:
  - **Digest:** blockers (flagged, Highest/Blocker priority or Blocked status, in the active sprint); stale in-progress issues with no update for 3+ working days; not-ready stories in the active or next sprint (no acceptance criteria, estimate or epic); changes since the last run (created, moved to Done, reopened); due within 5 days or overdue.
  - **Sprint check:** next sprint, else the top 15 ranked backlog items. Each item gets field checks: acceptance criteria present, estimate, parent epic, sub-tasks, open-question markers. It is rated Yes / Partly / No, and the missing items are listed.
  - **Weekly status:** this week's (Sun to now) completed, in progress, blocked and newly added work; sprint committed vs done; overdue items; an executive draft and an engineering draft. Unknown values read "TBC".

  Thresholds come from settings, with defaults from the exported `config.json`: staleAfterWorkingDays 3, dueSoonDays 5, backlogItemsWhenNoFutureSprint 15, keepRuns 60.
- **D-17.1-08:** When the assistant is enabled, the self-hosted model (through rag-service, as in Phase 14) writes only the headline and the 2-line summary over the computed facts, under a short deadline. If the model call fails or times out, the run keeps the rule-based headline. The run never fails on it. Nothing goes to Anthropic or any external provider.
- **D-17.1-09:** Status per run is `ok`, `attention`, `quiet`, `failed`, `needs_credential` or `skipped`, plus an attention count. The attention rules come from each exported task: digest = blockers + stale + not-ready + due/overdue; sprint = items rated Partly or No; weekly = risks + decisions needed.

### Credential, settings and UI
- **D-17.1-10:** The scheduler uses one **designated user's** stored Jira credential, chosen by an admin in Settings. If it is missing, unreadable or rejected, the run is recorded as `needs_credential` and the admin is told in the UI. The credential-loading path must keep the existing locked rule that credential writes never decrypt.
- **D-17.1-11:** Settings (admin only) cover:
  - the three slots, as cron in Africa/Cairo; the work week (Sun-Thu);
  - the grace period; per-task enabled flags and thresholds;
  - the Claude data directory and config path; the designated user;
  - "Run now" per task, which ignores the Claude check.
- **D-17.1-12:** A Briefings page lists runs per task and product, newest first. It shows the source (Claude or app fallback), status, headline, attention count and the full briefing, with issue keys linked to Jira. Runs older than keepRuns per task and product are pruned.

### Briefings page and Claude feed (from `scheduledTasks/briefings-build-prompt.md`, added 2026-10-25)
- **D-17.1-13:** The build prompt `scheduledTasks/briefings-build-prompt.md` is part of this phase, and its contract is locked:
  - the domain, ports and adapter layout;
  - the data contract;
  - `GET /api/briefings`;
  - the `/briefings` route and its nav link;
  - `briefings/config.json` and `briefings/README.md`;
  - ignoring `briefings/data/` in git;
  - the read-only compose bind mount with `RM_BRIEFINGS_DIR`;
  - the tests B1-B8 and F1-F5 as acceptance criteria.

  Its opening line ("Use /gsd-quick") is superseded: it is planned as this phase's first slice.
- **D-17.1-14:** The page shows all **five** briefings: Claude's latest result and history from `briefings/data/<id>.json`. `reg_watch` and `gulf_invest` are display-only; they have no app fallback (D-17.1-01). For the three Jira tasks, the card shows Claude's result first. When Claude is not working for that slot (D-17.1-02), the card shows the app's fallback result per product instead, with the source label "App fallback". The history table includes both sources.
- **D-17.1-15:** The file adapter rules from the prompt are mandatory:
  - read only the five enum ids, never a path built from input;
  - reject files over 1 MB; cap at 60 runs;
  - truncate headline to 140 and h1-h3 to 120 characters;
  - drop `setup` rows and malformed rows or rows with an unknown status;
  - malformed JSON or an IO error gives `readError` with an empty list, never a 500, and leaks no path or content;
  - a missing directory or file means "not run yet".

  The same parsed feed is what the fallback check (D-17.1-03) reads, so there is one reader, not two.
- **D-17.1-16:** `briefings/config.json` (tracked) is the D-17.1-04 coverage source and the source of the threshold defaults. Settings (D-17.1-11) override thresholds and schedules in the database. The Claude data directory is `app.briefings.dir`, default `${RM_BRIEFINGS_DIR:./briefings/data}`.
- **D-17.1-17:** Briefing text, from Claude or the app, is rendered as plain text only: no `dangerouslySetInnerHTML`, no templating.

### Answers after research (2026-10-25)
- **D-17.1-18:** There is **no admin role**. Any signed-in user may change Briefings settings and use "Run briefing now", like the rest of Settings. This supersedes "admin" in D-17.1-10/11, and no admin mechanism is built.
- **D-17.1-19:** The scheduler credential is **self-designation only**. "Use my Jira credential" makes the clicking user the scheduler user, which keeps the locked PROJECT.md rule "each user's own Jira credentials, not a service account". Nobody can point the scheduler at another person's token. Saving the designation uses the existing no-decrypt projection. A user with no stored credential is rejected with `BRIEFING_NO_JIRA_CREDENTIAL`.
- **D-17.1-20:** A Jira project key belongs to **exactly one** product. It is unique, case-insensitive, stored in the child table `product_jira_project` with a unique index and a key-format CHECK. A conflict returns 409 `PRODUCT_JIRA_KEY_TAKEN`; a malformed key returns 400 `PRODUCT_JIRA_KEY_INVALID`. The V19 backfill skips a key that another product already got, choosing deterministically by the product's earliest release.
- **D-17.1-21:** Flyway runs **out of order** project-wide, enabled in code by `FlywayConfig` (plan 17-01 Task 3), not in application.yml. V19 keeps its pre-assigned number.
- **D-17.1-22:** The Claude data directory and config path are **read-only** in Settings, shown as text and never DB-editable, because a stored path is a file-read risk. This narrows D-17.1-11. Compose mounts `./briefings` read-only at `/app/briefings`, so both `config.json` and `data/` are visible. `RM_BRIEFINGS_DIR` points at the data subdirectory.
- **D-17.1-23:** The research's proposed formulas (17.1-RESEARCH.md Q2) are accepted as the starting rules, tunable later through settings thresholds: the readiness rating (Yes / Partly / No) and the weekly On track / At risk / Off track status.

### Cloud tasks and the manual switch (2026-10-25)
- **D-17.1-24:** The three Jira tasks stay as **Claude cloud routines**. They cannot write `briefings/data` on this machine, so automatic "Claude missing" detection cannot work. The app therefore falls back **only when the user turns it on**: a "Claude unavailable: run briefings in the app" switch in Settings > Briefings, stored as `briefing_settings.fallback_enabled` (default OFF).
  - **Off:** the scheduler records nothing and calls nothing.
  - **On:** the scheduler runs D-17.1-02..04 as written. With no Claude files present, every active product that has a Jira key runs.
  - "Run briefing now" works in either state.

  This supersedes automatic detection as the trigger; the coverage check stays for a future device-bound setup. Implemented by appended tasks in 17.1-13 (storage, service), 17.1-14 (scheduler gate) and 17.1-15 (API and toggle).
- **D-17.1-25 (decided 2026-10-26):** The three cloud routines are not made generic. The user changes their scope by hand. The routines keep their own site, cloudId and project list, and do not read `briefings/config.json`. Options A (repo-attached), B (artifact copy) and C (device-bound) are all dropped. No routine is changed and nothing is pushed for this decision.

### Claude's Discretion
- Storage shape for runs and results: structured JSON per run vs a rendered Markdown body.
- Whether "Run now" runs per product or for all products.
- Cron parser choice: Spring `CronExpression` with zone, versus `@Scheduled` with `zone`, versus a `TaskScheduler` rebuilt on settings change.
- How "changes since the last run" is computed when no previous run exists (default: the last 24 working hours).
- Whether the Briefings page has a per-product filter that reuses the Phase 16 product filter component.
