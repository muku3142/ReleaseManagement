### Locked Decisions

**Scope and fallback**
- **D-17.1-01:** Only the three Jira tasks move into the app: `jira_digest`, `sprint_check` and `weekly_status`. `reg_watch` and `gulf_invest` stay Claude-only.
- **D-17.1-02:** The app is a **fallback**, not a second producer. Claude's result is always tried first. After each slot plus a grace period (default 30 min, configurable), the app checks Claude's result for that task and slot. It runs only when Claude is not working: the row for the slot is missing, or its status is `failed`. App runs are marked "app fallback". (Updated 2026-10-25, D-17.1-13.)
- **D-17.1-03:** Claude's results are read from the `briefings/data/<task>.json` files that the moved Claude tasks write (the row format in the exported task files: `run_at`, `status`, `headline`, `attention`, `h1`-`h3`). ## Summary

The phase splits cleanly into a Claude-feed slice that touches no Jira and no database (the Briefings page plus the hardened file adapter, BRIEF-08), and an app-fallback slice (scheduler, rule engines, credential, settings, V19). The first slice is independently shippable and its reader is the same reader the fallback check uses (D-17.1-15), so it should expose a parsed-feed method (`runs(task)` returning `BriefingFeed`) rather than a controller-shaped API.

Five facts in the codebase change the plan most. (1) `@EnableScheduling` exists only inside `AssistantConfig`, which is conditional on `app.assistant.enabled=true` (`config/AssistantConfig.java:11,13`), so with the assistant off (the default in `application.yml`) nothing is scheduled; the briefings fallback must work with the assistant off, so scheduling must be enabled by a new unconditional config. (2) There is no admin role anywhere in `src/main` (grep for admin, ROLE_, hasRole, authorit returns nothing relevant); every authenticated user can already change the Jira site URL (`JiraSiteConfigController.java:28`). "Admin only" (D-17.1-11) therefore needs a new, explicit mechanism. (3) `JiraAccessContextService` is request-bound by design (`currentContext()` keys on the signed-in principal, `JiraAccessContextService.java:32`), and `FieldMetadataService` calls it internally (`FieldMetadataService.java:130`), so a background job needs a separate credential-loading service and an access-context-taking variant of field resolution. (4) `GlobalExceptionHandler` maps `INVALID_CREDENTIALS` to HTTP 401 and the frontend treats 401 as the signed-in user's own Jira session failing; a "Run now" request that lets the scheduler credential's rejection escape would log the admin out or show their credential alert. (5) V19 is pre-assigned and V15/V16/V17/V18 do not exist yet; Flyway is configured with defaults (no `out-of-order` in either `application.yml`), so as soon as V19 is applied on the live DB, adding a lower-numbered migration later makes startup validation fail.

The rule engines are computable with the existing `/search/jql` cursor path plus a handful of additional fields (priority, Flagged, Sprint, parent, subtasks, duedate, created, resolutiondate, acceptance criteria) and JQL sprint functions (`openSprints()`, `futureSprints()`, `ORDER BY Rank`). No new Agile endpoint is required. The Agile endpoints (`/rest/agile/1.0/board`, `/board/{id}/sprint`) are already used by `JiraProjectAdapter.java:145,187` and exclude future sprints, so they are the wrong tool for "next sprint" anyway.

**Primary recommendation:** Poll with a single `@Scheduled(fixedDelay)` tick that evaluates the latest due slot per task against database state (idempotent through a unique `(task, product, slot_at)` index), parse cron with `CronExpression` in Africa/Cairo, put the whole V19 schema in one migration written in the schema slice, enable `spring.flyway.out-of-order=true` in both yml files, and ship the Claude-feed Briefings page first.

### Pattern 1: Polling tick with DB idempotency
**What:** One `@Scheduled(fixedDelay)` method calls `tick(Instant now)`. Slot instants are computed, not triggered. A unique index on `(task, product_id, slot_at)` (partial, `WHERE slot_at IS NOT NULL`) makes re-evaluation and a second instance harmless.
**When to use:** Always for this phase; the schedule is database-editable and must survive restart.
**Example:**
```java
// Source: Spring Framework CronExpression API (docs.spring.io/spring-framework/reference/integration/scheduling.html)
// Latest slot at or before `cutoff`: CronExpression only has next(), so walk forward from a lookback.
Instant latestSlotAtOrBefore(CronExpression cron, ZoneId zone, Instant cutoff, Duration lookback) {
    ZonedDateTime t = cron.next(cutoff.minus(lookback).atZone(zone));
    ZonedDateTime last = null;
    while (t != null && !t.toInstant().isAfter(cutoff)) {
        last = t;
        t = cron.next(t);
    }
    return last == null ? null : last.toInstant();
}
```
Spring cron is six fields, seconds first: the exported Unix cron `44 8 * * 0-4` becomes `0 44 8 * * SUN-THU`. Validate on save with `CronExpression.isValidExpression` and reject schedules that fire more often than once a minute. [CITED: docs.spring.io/spring-framework CronExpression Javadoc; ASSUMED for the Spring 7 specifics, confirm with a unit test]

### Pattern 2: Run state in the database, not memory
Run rows double as the idempotency record. Write the row once, on completion (status known). A JVM crash mid-run leaves no row, so the next tick re-runs that slot, which is correct. An in-JVM `AtomicBoolean` guard stops overlapping ticks. A second app instance could duplicate Jira calls but not rows (unique index); single instance is the deployment (one `app` service in `compose.app.yaml`).

### Pattern 3: One Jira search client, two mappers
`JiraRestTicketAdapter.searchAll` couples cursor paging and the 400/401/403/429/5xx mapping to `TicketDetail` mapping. Extract a package-private `JiraSearchClient.search(access, jql, fieldIds, maxIssues)` returning `JsonNode` issues (paging, `nextPageToken` termination, max-pages guard, exception mapping), have `JiraRestTicketAdapter` delegate to it (existing `JiraRestTicketAdapterTest` is the safety net), and give `JiraBriefingAdapter` its own mapper to a neutral `BriefingIssue`. This avoids a fourth copy of the catch ladder (already duplicated in `JiraRestTicketAdapter`, `JiraProjectAdapter`, `JiraIssueHistoryAdapter`). Add the `maxIssues` limit parameter here (sprint check needs the top 15; `searchAll` fetches everything up to `max-pages` 50 x 100).

### Anti-Patterns to Avoid
- **`@Scheduled(cron=..., zone=...)` per task:** schedules cannot be edited at runtime, no catch-up.
- **Reusing `JiraAccessContextService`:** its Javadoc and design say the only lookup key is the signed-in principal (AUTH-02). Do not add an `accountId` overload to it; add a separate class so the boundary stays checkable by ArchUnit.
- **Caching the access context between runs:** the designated user can replace the token at any login; read it fresh per run.
- **Parsing Claude rows into prompts or logs:** the fallback check reads only `run_at` and `status`; text fields are display-only.
- **Throwing from "Run now":** record the outcome and return it (see Pitfall 3).
- **Moving or re-using `@EnableScheduling` in `AssistantConfig`:** leave the assistant gate intact; add a separate unconditional config.

## Common Pitfalls

### Pitfall 1: Scheduling silently off when the assistant is off
**What goes wrong:** the fallback never runs in the default configuration.
**Why:** `@EnableScheduling` is only on `AssistantConfig`, which is `@ConditionalOnProperty(app.assistant.enabled=true)` (`AssistantConfig.java:11,13`); default is `false` (`application.yml`).
**How to avoid:** new `BriefingsConfig` with `@EnableScheduling` and `@EnableConfigurationProperties(BriefingsProperties.class)`, unconditional. `AssistantSwitchOffIT` only asserts assistant beans are absent, so it stays green. Add an IT that the tick bean exists with the assistant off.
**Warning signs:** no `briefing_run` rows after a slot with the assistant off.

### Pitfall 2: Virtual-thread scheduler semantics
`spring.threads.virtual.enabled=true` (`application.yml`), so Boot auto-configures a `SimpleAsyncTaskScheduler` on virtual threads, and pool properties under `spring.task.scheduling` are ignored. [CITED: docs.spring.io/spring-boot/reference/features/task-execution-and-scheduling.html] `fixedDelay` still waits for completion, but keep the in-JVM guard anyway. Do not declare a `TaskScheduler` bean (the comment in `AssistantConfig.java:8` explains it would replace Boot's).

### Pitfall 3: "Run now" propagating a Jira 401
`GlobalExceptionHandler.handleJiraAuthFailure` maps `INVALID_CREDENTIALS` to HTTP 401 (`GlobalExceptionHandler.java:102`) and states the frontend treats 401 as the user's own session failing (comment at line 76). The scheduler's credential is a different user's. `BriefingRunner` must catch `JiraAuthenticationException` and `RuntimeException` from credential load and Jira calls and return a recorded `needs_credential` / `failed` run with HTTP 200 (or 202). Test it: stubbed 401 from Jira on run-now returns 200 with `needs_credential`, never 401.

### Pitfall 4: Absolute JQL datetimes use the searching user's time zone
`created >= "2026-10-25 08:00"` is interpreted in the Jira profile time zone of the authenticating user, which is unrelated to Africa/Cairo. ```java
// A Claude row covers `slot` when its run_at lies in [slot, slot + grace] and status is not failed.
// Rows before the slot cannot belong to it; rows after the check belong to the next evaluation.
boolean claudeCovered(List<BriefingRun> rows, Instant slot, Duration grace) {
    Instant until = slot.plus(grace);
    return rows.stream().anyMatch(r ->
            !r.runAt().isBefore(slot) && !r.runAt().isAfter(until) && r.status() != BriefingStatus.FAILED);
}

### Working-day math (Sun-Thu, Cairo)
```java
// Elapsed working days between `from` (exclusive date) and `today` (inclusive), counting only configured work days.
static int workingDaysElapsed(LocalDate from, LocalDate today, Set<DayOfWeek> workDays) {
    int n = 0;
    for (LocalDate d = from.plusDays(1); !d.isAfter(today); d = d.plusDays(1)) {
        if (workDays.contains(d.getDayOfWeek())) n++;
    }
    return n;   // stale when n >= staleAfterWorkingDays
}
```
Convert both instants with `atZone(ZoneId.of("Africa/Cairo")).toLocalDate()`. Week start for the weekly status: the most recent Sunday 00:00 in Cairo (`TemporalAdjusters.previousOrSame(DayOfWeek.SUNDAY)`), converted to an instant.

### Q4. Products and Jira project keys
- **Schema after V14:** `product(id uuid, name varchar(100), created_at, archived_at)` with unique `lower(name)`; `release_product(release_id, product_id)`; `release.jira_project_key varchar(64)` nullable (`V14__portfolio.sql`, `V3__release_assembly.sql:11`). Domain record `Product(id, name, archivedAt)`; `ProductRepository` has no keys today.
- **Recommendation: child table** `product_jira_project(product_id uuid references product on delete cascade, project_key varchar(20), primary key (product_id, project_key))` with `CHECK (project_key ~ '^[A-Z][A-Z0-9_]+$')` and a **unique index on `project_key`** (one product per key, so a key never produces two briefings and coverage stays unambiguous). A child table fits D-17.1-05 "key(s)" and coverage is per key (D-17.1-04). A column would force a delimiter list and awkward validation.
- **Backfill SQL (V19):** for each distinct valid key on a product's releases, assign the key to one product, preferring the product whose name equals the key, then the product with the most releases carrying it, then name:
```sql
INSERT INTO product_jira_project (product_id, project_key)
SELECT DISTINCT ON (k.project_key) k.product_id, k.project_key
FROM (SELECT rp.product_id, upper(btrim(r.jira_project_key)) AS project_key,
             (lower(p.name) = lower(btrim(r.jira_project_key))) AS name_match, count(*) AS n, lower(p.name) AS lname
      FROM release r JOIN release_product rp ON rp.release_id = r.id JOIN product p ON p.id = rp.product_id
      WHERE upper(btrim(r.jira_project_key)) ~ '^[A-Z][A-Z0-9_]+$'
      GROUP BY rp.product_id, upper(btrim(r.jira_project_key)), p.name) k
ORDER BY k.project_key, k.name_match DESC, k.n DESC, k.lname;
```

### Q8. Working-day math, slots, and matching Claude rows
- **Africa/Cairo has DST**, ending Thursday 2026-10-29: verified with the local JDK 25 tzdata (`2026-10-29 Thu 08:44 +03:00 = 05:44Z`; `2026-10-30 +02:00`; `2026-11-01 Sun 08:44 = 06:44Z`; `2026-04-24 Fri +03:00`). So slot instants shift by one hour in UTC across the change, and the Thursday 13:41 weekly slot on 2026-10-29 is still +03:00. [VERIFIED: ran `Tz.java` on JDK 25.0.4] Always build slots as `ZonedDateTime` in Africa/Cairo; never add 24 h to an instant.
- **Stale, week and due math:** see the code example. "Stale 3+ working days": elapsed work days after the last-updated date through today >= 3 (updated Wednesday, today Monday: Thu, Sun, Mon = 3). Week start: previous-or-same Sunday 00:00 Cairo. Both use the configured `work_days` set.
- **Changes since last run, no previous run:** use the start of the previous working day in Cairo (the "last 24 working hours" default); with a previous successful run for the same task and product, use its `finished_at`.
- **Slot and grace evaluation:** `slot` = latest cron instant `<= now - grace`; evaluate when `now - slot <= catch-up`. A Claude row identifies its slot only by `run_at` (rows have no slot field). Claude writes `run_at` at the **end** of its run (dashboard update step after the message is sent), so `run_at >= slot` always, and a row in `[slot, slot + grace]` is the slot's result. Recommend counting `run_at` in `[slot - 5 min, slot + grace]` to tolerate clock skew and a scheduler that fires marginally early. A Claude run that finishes after `slot + grace` is missed; the app then runs and its result is shown only if newer (below). That is the intended cost of a finite grace period.
- **Covered:** a product is covered when **every** one of its keys is in the covered project set (`tasks.<id>.projects`, else `jira.projects`) and a matching non-failed row exists. All-or-nothing keeps the run to one JQL scope; partial coverage is not worth the second code path. If `config.json` is missing or unparseable, coverage is empty (app runs for all), consistent with D-17.1-03.
- **Page rule (D-17.1-14):** per task and product, the card shows whichever of {Claude's latest row, the app's latest non-`skipped` run} is **newer**, labelled by source. Because the app only runs when Claude's row is missing or failed, newest-wins equals "Claude first, fallback when Claude isn't working", without a second coverage computation on the read path. History merges both sources.
- **`skipped` rows:** write one `skipped` marker (reason `CLAUDE_COVERED`) when a product is covered, so each slot is evaluated once and BRIEF-01's "skips covered products" is observable and testable. Hide them from the card and show them muted in history. Do not count them toward `keepRuns`.

### Q10. Security
- **File read (D-17.1-15):** file name from the enum only (`task.id() + ".json"`, `Path.resolve` on the configured base, `normalize`, assert `startsWith(base)` as defence in depth); reject symlinks and non-regular files (`Files.readAttributes(..., NOFOLLOW_LINKS)`); enforce the 1 MB cap while reading (read at most 1 MB + 1 bytes from the stream), not by a prior `size()` alone, so a growing file cannot slip past; parse into `JsonNode` and extract fields manually (so unknown fields and a wrong type in one row drop only that row); `run_at` via `Instant.parse`/`OffsetDateTime.parse` else drop; `attention` must be an integer >= 0 or null; truncate by code points (never split a surrogate pair); strip control characters (including bidi controls) from text; keep newest 60. All failures produce `readError=true` with an empty list; the error carries no path or content (log the exception class only, never the message, which can contain the path). B6 test: assert only the five names are ever opened (use a temp directory with decoy files such as `other.json` and a `..` symlink and assert not read).
- **Plain text (D-17.1-17):** render with React text nodes only. Issue keys are linked by a fixed pattern `^[A-Z][A-Z0-9_]+-\d+$` from structured `items[].key` for app runs, and by the same pattern for Claude's `h1..h3` text; the href is `${jiraBaseUrl}/browse/${key}` where the base is the validated site URL (`^https://[A-Za-z0-9-]+\.atlassian\.net$`, `JiraSiteConfigService`). No scheme injection is possible. Add a vitest case with `<img onerror>` and `javascript:` in a headline.
- **Admin-only settings:** no role model exists (Q-summary fact 2). Recommend `BriefingAdminPolicy`: allowlist `app.briefings.admin-emails` (env `RM_BRIEFINGS_ADMINS`, comma separated) matched case-insensitively against the signed-in user's email resolved through `ActorDirectory.findEmailsByAccountId(currentAccountId)` (projection, no decrypt). Enforce in the service (not only the controller); add a ProblemDetail reason `ADMIN_REQUIRED` with HTTP 403 (a 403 is safe: the frontend only special-cases 401) and a settings payload flag `canEdit` so the UI can render read-only for others. Empty allowlist means nobody can edit, which is a safe default but must be documented in `docs/docker.md` and `.env.example`. See Open Question 1.
- **Cron and input validation (ASVS V5):** `CronExpression.isValidExpression`, minimum interval 1 minute, grace 0..240, thresholds bounded, keys by regex; Bean Validation on request records.
- **Credential:** no token in logs, run bodies, or exceptions; token only inside `JiraAccessContext` for the duration of the run (the record has no `toString` redaction today: do not log the context).
- **Logging:** metadata only (counts, status, ms, exception class), never Jira summaries, Claude headlines or file paths (SAFE-03 convention).
- **Read-only Jira:** the `JiraBriefingPort` exposes only searches and reads; add `briefingPortExposesNoMutation` ArchUnit rule like `ragChatPortExposesNoMutation`, and a rule that the new port is not used from the web adapter.
- **Supply chain / SSRF:** the Jira host is the configured `*.atlassian.net` URL; no URL is taken from a Claude row or from config.json (`jira.site` in config.json is informational and must be ignored by the app).

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Stored XSS via Claude row or Jira summary | Tampering | React text nodes only; key links from a fixed regex; no `dangerouslySetInnerHTML` |
| Path traversal / symlink read | Information disclosure | Enum file names, `normalize` + `startsWith`, `NOFOLLOW_LINKS`, no config-editable dir |
| Oversized or hostile JSON file | Denial of service | 1 MB bounded read, 60-row cap, manual field extraction |
| JQL injection through a project key | Tampering | DB regex CHECK, service validation, quoted keys in `project in (...)` |
| Prompt injection steering the headline | Tampering | Output validation (length, single line, keys must come from facts), model output limited to headline/summary |
| Credential misuse (token used while owner absent) | Elevation of privilege | Self-designation only (recommended), read access equals that user's Jira permissions, run attribution in the run row |
| Credential rejection turning into admin logout | Denial of service | Run-now catches and records; never throws a 401 |
| Cron abuse (every-second schedule) | Denial of service | Reject schedules firing more than once per minute |
| Log leakage of summaries or paths | Information disclosure | Metadata-only logging, exception class names only |
| Scheduler hammering Jira after 429/401 | Denial of service | No retry/backoff loop; one evaluation per slot; stop remaining products on first 401 |
