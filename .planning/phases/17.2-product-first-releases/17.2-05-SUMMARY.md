# Phase 17.2 Plan 05: Product-first Tickets page and add-to-release dialog Summary

The Tickets page now starts with a product select (deep-linkable via `?product=`). It searches only that product's Jira projects and shows the no-Jira-project notice instead of the browser when the product has none. AddToReleaseDialog is fixed to that product: it lists only the product's open releases and creates releases with `{ name, version, ticketKeys, productId }`. With `?new=true` it opens straight on the create form.

## Deviations from Plan

1. **[Rule 1] The dialog mounts only for a product with keys.** When I mounted it for any chosen product, the `startWithForm` form was in the DOM (inside a closed dialog) while the no-Jira-project notice showed. The must-have says no form is offered, so the dialog now renders only when the browser does.
2. **The TicketBrowser test call sites needed no change.** `TicketBrowserCodeLinks.test.tsx` and `TicketBrowserProduct.test.tsx` already pass single-argument or `vi.fn()` handlers, so those files are untouched.
3. **The TicketsRoute browser-behaviour tests were kept and adapted rather than dropped.** These cover sprints, the status filter, JQL, select-all, expand, the empty hint and the search failure. They now run inside product Alpha, picking a single mapped project where sprints matter. The fixtures use placeholder keys (ABC/XYZ/OTH) instead of CNV.
4. **The Task 2 commit carries a small type fix to the Task 1 test.** The handler type in `AddToReleaseDialog.test.tsx` was widened, because `tsc -b` (first run in Task 2) rejected an async handler that returns `undefined`.

## TDD Gate Compliance
