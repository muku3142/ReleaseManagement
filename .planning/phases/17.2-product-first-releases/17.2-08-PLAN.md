<objective>
Store ticket bundles (D-17.2-07) on the release and expose them through the existing release API. A bundle is an optional name on each `release_ticket_item` row. Tickets added together with a name share it, they are listed and removed together, and the documents plan (17.2-11) groups by it.

Purpose: D-17.2-07, "kept as one named group on a release" and "added and removed together". There is no REQUIREMENTS.md ID for D-17.2-07. It is filed under REL-PF-01 (selecting tickets for a release) for traceability.

Storage choice (D-17.2-07 discretion): a nullable `release_ticket_item.bundle VARCHAR(100)` column, not a `release_bundle` table.
- It is the smallest correct change. The existing `release_ticket_item_key_unique (release_id, ticket_key)` already makes "a ticket belongs to at most one bundle per release" structural.
- A bundle belongs to a release because its rows do. Deleting the release cascades.
- A bundle with no tickets simply stops existing.
- A table would add a second aggregate with its own lifecycle (an empty bundle, rename and orphan rules) that nothing here needs.

Scope choices (D-17.2-07 discretion):
- A bundle cannot be renamed.
- More tickets join an existing bundle by naming it. The name match ignores case and surrounding spaces, and the bundle keeps its first spelling.
- Adding a ticket that is already on the release is still the existing no-op. It is counted in `alreadyPresent` and does not move the ticket into the named bundle.
- Out of scope per D-17.2-07: moving bundles between releases, promoting a bundle on its own, and any rename endpoint.

Output: V24, the bundle-aware item domain/persistence/service/web, and tests.
</objective>
