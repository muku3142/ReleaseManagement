# Phase 17.2 Plan 08: Ticket bundle column and bundle-aware release API Summary

Ticket bundles (D-17.2-07) are stored as a nullable `release_ticket_item.bundle` column (V24). Create and add accept an optional bundle name. The name is trimmed, and it reuses an existing bundle's spelling regardless of case. `DELETE ...?withBundle=true` removes the whole bundle through the new `ReleaseRepository.removeBundle`, which keeps the freeze lock and the items_changed_at staleness rules.

## What was built

- **V24:** `ALTER TABLE release_ticket_item ADD COLUMN bundle VARCHAR(100)` with no backfill. It also drops `template_grouping_dimension_check` and re-adds it as `IN ('ISSUE_TYPE','COMPONENT','BUNDLE')`.
- **Confirmed V5 constraint name: `template_grouping_dimension_check`.** Flyway applied the strict `DROP CONSTRAINT` (no `IF EXISTS`) successfully on a fresh Postgres, which confirms the name. The IT also asserts it via `pg_constraint`.
- **Domain/persistence:**
  - `ReleaseItem` gains a trailing `bundle`, and the 3-arg constructor means ungrouped.
  - `toEntity` and `toDomain` map the bundle. `overwriteSnapshot` is untouched, so a refresh keeps bundles.
  - `removeBundle` runs lockOpen, then `deleteByReleaseIdAndBundle`, then stamps only when rows were deleted, then publishes `ReleaseIndexInvalidated`.
- **Service:**
  - `createWithTickets(..., productId, bundle, actor)` and `addTickets(releaseId, keys, bundle)` resolve the name with `bundleName(raw, existing)`.
  - `removeTicket(releaseId, key, withBundle)` checks `requireOpen()` first. It then calls `removeBundle` when the flag is set and the ticket is bundled, and `removeItem` otherwise (an unknown key is still a no-op).
- **Web:**
  - Both request DTOs take `@Size(max=100)` plus a no-control-characters `@Pattern` `bundle`.
  - `ReleaseItemResponse` gains a trailing `bundle` field.
  - DELETE takes `withBundle` (default false).
