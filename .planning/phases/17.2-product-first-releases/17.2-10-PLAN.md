<objective>
Implement the server side of D-17.2-06. `POST /api/tickets/search` gains an optional `hideAlreadyInRelease` flag. When it is true, every ticket whose key is already on a release is dropped from the Jira results.

Purpose: D-17.2-06. It completes the client half in 17.2-09. There is no REQUIREMENTS.md ID; it is filed under REL-PF-01 for traceability.

**Dedup decision, recorded here as D-17.2-06 asks research to settle it.**
- **Release status does not matter.** Every release counts.
  - There are only two statuses, OPEN and FROZEN (V3 CHECK). "Shipped" is a FROZEN release with promotions or installs.
  - A ticket on a frozen or shipped release is exactly the one that "should not be picked again by accident".
  - A ticket on an open release is about to ship, and picking it again would duplicate it.
  - A deleted release cascades its items away, so its tickets become pickable again with no special case.
- **"Every release of the selected product" is implemented as "every release".**
  - D-17.1-20 makes each Jira project key belong to exactly one product (unique index on `product_jira_project`).
  - D-17.2-02 gives each release one product.
  - So for a product-scoped browse, the two sets differ only for a ticket that was moved between Jira projects, or that Advanced JQL put on another product's release. That ticket is still "already in a release", which is what the checkbox label says.
  - One rule for every mode (product, a single narrowed project, Advanced JQL, and the add-tickets dialog) also matches D-17.2-06's JQL bullet ("hides tickets in any release"). It needs no product join, and it never changes what is hidden when the user narrows from "All projects" to one project.

Output: the repository lookup, the request flag, service filtering and tests.
</objective>
