# Phase 17.2 Plan 12: Bundle name when adding tickets Summary

All three add paths (New release, Add to release, and the release page's Add tickets dialog) now take an optional bundle name. The release page dialog suggests the release's existing bundles through a `<datalist>`. The API wrappers send `bundle` only when it is non-blank after trimming, so an ungrouped add posts exactly the same body as before.

## What was built

- `api/releases.ts`:
  - `ReleaseItem.bundle: string | null`.
  - `bundle?` on create and add, trimmed and omitted when blank.
  - `withBundle?` on `useRemoveTicketItem`, which appends `?withBundle=true` only when true.
  - `releaseBundles()`.
  - `useRelease(releaseId, enabled = true)`.
- `AddToReleaseDialog`: one "Bundle name (optional)" input (`#bundleName`, maxLength 100, with help text) above both the release list and the create form. It is reset on open and passed to both `addTickets.mutate` and `createRelease.mutate`.
- `AddTicketsToReleaseDialog`: a "Bundle name (optional)" input (`#addTicketsBundle`, `list="addTicketsBundle-options"`, maxLength 100) above the TicketBrowser.
  - The datalist is filled from `releaseBundles(useRelease(releaseId, open).data?.items ?? [])`.
  - The input is reset on open, and its value is passed to the add.
  - `ReleaseDetailRoute.tsx` is untouched.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Always-enabled useRelease in the always-mounted dialog refetched a deleted release**
- **Found during:** Task 2 (full suite run)
- **Issue:** `ReleaseDetailRoute > does not refetch the release it just deleted` failed. The dialog's extra `useRelease` observer kept `['release', id]` active through `removeQueries({ type: 'inactive' })`, so the deleted release was fetched again.
- **Fix:** `useRelease` gained an optional `enabled` parameter (default `true`, so existing callers are unchanged). The dialog passes `props.open`.
- **Files modified:** frontend/src/api/releases.ts, frontend/src/components/AddTicketsToReleaseDialog.tsx
- **Commit:** 535f76f

**2. [Rule 1 - Bug] releaseBundles crashed on items with no bundle field**
- **Found during:** Writing the summary
- **Issue:** Until 17.2-08 lands, responses omit `bundle`, and the original `!== null` filter passed `undefined` to `localeCompare`.
- **Fix:** Filter by truthiness instead.
- **Commit:** a56b42d

**3. [Rule 3 - Blocking] Test fetch mock threw on GET /api/releases/r1**
- The plan anticipated this. The `AddTicketsToReleaseDialog` test mock now serves the release, with an optional `releaseItems` override.

## Known Stubs

None. The backend contract (17.2-08) is being built in parallel and is not on this branch yet. Until it lands, the server ignores `bundle` and `withBundle`, and `ReleaseItem.bundle` will be absent (undefined) in responses. `releaseBundles` filters by truthiness, so an item with no `bundle` field (or an empty one) is skipped and the list stays empty. A `!== null` check would have let `undefined` reach `localeCompare`.
