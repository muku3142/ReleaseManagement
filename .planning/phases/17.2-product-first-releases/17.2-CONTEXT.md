# Phase 17.2: Product-First Releases - Context

**Gathered:** 2026-10-26 (decided in conversation, no separate discuss session)
**Status:** Ready for research and planning

<domain>
## Phase Boundary

A release belongs to **exactly one product**, and creating one starts from that product. The product's Jira projects come from the Portfolio › Products mapping built in Phase 17.1 (`product_jira_project`), and tickets are picked from those projects.

This replaces the tickets-first flow:
- Today you browse a Jira project, select tickets, then "Add to release".
- A release can currently cover several products, picked separately from its Jira key.

Out of scope:
- changing the product ↔ Jira project mapping UI (it already exists)
- restyling (Phase 23 / 23.1 own the visuals). New UI here should use the Phase 23 components if Phase 23 has merged by then.
</domain>

<decisions>
## Implementation Decisions

- **D-17.2-01: Product first, everywhere.**
  - The Releases page gets "New release": pick a product, the ticket browser opens scoped to its Jira projects, select tickets, then enter name and version.
  - The Tickets page also asks for the product first, instead of a free Jira project choice.
  - Adding tickets to an existing release (AddTicketsToReleaseDialog) browses the release's product's projects.
- **D-17.2-02: One product per release.** Phase 15 allowed several products per release (`release_product` M:N, editable even when frozen); that is superseded.
  - Storage enforces a single product.
  - Live data has 1 release with 1 product (CNV), so the migration has nothing to merge.
  - The research decides whether to add `release.product_id` or keep `release_product` with a uniqueness constraint, choosing the smaller change that keeps portfolio, installs (`client_deployment`), "clients behind", `current_client_release` and the assistant tools working.
  - Changing a release's product stays possible under the existing rules: products are editable when frozen, and removal is blocked once installs exist (D-15-15).
- **D-17.2-03: A product with several Jira projects means browsing all of them.** The ticket browser searches every Jira project mapped to the product: JQL `project in (...)` through the existing `/search/jql` client.
- **D-17.2-04: No Jira project mapped blocks creation.** The message is "{Product} has no Jira project. Add one in Portfolio › Products", with a link. The release cannot be created until a project is mapped.

- **D-17.2-05:** Advanced JQL stays **unscoped**. A user typing their own JQL can search any project; only the product-driven browse is scoped (user, 2026-10-26).

**Added 2026-10-27, after plans 01–06 were executed** (user, in conversation). The new plans come before the 17.2-07 walk-through, so both are verified together.

- **D-17.2-06: Browse tickets hides tickets that are already in a release.**
  - Problem: on the Tickets page, tickets already added to a release still show up, so they get picked again.
  - A checkbox "Hide tickets already in a release" sits with the filters. It is **on by default** and hides every ticket that belongs to any release of the selected product.
  - Turning it off shows everything, as today.
  - The search already takes `releaseId` to exclude a single release's tickets (D-05.2-05, used by AddTicketsToReleaseDialog). This adds an "exclude every release of the product" option.
  - Advanced JQL is unscoped (D-17.2-05), so the toggle there hides tickets in any release.
  - Research decides whether release status matters (open, frozen, shipped). Default: every release counts, because a ticket that has shipped should not be picked again by accident.
- **D-17.2-07: Ticket bundles: tickets selected together can be kept as one named group on a release.**
  - When adding selected tickets to a release, from New release, Add to release or AddTicketsToReleaseDialog, the user can optionally name a bundle, e.g. "Payments fixes". The selected tickets are saved as that bundle on the release. Leaving the name empty adds them ungrouped, as today.
  - A ticket belongs to at most one bundle per release. Bundles belong to a release, not a product.
  - **Shown as a group.** The release view lists a bundle's tickets under the bundle name, with ungrouped tickets in their own section. Generated documents can group by bundle: a third grouping choice, BUNDLE, beside ISSUE_TYPE and COMPONENT (`GroupingDimension`, V5 CHECK constraint). Ungrouped tickets fall into an "Other" group.
  - **Added and removed together.** Removing one ticket of a bundle asks: remove the whole bundle, or only that ticket, which leaves the rest of the bundle in place.
  - Out of scope:
    - promoting a bundle separately from its release, because promotion stays per release (D-07-06)
    - moving a bundle between releases
  - The existing release rules still apply. A frozen release accepts no ticket changes until it is unfrozen (D-15.1-01), and changing tickets makes documents stale (D-15.1-04).
  - Claude's discretion:
    - storage: a `release_ticket.bundle` column or a `release_bundle` table
    - whether a bundle can be renamed or have tickets added later. At minimum, the user can add more tickets to an existing bundle by choosing it by name.

### Claude's Discretion

  - kept as the first or primary key for document templates, which use `{{jiraProjectKey}}`-style tokens

  Research must check the templates and documents that use it.

</decisions>
