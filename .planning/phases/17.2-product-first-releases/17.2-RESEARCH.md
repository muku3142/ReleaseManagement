## Summary

The smallest correct schema change is **keep `release_product` and add `UNIQUE (release_id)` in V23**. The deciding fact is that `client_deployment` holds a composite FK `(release_id, product_id) → release_product` (`V14__portfolio.sql:74-75`), which is precisely the D-15-15 guard. That FK, the `current_client_release`/`effective_client_deployment` views, and ~12 native queries reading `release_product` (portfolio, dashboard filter, "clients behind", product counts, template `{{#products}}`) all keep working untouched. The alternative (`release.product_id NOT NULL` + drop `release_product`) would need the ledger FK rewired, every reader rewritten or shimmed with a view, and — because `NOT NULL` lands on `release` — **26 test files** that create releases without a product would break (`grep -rl "Release.create(\|INSERT INTO release " src/test/java` = 26). The "at least one" half stays service-enforced exactly as D-15-18 already does today.

`release.jira_project_key` is **kept and derived server-side at creation** as the product's first mapped key (keys come back upper-case and sorted from `ProductRepository.jiraProjectKeys()`). It feeds a user-facing template token (`{{release.jiraProjectKey}}`, `PlaceholderCatalog.java:19`, used by the bundled `starter-runbook.md:4` and possibly by user-authored templates in the live DB), the assistant index metadata `project_key` (`IndexDocumentMapper.java:109,127,139`), the ReleasesTool row and two UI columns. Removing it would silently blank user templates; deriving it keeps every consumer valid with no migration. The client stops sending it.

Ticket browsing gets a third search mode, **`productId`**: the server resolves the product's keys and composes `project in ("ABC", "CNV")` (keys quoted — JQL reserved words), reusing the existing `/search/jql` client, status filter and release-scope hiding. Sprint narrowing remains available by picking a single project of the product, which falls back to the existing `projectId` mode. Both entry points reuse the Tickets page: "New release" on Releases links to `/tickets?new=true`, the page asks for a product first, and the existing AddToReleaseDialog opens straight onto its create form with the product fixed.

**Primary recommendation:** V23 = one `ALTER TABLE release_product ADD CONSTRAINT release_product_one_per_release UNIQUE (release_id)`; single-`productId` create/set APIs; `productId` search mode; `PRODUCT_NO_JIRA_PROJECT` 422; reuse Tickets page + AddToReleaseDialog for both entry points.

### System flow

```

                                    v
```

### Pattern 2: `productId` search mode

`TicketSearchRequest` gains `UUID productId`; the `@AssertTrue` becomes "exactly one of projectId / productId / jql; sprintId only with projectId". `TicketSearchCriteria` gains `List<String> projectKeys` and:

### Anti-Patterns to Avoid
- **Moving the product onto `release` (`product_id NOT NULL`)**: rewires the ledger FK, invalidates the D-15-15 mechanism, breaks 26 test files that create bare releases, and `TRUNCATE product … CASCADE` in test cleanup (`BriefingRunPersistenceIT.java:50`) would start wiping releases.
- **Changing `products: []` to `product: {}` in responses**: churns Portfolio/ReleasesRoute/installs/`{{#products}}` templates for no behavioural gain.
- **Inserting before deleting** in `setProduct`: the non-deferred UNIQUE fires on the insert.
- **Unquoted keys in `project in (...)`**: a valid key such as `IN`/`OR` (2-char keys pass the regex) is a JQL reserved word.
- **Updating `jira_project_key` on product change**: it records where the release's tickets were picked from (D-03-05 "advisory key"); leave it.

## Common Pitfalls

### Pitfall 1: Multi-product test fixtures break under the UNIQUE constraint
**What goes wrong:** fixtures put two products on one release.
**Where (verified):** `ClientDeploymentPersistenceIT.java:102`, `PortfolioDashboardPersistenceIT.java:87,162`, `PortfolioReadPersistenceIT.java:84`, `DashboardPersistenceIT.java:284` (R covers {A,B}), `ClientDeploymentSchemaIT.java:195-218` (`cover(release, p2)`), `PortfolioDashboardFlowIT.java:131` (`release("R", …, core, mobile)`), `ClientInstallFlowIT.java:176-183` (empty set / two products / RELEASE_LAST_PRODUCT).
**How to avoid:** split each multi-product release into one release per product and re-derive the expected counts ("clients behind", matrix, `releaseIdsCoveringAny`); assert the second insert is rejected (new schema assertion).

### Pitfall 2: A mapped key Jira doesn't know fails the whole search
**What goes wrong:** Jira answers `project in ("ABC","TYPO")` with HTTP 400 rather than ignoring the unknown value [ASSUMED; consistent with the 400-on-unknown-key behaviour already handled at `JiraSearchClient.java:74-79`]; it maps to `JIRA_ERROR`.
**How to avoid:** no new backend logic. In TicketBrowser, compare the product's keys to `useJiraProjects()` keys and show "{KEY} isn't a Jira project you can see" so the user fixes the mapping. Do not add an extra Jira call server-side.

### Pitfall 3: Wrong Flyway number
V20/V21/V22 are claimed though not yet on `main` (quick tasks and the licensing branch). Using "next file number after V19" would collide. Use V23.

### Pitfall 4: Dialog state across product switches
TicketsRoute keeps AddToReleaseDialog permanently mounted (reset-on-open effect, `AddToReleaseDialog.tsx:79-95`); TicketBrowser holds selection state. Key TicketBrowser by `productId` so a product change clears loaded tickets and selection.

### Pitfall 5: Phase 23 collisions
23-09 rewrites `ReleasesRoute.tsx` and its test wholesale. 17.2 must start after 23-09 is committed (ROADMAP dependency) and touch only the actions slot/empty copy there; 23-09's grep criteria forbid raw `gray-/blue-` classes in that file, so new markup there uses tokens/`Button`.

### Pitfall 6: Uncommitted user files
`src/main/resources/application.yml` and `src/test/resources/application.yml` are modified in the working tree; the 2 `AssistantPropertiesTest` failures come from them (kyg plan notes). Never stage them; treat those failures as known noise.
