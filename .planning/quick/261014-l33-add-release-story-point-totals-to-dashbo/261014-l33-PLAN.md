<objective>
INSIGHT-04: show the total story points of each release on the dashboard, summed from the Jira story-point
field of the release's Jira tickets, with unestimated tickets counted and shown separately. Only the
per-release total: no velocity, per-sprint points or burndown.

Purpose: a release's ticket count says nothing about its size; the total, plus an explicit unestimated
count, stops a low total being mistaken for a small release (PROJECT.md "Story points partially reversed
2026-10-14").
Output: story points captured into the ticket snapshot (V11), aggregated by the dashboard read path,
rendered as a new dashboard column.
</objective>

Design decisions made in planning (Claude's discretion; follow exactly):

1. **Where story points live.** Ticket data the dashboard reads is the per-item snapshot in
   `release_ticket_item`, written by `ReleaseRepositoryAdapter.overwriteSnapshot` on add and on refresh,
   and read for the dashboard by `DashboardJpaRepository.churnItems` (one row per ticket item). Story
   points ride the same path: Jira search -> `TicketDetail` -> snapshot columns -> `churnItems` row ->
   `ChurnItem` -> new `ReleaseStoryPoints` aggregate -> `DashboardResponse.ReleaseRow.storyPoints`.
2. **Three per-ticket states**, stored as two columns:
   - `story_points_read = TRUE, story_points = 5` -> estimated
   - `story_points_read = TRUE, story_points = NULL` -> read, no estimate in Jira ("unestimated")
   - `story_points_read = FALSE` -> not read (row snapshotted before V11, or the site's field id could not be resolved)
3. **Existing releases.** V11 adds `story_points_read BOOLEAN NOT NULL DEFAULT FALSE`, so every existing
   row reads as "not read" with no backfill. An OPEN release picks values up on its next Refresh (or for
   tickets added afterwards). A FROZEN release is never re-snapshotted (refresh calls `requireOpen()`,
   D-03-11 audit snapshot), so frozen releases created before this change show "Unknown" permanently.
   That is correct: the frozen snapshot is the audit record, and we do not rewrite it.
4. **Field resolution must never break ticket search.** `FieldMetadataService.resolve` throws on any
   missing or ambiguous name, and duplicate custom "Story Points" fields are common (see
   `FieldMetadataServiceTest.duplicateNameNotRequestedDoesNotThrow`). So STORY_POINTS is resolved
   separately and optionally:
   - New config `app.jira.story-points.field-id` (env `RM_JIRA_STORY_POINTS_FIELD_ID`, default blank).
     Non-blank -> used as the field id verbatim (admin pin for sites with duplicate names).
   - Blank -> look up display name "Story Points" in the existing cache using the existing
     `disambiguate` rule (single system field wins, single candidate wins, otherwise undecidable).
   - Absent or undecidable -> `Optional.empty()` plus one `log.warn` naming the candidate ids and
     saying to set `RM_JIRA_STORY_POINTS_FIELD_ID`. **No cache refresh on a miss** (unlike `resolve`):
     a site that simply has no such field would otherwise re-fetch `/rest/api/3/field` on every search.
   - When an id is resolved, a missing or non-numeric value on a ticket means "read, no estimate".
5. **Value type**: `BigDecimal` in Java, unbounded `NUMERIC` in Postgres (Jira story points are floats
   such as 0.5; an unbounded column cannot overflow on a silly value and fail a refresh). JSON number on
   the wire; TS `number`.
6. **Manual items** have no story points and are excluded (same as code-link counts).
