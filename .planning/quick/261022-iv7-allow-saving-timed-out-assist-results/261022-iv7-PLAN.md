## Decisions made in this plan (state them in the SUMMARY)

- **D-Q1 Mechanism — explicit `remainder {keep, text}` event.** The server cannot unsend tokens, so on a stop it sends
  one SSE event `remainder` with `keep` = number of characters (UTF-16 code units; Java `String.length()` == JS
  `string.length`) the server had already sent through the listener BEFORE the stopped part's loop iteration began, and
  `text` = the original text of the stopped part and every part after it (`DocumentSections.Part.text()` joined; joining
  all parts reproduces the document exactly). The browser does `buffer = buffer.slice(0, keep) + text`. This removes the
  stopped section's partial model output, and also a verbatim heading whose send succeeded just before the app deadline
  check threw (that heading is in `text` again). Chosen over "buffer each section server-side" (kills streaming) and
  over "frontend records offset at each `progress` event" (progress is only sent when sections > 1 and the offset would
  then depend on two independent event streams).
- **D-Q2 'failed' is saveable too when filled.** Same mechanism, any stop cause after at least one finished section is
  filled: rag `Failed` outcomes (DEADLINE, BUSY, OFFLINE, MODEL_MISSING, REJECTED), rag `TooLarge` mid-run, the app
  stream deadline (`StreamDeadlineExceeded`), and any other `RuntimeException` except `ClientGoneException`. In the
  browser a filled stream that then gets `error` (DEADLINE → partial 'deadline', anything else → partial 'failed') or
  ends without a terminal event becomes saveable.
- **D-Q3 'length' stays blocked.** A section that ends with `finishReason != stop`/`truncated` does not stop the run
  (current behaviour: it continues to the next section), so the buffer has a section cut off mid-text and no original
  for the lost end of THAT section. The fill cannot make it whole; saving would silently drop text. Unchanged.
- **D-Q4 No fill when no section finished.** If the stop happens in the first transform section, the fill would just
  reproduce the original document; saving it would create a revision identical to N. So the server only sends
  `remainder` when `completed >= 1`; otherwise behaviour is unchanged (incomplete/error, not saveable).
- **D-Q5 Summarize stays unsaveable.** Summarize is one request with no original tail to fill (`prepared.sections()`
  is null, `runSections` is not used), and a partial summary is not a revision of the document. No `remainder` is ever
  sent for it, so the frontend keeps it blocked with no mode-specific code.
- **D-Q6 User Stop stays unsaveable.** Stop aborts the fetch; the server can no longer send anything. Unchanged.
- **D-Q7 Server save path unchanged.** `saveAiRevision` stays UI-gated (existing comment holds); no new server check.
