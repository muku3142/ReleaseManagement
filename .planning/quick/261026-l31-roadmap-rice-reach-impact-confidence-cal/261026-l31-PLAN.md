Design choices made by the planner (decision 1 and 5 left them open):
- Reach is computed at read time from the `current_client_release` view (single home of D-15-05), counting DISTINCT clients that are NOT archived (same default as the Phase 16 dashboard). A product nobody runs gives Reach 0 (a real value, so the item is scored). Nothing is stored, so there is no staleness and no refresh rule.
- Impact/Confidence inputs are stored as raw Jira facts (`jira_priority`, `jira_readiness` 0..3) written at import/refresh; the mapping to RICE values happens in the domain on read, so the rules can change without a migration.
- Stored `reach/impact/confidence` columns now hold only user-entered values: an override (paired with a non-null reason column) for calculated fields, or the plain hand value for a manual item's Impact/Confidence. Effective = entered ?? calculated, per field.
- History: only user actions write rows. Existing rows become kind ENTERED; overrides write OVERRIDDEN (old = effective before, new = override, reason); resets write RESET (old = override, new = calculated at that moment). Calculated values changing (refresh, installs) never write history rows.
- Readiness uses `SprintCheckRules`' own essential checks exactly, so a site with no Acceptance Criteria or Story Points field counts that signal as not met (rule says "not checked") and caps Confidence at 80.
- Add from release now makes one batched Jira call per 100 keys to read priority/readiness (it previously made none); a Jira failure fails the add the same way add-from-Jira does, before anything is written.

Output: V21 migration, domain calculation/override model, Reach query, Jira derivation, override/reset API, frontend override UI. Three tasks, one commit each.
