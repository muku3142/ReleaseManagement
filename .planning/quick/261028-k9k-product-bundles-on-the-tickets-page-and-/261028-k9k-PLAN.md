<objective>
Product bundles on the Tickets page, and click-to-select ticket rows.

Purpose: bundling now happens before a release. A release manager groups tickets into a named product bundle on the Tickets page, then selects that bundle like a ticket and adds it to a release, where it becomes a 17.2 release bundle of the same name. Separately, a single click on a ticket row selects it and a double click expands it.

Output: V25 migration and a bundles REST API (Task 1); row clicks and group-based release adds with the free-text bundle inputs removed (Task 2); bundle rows and the Add to bundle dialog (Task 3); licensing touches on their own (Task 4).

</objective>

<decisions>
- **K-01 Storage (V25):** a `product_bundle` row (id, product_id, name ≤100, created_at) with the name unique per product, case-insensitive (`UNIQUE (product_id, lower(name))`). Its `product_bundle_ticket` rows (bundle_id, product_id, ticket_key VARCHAR(64) to match `release_ticket_item.ticket_key`) carry `UNIQUE (product_id, ticket_key)`, which makes "a key is in at most one bundle per product" a database guarantee. A composite FK `(bundle_id, product_id) -> product_bundle(id, product_id)` with ON DELETE CASCADE keeps product_id honest.
- **K-02 Add to an existing bundle moves tickets:** saving keys into bundle X first removes those keys from any other bundle of the same product, then inserts them into X. Any bundle left empty is deleted. All of this happens in one transaction. An existing bundle's name is matched case-insensitively, and the stored spelling is kept, mirroring `ReleaseService.bundleName`.
- **K-03 Delete is idempotent:** `DELETE /api/products/{productId}/bundles/{bundleId}` returns the current list even if the bundle is already gone, and is scoped to the product. No new 404 reason is needed. The frontend asks for no confirmation, because deleting only ungroups the tickets and no ticket or release data is lost.
- **K-04 After a bundle is added to a release it stays** and can be reused until deleted. The existing "Hide tickets already in a release" search filter still applies to its tickets, because bundle rows are built only from tickets in the loaded search results.
- **K-05 A bundle row covers only its loaded members.** It appears only when at least one member key is in the current search results. Selecting it selects those loaded members. Members filtered out of the search (for example, already in a release) are listed by key in the expanded view as "not in these results" and are never sent. Its count reads "n tickets", or "n of m tickets" when some members are missing.
- **K-06 Release adds use one call per group, with no backend change:** TicketBrowser emits `TicketGroup[]`: one ungrouped group for the loose keys, if any, plus one group per selected bundle. Add to an existing release sends one `POST /api/releases/{id}/items` per group. Create release sends `POST /api/releases` with the first group, so the release is never empty and D-03-02's no-orphan intent holds, then one items POST per remaining group. The results are merged by summing added, alreadyPresent and notFound, with `release` taken from the last response. If a follow-up call fails, the mutation errors, `['releases']` is invalidated in `onSettled`, and the user can re-add the selection to the now-existing release. Already-present tickets come back counted as alreadyPresent, so a retry is safe. This was chosen over extending CreateReleaseRequest/AddTicketsRequest, which would change the ReleaseService signatures used by 53 call sites.
- **K-07 Row clicks:** the row's `onClick` toggles selection on every click, so the two clicks of a double click cancel out. `onDoubleClick` then only expands or collapses and clears the word the browser highlighted (`window.getSelection()?.removeAllRanges()`). The existing "text is selected, ignore" guard applies only when `event.detail === 1`; otherwise the second click of a double click would see the highlighted word and skip its toggle, leaving the row selected. Clicks and double clicks on `button, a, input, label` are ignored by both row handlers, as today. The checkbox cell stays the full-cell label from 72e61343. Bundle rows behave the same way.
- **K-08 Bundles appear wherever TicketBrowser has a `productId`:** the Tickets page and AddTicketsToReleaseDialog. Roadmap's AddFromJiraDialog (no productId) is unchanged. `onAction` becomes `(ticketKeys: string[], groups: TicketGroup[])`, where `ticketKeys` is the flattened list, so the roadmap caller compiles unchanged.
</decisions>
